# Валидация данных и переопределения в узлах

Статус: проектирование. Документ отделяет принятые правила от вопросов, которые ещё обсуждаются.

## Два уровня описания

Datatype задаёт нативный Java-тип, начальное значение, преобразования между нативным значением и текстом, ожидаемую ошибку разбора и базовую валидацию значения. Несколько типов узлов могут использовать один datatype.

Узел вправе переопределить начальное значение и валидацию для своего назначения. Такое переопределение не создаёт новый datatype и не разрешает менять унаследованный тип данных. javaType, serialize, parse и parseError не входят в согласованный набор переопределяемых параметров узла.

Пример размещения параметров:

```text
datatype Int {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
    validate(value) = "true";
}

node PositiveInteger<Int> {
    default = "1";
    validate(value) = "value > 0";
}
```

Int в примере допускает любое значение, уже представленное Java-типом int. PositiveInteger задаёт начальное значение 1 и ограничение положительности. Проверка узла полностью заменяет проверку datatype (D049). Без переопределения используется проверка datatype.

Возможность этих переопределений принята. Замена проверки datatype может как усилить, так и ослабить ограничение:

```text
datatype NonNegativeInt {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
    validate(value) = "value >= 0";
}

node Offset<NonNegativeInt> {
    validate(value) = "value > -10";
}
```

Значение -5 допустимо для Offset: проверка value >= 0 здесь больше не применяется. Имя datatype не накладывает дополнительных ограничений. Параметр validate необязателен (D050). Если он отсутствует в datatype, дополнительных ограничений на нативное значение нет — это эквивалент validate(value) = "true". В первом примере строку validate(value) = "true" можно опустить. Без локального validate сохраняется единственная унаследованная проверка узла, а при её отсутствии используется проверка datatype (D059).

## Явное снятие проверки — D063

Для снятия проверки используется обычное переопределение validate(value) = "true". Это Java-выражение с булевым результатом, поэтому отдельного ключевого слова или особого режима отключения не требуется.

```text
abstract Positive<Int> { validate(value) = "value > 0"; }
node AnyInteger : Positive { validate(value) = "true"; }
```

AnyInteger принимает любое значение своего нативного типа с точки зрения validate. Отсутствие validate, напротив, сохраняет унаследованную проверку. Разбор текста и правила типа данных остаются в силе. Это обычное объявление validate: оно не устраняет конфликт проверок нескольких баз и не требует распознавания Java-выражения генератором (D059–D062).

## Проверка значения

validate(value) — Java-выражение с логическим результатом. value обозначает нативное значение, а не входную строку. true означает допустимое значение, false — недопустимое.

Явно заданные данные проверяются и после успешного parse при setData, и при прямой передаче нативного значения через setValue. Методы setData и setValue возвращают boolean (D056): true — значение принято, false — validate отклонил значение. setData также возвращает false при ожидаемой ошибке parse, указанной в parseError. Разбор и валидация — разные причины отказа, но результат boolean их не различает; отдельный API диагностики пока не вводится.

Проверка default на соответствие валидатору автоматически не выполняется. За корректное начальное значение отвечает автор DSL (D047). Переопределение default в узле позволяет, например, использовать общий Int с начальным нулём и установить 1 для положительного значения.

Синтаксис и типы сгенерированного Java-кода проверяет обычный Java-компилятор, а не Astranaut (D062). Также нельзя считать технически невозможным выполнение валидатора для default: от такой автоматической проверки отказались проектным решением.

При validate = false методы setData и setValue отклоняют присваивание и сохраняют прежние данные построителя (D055). Например, при значении 5 и проверке value > 0 попытка установить -1 не меняет значение. setData сохраняет новое значение только после успешного parse и validate; неуспешный разбор также не меняет прежние данные. Отказ не сбрасывает значение к default. Форма сообщения об отказе — boolean (D056). Исключения валидатора выходят наружу (D057).

### Исключения

Перехват по parseError охватывает только выполнение parse, включая исключения указанного класса и его подклассов. При parseError = none специального перехвата нет. validate выполняется вне этой области: его исключения выходят наружу даже при совпадении класса с parseError. Неожиданные исключения parse также выходят наружу. Автоматический общий catch для Exception или Throwable не вводится.

При исключении новое значение не присваивается. Это не означает отката произвольных побочных эффектов пользовательского кода; контракт чистоты установлен в D058.

### Чистота проверок

validate не должен изменять проверяемое значение или внешнее состояние и при одинаковом значении должен давать одинаковый результат (D058). Нельзя делать результат зависимым от часов, случайности или изменяющегося внешнего состояния. Требование одинаково для datatype и узлов, включая наследуемые проверки.

Это документированный контракт автора DSL, без обещания автоматически доказать чистоту произвольного Java-кода. Исключения валидатора по-прежнему выходят наружу согласно D057.

## Наследование проверки — D059

Локальный validate полностью заменяет унаследованную проверку узла или проверку datatype. Никакого автоматического объединения через И или ИЛИ нет. Без локального validate сохраняется унаследованная проверка узла, а при её отсутствии используется проверка datatype.

```text
abstract Positive<Int> { validate(value) = "value > 0"; }
node SmallNumber : Positive { validate(value) = "value < 10"; }
```

SmallNumber допускает отрицательные значения: проверка Positive заменена целиком.

Запрещено наследование от баз с конфликтующими объявлениями проверок; собственный validate потомка не устраняет конфликт. По уточнению D060 несколько путей к одному объявлению общего предка разрешены. Совпадение текста независимых объявлений не устраняет конфликт. Базы без проверок могут участвовать в множественном наследовании при соблюдении остальных правил.

Общий datatype с одной проверкой разрешён для нескольких баз (D060). Правила default, чистоты, отказа и исключений сохраняются.

Объединение через И отменено. Для ромба действует уточнение D060:

Несколько баз, использующих один datatype с validate без собственных проверок узлов, разрешены: используется одна проверка общего datatype.

Ромбовидное наследование также разрешено, если обе ветки несут одно и то же объявление validate общего предка без переопределений:

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A;
abstract C : A;
node D : B, C;
```

D использует одну проверку из A. Сравнивается происхождение объявления, а не текст выражения. Разные независимые объявления не становятся одной проверкой из-за совпадения текста. Полная замена validate сохраняется; объединения проверок нет. Запрет D059 уточняется: несколько путей к одному объявлению сами по себе не являются конфликтом. Переопределение только в одной ветке создаёт запрещённый конфликт (D061).

### Конфликт веток — D061

Если в ромбе одна ветка переопределила validate, а другая сохранила объявление общего предка, наследование от обеих веток запрещено.

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A { validate(value) = "value < 10"; }
abstract C : A;
node D : B, C; // Ошибка: разные объявления проверки.
```

Приходят два разных объявления — из B и из A. Автоматического выбора более нового или более близкого объявления нет; порядок баз не даёт приоритета. Собственный validate в D не устраняет конфликт баз (D059). Одна проверка, пришедшая несколькими путями без переопределений, разрешена (D060).

Мотивировка пользователя: правила должны быть простыми, легко запоминаться и реализовываться; скрытые правила приоритета переопределений усложняют работу конечного пользователя.

## Наследование начального значения

Переопределённый default абстрактного узла наследуется потомками (D051). Без собственного default потомок сохраняет начальное значение базы; явный default потомка заменяет его.

```text
abstract Positive<Int> {
    default = "1";
}

node Literal : Positive;
node AnotherLiteral : Positive {
    default = "2";
}
```

Literal получает 1, AnotherLiteral — 2. То же правило действует для абстрактного потомка. Автоматическая проверка default не выполняется.

### Разные начальные значения баз

Если абстрактные базы с одним datatype задают разные default, потомок обязан явно указать собственный default (D052). Порядок баз ничего не выбирает; отсутствие переопределения — ошибка неоднозначности.

```text
abstract A<Int> { default = "1"; }
abstract B<Int> { default = "2"; }

node C : A, B { default = "3"; }
```

Можно выбрать любое своё начальное значение, не обязательно одно из базовых. Правило действует и для абстрактного потомка. Конфликт разных datatype этим не устраняется. Совпадение default определяется по точному тексту Java-выражения после декодирования строки DSL (D053). Вычисления и нормализации Java-кода нет. "1" и "1" совпадают, поэтому default можно не повторять. "1" и "1 + 0", а также "1+0" и "1 + 0" различаются и требуют явного default потомка. Пробелы и комментарии внутри выражения значимы для сравнения; форматирование самого объявления DSL вне строки — нет.

## Встроенный Java-код — D062

Встроенный в DSL Java-код переносится в генерируемую Java, после чего компилируется обычным Java-компилятором. Astranaut не реализует Java-парсер, не проверяет синтаксис и типы этих фрагментов и не анализирует выбрасываемые ими исключения. Если пользовательский код некорректен, включая необработанные checked-исключения, ошибку выдаёт Java-компилятор; исправление пользовательского кода — ответственность автора DSL.

Отдельная проверка DSL на checked-исключения validate не вводится. Генератор не выводит автоматически throws и не добавляет общий catch или оборачивание исключений для исправления пользовательского кода. Явный parseError и согласованные правила генерации сохраняются. Сам синтаксис DSL, обязательные поля и правила наследования по-прежнему проверяются: отказ от анализа касается именно встроенного Java-кода. Контракт чистоты validate остаётся документированным требованием к автору.

## Однократное задание параметров — D064

Каждый параметр в одном блоке datatype или узла можно задать только один раз. Повтор default, validate или другого параметра — ошибка DSL, даже если значения совпадают. Правило «последний побеждает» не применяется.

Разные параметры могут находиться в одном блоке, например default вместе с validate. Ограничение относится к повторам одного параметра, а не к общему числу параметров. Разрешённое переопределение унаследованного параметра в объявлении потомка сохраняется. Проверка дубликатов относится к структуре DSL и не требует анализа встроенного Java-кода.

## Неизвестные параметры — D065

Неизвестное имя параметра в блоке datatype или узла является ошибкой DSL. Например, validte(value) вместо validate(value) не игнорируется и не рассматривается как произвольная дополнительная настройка. Это проверка структуры DSL; содержимое строк с Java-кодом по-прежнему не анализируется (D062).

## Порядок параметров — D066

Параметры внутри блока datatype, абстрактного или конкретного узла можно записывать в любом порядке. Порядок записи не влияет на смысл: default перед validate и validate перед default равнозначны. Это декларации настроек, а не последовательность выполняемых команд. Требования обязательности параметров, запрет дубликатов (D064) и неизвестных имён (D065) сохраняются.

## Порядок объявлений — D067

Во всех исходниках DSL объявления можно размещать в любом порядке. Разрешение ссылок не зависит от позиции объявления в файле или от порядка обработки файлов, входящих в одну компиляцию. Правило общее, включая datatype, абстрактные и конкретные типы узлов; предварительные декларации не требуются.

Сначала собираются объявления из подключённых исходников, затем разрешаются ссылки и проверяются семантические ограничения. Неизвестная ссылка является ошибкой после рассмотрения всего доступного набора объявлений, а не только уже прочитанной части файла. Встроенные типы также учитываются.

Это расширяет D028 за пределы одного файла. Механизм подключения файлов, импорты и области видимости ещё предстоит определить; произвольный порядок не означает автоматического подключения любых файлов. Ограничения на циклы наследования и повторные объявления сохраняются. Порядок детей в схеме остаётся значимым; это отдельное понятие от порядка объявлений.
