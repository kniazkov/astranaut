# Валидация данных и переопределения в узлах

Статус: проектирование. Документ отделяет принятые правила от вопросов, которые ещё обсуждаются.

## Два уровня описания

Datatype задаёт нативный Java-тип, начальное значение, преобразования между нативным значением и текстом, ожидаемую ошибку разбора и базовую валидацию значения. Несколько типов узлов могут использовать один datatype.

Узел вправе переопределить начальное значение и валидацию для своего назначения. Такое переопределение не создаёт новый datatype и не разрешает менять унаследованный тип данных. javaType, serialize, parse и parseError не входят в согласованный набор переопределяемых параметров узла.

Пример размещения параметров:

```text
datatype Int {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
    validate(value) = "true";
}

node PositiveInteger<Int> {
    default = "1";
    validate(value) = "value > 0";
}
```

Int в примере допускает любое значение, уже представленное Java-типом int. PositiveInteger задаёт начальное значение 1 и ограничение положительности. Пример с базовой проверкой true намеренно не выбирает между заменой и логическим И: оба способа здесь дают один результат.

Возможность этих переопределений принята. Обязательность validate в datatype, значение при его отсутствии и точные правила объединения проверки datatype с проверкой узла пока не определены.

## Проверка значения

validate(value) — Java-выражение с логическим результатом. value обозначает нативное значение, а не входную строку. true означает допустимое значение, false — недопустимое.

Явно заданные данные проверяются и после успешного parse при setData, и при прямой передаче нативного значения через setValue. Ошибку синтаксического разбора и отрицательный результат валидатора необходимо различать; конкретный API отказа пока обсуждается.

Проверка default на соответствие валидатору автоматически не выполняется. За корректное начальное значение отвечает автор DSL (D047). Переопределение default в узле позволяет, например, использовать общий Int с начальным нулём и установить 1 для положительного значения.

Это не отменяет проверки синтаксиса и типов сгенерированного Java-кода. Также нельзя считать технически невозможным выполнение валидатора для default: от такой автоматической проверки отказались проектным решением.

## Наследование

Узлы наследуют datatype от абстрактных баз. Разные datatype баз конфликтуют; база без данных не мешает наследованию данных. Унаследованный datatype нельзя заменить другим (D040–D041).

Предложение о наследовании проверок абстрактных узлов и их объединении через И пользователь поддержал с требованием отдельно описать модель, начиная с валидации datatype. Проверка потомка не должна снимать ограничения его баз: для базы value > 0 и дополнительной проверки потомка value <= 100 итоговое ограничение — 0 < value <= 100.

При этом отношение проверки самого datatype к локальному переопределению узла требует отдельного уточнения. Переопределение параметра datatype и отмена ограничения абстрактной базы — разные операции; их нельзя неявно приравнивать.

## Открытые вопросы

- Заменяет ли validate узла проверку datatype или дополняет её через И?
- Обязателен ли validate в datatype; что означает его отсутствие?
- Как наследуются переопределённые default и как разрешаются разные default нескольких баз?
- Как учитываются проверки общего предка при ромбовидном наследовании?
- Что происходит при false или исключении валидатора и сохраняется ли прежнее значение построителя?
- Какие требования предъявляются к чистоте проверок, null и изменяемым нативным объектам?
- Как обеспечить одинаковые проверки при генерации и интерпретации?
