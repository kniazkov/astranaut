# Задача №18: Unicode, диагностики и интеграция

Журнал согласования: https://github.com/kniazkov/astranaut/issues/18

## Q29.1. Версия Unicode и преобразование регистра

Ответ автора: «Да» (2 ноября 2026 года).

Для преобразования регистра используются стандартные строковые операции Java с явно заданной Locale.ROOT. Версия Unicode определяется используемой JDK; собственные таблицы Unicode и независимая фиксированная версия Unicode не вводятся. При обновлении JDK поведение для отдельных символов может измениться. Это принятая цена использования стандартной библиотеки.

Использование локали окружения вместо Locale.ROOT недопустимо. Преобразуется строка целиком, а не каждый символ независимо: сохраняются контекстные преобразования и преобразования с изменением длины.

Ранее принятые контракты не меняются: индексы и длина измеряются в кодовых точках; автоматической нормализации Unicode нет.

Контрольные примеры:

| Выражение DSL | Ожидаемый результат |
|---|---|
| `"straße".toUpperCase()` | `"STRASSE"` |
| `"ΟΣ".toLowerCase()` | `"ος"` (конечная сигма) |
| `"A😀Б".length()` | `3` |
| `"é" == "e\u{301}"` | `false` |

Это поведение строковых выражений при выполнении; перечисленные корректные выражения сами по себе не требуют диагностики.

## Q29.2. Некорректная UTF-16 от пользовательского Java

Ответ автора: «Да. Мы, кажется, уже обсуждали это, но все равно да» (2 ноября 2026 года).

Любая строковая операция DSL на строке с непарным суррогатом отвергает весь кандидат правила. Частичный результат, пропуск повреждённого символа и замена на U+FFFD не допускаются. Политика распространяется на length, charAt, substring, сравнение и остальные строковые операции. Если сериализация данных при построении результата возвращает такую строку, кандидат также отвергается. Это обобщает ранее принятое правило chars.

Контрольный источник из пользовательского Java:

```java
new String(new char[]{(char) 0xD800})
```

Для полученного значения s:

| Операция | Ожидаемый результат |
|---|---|
| `s.length()` | Отказ всего кандидата, не число 1 |
| `s.charAt(0)` | Отказ, не строка с суррогатом |
| `s.substring(0, 1)` | Отказ, не частичный результат |
| `s == s` | Отказ, не true |
| Сериализация данных результата в s | Отказ, некорректный узел не публикуется |
| `chars(s)` | Прежний отказ всего кандидата |

Отказ происходит при выполнении, когда некорректная строка участвует в операции или получается при сериализации данных результата. Сам факт наличия пользовательского Java-фрагмента не является статической ошибкой. Некорректный Unicode-escape в исходнике DSL по-прежнему отвергается при чтении исходника.

Граничный допустимый пример: строка `"😀"` содержит корректную суррогатную пару; length возвращает 1, charAt(0) и substring(0, 1) возвращают весь символ, сравнение строки с собой даёт true, сериализация сохраняет символ, chars создаёт один Character.

Q29 разобран полностью.

## Q30.1. Восстановление разбора без каскада ошибок

Ответ автора: «Да, насколько это возможно. Проблема в том, что если увлечься процессом, то можно потом сказать, что у нас правила не сходятся, потому что какой-то узел не определен. И выкатить сотню сообщений внизу. А узел просто битый» (2 ноября 2026 года).

После синтаксической ошибки разбор продолжается, насколько возможно надёжное восстановление. Продолжение разбора не означает разрешение выполнять все последующие семантические проверки: анализируются только независимые части. Ошибочный фрагмент не подвергается дальнейшим проверкам, порождающим производные сообщения. При наличии ошибки генерация не запускается.

Контрольный пример при корректно объявленных A, B, C:

```text
A -> ;
B -> C;
```

На этапе синтаксического анализа сообщается об отсутствующем результате первого правила. В этом примере его завершающая точка с запятой служит надёжной границей восстановления. Первое правило пропускается, второе разбирается и проверяется независимо. Это не правило безусловного поиска ближайшего символа «;» при любом повреждении исходника.

Если повреждено объявление узла, его использования не должны порождать каскад «тип не определён», несовместимостей схем и невозможных правил, вызванных единственной исходной ошибкой. Когда имя повреждённого объявления надёжно установлено, зависимые от него проверки пропускаются; нельзя считать его просто отсутствующим или выдумывать корректную схему.

Граничный случай: если восстановление не позволяет надёжно определить объявления или зависимости, зависимый анализ не продолжается на предположениях. Точные границы восстановления при ошибке include и незакрытой кавычке остаются следующими частями Q30.

Пример зависимости: повреждено объявление A, ниже стоят `A -> B;` и `C -> D;`. При корректных независимых B, C, D первое правило не получает производных ошибок из-за повреждения A; второе можно проверить. Первичная ошибка объявления A сохраняется.

## Q30.2. Недоступный include и независимые ошибки

Ответ автора: «Да» (2 ноября 2026 года).

Если подключаемый файл недоступен, сообщается первичная ошибка include. Разбор доступного исходника продолжается; независимые синтаксические ошибки сохраняются. Ошибка «тип не объявлен» подавляется, если отсутствующее объявление могло находиться в недоступном файле. Производные проверки такого типа также пропускаются по Q30.1. Независимые проверки известных типов продолжаются. При наличии ошибки генерация не запускается.

Обязательный пример при корректно объявленных A, B, C и Marker:

```text
include "missing.dsl";
Unknown -> Marker;
A -> ;
B -> C;
```

Ожидаемые сообщения и этапы:

- При загрузке include: файл missing.dsl недоступен.
- При синтаксическом анализе: у правила A отсутствует результат.
- При разрешении имён: сообщение «Unknown не объявлен» подавляется, поскольку определение могло находиться в missing.dsl. Зависимые проверки Unknown не выполняются.
- Правило B -> C разбирается и проверяется в независимой части на основании известных объявлений. Предположение о содержимом missing.dsl не используется.

Граничный случай: если все include успешно прочитаны и объявления разобраны, но Unknown действительно нигде не объявлен, обычная ошибка неизвестного типа сохраняется. Подавление не превращает неизвестный тип в допустимый и не разрешает генерацию.

## Q30.3. Незакрытая кавычка и границы восстановления

Ответ автора: «Да» (2 ноября 2026 года).

Буквальный перевод строки внутри литерала DSL запрещён. При незакрытой кавычке на переводе строки сообщается «незакрытая строка», чтение повреждённого литерала прекращается. Дальнейший разбор этого файла продолжается только при надёжно установленном начале следующей конструкции. Если восстановление ненадёжно, разбор файла останавливается без каскада сообщений. Проверка независимых файлов продолжается.

Контрольный пример:

```text
Identifier<"abc
B -> C;
```

Первичная диагностика возникает при лексическом анализе литерала. Перевод строки прекращает чтение повреждённого литерала, но сам по себе не гарантирует восстановления синтаксического контекста. При надёжно найденном начале правила B -> C оно разбирается, и его независимые проверки выполняются. В противном случае оставшаяся часть файла не анализируется. Повреждённый фрагмент не порождает производных сообщений о незакрытых конструкциях или неизвестных типах. Генерация не запускается.

Граничный пример: `Identifier<"abc"> -> Marker;` при корректных объявлениях не содержит ошибки кавычек и разбирается обычным образом. Точка с запятой внутри строки не является границей восстановления правила. При невозможности надёжно восстановить границу предпочтительна остановка разбора файла, а не предположение о структуре оставшегося текста.

Q30 разобран полностью: восстановление допускается насколько возможно, с обязательным подавлением каскада зависимых ошибок (Q30.1–Q30.3).

## Q31.1. Координаты и диапазоны диагностик

Ответ автора: «Да. Принимаем все» (2 ноября 2026 года), в ответ на предложение правил координат.

Строки и столбцы нумеруются с 1. Столбцы измеряются в кодовых точках Unicode, а не байтах UTF-8 или кодовых единицах UTF-16. Символ 😀 занимает одну позицию; TAB также занимает одну позицию независимо от его визуальной ширины в редакторе. CRLF считается одним переводом строки. Диапазон включает начало и исключает конец.

Обязательный пример:

```text
Identifier<"😀"> -> Missing;
```

При неизвестном типе Missing и отсутствии причин подавить ошибку диагностируется имя Missing. Канонический диапазон: строка 1, столбцы [20, 27). Следующая таблица показывает различия единиц для того же диапазона, а не вводит три формата диагностик:

| Единицы, позиции с 1 от начала строки | Начало | Конец, не включён |
|---|---:|---:|
| Кодовые точки (контракт диагностики) | 20 | 27 |
| Кодовые единицы UTF-16 | 21 | 28 |
| Байты UTF-8 | 23 | 30 |

Пример с предшествующим переводом строки CRLF и TAB перед правилом: исходный текст состоит из CR, LF, TAB, затем приведённого выше правила. Missing находится в строке 2, столбцах [21, 28) по контракту диагностики. В этой второй строке соответствующие позиции UTF-16 — [22, 29), UTF-8 — [24, 31). CRLF не создаёт дополнительной пустой строки между CR и LF; TAB добавляет ровно одну позицию. Вычисление столбцов по визуальным табуляционным остановкам недопустимо.

Координаты относятся к тексту исходника: наличие многобайтного символа до ошибки не сдвигает столбцы к байтовому или UTF-16 счёту. Данное решение определяет представление координат; стабильные коды, связанные места, порядок и дедупликация диагностик остаются в Q31.

## Q31.2. Классы диагностик и локализация

Предложение постоянных строковых кодов UNKNOWN_TYPE, INCLUDE_NOT_FOUND, UNCLOSED_STRING и MISSING_RULE_RESULT отклонено.

Ответ автора: «Нет. Сделай их классами. Интерфейс ошибки/предупреждения должен по крайней мере иметь методы getMessage (на английском), getLocalizedMessage (на английском и русском), getSeverity (возвращает enum)» (2 ноября 2026 года).

Виды ошибок и предупреждений представляются отдельными классами с общим интерфейсом диагностики. Минимальный контракт:

| Метод | Обязательное поведение |
|---|---|
| getMessage | Возвращает сообщение на английском языке |
| getLocalizedMessage | Поддерживает сообщения на английском и русском языках |
| getSeverity | Возвращает уровень диагностики в виде enum |

Это минимальный набор методов, а не запрет на дополнительные свойства. Имена Diagnostic и Severity, сигнатуры и выбор языка уточнены в Q31.3. Конкретные имена классов отдельных диагностик этим пунктом не задаются. Предложение строковых кодов не является действующим решением.

Пример: неизвестный тип Missing порождает экземпляр соответствующего класса диагностики. getMessage возвращает английский текст, локализованное сообщение может быть русским. Диапазон Missing определяется Q31.1; подавление зависимых ошибок — Q30. Замена отдельного класса только строковым идентификатором UNKNOWN_TYPE не соответствует решению.

Речь идёт о контракте диагностики компилятора; реализация интерфейса и классов этим документом не заявляется.

## Q31.3. Интерфейс Diagnostic и явный выбор локали

Ответ автора: «Да» (2 ноября 2026 года).

Согласован минимальный интерфейс:

```java
interface Diagnostic {
    String getMessage();
    String getLocalizedMessage(Locale locale);
    Severity getSeverity();
}

enum Severity {
    ERROR,
    WARNING
}
```

Locale — java.util.Locale. getMessage() всегда возвращает английский текст. getLocalizedMessage(Locale locale) выбирает русский для языка ru, английский для en и любого неподдерживаемого языка. Язык задаётся явно аргументом; локаль окружения не определяет результат этого вызова. Severity содержит ERROR и WARNING.

Контрольные примеры для одного экземпляра диагностики неизвестного типа Missing:

| Вызов | Ожидаемое поведение |
|---|---|
| getMessage() | Английское сообщение |
| getLocalizedMessage(Locale.ENGLISH) | Английское сообщение |
| getLocalizedMessage(Locale.forLanguageTag("ru-RU")) | Русское сообщение |
| getLocalizedMessage(Locale.FRENCH) | Английское сообщение как запасной вариант |
| getSeverity() | Severity.ERROR |

Точная формулировка сообщения не фиксируется этими примерами. Отсутствие перевода на французский не является ошибкой и не меняет severity. Возвращать русский из getMessage() из-за настроек окружения недопустимо.

## Q31.4. Основное и связанные места диагностики

Ответ автора: «Да» (2 ноября 2026 года).

Интерфейс Diagnostic дополнен методами:

```java
Optional<SourceRange> getLocation();
List<RelatedLocation> getRelatedLocations();
```

SourceRange содержит файл и диапазон текста по правилам Q31.1. Основное место необязательно: ошибка настройки может не относиться к исходному файлу. В этом случае getLocation() возвращает Optional.empty(), без выдуманного диапазона.

RelatedLocation содержит диапазон и пояснение с поддержкой английского и русского языков. Связанные места дают контекст первичной диагностике.

Контрольный пример:

```text
node Item;
node Item;
```

При повторном объявлении типа основное место указывает на второе объявление, связанное — на первое, с пояснением о предыдущем объявлении. Диагностика возникает при проверке объявлений. Если объявление единственное и корректное, эта ошибка не возникает.

Граничный пример: ошибка значения настройки без привязки к DSL имеет пустое основное место; нельзя приписывать ей строку 1 произвольного исходника. Решение не определяет пока порядок диагностик и объединение повторных сообщений.

## Q31.5. Объединение повторных диагностик

Ответ автора: «Да» (2 ноября 2026 года).

Повторные сообщения об одной ошибке объединяются по классу диагностики, исходному файлу, диапазону и параметрам ошибки. Текст сообщения и его перевод не определяют идентичность диагностики. Одинаковые ошибки в разных местах остаются отдельными.

Обязательный пример: a.dsl и b.dsl подключают один и тот же types.dsl с ошибочным объявлением. Первичная ошибка этого объявления сообщается один раз; оба места подключения добавляются как связанные места. Основное место остаётся в types.dsl. Повторное обнаружение при обходе подключений не создаёт вторую первичную диагностику.

Контрольная схема файлов:

```text
// a.dsl
include "types.dsl";

// b.dsl
include "types.dsl";

// types.dsl
node Item;
node Item;
```

При анализе обоих подключений ошибка повторного объявления Item в одном исходном месте types.dsl представлена одной диагностикой. Связанные места сохраняют первое объявление Item (Q31.4) и оба подключения. Это правило объединения диагностик, а не изменение семантики include.

Граничные случаи:

- Одна диагностика, отображённая по-английски и по-русски, не становится двумя разными ошибками.
- Совпадающий текст сообщений в разных файлах или диапазонах не является основанием объединить ошибки.
- Разные классы или параметры ошибок в одном диапазоне не объединяются только из-за совпадения места.

## Q31.6. Порядок вывода диагностик

Ответ автора после поясняющего примера: «Да» (2 ноября 2026 года).

Сначала выводятся диагностики без привязки к исходнику. Затем диагностики упорядочиваются по пути файла, строке и столбцу основного места. При совпадении позиции ошибки предшествуют предупреждениям; далее порядок определяется именем класса диагностики и параметрами. Связанные места также упорядочиваются по файлу и позиции.

Порядок не зависит от языка сообщений и очередности обнаружения ошибок. Диагностики без исходного места также упорядочиваются по уровню, имени класса и параметрам, без зависимости от перевода или порядка обнаружения.

Согласованный пример порядка вывода (иллюстрация сортировки, не синтаксис исходника и не закреплённая формулировка сообщений):

```text
ERROR: Некорректный Java-пакет в настройках.

a.dsl:3:1 ERROR: Неизвестный тип Missing.
a.dsl:8:1 ERROR: Повторное объявление Item.
    Связанное место: a.dsl:2:1 — первое объявление Item.
a.dsl:8:1 WARNING: Избыточная конструкция.

b.dsl:1:1 ERROR: Отсутствует результат правила.
```

Ошибка в b.dsl не обгоняет предупреждение в a.dsl: расположение имеет приоритет над уровнем. Для двух разных ошибок в a.dsl:8:1 порядок определяется именами классов, затем параметрами (например, именем проблемного типа). Перевод сообщений порядок не меняет.

Граничный случай: нельзя сначала собрать все ERROR из всех файлов, а затем все WARNING; это нарушило бы согласованный приоритет файла и позиции. Связанные места относятся к своей первичной диагностике и не превращаются в самостоятельные первичные сообщения.

Q31 разобран полностью: вместо каталога строковых кодов приняты классы диагностик, интерфейс, локализация, координаты, связанные места, дедупликация и порядок (Q31.1–Q31.6).

## Q32.1. Предупреждения в обычном и строгом режимах

Ответ автора: «Да» (2 ноября 2026 года).

CLI, Maven и Java API одинаково трактуют предупреждения. В обычном режиме предупреждения не препятствуют генерации; при отсутствии других ошибок результат успешен. В строгом режиме наличие предупреждения блокирует запуск генерации и означает неуспех. В обоих режимах getSeverity() возвращает Severity.WARNING: строгий режим не превращает предупреждение в ERROR.

Обязательный пример при корректных совместимых объявлениях:

```text
(Identifier & Identifier<startsWith("a")>) -> Marker;
```

Пример служит контролем предупреждения об избыточности шаблона.

| Режим | getSeverity() | Запуск генерации | Результат при отсутствии других ошибок |
|---|---|---|---|
| Обычный | WARNING | Да | Успех |
| Строгий | WARNING | Нет | Неуспех |

Предупреждение обнаруживается при анализе DSL; решение о запуске генерации принимается после анализа с учётом режима. Строгий режим не отменяет сбор независимых диагностик.

Граничные случаи: при отсутствии ошибок и предупреждений строгий режим сам по себе не блокирует генерацию. При наличии ERROR генерация не запускается в обоих режимах. Вывод предупреждения как ERROR только из-за строгого режима недопустим.

Подавление отдельных предупреждений отклонено в Q32.2.

## Q32.2. Подавление предупреждений не вводится

Ответ автора: «Нет» (2 ноября 2026 года) на предложение подавлять отдельные виды предупреждений по их классам в настройках компилятора.

Механизм подавления отдельных предупреждений не вводится. Нет списка отключённых классов диагностик в настройках и нового синтаксиса DSL для подавления. Все обнаруженные предупреждения сохраняются с учётом общих правил дедупликации.

Для контрольного предупреждения об избыточном шаблоне из Q32.1 нельзя отключить только этот вид диагностики. В обычном режиме предупреждение выводится и не препятствует генерации; в строгом режиме оно выводится как WARNING и блокирует генерацию. То же относится к остальным предупреждениям в CLI, Maven и Java API.

Q32 разобран полностью: строгий режим согласован в Q32.1, подавление отдельных предупреждений отклонено в Q32.2.
