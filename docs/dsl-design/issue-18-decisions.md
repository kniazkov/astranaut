# Задача №18: Unicode, диагностики и интеграция

Журнал согласования: https://github.com/kniazkov/astranaut/issues/18

## Q29.1. Версия Unicode и преобразование регистра

Ответ автора: «Да» (2 ноября 2026 года).

Для преобразования регистра используются стандартные строковые операции Java с явно заданной Locale.ROOT. Версия Unicode определяется используемой JDK; собственные таблицы Unicode и независимая фиксированная версия Unicode не вводятся. При обновлении JDK поведение для отдельных символов может измениться. Это принятая цена использования стандартной библиотеки.

Использование локали окружения вместо Locale.ROOT недопустимо. Преобразуется строка целиком, а не каждый символ независимо: сохраняются контекстные преобразования и преобразования с изменением длины.

Ранее принятые контракты не меняются: индексы и длина измеряются в кодовых точках; автоматической нормализации Unicode нет.

Контрольные примеры:

| Выражение DSL | Ожидаемый результат |
|---|---|
| `"straße".toUpperCase()` | `"STRASSE"` |
| `"ΟΣ".toLowerCase()` | `"ος"` (конечная сигма) |
| `"A😀Б".length()` | `3` |
| `"é" == "e\u{301}"` | `false` |

Это поведение строковых выражений при выполнении; перечисленные корректные выражения сами по себе не требуют диагностики.

## Q29.2. Некорректная UTF-16 от пользовательского Java

Ответ автора: «Да. Мы, кажется, уже обсуждали это, но все равно да» (2 ноября 2026 года).

Любая строковая операция DSL на строке с непарным суррогатом отвергает весь кандидат правила. Частичный результат, пропуск повреждённого символа и замена на U+FFFD не допускаются. Политика распространяется на length, charAt, substring, сравнение и остальные строковые операции. Если сериализация данных при построении результата возвращает такую строку, кандидат также отвергается. Это обобщает ранее принятое правило chars.

Контрольный источник из пользовательского Java:

```java
new String(new char[]{(char) 0xD800})
```

Для полученного значения s:

| Операция | Ожидаемый результат |
|---|---|
| `s.length()` | Отказ всего кандидата, не число 1 |
| `s.charAt(0)` | Отказ, не строка с суррогатом |
| `s.substring(0, 1)` | Отказ, не частичный результат |
| `s == s` | Отказ, не true |
| Сериализация данных результата в s | Отказ, некорректный узел не публикуется |
| `chars(s)` | Прежний отказ всего кандидата |

Отказ происходит при выполнении, когда некорректная строка участвует в операции или получается при сериализации данных результата. Сам факт наличия пользовательского Java-фрагмента не является статической ошибкой. Некорректный Unicode-escape в исходнике DSL по-прежнему отвергается при чтении исходника.

Граничный допустимый пример: строка `"😀"` содержит корректную суррогатную пару; length возвращает 1, charAt(0) и substring(0, 1) возвращают весь символ, сравнение строки с собой даёт true, сериализация сохраняет символ, chars создаёт один Character.

Q29 разобран полностью.

## Q30.1. Восстановление разбора без каскада ошибок

Ответ автора: «Да, насколько это возможно. Проблема в том, что если увлечься процессом, то можно потом сказать, что у нас правила не сходятся, потому что какой-то узел не определен. И выкатить сотню сообщений внизу. А узел просто битый» (2 ноября 2026 года).

После синтаксической ошибки разбор продолжается, насколько возможно надёжное восстановление. Продолжение разбора не означает разрешение выполнять все последующие семантические проверки: анализируются только независимые части. Ошибочный фрагмент не подвергается дальнейшим проверкам, порождающим производные сообщения. При наличии ошибки генерация не запускается.

Контрольный пример при корректно объявленных A, B, C:

```text
A -> ;
B -> C;
```

На этапе синтаксического анализа сообщается об отсутствующем результате первого правила. В этом примере его завершающая точка с запятой служит надёжной границей восстановления. Первое правило пропускается, второе разбирается и проверяется независимо. Это не правило безусловного поиска ближайшего символа «;» при любом повреждении исходника.

Если повреждено объявление узла, его использования не должны порождать каскад «тип не определён», несовместимостей схем и невозможных правил, вызванных единственной исходной ошибкой. Когда имя повреждённого объявления надёжно установлено, зависимые от него проверки пропускаются; нельзя считать его просто отсутствующим или выдумывать корректную схему.

Граничный случай: если восстановление не позволяет надёжно определить объявления или зависимости, зависимый анализ не продолжается на предположениях. Точные границы восстановления при ошибке include и незакрытой кавычке остаются следующими частями Q30.

Пример зависимости: повреждено объявление A, ниже стоят `A -> B;` и `C -> D;`. При корректных независимых B, C, D первое правило не получает производных ошибок из-за повреждения A; второе можно проверить. Первичная ошибка объявления A сохраняется.

## Q30.2. Недоступный include и независимые ошибки

Ответ автора: «Да» (2 ноября 2026 года).

Если подключаемый файл недоступен, сообщается первичная ошибка include. Разбор доступного исходника продолжается; независимые синтаксические ошибки сохраняются. Ошибка «тип не объявлен» подавляется, если отсутствующее объявление могло находиться в недоступном файле. Производные проверки такого типа также пропускаются по Q30.1. Независимые проверки известных типов продолжаются. При наличии ошибки генерация не запускается.

Обязательный пример при корректно объявленных A, B, C и Marker:

```text
include "missing.dsl";
Unknown -> Marker;
A -> ;
B -> C;
```

Ожидаемые сообщения и этапы:

- При загрузке include: файл missing.dsl недоступен.
- При синтаксическом анализе: у правила A отсутствует результат.
- При разрешении имён: сообщение «Unknown не объявлен» подавляется, поскольку определение могло находиться в missing.dsl. Зависимые проверки Unknown не выполняются.
- Правило B -> C разбирается и проверяется в независимой части на основании известных объявлений. Предположение о содержимом missing.dsl не используется.

Граничный случай: если все include успешно прочитаны и объявления разобраны, но Unknown действительно нигде не объявлен, обычная ошибка неизвестного типа сохраняется. Подавление не превращает неизвестный тип в допустимый и не разрешает генерацию.
