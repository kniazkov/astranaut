## Принятые ответы


### D378. Порядок фильтра данных и проверки детей — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

В узловом шаблоне фильтр данных и проверка детей могут присутствовать одновременно. Порядок фиксирован: тип → фильтр данных → проверка детей; внешние кратность и захват as применяются к полученному шаблону по §13.1. Фильтр можно опустить, проверку детей можно опустить. D378 не решает вопрос совместного использования позиционной и именованной проверок детей (Q10).

Identifier<$text>[] проверяет тип Identifier, связывает сериализованные данные с text и требует отсутствия всех фактических детей. Его дерево разбора: NodePattern(type=Identifier, data=Capture(text), children=Positional([])). Identifier с данными "abc" без детей совпадает и связывает text="abc"; наличие ребёнка означает несовпадение. Действуют обычные статические проверки схем и захватов.

Container<"box">[Identifier] проверяет данные и весь список детей; Container<"box">(value: Identifier) проверяет данные и указанное место. В этих примерах предполагаются совместимые объявления типов с данными.

Обратный порядок Identifier[]<$text> и Container(value: Identifier)<"box"> — синтаксическая ошибка до сопоставления. Это правило относится к шаблонам; грамматика построения результата обсуждается отдельно.

Частичная продукция EBNF для шаблона с одной формой проверки детей (не полная грамматика Q06; совместная форма Q10 пока не определена):

```ebnf
typed-node-pattern = type-name, [ data-filter ], [ children-check ];
children-check = positional-children | named-children ;
```




### D379. Единственная форма списка детей — принято 01.11.2026

Задача #14, Q10. Ответ автора: «Да».

В одном узловом шаблоне или конструкторе результата разрешена только одна форма списка детей: позиционная либо именованная. Сочетание обеих форм в любом порядке — синтаксическая ошибка до сопоставления или построения результата (D379).

```text
Pair[Identifier, Number](left: Identifier) // Ошибка синтаксиса.
Pair(left: Identifier)[Identifier, Number] // Ошибка синтаксиса.
Pair(left: $a)[$a, $b]                    // Ошибка синтаксиса.
Pair[$a, $b](left: $a)                    // Ошибка синтаксиса.
```

В шаблоне совместные ограничения выражаются пересечением отдельных одноузловых шаблонов. Оба операнда проверяют один и тот же узел; действуют обычные правила пересечения. В результате выбирается одна форма задания детей, без смешивания назначений.

```text
Pair[Identifier, Number] & Pair(left: Identifier)
// Альтернативные формы результата:
Pair[$a, $b]
Pair(left: $a, right: $b)
```

Для схемы node Pair(left: Node, right: Node) пересечение совпадает с Pair, у которого left — Identifier, right — Number. Pair с переставленными детьми не совпадает. В результате при обязательных одиночных захватах a и b совместимых типов обе показанные формы строят Pair с left=$a и right=$b. Примеры предполагают объявленные Identifier и Number.



### D380. Краткие строковые проверки в условиях — принято 01.11.2026

Задача #14, Q07. Ответ автора: «Да».

В условии фильтра отдельный строковый литерал, в том числе в группирующих скобках, является краткой проверкой равенства текущих сериализованных данных этому литералу. Сокращение разрешено в целом условии и в операндах логических !, & и |. Это синтаксическое сокращение, а не неявное преобразование строки в boolean (D380).

Сначала выражение разбирается с приоритетами §13.2: вызовы и цепочки методов связываются сильнее !. Затем в позиции условия литерал заменяется на data() == литерал; группировка сохраняет этот контекст, а !, & и | передают его своим операндам. В получателе метода, аргументе вызова, конкатенации и операндах сравнения литерал остаётся строковым значением. Прочие выражения в позиции условия должны иметь булев тип. Скобки не меняют строковый тип выражения, используемого как получатель метода или операнд сравнения.

```text
Identifier<!"x">             // !(data() == "x").
Identifier<"a" | "b">         // (data() == "a") | (data() == "b").
Identifier<("a")>             // data() == "a".
Identifier<!"a".isEmpty()>    // !("a".isEmpty()), всегда true.
Identifier<data() == "a">    // Явное сравнение строк.
Identifier<("a" | "b") & !"x"> // Логическая композиция кратких проверок.
```

Для данных "a" проверка "a" | "b" успешна; для "c" — нет. ("a") совпадает только с данными "a". !"x" совпадает с любыми данными, кроме "x". !"a".isEmpty() не зависит от данных: метод получает буквальную строку "a", возвращает false, отрицание даёт true. По-прежнему отдельно проверяется тип узла Identifier.

```text
Identifier<data() == $prefix + "a"> // Допустимо при доступном prefix.
Identifier<$prefix + "a">           // Ошибка типов: строка вместо условия.
Identifier<("a" + "b")>             // Ошибка типов, даже для константной строки.
Identifier<"a".toUpperCase()>       // Ошибка типов: результат метода — строка.
Identifier<("a").isEmpty()>         // Булево выражение, всегда false.
```

Ошибка строкового выражения вместо условия обнаруживается при компиляции, а ложный допустимый фильтр означает несовпадение при выполнении. Доказанно невозможные шаблоны дополнительно подчиняются общим статическим проверкам. Краткая форма захвата Identifier<$name> сохраняется: это захват по §10.1, а не преобразование строки в условие. В результате правила строковые выражения по-прежнему задают данные; сокращение проверки к ним не применяется.



### D381. Десятичные числа с ведущими нулями — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

В десятичной целочисленной записи выражений данных ведущие нули разрешены и не меняют основание счисления: 01 имеет значение 1, 010 — значение 10, 000 — значение 0. Восьмеричная интерпретация по начальному нулю не применяется (D381).

Минус остаётся отдельным унарным оператором: -01 означает отрицание числа 1. Ранее установленный запрет унарного плюса сохраняется; +1 в позиции выражения является синтаксической ошибкой. Значения целых имеют произвольную точность по §10.2.

```text
Identifier<length() == 01>  // Длина равна 1.
Identifier<length() == 010> // Длина равна 10, не 8.
Identifier<length() == 000> // Пустые данные.
Identifier<length() == +1> // Ошибка синтаксиса: унарный плюс запрещён.
```

Identifier с данными "a" соответствует первому фильтру, а с данными "ab" — нет. Данные длиной 10 соответствуют второму фильтру; длиной 8 — нет. Эти результаты определяются при сопоставлении, если программа прошла статический анализ. Запись числа в исходнике не сохраняется в значении: toString(0010) даёт "10". Правило относится к числовым выражениям DSL, а не к разбору строк пользовательским datatype.



### D382. Булевы литералы true и false — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

В выражениях данных разрешены булевы литералы true и false, строго в нижнем регистре (D382). True и FALSE булевыми литералами не являются. Литерал имеет булев тип; строка в кавычках остаётся строкой и в позиции условия подчиняется правилу краткой проверки D380.

```text
Identifier<true>    // Проверка данных всегда выполнена; тип Identifier всё ещё проверяется.
Identifier<false>   // Ошибка компиляции: заведомо невозможный шаблон.
Identifier<"true">  // data() == "true", проверка строковых данных.
Identifier<True>    // Ошибка: True не булев литерал и не допустимое выражение здесь.
Identifier<FALSE>   // Та же ошибка.
```

Identifier<true> допускает любые данные узла Identifier. Identifier<"true"> совпадает с данными "true", но не с "false" или "True". Identifier<false> синтаксически разбирается как фильтр с булевым литералом false, однако отвергается статическим анализом как доказанно невозможный шаблон; это не ошибка лексики и не отложенный отказ при сопоставлении.

Решение фиксирует литералы выражений и не определяет возможность использования этих слов в качестве имён объявлений или захватов: полный набор зарезервированных слов и их контекстность остаются открытой частью Q08.



### D383. Межтокенные пробелы и одиночный CR — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Между токенами DSL разрешены только обычный пробел U+0020, TAB (U+0009), LF (U+000A) и CR (U+000D). CRLF считается одним переводом строки; одиночные LF и CR также являются переводами строки. Одиночный CR завершает комментарий // так же, как LF или CRLF (D383).

Неразрывный пробел U+00A0 и прочие Unicode-пробелы вне строк и комментариев являются лексической ошибкой. В строках и комментариях Unicode сохраняется по прежним правилам. Разрешение BOM в начале файла (§2.1) сохраняется; BOM не добавляется в набор межтокенных пробелов. Переводы строк внутри литералов по-прежнему запрещены (§2.4).

```text
node⟦TAB⟧A;                     // Допустимо.
node⟦U+00A0⟧A;                  // Лексическая ошибка.
node A;⟦CR⟧node B;              // Два объявления на двух строках.
// комментарий⟦CR⟧node A;       // Комментарий окончен; A объявляется.
node A;⟦CRLF⟧node B;            // Два объявления на двух строках.
```

Обозначения ⟦TAB⟧, ⟦CR⟧, ⟦CRLF⟧ и ⟦U+00A0⟧ в примерах обозначают фактические символы входного файла, а не синтаксис DSL. Недопустимый межтокенный символ обнаруживается лексическим анализом при компиляции. Это правила исходника DSL, а не политика разбираемого пользовательского текста.



### D384. Самый длинный токен и разделённые знаки — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Лексический анализ выбирает самый длинный допустимый токен, начинающийся в текущей позиции. Соседние знаки !=, ==, <=, >=, -> и <- распознаются как цельные токены. Выбор токена не зависит от того, удобен ли он для дальнейшего синтаксического разбора; разбиение на более короткие знаки для спасения ошибочной конструкции не выполняется (D384).

Пробел, перевод строки или комментарий разделяет токены. Знаки по разные стороны такого разделителя не склеиваются в составной оператор. Это правило не меняет приоритеты выражений, требования скобок для сравнений порядка в фильтрах и правила содержимого строк, символьных литералов и комментариев.

```text
Identifier<data()!="x">       // Допустимо: единый токен !=.
Identifier<data() ! = "x">    // Ошибка синтаксиса: отдельные ! и =.
Identifier<data() !/**/="x">  // Ошибка синтаксиса: комментарий разделяет знаки.
Identifier<!"x">             // Отдельный ! перед строковым литералом.
Identifier<(length()>=1)>    // Единый >=; скобки сравнения сохранены.
Identifier -> Token;         // Единый ->.
Identifier - > Token;        // Ошибка синтаксиса: это не стрелка.
```

При данных "x" первый фильтр не совпадает, при "y" совпадает. Две разорванные записи != отвергаются при синтаксическом анализе до сопоставления. Лексер в них распознаёт отдельные знаки; он не восстанавливает подразумеваемый оператор. Пример со стрелкой предполагает совместимые объявления и допустимое построение Token.



### D385. Завершающая запятая в списках детей — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

В непустом списке детей шаблона или конструктора результата разрешена одна завершающая запятая непосредственно перед закрывающей скобкой. Это относится к позиционным и именованным спискам. Запятая не добавляет элемент, отсутствие ребёнка или дополнительное место схемы; смысл совпадает с записью без неё (D385). Разрешение завершающей запятой в объявлениях сохраняется.

```text
Pair[Identifier, Number,]
Pair(left: Identifier, right: Number,)
Pair[$a, $b,]
Pair(left: $a, right: $b,)

Pair[,]        // Ошибка синтаксиса: элемент отсутствует.
Pair[$a,, $b]  // Ошибка синтаксиса: пустой элемент между запятыми.
Pair(left: $a,,) // Ошибка синтаксиса: две завершающие запятые.
```

Для схемы node Pair(left: Node, right: Node) первые два шаблона проверяют соответственно позиционный список и именованные места по прежним правилам. Pair с left типа Identifier и right типа Number проходит обе проверки; перестановка этих детей не проходит. Последние две допустимые формы результата при совместимых обязательных одиночных захватах строят тот же Pair, что и без последней запятой. Все обычные проверки типов и схем сохраняются.

В пустом списке запятая запрещена: пустые формы остаются [] и (). Недопустимые пустые элементы обнаруживаются при синтаксическом анализе до сопоставления или построения. D385 не разрешает завершающие запятые в аргументах функций, фильтрах данных, списках базовых типов либо самостоятельных цепочках шаблонов; эти контексты требуют отдельного решения Q08.



### D386. Завершающая запятая в аргументах — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

В непустом списке аргументов функции или метода разрешена одна завершающая запятая перед закрывающей круглой скобкой. Она не создаёт дополнительный аргумент и не меняет число или типы переданных значений (D386). Разрешение применяется к допустимым формам вызовов; оно не вводит новые функции, методы или перегрузки.

```text
toString(123,)          // "123", как toString(123).
$name.substring(0, 3,)  // Как $name.substring(0, 3).
$name.length()          // Корректный вызов без аргументов.
$name.length(,)         // Ошибка синтаксиса: нет последнего аргумента.
toString(123,,)         // Ошибка синтаксиса: двойная запятая.
$name.substring(, 3)   // Ошибка синтаксиса: отсутствует первый аргумент.
```

При $name = "abcd" вызов $name.substring(0, 3,) возвращает "abc". Пустой список аргументов записывается только как (). Пустые элементы и повторная завершающая запятая отвергаются синтаксическим анализом при компиляции. После синтаксического разбора сохраняются обычные проверки сигнатур: например, toString(123, 456,) содержит два аргумента и ошибочен по их количеству.



### D387. Запрет завершающей запятой в угловых скобках — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да. Там всего один или два аргумента, и они очень хорошо описаны».

Завершающая запятая на уровне угловых скобок <…> запрещена как в фильтре шаблона, так и в данных результата (D387). Фильтр содержит одну часть — условие либо захват — или две части с фиксированными ролями: условие, затем захват. Это не произвольный список аргументов. Результат содержит одно строковое выражение данных.

```text
Identifier<"a", $name>   // Допустимо: условие и захват.
Identifier<"a">          // Допустимо: только условие.
Identifier<$name>        // Допустимо: только захват в шаблоне.
Identifier<"a",>         // Ошибка синтаксиса.
Identifier<"a", $name,>  // Ошибка синтаксиса.
Identifier<$name,>       // Ошибка синтаксиса.
// В позиции результата:
Identifier<"a",>         // Ошибка синтаксиса.
Identifier<"a">          // Допустимая форма данных результата.
```

На узле Identifier с данными "a" первый шаблон совпадает и связывает name="a"; с данными "b" он не совпадает. Все отмеченные лишние запятые отвергаются синтаксическим анализом при компиляции, до сопоставления или построения результата. Обычные требования к типам, доступности захватов и схемам сохраняются.

Запрет относится к запятой самой конструкции <…>, а не к вложенным вызовам: Identifier<startsWith("a",), $name> остаётся допустимым по D386; Identifier<startsWith("a",), $name,> ошибочен из-за последней запятой фильтра. Аналогично результат Identifier<toString(123,)> синтаксически допустим, а Identifier<toString(123,),> — нет.



### D388. Запрет завершающей запятой в списке баз — принято 01.11.2026

Задача #14, часть Q08. Предложение разрешить завершающую запятую отклонено. Ответ автора: «Нет. Она тут некрасиво смотрится». Принято сохранять список без завершающей запятой.

В списке базовых типов завершающая запятая запрещена (D388). Запятая здесь разделяет два имени базовых типов и не может стоять после последнего имени, в том числе перед точкой с запятой, списком детей или блоком параметров данных. При наличии двоеточия требуется непустой список баз; пустой элемент и двойная запятая также запрещены. Все эти нарушения являются синтаксическими ошибками компиляции.

```text
abstract Named;
abstract Printable;

node Document : Named, Printable;  // Допустимо: две абстрактные базы.
node Document : Named, Printable,; // Ошибка: завершающая запятая.
node Document : Named, ();         // Ошибка: запятая перед списком детей.
node Document : ;                 // Ошибка: пустой список баз.
node Document : Named,, Printable; // Ошибка: пустой элемент.
```

Строки с объявлением Document — независимые альтернативы примера, а не повторные объявления в одном файле. Допустимая форма объявляет потомка Named и Printable. Неверные формы отвергаются синтаксическим анализом, до построения иерархии. Ранее разрешённые завершающие запятые в списках детей и аргументах вызовов сохраняются.



### D389. Запрет завершающей запятой в цепочке — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Завершающая запятая в самостоятельной цепочке шаблонов запрещена, в том числе перед стрелкой правила и перед закрывающей скобкой группировки. Запятая цепочки требует следующего шаблона. Нарушение является синтаксической ошибкой компиляции (D389).

```text
Identifier, Number -> Pair;  // Допустимая цепочка.
Identifier, Number, -> Pair; // Ошибка: нет следующего шаблона.
(Identifier, Number,)        // Ошибка: запятая перед концом группировки.
Pair[Identifier, Number,]    // Допустимо по D385: список детей.
```

Первое правило предполагает отдельно объявленные Identifier и Number и допустимое построение Pair без явно заданных детей. Оно сопоставляет два соседних узла в указанном порядке. Здесь имя Pair не означает автоматический перенос совпавших узлов в результат. Последний пример — независимый шаблон для Pair с совместимой схемой детей; список детей проверяется целиком, последняя запятая не добавляет элемент.

Разрешение D385 относится к завершающей запятой самого списка детей. Оно не разрешает завершающую запятую внутри вложенной группировки цепочки: Pair[(Identifier, Number,)] ошибочен. Запятые в цепочке не создают пустых шаблонов или пустых совпадений.



### D390. Десятичные целочисленные литералы ASCII — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Числовой литерал выражения DSL состоит из одной или более цифр ASCII 0–9: [0-9]+. Основание всегда десятичное; ведущие нули разрешены по D381. Значение — целое произвольной точности. Знак минус является отдельным унарным оператором, а унарный плюс запрещён (D390).

```text
123     // Допустимо: 123.
00123   // Допустимо: 123.
0xFF    // Ошибка: шестнадцатеричной формы нет.
0b101   // Ошибка: двоичной формы нет.
1_000   // Ошибка: разделители цифр не разрешены.
1.5     // Ошибка: дробной формы нет.
1e3     // Ошибка: экспоненциальной формы нет.
```

Эти примеры рассматриваются как целые выражения в позиции числового значения, например справа от == в Identifier<length() == …>. При значении 00123 фильтр сравнивает длину с числом 123. Недопустимые формы отвергаются при компиляции до сопоставления; они не преобразуются молча в десятичное число и не обрезаются до начального числового токена. Лексер распознаёт допустимые токены по D384; если ошибочная запись разбивается на несколько токенов, синтаксический анализ всё равно отвергает её как выражение. Точный код диагностики относится к Q31.

Ограничение относится к числовым выражениям DSL. Содержимое строк не ограничивается этой лексемой: "0xFF", "1.5" и "1e3" являются строками, а их возможный разбор в данные узла определяется соответствующим datatype. Не-ASCII цифры не образуют числовой литерал DSL.



### D391. Восемь зарезервированных слов — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Слова abstract, node, datatype, include, as, none, true и false зарезервированы: их нельзя использовать как имена типов узлов, datatype, дочерних тегов и захватов узлов или данных (D391). Запрет относится к точному написанию целого имени и действует также после $ в захватах данных. Регистр значим: Include, True и includeFile остаются допустимыми именами при соблюдении остальных правил.

```text
node include;              // Ошибка: зарезервированное имя типа.
datatype true : String;     // Ошибка: зарезервированное имя datatype.
Identifier as true         // Ошибка: зарезервированное имя захвата узла.
Identifier<$false>         // Ошибка: зарезервированное имя захвата данных.
node Box(none: Node);      // Ошибка: зарезервированный тег.

node Include;             // Допустимое имя.
node True;                // Допустимое имя.
node includeFile;         // Допустимое имя.
```

Использование зарезервированного слова в позиции имени отвергается при компиляции, до сопоставления или построения результата. Для обычных имён правило целого токена сохраняется: includeFile — одно имя, а не ключевое слово include с остатком File. Слова внутри строк и комментариев не становятся ключевыми словами. Разрешённое имя True не является булевым литералом true.

D391 не отменяет отдельные ограничения на встроенные имена типов и универсальный шаблон _. Контекстность имён параметров datatype и имён встроенных функций обсуждается отдельно; из D391 не следует их глобальное резервирование.



### D392. Контекстность имён параметров datatype — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Имена javaType, default, serialize, parse, parseError и validate являются контекстными: они обозначают параметры только в позиции имени параметра соответствующего блока описания данных. Вне этой позиции они доступны как обычные имена типов, тегов и захватов, с сохранением общих ограничений имён (D392). Глобально зарезервированными словами из D391 они не являются.

```text
node default;                 // Допустимое имя типа.
node Box(parse: Node);        // Допустимое имя тега.
Identifier as validate        // Допустимое имя захвата узла.
Identifier<$parse>            // Допустимое имя захвата данных.

datatype TextValue : String {
    default = "\"\"";         // Здесь default — имя параметра.
}

datatype BadText : String {
    unknown = "\"\"";         // Ошибка: неизвестный параметр.
}
```

Примеры независимы и предполагают необходимые объявления. Объявление типа default не меняет значение default в блоке параметров. Допустимость обычного имени не разрешает неизвестные параметры внутри такого блока: unknown отвергается при компиляции при проверке описания данных. Сохраняются прежние ограничения состава параметров datatype и параметров данных узла; D392 не добавляет параметры в блоки, где они ранее запрещены.



### D393. Контекстность имён встроенных функций и методов — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

Имена встроенных функций и методов (например, length, data, toString и toUpperCase) не резервируются глобально. Они доступны как обычные имена типов, тегов и захватов при соблюдении общих ограничений имён. В позиции вызова выражения данных они сохраняют встроенный смысл; одноимённое объявление или захват не переопределяет функцию или метод (D393).

```text
node length;                  // Допустимое имя типа.
node Box(length: Node);       // Допустимое имя тега.
Identifier<$length>           // Допустимый захват данных.
Identifier as length          // Допустимый захват узла.
Identifier<length() == 3>      // Встроенная проверка длины.
Identifier<$length>, Identifier<length() == $length.length()>
```

Примеры независимы и предполагают необходимые объявления. В последней цепочке первый Identifier захватывает строку length; у второго length() возвращает длину его собственных данных, а $length.length() — длину ранее захваченной строки. При данных "abc" и "xyz" цепочка совпадает, при "abc" и "xy" — нет.

Неизвестное имя вызова, например unknownFunction() в фильтре, остаётся ошибкой компиляции при проверке выражений: объявление одноимённого типа не создаёт функцию. Разрешение имён не добавляет новых форм вызовов и перегрузок; их таблица остаётся предметом Q09.


### D394. Строковое выражение в свободном преобразовании регистра — принято 01.11.2026

Задача #14, часть Q09. Ответ автора: «Да».

Свободные формы toUpperCase(s) и toLowerCase(s) принимают любое корректное строковое выражение s, а не только захват. Они эквивалентны соответственно (s).toUpperCase() и (s).toLowerCase(), возвращают строку и сохраняют ранее согласованные правила Unicode без локали (D394).

```text
toUpperCase($prefix + $name)      // Как ($prefix + $name).toUpperCase().
toLowerCase("HELLO")             // "hello".
toUpperCase("a".concat("b"))     // "AB".
toUpperCase(123)                 // Ошибка типов.
toLowerCase(true)                // Ошибка типов.
```

При доступных захватах prefix="pre" и name="fix" первый вызов возвращает "PREFIX". Числа и булевы значения не преобразуются в строку неявно: недопустимый тип аргумента обнаруживается при компиляции при проверке выражений.

Форма с одним явным строковым аргументом доступна в выражениях фильтра и данных результата при соблюдении правил доступности захватов. В фильтре строковый результат сам по себе не становится условием: Identifier<toLowerCase("HELLO")> ошибочен по типу, а Identifier<data() == toLowerCase("HELLO")> проверяет равенство данных строке "hello". Ранее разрешённые вызовы без аргументов внутри фильтра по-прежнему используют данные текущего узла. D394 не распространяет свободную форму с явным получателем на остальные строковые методы: эта часть Q09 остаётся открытой.


### D395. Метод toString() в выражениях данных — принято 01.11.2026

Задача #14, часть Q09. Ответ автора: «Да».

Метод toString() разрешён на строковом, числовом и булевом получателе выражения данных. Он не принимает аргументов и эквивалентен свободной функции toString(value) с тем же значением получателя (D395). Результат всегда строка. Для строки возвращается её значение без изменений; числа преобразуются без локали и разделителей, булевы значения — в "true" или "false" по ранее согласованным правилам.

```text
toString($name.length())     // Свободная функция.
$name.length().toString()    // Равнозначный метод.
"hello".toString()           // "hello".
(123).toString()             // "123".
true.toString()              // "true".
$name.length().toString(10)  // Ошибка: у метода нет аргументов.
```

При name="abc" первые два выражения возвращают "3". Метод доступен в выражениях фильтров и данных результата с обычными ограничениями доступности захватов. Вызов на захваченном узле или списке узлов ошибочен по типу: D395 не вводит сериализацию деревьев через toString(). Ненулевое число аргументов метода отвергается при компиляции при проверке сигнатуры.

Строковый результат не становится булевым условием: Identifier<true.toString()> ошибочен по типу; Identifier<data() == true.toString()> проверяет данные на равенство "true". Решение не добавляет свободную форму toString() без аргументов: ранее согласованная функция по-прежнему требует один явный аргумент.


### D396. Свободная форма всех строковых методов — принято 01.11.2026

Задача #14, часть Q09. Ответ автора: «Да».

Для всех согласованных строковых методов разрешена свободная форма с явной строкой первым аргументом: s.method(args) равнозначно method(s, args). Строка s может быть любым корректным строковым выражением; остальные аргументы, результат и граничные случаи сохраняют контракт исходного метода (D396).

```text
length($name)                    // $name.length().
startsWith($name, "get")         // $name.startsWith("get").
substring($name, 1, 3)           // $name.substring(1, 3).
substring($name, 1)              // $name.substring(1).
replace($name, "a", "b")         // $name.replace("a", "b").
trim($prefix + $name)            // ($prefix + $name).trim().
length(123)                     // Ошибка типов: получатель должен быть строкой.
```

При name="getName" length($name) возвращает 7, startsWith($name, "get") — true, substring($name, 1, 3) — "et". Неверные типы и число аргументов отвергаются при компиляции при проверке сигнатуры; неявное преобразование числа или boolean в строку не добавляется.

Правило распространяется на length, isEmpty, charAt, обе формы substring, startsWith, endsWith, contains, indexOf, lastIndexOf, replace, replaceFirst, trim, trimStart, trimEnd, concat, toLowerCase и toUpperCase из §10.3. Метод toString() и свободная функция toString(value) сохраняют отдельный контракт D395 для строки, числа и boolean. data() сохраняет прежний контракт доступа к данным текущего узла; новых форм data(s) или s.data() это решение не вводит.

Внутри фильтра сохраняются вызовы строковых методов с неявным получателем data(): startsWith("get") проверяет данные текущего узла, length() возвращает их длину. Свободная форма с явной строкой доступна также в данных результата. В результате опускать получатель нельзя.

```text
Identifier<startsWith("get"), $name>
    -> Variable<substring($name, 3)>;
Identifier<substring(1, 3) == "et">  // Неявная строка: данные текущего узла.
Identifier<substring("get", 1) == "et"> // Явная строка "get".
```

В последнем примере условие не зависит от данных, но тип Identifier всё ещё проверяется. В предпоследнем примере данные "get" проходят фильтр, а "got" — нет. При исходных данных "getName" первое правило строит Variable с данными "Name", если объявления типов и схема допускают такое построение. Различие явной и неявной формы определяется согласованными сигнатурами вызовов.


### D397. Порядок данных и детей в конструкторе результата — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

В конструкторе нового узла результата установлен порядок: тип → данные → дети. После имени типа может следовать одно выражение данных в угловых скобках, затем один список детей — позиционный либо именованный. Обратный порядок является синтаксической ошибкой компиляции (D397).

```text
Container<"box">[$child]         // Допустимый порядок.
Container<"box">(value: $child)  // Допустимый порядок.
Container[$child]<"box">         // Ошибка синтаксиса.
Container(value: $child)<"box">  // Ошибка синтаксиса.
```

Примеры подразумевают объявленный Container со строковыми данными и одним обязательным местом value, а также доступный обязательный одиночный захват child совместимого типа. Обе допустимые формы строят Container с данными "box" и ребёнком $child в месте value. Обе неверные формы отвергаются до построения результата.

Данные и список детей можно опускать, если это допускает объявление типа и ранее согласованные правила построения. Само разрешение опускать синтаксические части не разрешает терять обязательных детей, не вводит автоматического переноса совпавших узлов и не меняет обработку данных по умолчанию. Сочетание позиционного и именованного списков остаётся запрещено D379.

Частичная продукция EBNF для конструктора результата (не полная грамматика Q06):

```ebnf
node-construction = type-name, [ result-data ], [ result-children ];
result-children = positional-result-children | named-result-children ;
```

Здесь result-data содержит одно строковое выражение по правилам результата, а не фильтр шаблона. Синтаксическая допустимость отдельно проверяется на соответствие типам, схеме детей и доступности захватов.


### D398. Запрет группировки самостоятельного результата — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Нет. Нет смысла». Предложение разрешить группировку отклонено.

Группирующие круглые скобки вокруг самостоятельного результата не разрешены (D398). Предложение добавить их отклонено автором как не имеющее смысла. Результат записывается непосредственно, без дополнительной группировки.

```text
A as x -> $x;       // Допустимая форма.
A -> Result;        // Допустимая форма.
Comment -> none;    // Допустимая форма.

A as x -> ($x);     // Ошибка синтаксиса.
A -> (Result);      // Ошибка синтаксиса.
Comment -> (none);  // Ошибка синтаксиса.
A -> ((Result));    // Ошибка синтаксиса.
```

Примеры независимы и предполагают совместимые объявления типов. Первое правило возвращает захваченный узел, второе строит Result, третье удаляет совпавший Comment при сохранении корректности дерева. Недопустимые формы отвергаются при синтаксическом анализе до построения результата.

Запрет согласован с ранее принятым отсутствием группирующих скобок вокруг объединения детей (§12.3, D155). Он не запрещает круглые скобки именованного конструктора Result(value: $x), аргументов функций или группировки выражений данных, например Result<($prefix + $name).toUpperCase()>. Скобки в шаблонах также сохраняются по своим правилам.


### D399. Один as на уровень шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

На одном уровне узлового шаблона допускается не более одного захвата as. Последовательная запись нескольких as без группировки запрещена синтаксисом. Для дополнительного захвата используется явная группировка уже захваченного шаблона (D399).

```text
Identifier as x as y       // Ошибка синтаксиса.
(Identifier as x) as y     // Допустимо: два имени одного вхождения.
((Identifier as x) as y) as z // Допустимая вложенность.
(Identifier as x) as x     // Ошибка: повторное объявление имени.
```

При совпадении с узлом Identifier во второй форме x и y обозначают одно и то же вхождение исходного дерева. В третьей форме его обозначают x, y и z. Скобки не создают дополнительного узла и не меняют кратность совпадения.

Первая форма отвергается при синтаксическом анализе до сопоставления. Последняя синтаксически имеет допустимую структуру, но отвергается статической проверкой имён захватов. Общие ограничения доступности, типов и захватов внутри повторений сохраняются. Правило не запрещает независимые захваты в разных частях составного шаблона: Pair(left: Identifier as x, right: Identifier as y) содержит по одному as в каждом дочернем шаблоне.


### D400. Кратность перед захватом и явная группировка — принято 01.11.2026

Задача #14, часть Q06. Автор сначала предпочёл только запись Identifier? as x, затем уточнил: «Нет, давай такую обертку тоже не будем запрещать. Просто я говорю, что она выглядит странно, но мы её разрешим». Итог: порядок без скобок фиксирован, обёртка (Identifier as x)? разрешена; обсуждавшийся запрет обёртки не принят.

На одном уровне шаблона суффикс кратности ?, * или + ставится до захвата as: шаблон → кратность → as и имя. Суффикс непосредственно после имени захвата не разрешён. Кратность можно применять к явно сгруппированному шаблону, содержащему захват; сама такая обёртка не запрещается (D400).

```text
Identifier? as x       // Допустимый порядок.
Identifier as x?       // Ошибка синтаксиса.
(Identifier as x)?     // Допустимая группировка.
Start, (Identifier as name, Colon)? // Необязательна вся пара.
```

Первые и третья формы в составе допустимого полного шаблона связывают x с Identifier при наличии совпадения и оставляют x отсутствующим при пропуске необязательной части. Для одиночного узла первая форма проще, но это предпочтение записи, а не запрет третьей формы. Во втором примере ошибка обнаруживается при синтаксическом анализе до сопоставления.

В последнем примере Start обязателен. Если за ним совпала пара Identifier, Colon, name обозначает только Identifier; если пара пропущена, name отсутствует. Внешний захват пары обозначал бы весь фрагмент и не заменяет этот внутренний захват.

Группировка не отменяет ранее согласованных статических ограничений: обычные захваты внутри * и + по-прежнему запрещены, а полный шаблон правила обязан иметь положительное минимальное потребление. Поэтому Start, (Identifier as x)* синтаксически использует допустимый порядок, но отвергается статическим анализом из-за обычного захвата внутри повторения. Самостоятельный полный шаблон Identifier? as x также не разрешается из-за возможности пустого совпадения.


### D401. Единственная форма операции chars — принято 01.11.2026

Задача #14, часть Q09. Ответ автора: «Да».

Операция chars, создающая список узлов Character из строки, допускается только в форме chars(s) с одним строковым выражением. Методная форма s.chars() не разрешена (D401). Правило D396 о свободных формах строковых методов не распространяется на эту операцию построения детей.

```text
Text[chars($name)]       // Допустимая форма.
Text[chars("ab")]        // Два новых Character: "a", "b".
Text[$name.chars()]      // Ошибка: методная форма chars не предусмотрена.
Text[chars(123)]         // Ошибка типов: требуется строка.
```

Примеры предполагают Text с совместимой группой детей Character и доступный строковый захват name. При name="ab" первая форма создаёт те же символы, что и вторая. Методная форма отвергается при компиляции до построения результата; точный код диагностики относится к Q31. Неверный тип аргумента проверяется статически.

Сохраняется контракт §12.5: chars возвращает список даже для строки из одного символа; самостоятельно результатом правила быть не может. Аргументом может быть любое допустимое строковое выражение с доступными захватами. Правила Unicode, обработки пустой строки и ошибок не меняются. Решение не вводит новые места применения chars.


### D402. Пустая именованная проверка детей — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

Пустая именованная проверка детей в шаблоне разрешена. Container() эквивалентен Container: ни одного дочернего места не проверяется. Наличие детей само по себе не мешает совпадению. Пустая позиционная проверка Container[] имеет другой смысл: она требует полного отсутствия фактических детей (D402).

```text
Container()          // Проверка типа без ограничений на детей.
Container            // Тот же смысл.
Container[]          // Проверка типа и отсутствия всех детей.
Container<"box">()    // Проверка типа и данных, без ограничений на детей.
```

Для схемы node Container(items: Node*) первые два шаблона совпадают как с пустым Container, так и с Container, содержащим детей. Третий совпадает только с пустым Container. Пример с данными предполагает отдельное совместимое объявление Container с данными; пустые круглые скобки не отменяют фильтр "box".

Если схема типа обязательно требует детей и отсутствие детей доказанно невозможно, Container[] подчиняется общему правилу статического отклонения невозможного шаблона. Container() не вводит такого требования. Запятая в пустом списке по-прежнему запрещена: Container(,) — синтаксическая ошибка по D385.

Решение относится к проверке существующего узла в шаблоне. Оно не меняет значение пустого списка детей в объявлении или правила заполнения детей при построении результата.


### D403. Проверка детей универсального шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

Универсальный шаблон _ допускает позиционную проверку детей и пустую именованную проверку. Тип родителя при этом не ограничивается: проверяются существующий узел и его фактические дети по обычным правилам соответствующей формы (D403).

```text
_[]             // Любой узел без детей.
_[Identifier]   // Любой узел с единственным ребёнком Identifier.
_()             // Любой узел, без проверки детей.
```

_[] совпадает с любым листом и не совпадает с узлом, имеющим хотя бы одного ребёнка. _[Identifier] совпадает с узлом любого типа, если полный список его фактических детей состоит из одного Identifier; ноль детей, ребёнок другого несовместимого типа или дополнительный ребёнок означают несовпадение. Проверка типа ребёнка сохраняет обычные правила подтипов. _() эквивалентен _ по D402 и совпадает с любым одним существующим узлом независимо от детей.

Эти формы проверяют исходное дерево и не создают узлы. Они не снимают общие ограничения вложенных шаблонов, захватов и кратностей. Внешний захват, например _[Identifier] as parent, по-прежнему имеет статический тип Node: структура детей сама по себе не задаёт конкретный тип родителя.

D403 разрешает позиционные списки, включая пустой, и пустую именованную форму. Фильтр данных у _ и непустая именованная проверка его детей требуют отдельного согласования в Q06; из этих примеров их допустимость не следует.


### D404. Запрет именованных мест у универсального шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

Непустая именованная проверка детей у универсального шаблона _ запрещена (D404). У _ нет объявленных дочерних тегов. Для проверки места по тегу требуется тип шаблона, у которого этот тег объявлен. Наличие такого тега у фактического узла не снимает статического ограничения.

```text
_(value: Identifier)         // Ошибка: у _ нет объявленного тега value.
_()                         // Допустимо: пустая проверка по D402–D403.
_[Identifier]               // Допустимо: позиционная проверка по D403.
Container(value: Identifier) // Допустимо, если Container объявляет value.
```

Первая форма отвергается при компиляции при проверке дочерних тегов, до сопоставления. Она не становится динамической проверкой наличия тега у любого узла. Для схемы node Container(value: Node) последняя форма совпадает с Container, чей ребёнок value имеет подходящий тип Identifier; другой несовместимый тип ребёнка означает несовпадение.

Пустая форма _() остаётся эквивалентной _, а позиционные проверки не требуют объявленных тегов. D404 не меняет правила именованных проверок у конкретных и абстрактных типов: проверяемое место должно существовать у объявленного типа шаблона, а не только у некоторых его потомков.


### D405. Данные универсального шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

Универсальный шаблон _ допускает фильтр и захват данных по тем же правилам, что и узловой шаблон с именем типа. Используется сериализованная строка фактического сопоставляемого узла; для узла без datatype это пустая строка по §6.3 (D405).

```text
_<"hello">          // Любой узел с данными "hello".
_<$text>           // Захват данных любого узла.
_<startsWith("a")>  // Проверка префикса данных.
_<$text>[]         // Захват данных узла без детей.
```

Первый шаблон совпадает с узлом любого типа, чьи сериализованные данные равны "hello", и не совпадает с узлом без datatype. Второй захватывает строку фактического узла, в том числе "" у узла без datatype. Третий совпадает с данными "abc", но не "xyz" или "". Четвёртый дополнительно требует полного отсутствия детей: при наличии ребёнка весь шаблон не совпадает.

Порядок частей сохраняется: _ → фильтр данных → проверка детей. Поэтому _[]<$text> — синтаксическая ошибка. Пустая именованная проверка после фильтра разрешена, например _<"hello">(); непустая именованная проверка по-прежнему запрещена D404.

Краткие строковые условия, вызов data(), неявный строковый получатель методов, условия с захватом и аккумуляторы подчиняются общим правилам фильтров. D405 не отменяет ограничений захватов под отрицанием, необязательностью и повторением и не вводит преобразование данных через datatype при сопоставлении.


### D406. Запрет фильтра и проверки детей после группировки — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

После группировки шаблона запрещены фильтр данных и проверка детей: ограничения записываются внутри группы (D406). Запрет относится и к группе из единственного узлового шаблона. Скобки не создают новый узловой шаблон, к которому можно приписать эти части.

```text
(Identifier)<"abc">   // Ошибка синтаксиса.
(Identifier)[]        // Ошибка синтаксиса.
(Container)(value: Identifier) // Ошибка синтаксиса.
(Identifier<"abc">)   // Допустимо.
(Identifier[])        // Допустимо.
(Identifier)? as x    // Допустимая форма в непустом полном шаблоне.
```

Ошибочные формы отвергаются при синтаксическом анализе до сопоставления. Допустимые формы внутри скобок сохраняют обычный смысл: проверку данных "abc" либо отсутствия детей. Примеры предполагают совместимые объявления типов.

Внешние кратность и захват as после группы сохраняются по D399–D400; все ограничения доступности захватов, повторений и положительного минимального потребления полного шаблона остаются в силе. Это решение касается группировки шаблона, а не скобок выражений данных.


### D407. Запрет проверки детей после строкового шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

Непосредственно после строкового шаблона запрещена проверка детей — как позиционная, так и именованная, включая пустые списки. Ограничение не зависит от числа символов строки (D407). Строковый шаблон обозначает цепочку Character, а не отдельный родительский узел для проверки детей.

```text
"ab"[Identifier]  // Ошибка синтаксиса.
"a"[]             // Ошибка синтаксиса даже для одного символа.
"a"()             // Ошибка синтаксиса: именованная форма тоже запрещена.
Character<"a">[]   // Допустимая явная проверка одного узла.
"ab"<$text>       // Захват данных сохраняется.
"ab"+ as xs       // Кратность и захват узлов сохраняются.
```

Недопустимые формы отвергаются при синтаксическом анализе до сопоставления. Character<"a">[] проверяет один узел Character с данными "a" и отсутствием фактических детей. Проверка детей также не разрешается после захвата данных строки: "ab"<$text>[] является синтаксической ошибкой.

Разрешённые захват данных, кратность и as после строки сохраняют смысл §9.5 и прежние статические ограничения. Решение не меняет синтаксис символьного литерала в одинарных кавычках и не разрешает пустую строку в позиции шаблона.


### D408. Запрет повторных тегов в именованной проверке — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

В одном именованном списке проверок детей каждый тег разрешено указывать не более одного раза. Повтор тега является ошибкой DSL, даже если повторённые проверки одинаковы (D408). Повторные записи не объединяются автоматически в пересечение и не заменяют друг друга.

```text
Box(value: Expression, value: Identifier) // Ошибка: повтор тега value.
Box(value: Identifier, value: Identifier) // Ошибка и при одинаковых проверках.
Box(value: Expression & Identifier)       // Допустимая форма пересечения.
```

Ошибка обнаруживается при статической проверке тегов, до сопоставления. Примеры предполагают объявленное одиночное место value совместимого типа. В третьей форме оба ограничения проверяют одного ребёнка; обычные проверки совместимости, невозможности и избыточности сохраняются. Например, если Identifier является подтипом Expression, проверка Expression избыточна.

Уникальность проверяется отдельно для каждого именованного списка. Во вложенных узлах или отдельных операндах пересечения один и тот же тег может встречаться независимо:

```text
Box(value: Box(value: Identifier)) // Разные списки; повторного тега нет.
Box(value: Expression) & Box(value: Identifier) // Разные списки.
```

Вложенный пример предполагает схему Box с местом value типа Node. Ограничение относится к проверкам детей в шаблоне; назначение детей в результате этим решением не определяется.


### D409. Запрет повторных тегов в конструкторе результата — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Конечно».

В одном именованном конструкторе результата каждый тег разрешено указывать не более одного раза (D409). Повтор тега является ошибкой DSL даже при одинаковых выражениях. Назначения не перезаписывают друг друга и не объединяются неявно.

```text
Box(value: $a, value: $b) // Ошибка: повтор тега value.
Box(value: $a, value: $a) // Ошибка и при одинаковых значениях.
Block(items: $xs + $ys)  // Допустимое явное объединение детей.
```

Повтор обнаруживается при статической проверке назначений детей, до построения результата. Примеры предполагают доступные захваты и совместимые схемы: одиночное место value у Box и группу items у Block. В последней форме группа назначается один раз; дети xs и ys объединяются в указанном порядке по обычным правилам оператора +.

Уникальность проверяется отдельно для каждого конструктора. Один тег можно использовать в разных вложенных конструкторах; одно захваченное значение можно подставить в разные места. Требования совместимости типов и кратностей сохраняются.

### D410. Фильтр данных после символа или диапазона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Ответ “да” на все 4 вопроса».

После символьного литерала или диапазона разрешён обычный фильтр данных: условие, захват или условие с захватом. Условие проверяет сериализованные данные фактического Character и дополняет ограничение литерала или диапазона, а не заменяет его.

~~~text
'a..z'<!"q", $letter> // Строчная латинская буква, кроме q; захват её строки.
'a'<$letter>         // Как Character<"a", $letter>.
'a..z'<startsWith("a")> // Совпадает только с a.
'a'<"b">             // Разбор допустим, но шаблон доказанно невозможен.
~~~

Первый шаблон совпадает с r и связывает letter="r"; q не совпадает из-за фильтра, A — из-за диапазона. Последний пример отвергается статическим анализом до сопоставления. Доступность захватов и ограничения аккумуляторов остаются общими для языка.

### D411. Запрет проверки детей после символа или диапазона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Ответ “да” на все 4 вопроса».

После символьного литерала или диапазона запрещены позиционные и именованные проверки детей, включая пустые списки и запись после фильтра данных.

~~~text
'a'[]              // Ошибка синтаксиса.
'a..z'[]           // Ошибка синтаксиса.
'a'()              // Ошибка синтаксиса.
'a'<$letter>[]     // Ошибка синтаксиса.
Character<"a">[]   // Допустимая явная форма проверки узла.
~~~

Ошибки обнаруживаются при синтаксическом анализе, до сопоставления. Последняя форма сохраняет обычный смысл проверки типа, данных и отсутствия детей. Кратность и as после символьного шаблона остаются разрешены по общим правилам.

### D412. Только захват данных после строкового шаблона — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Ответ “да” на все 4 вопроса».

У строкового шаблона в двойных кавычках разрешены только формы захвата данных <$text> и <$text+>. Произвольный фильтр условия, в том числе условие вместе с захватом, запрещён. Ограничение действует также для строки из одного символа.

~~~text
"ab"<$text>              // Захват строки "ab" при совпадении.
"ab"<$text+>+            // Накопление данных совпавших повторений.
"ab"<startsWith("a")>    // Ошибка синтаксиса.
"ab"<true, $text>        // Ошибка синтаксиса.
"a"<!"b">               // Ошибка синтаксиса.
'a'<!"b">               // Допустимый символьный фильтр по D410.
~~~

Для входа ababab второе выражение накапливает "ababab". Обычные ограничения захватов под необязательностью и повторениями сохраняются. Двойные кавычки задают шаблон цепочки; одинарные — символьный шаблон. Условие после строки отвергается при синтаксическом анализе, а несовпадение допустимой строки — при выполнении.

### D413. Неразрывный токен ссылки на захват — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Ответ “да” на все 4 вопроса».

$name является единым токеном: между $ и именем нельзя вставлять пробел, перевод строки или комментарий. Это относится к связыванию и использованию захватов данных и узлов. Знак + аккумулятора — отдельный токен, поэтому пробел перед ним допустим.

~~~text
Identifier<$text>       // Захват данных.
Identifier<$text+>      // Аккумулятор.
Identifier<$text +>     // Тот же аккумулятор.
Identifier<$ text>      // Лексическая ошибка.
Identifier<$/**/text>   // Лексическая ошибка.
Identifier as item -> $item; // Ссылка на захваченный узел.
~~~

Разрыв после $ отвергается лексическим анализом до сопоставления. Общие ограничения имён, включая запрет зарезервированных слов после $, сохраняются. Пробел между as и именем не относится к этому правилу: as и имя — отдельные токены.

### D414. Заглавная первая буква имени типа узла — принято 01.11.2026

Дополнение автора: «имя типа узла начинается только с большой буквы»; основание — генерация Java-класса из этого имени.

Имя конкретного или абстрактного типа узла имеет форму [A-Z][A-Za-z0-9_]*. Первая буква — заглавная ASCII-буква; оставшиеся символы следуют ранее согласованной лексике идентификаторов. Дополнительное требование полного стиля CamelCase не вводится. Имена datatype, дочерних тегов и захватов сохраняют прежнюю форму [A-Za-z_][A-Za-z0-9_]* и ограничения зарезервированных имён.

~~~text
node Identifier;        // Допустимо.
abstract Expression;    // Допустимо.
abstract node Value;    // Допустимо.
node identifier;        // Ошибка имени типа.
abstract _Expression;   // Ошибка имени типа.
node Box(value: Node);  // Тег может начинаться со строчной буквы.
Identifier as item      // Захват может начинаться со строчной буквы.
~~~

Недопустимое имя типа отвергается при компиляции до генерации Java. Это правило сужает допустимость имён из D391–D393: прежние примеры node includeFile, node default и node length теперь ошибочны из-за первой буквы. Эти слова не становятся глобально зарезервированными: например, тег length и захват $length по-прежнему допустимы.
