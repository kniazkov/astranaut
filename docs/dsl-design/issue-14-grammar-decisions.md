### D378. Порядок фильтра данных и проверки детей — принято 01.11.2026

Задача #14, часть Q06. Ответ автора: «Да».

В узловом шаблоне фильтр данных и проверка детей могут присутствовать одновременно. Порядок фиксирован: тип → фильтр данных → проверка детей; внешние кратность и захват as применяются к полученному шаблону по §13.1. Фильтр можно опустить, проверку детей можно опустить. D378 не решает вопрос совместного использования позиционной и именованной проверок детей (Q10).

Identifier<$text>[] проверяет тип Identifier, связывает сериализованные данные с text и требует отсутствия всех фактических детей. Его дерево разбора: NodePattern(type=Identifier, data=Capture(text), children=Positional([])). Identifier с данными "abc" без детей совпадает и связывает text="abc"; наличие ребёнка означает несовпадение. Действуют обычные статические проверки схем и захватов.

Container<"box">[Identifier] проверяет данные и весь список детей; Container<"box">(value: Identifier) проверяет данные и указанное место. В этих примерах предполагаются совместимые объявления типов с данными.

Обратный порядок Identifier[]<$text> и Container(value: Identifier)<"box"> — синтаксическая ошибка до сопоставления. Это правило относится к шаблонам; грамматика построения результата обсуждается отдельно.

Частичная продукция EBNF для шаблона с одной формой проверки детей (не полная грамматика Q06; совместная форма Q10 пока не определена):

```ebnf
typed-node-pattern = type-name, [ data-filter ], [ children-check ];
children-check = positional-children | named-children ;
```




### D379. Единственная форма списка детей — принято 01.11.2026

Задача #14, Q10. Ответ автора: «Да».

В одном узловом шаблоне или конструкторе результата разрешена только одна форма списка детей: позиционная либо именованная. Сочетание обеих форм в любом порядке — синтаксическая ошибка до сопоставления или построения результата (D379).

```text
Pair[Identifier, Number](left: Identifier) // Ошибка синтаксиса.
Pair(left: Identifier)[Identifier, Number] // Ошибка синтаксиса.
Pair(left: $a)[$a, $b]                    // Ошибка синтаксиса.
Pair[$a, $b](left: $a)                    // Ошибка синтаксиса.
```

В шаблоне совместные ограничения выражаются пересечением отдельных одноузловых шаблонов. Оба операнда проверяют один и тот же узел; действуют обычные правила пересечения. В результате выбирается одна форма задания детей, без смешивания назначений.

```text
Pair[Identifier, Number] & Pair(left: Identifier)
// Альтернативные формы результата:
Pair[$a, $b]
Pair(left: $a, right: $b)
```

Для схемы node Pair(left: Node, right: Node) пересечение совпадает с Pair, у которого left — Identifier, right — Number. Pair с переставленными детьми не совпадает. В результате при обязательных одиночных захватах a и b совместимых типов обе показанные формы строят Pair с left=$a и right=$b. Примеры предполагают объявленные Identifier и Number.



### D380. Краткие строковые проверки в условиях — принято 01.11.2026

Задача #14, Q07. Ответ автора: «Да».

В условии фильтра отдельный строковый литерал, в том числе в группирующих скобках, является краткой проверкой равенства текущих сериализованных данных этому литералу. Сокращение разрешено в целом условии и в операндах логических !, & и |. Это синтаксическое сокращение, а не неявное преобразование строки в boolean (D380).

Сначала выражение разбирается с приоритетами §13.2: вызовы и цепочки методов связываются сильнее !. Затем в позиции условия литерал заменяется на data() == литерал; группировка сохраняет этот контекст, а !, & и | передают его своим операндам. В получателе метода, аргументе вызова, конкатенации и операндах сравнения литерал остаётся строковым значением. Прочие выражения в позиции условия должны иметь булев тип. Скобки не меняют строковый тип выражения, используемого как получатель метода или операнд сравнения.

```text
Identifier<!"x">             // !(data() == "x").
Identifier<"a" | "b">         // (data() == "a") | (data() == "b").
Identifier<("a")>             // data() == "a".
Identifier<!"a".isEmpty()>    // !("a".isEmpty()), всегда true.
Identifier<data() == "a">    // Явное сравнение строк.
Identifier<("a" | "b") & !"x"> // Логическая композиция кратких проверок.
```

Для данных "a" проверка "a" | "b" успешна; для "c" — нет. ("a") совпадает только с данными "a". !"x" совпадает с любыми данными, кроме "x". !"a".isEmpty() не зависит от данных: метод получает буквальную строку "a", возвращает false, отрицание даёт true. По-прежнему отдельно проверяется тип узла Identifier.

```text
Identifier<data() == $prefix + "a"> // Допустимо при доступном prefix.
Identifier<$prefix + "a">           // Ошибка типов: строка вместо условия.
Identifier<("a" + "b")>             // Ошибка типов, даже для константной строки.
Identifier<"a".toUpperCase()>       // Ошибка типов: результат метода — строка.
Identifier<("a").isEmpty()>         // Булево выражение, всегда false.
```

Ошибка строкового выражения вместо условия обнаруживается при компиляции, а ложный допустимый фильтр означает несовпадение при выполнении. Доказанно невозможные шаблоны дополнительно подчиняются общим статическим проверкам. Краткая форма захвата Identifier<$name> сохраняется: это захват по §10.1, а не преобразование строки в условие. В результате правила строковые выражения по-прежнему задают данные; сокращение проверки к ним не применяется.



### D381. Десятичные числа с ведущими нулями — принято 01.11.2026

Задача #14, часть Q08. Ответ автора: «Да».

В десятичной целочисленной записи выражений данных ведущие нули разрешены и не меняют основание счисления: 01 имеет значение 1, 010 — значение 10, 000 — значение 0. Восьмеричная интерпретация по начальному нулю не применяется (D381).

Минус остаётся отдельным унарным оператором: -01 означает отрицание числа 1. Ранее установленный запрет унарного плюса сохраняется; +1 в позиции выражения является синтаксической ошибкой. Значения целых имеют произвольную точность по §10.2.

```text
Identifier<length() == 01>  // Длина равна 1.
Identifier<length() == 010> // Длина равна 10, не 8.
Identifier<length() == 000> // Пустые данные.
Identifier<length() == +1> // Ошибка синтаксиса: унарный плюс запрещён.
```

Identifier с данными "a" соответствует первому фильтру, а с данными "ab" — нет. Данные длиной 10 соответствуют второму фильтру; длиной 8 — нет. Эти результаты определяются при сопоставлении, если программа прошла статический анализ. Запись числа в исходнике не сохраняется в значении: toString(0010) даёт "10". Правило относится к числовым выражениям DSL, а не к разбору строк пользовательским datatype.
