# Astranaut DSL: утверждённый синтаксис и семантика

**Редакция для чтения и печати · 30 октября 2026 года**

## О документе

Это связное описание согласованной части нового Astranaut DSL, зафиксированной в решениях D001–D357. Оно предназначено для последовательного чтения, а не для восстановления хронологии обсуждения. История, отменённые варианты и основания решений сохранены в [журнале проектирования](README.md).

**Статус: итог текущего этапа проектирования, не окончательная спецификация всего языка и не описание уже работающего компилятора.** Текущий материал относится к задаче №10; она остаётся открытой до завершения грамматики. Слияние PR №11 фиксирует промежуточный результат для анализа. Открытые вопросы перечислены в конце документа; их наличие не отменяет принятые решения. Реализация DSL, генератор и новая модель Node потребуют дальнейшей работы.

Существующие интерфейсы core не ограничивают новый DSL. Напротив, Node и связанные API будут переработаны под утверждённую модель. Обратная совместимость со старым DSL и старым Node не является целью.

Примеры используют согласованную запись. Фрагменты без полного набора объявлений иллюстрируют отдельную конструкцию; неявно упомянутые типы должны быть объявлены в полном исходнике. Запись цепочек с буквами a, b, c в объяснениях — обозначение узлов, а не утверждённая грамматика исходного языка. Точная проверка литеральных данных в шаблонах определена в §9.8; константные данные в результатах — в §11.7. Захват и перенос данных определены в §11.8; принятые выражения данных — в §9.10–9.43 и §11.10–11.11. Сводный аудит оставшихся вопросов находится в §22.

## 1. Назначение и основные понятия

### 1.1. Как появился Astranaut

Astranaut вырос из работы команды Ивана Князькова с синтаксическими деревьями и статическим анализом. Команда разрабатывала исследовательские проекты и писала научные статьи. Часть кода было разрешено опубликовать в open source: представление деревьев, средства их обработки и алгоритмы над ними.

Первой практической задачей была унификация синтаксических деревьев, полученных из разных источников. Команда не начинала с написания собственных парсеров для каждого языка: использовались готовые инструменты, каждый со своей формой представления дерева.

Для Java применялся готовый парсер, представлявший дерево объектами собственных классов. Для некоторых других языков использовался ANTLR с готовыми грамматиками из размещённого на GitHub проекта, собиравшего правила разбора многих языков. В других случаях источником дерева был компилятор языка. Например, в работе с Clang из проекта LLVM дерево получали в виде JSON, затем загружали и десериализовали в собственное представление.

Различия этих источников скрывались за адаптерами. Каждый адаптер приводил дерево к общей модели Astranaut — узлам и типам, описанным общими интерфейсами. После этого алгоритмам обработки не требовалось работать напрямую с классами конкретного Java-парсера, представлением ANTLR или структурой выгрузки компилятора.

Таким образом, на этом этапе унификация означала прежде всего единый интерфейс доступа к деревьям разных инструментов. Она сама по себе ещё не означала, что языковые конструкции разных языков уже сведены к одним и тем же семантическим типам узлов. Адаптация представления создавала основу для дальнейшего анализа и преобразований общими алгоритмами. По опыту команды, такой подход оказался удобным и оправданным.

Одной из основных практических проблем стали деревья разбора, полученные через ANTLR из использовавшихся грамматик. В них часто встречались вырожденные поддеревья: узел содержал единственного ребёнка, тот — ещё одного, и так далее. Возникали длинные цепочки промежуточных узлов, отражавшие устройство грамматики, но неудобные для последующего анализа.

При работе с выбранными готовыми грамматиками команда принимала такую форму результата как исходное условие. Адаптер приводил узлы к общему интерфейсу, однако сами цепочки от этого не исчезали. Поэтому требовался следующий этап — структурное преобразование дерева в более удобный для работы вид, в частности свёртка ненужных для конкретного анализа промежуточных уровней.

Это была конкретная мотивация для механизма преобразований: получить из дерева, устроенного по правилам грамматики, представление, с которым проще работать общим алгоритмам. Речь шла о преобразованиях с учётом назначения узлов, а не об обязательном удалении любого узла с одним ребёнком.

ANTLR занимает важное место в этой истории: команда пользовалась им и продолжает пользоваться. Автор проекта подчёркивает благодарность и восхищение работой его создателей. Причины разработки Astranaut не умаляют достоинств ANTLR как инструмента построения парсеров.

При этом полученного дерева разбора было недостаточно для требований команды к дальнейшей работе с деревьями сложных языков, в частности C. Требовалось явно описывать допустимую структуру узлов и сохранять её корректность на каждом этапе преобразования. В использовавшемся процессе получение дерева разбора через ANTLR само по себе не предоставляло этот контракт модели Astranaut: его нужно было обеспечивать отдельно.

По опыту команды, среди рассмотренных решений не нашлось инструмента, сочетавшего нужные гарантии с настолько простым языком описания деревьев и преобразований. Найдись подходящий готовый продукт, команда предпочла бы использовать его. Это описание причин собственного проекта и опыта выбора инструментов, а не утверждение о принципиальной невозможности построить типизированный AST поверх ANTLR или об отсутствии таких подходов во всех других проектах.

Следующим шагом стало желание сделать переиспользуемыми не только алгоритмы работы с деревьями, но и сами описания деревьев. Их требовалось выделить в самостоятельную сущность, которую можно использовать в разных проектах. Из этой потребности появилась первая версия Astranaut DSL.

Первая версия DSL поддерживала только преобразование одного узла вместе с его дочерним поддеревом в другое, менее ветвистое дерево. Исходное поддерево могло быть достаточно сложным: операция не ограничивалась устранением цепочек узлов с единственным ребёнком. Однако у сопоставляемого фрагмента был один корневой узел, и правило преобразовывало это поддерево целиком.

Свёртка нескольких соседних узлов в один узел изначально в DSL не предусматривалась. Такие операции были добавлены позже, по мере развития языка. Поэтому современную обработку цепочек не следует переносить на описание возможностей первой версии.

Ещё значительно позже появилась отдельная возможность — свёртка отдельных символов и их последовательностей. Она позволила использовать механизм преобразования деревьев для лексического и синтаксического анализа самого исходного текста, а не только для обработки дерева, уже построенного внешним парсером.

Для этого исходный код программы сначала проходил через преобразователь, создававший вырожденное плоское дерево: один родительский узел и последовательность дочерних узлов, каждый из которых представлял один символ текста. Затем те же правила преобразований объединяли отдельные символы и их последовательности в более крупные элементы — ключевые слова, строковые литералы и другие конструкции. Дальнейшие преобразования собирали из этих элементов синтаксическую структуру программы.

Так механизм постепенно приобрёл возможности лексера и парсера. По опыту автора, на этой основе стало возможно реализовать полноценный разбор, в том числе высокоуровневого языка программирования. Это отдельный этап развития: сначала преобразование готовых поддеревьев, затем свёртка нескольких соседних узлов и лишь существенно позже — построение дерева непосредственно из последовательности символов.

Это описание истории проекта, а не утверждение ещё не согласованного синтаксиса символьных правил нового DSL. Конкретное представление символа, обработка Unicode и запись шаблонов для символов и их данных в новой версии требуют отдельной спецификации.

Таким образом, язык возник из практических задач работы с деревьями: сначала были структуры и алгоритмы, затем — потребность в переиспользуемом описании узлов и их преобразований.

### 1.2. Цель проекта и назначение DSL

Цель Astranaut — получить инструмент для создания парсеров и преобразователей синтаксических деревьев. Его DSL должен быть интуитивно понятным автору правил и достаточно выразительным для описания разбора программ на высокоуровневых языках программирования.

Ожидаемый итог разработки — набор правил на новом DSL, достаточный для успешного разбора некоторого подмножества языка C. Состав этого подмножества ещё предстоит определить; поддержка всего языка C этим требованием не заявляется. Этот пример должен стать демонстрацией возможностей инструмента и основанием для публичного представления проекта как успешного эксперимента.

Выбор C связан в том числе со сложностью его конструкций. Показательный случай — объявления с указателями на функции: например, функция принимает указатель на функцию и возвращает указатель на функцию. Можно составить и более сложные вложенные объявления. В точном описании следует различать функцию и указатель на неё: в C функция не возвращается непосредственно как значение. Сложность таких деклараций связана с устройством деклараторов; адресная арифметика — другая особенность языка.

Этот пример иллюстрирует желаемый уровень выразительности, а не фиксирует сейчас полный набор конструкций демонстрационного подмножества. Окончательные правила, тестовые программы и критерии успешного разбора предстоит подготовить. Здесь зафиксирована цель, а не утверждение, что новый DSL уже реализует такой парсер.

Язык описывает типы узлов, допустимые данные и детей, шаблоны сопоставления и правила построения нового дерева. Узлы неизменяемы: преобразование создаёт результат, а не редактирует исходные объекты.

Нужно различать три действия:

- **Объявление** задаёт схему допустимого узла.
- **Шаблон** проверяет существующий узел или последовательность узлов.
- **Выражение результата** создаёт узел либо подставляет ранее захваченные узлы.

Похожие скобки в этих контекстах не означают одинаковые операции. Например, круглый список в объявлении перечисляет полную схему, а круглый список в шаблоне может проверять только часть тегов.

### 1.3. Узел, тип, данные, дети

У узла есть конкретный именованный тип и упорядоченная дочерняя структура. Узел может содержать данные определённого типа, представленные нативным значением Java. Описание datatype задаёт нативный тип этих данных и преобразования между нативным значением и строковым представлением, доступным через getData().

Данные принадлежат самому узлу. В объявлении типа узла указывается, данные какого типа могут содержать его экземпляры; это описание допустимых данных, а не само значение.

Имя однозначно определяет тип. Разные описания типов под одним именем недопустимы. Java-класс реализации не определяет тип DSL.

Дети принадлежат местам схемы. Место бывает обязательным одиночным, необязательным одиночным или повторяющимся. Повторяющееся место называется группой. Вопрос, следует ли представлять одиночное место как вырожденную группу, поставлен пользователем, но ещё не обсуждён и не решён. В этом документе одиночные позиции и повторяющиеся группы не отождествляются.

### 1.4. Тег и позиция

Тег — имя места схемы. Позиция ребёнка в плоском списке — другой индекс. Если необязательное место пусто, фактические дети сдвигаются в плоском списке, но места схемы не меняются.

Два одинаковых объекта могут встречаться в разных местах результата. Совместное использование неизменяемого объекта не объединяет эти вхождения.

### 1.5. «Если дерево существует, оно корректно»

Один из ключевых принципов Astranaut: **если синтаксическое дерево существует, это означает, что оно корректно**. Для деревьев, описанных DSL и созданных средствами, соблюдающими его контракт, корректность гарантируется самим построением. Она должна сохраняться на каждом этапе преобразования, а не проверяться только в самом конце.

Например:

~~~text
abstract Expression;

node Addition : Expression(
    left: Expression,
    right: Expression
);
~~~

Если узел Addition успешно создан, можно полагаться на следующие свойства:

- Он относится к Expression.
- У него ровно два ребёнка: не один и не три.
- Каждый ребёнок относится к Expression или одному из его допустимых подтипов.
- Оба обязательных места заполнены и соответствуют объявленной схеме.

Алгоритмам, работающим с таким узлом, не требуется каждый раз заново доказывать эти свойства. Неизменяемость узлов позволяет сохранять гарантии после создания; преобразование должно построить новый допустимый результат. Неудачное построение не должно выдавать некорректный узел за готовое дерево.

Здесь под корректностью понимается структурная правильность относительно схем DSL, а для данных — соблюдение согласованных контрактов datatype и проверок. Само наличие узла Addition не доказывает, например, разрешимость всех имён программы или сохранение её поведения после преобразования. Эти свойства требуют соответствующего анализа. Гарантия также не распространяется автоматически на произвольную стороннюю реализацию Java-интерфейса, нарушающую контракт, или на непроверенный промежуточный объект построителя.

Цель простого DSL — сделать такие структурные гарантии явными и доступными автору описания дерева. Это существенная часть замысла Astranaut наряду с удобством записи парсеров и преобразований.

## 2. Исходные файлы, имена и комментарии

### 2.1. Кодировка и окончания строк

Исходники читаются как UTF-8. BOM в начале файла разрешён. Поддерживаются LF и CRLF. Некорректный UTF-8 является ошибкой: подстановка символов замены не допускается.

Unicode разрешён в строках и комментариях. Идентификаторы пока ограничены ASCII.

### 2.2. Идентификаторы

Форма идентификатора:

~~~text
[A-Za-z_][A-Za-z0-9_]*
~~~

Регистр значим. Одиночное имя _ занято универсальным шаблоном; имена вроде _value допустимы.

Имена типов узлов и datatype находятся в общем пространстве имён. Встроенные имена уже объявлены и не могут быть переобъявлены. Повторное объявление типа ошибочно даже при одинаковом содержимом.

Используемые служебные слова включают abstract, node, datatype, include, as и none. Окончательный полный лексический перечень и контекстность всех слов ещё требуют общей грамматики.

### 2.3. Комментарии

~~~text
// Комментарий до конца строки.

/* Блочный комментарий.
   Может занимать несколько строк. */
~~~

Блочные комментарии не вкладываются. Комментарии разделяют токены. Маркеры комментариев внутри строки являются содержимым строки.

### 2.4. Строки и экранирование

Строки заключаются в двойные кавычки. Базовый перечень допустимого экранирования приведён ниже. D329–D330 (§9.9.13–9.9.14) дополнительно разрешают Unicode-экранирование во всех строковых литералах DSL.

| Запись | Значение |
|---|---|
| `\"` | Двойная кавычка |
| `\\` | Обратная косая черта |
| `\n` | Перевод строки |
| `\r` | Возврат каретки |
| `\t` | Табуляция |

Неизвестное экранирование и буквальный перевод строки внутри строкового литерала — ошибки. Сначала снимается экранирование DSL; затем полученный Java-фрагмент передаётся генератору.

~~~text
datatype MyText : String {
    default = "\"\"";
}
~~~

Здесь содержимое default после декодирования — Java-выражение пустой строки.

### 2.5. Подключение файлов

~~~text
include "../shared/common.dsl";
~~~

Директива располагается на верхнем уровне, в любом месте файла. Путь относительный, разделитель на всех ОС — /. Разрешены компоненты пути `.` и `..`. Абсолютные пути, буквы дисков, UNC-пути и обратная косая черта в декодированном пути запрещены.

Файл определяется каноническим абсолютным путём с разрешением символических ссылок. Вложенные include разрешаются относительно реального файла, а не каталога ссылки на него.

Каждый файл обрабатывается один раз. Повторные подключения и циклы include разрешены: повторно посещённый файл пропускается. При ошибке подключения компиляция прекращается с диагностикой пути, причины, места директивы и цепочки подключений.

### 2.6. Имена разрешаются независимо от порядка, правила — нет

Ссылаться на тип до объявления можно. Объявления собираются из всех подключённых файлов, затем разрешаются ссылки. Рекурсия через детей разрешена, циклы наследования запрещены.

Для правил порядок имеет значение. Просмотр начинается с главного файла, переданного на вход. Include вставляет правила подключённого файла на своём месте, рекурсивно. Если главный файл содержит правило A, include с B и C, затем D, порядок будет A, B, C, D. Повторный include ничего не добавляет.

## 3. Объявления типов узлов

### 3.1. Абстрактные и конкретные типы

~~~text
abstract Expression;
abstract node Statement;

node Marker;
node Identifier<String> : Expression;
~~~

abstract и abstract node равнозначны. Абстрактный тип нельзя создать непосредственно. node без abstract объявляет конкретный тип.

Базами могут быть только абстрактные типы. Конкретные типы не наследуются друг от друга. Это ограничение DSL, а не зависимость от возможностей старого core.

### 3.2. Полная форма

~~~text
node TypeName<Datatype> : BaseA, BaseB (
    first: ChildType,
    second: OtherType?,
    rest: ChildType*
);
~~~

Привязка datatype, базы и список детей необязательны. Привязка данных стоит сразу после имени, до списка баз.

Вместо завершающей точки с запятой объявление с параметрами данных имеет блок:

~~~text
node PositiveLiteral<Int> : Expression {
    default = "1";
    validate(value) = "value > 0";
}
~~~

После непустого списка детей разрешена завершающая запятая. Пустой список () означает отсутствие детей, но не разрешает удалить унаследованных детей.

### 3.3. Встроенный Node

Node — абстрактный общий предок всех типов узлов. Наследование от него автоматическое. Он не объявляет детей и datatype, создать его нельзя.

В шаблоне Node as x и _ as x имеют одинаковый охват и статический тип захвата Node. Подстановка такого захвата в более узкое место запрещена без доказанного статического типа; фактический вид пойманного узла не даёт неявного сужения.

## 4. Дочерние позиции и группы

### 4.1. Три кратности объявления

| Объявление | Допустимое число детей |
|---|---:|
| value: Expression | 1 |
| value: Expression? | 0 или 1 |
| items: Expression* | 0 и более |

Суффикс + принят для повторения шаблона, но не как новая кратность схемы объявления.

В абстрактных типах все места обязательно именованы. В конкретных типах собственные места могут не иметь тегов, включая повторяющиеся места. Все рассмотренные ниже формы разрешены.

### 4.2. Одна группа

~~~text
node AnonymousBlock(Statement*);
node NamedBlock(items: Statement*);
~~~

В обоих типах все дети относятся к одной группе. Именованный вариант позволяет обращаться по тегу items. Пустая группа допустима.

### 4.3. Одиночные позиции вокруг группы

~~~text
node Section(
    heading: Heading,
    Statement*,
    ending: Ending
);
~~~

heading и ending содержат по одному ребёнку; среднее место — произвольное число Statement. При пустой средней группе у узла два фактических ребёнка.

Размеры мест в этом примере — 1, N, 1. Это характеристика кратности, а не решение считать все места группами. Внутреннее представление одиночных позиций остаётся открытым.

### 4.4. Несколько групп

~~~text
node Function(Parameter*, Statement*);
node AnonymousParts(Node*, Node*);
node NamedParts(left: Node*, right: Node*);
node MixedParts(prefix: Node*, Node*, Node*);
~~~

Все объявления допустимы. Разные типы групп не всегда позволяют восстановить границу: при множественном наследовании их множества допустимых узлов могут пересекаться.

Два места одинакового типа остаются разными местами. Их нельзя автоматически объединять в одну группу.

### 4.5. Границы — часть структуры

Плоские дети [A, B] могут означать размеры групп [0, 2], [1, 1] или [2, 0]. Эти узлы структурно различны.

При построении NamedParts(left: $xs, right: $ys) или AnonymousParts[$xs, $ys] назначение известно: каждое выражение заполняет своё место. Готовый узел обязан сохранить это назначение.

Теги помогают именованным группам, но не решают задачу нескольких безымянных групп. Пустые места также должны оставаться представленными. Принят доступ к числу детей каждого места; конкретный API Node ещё не выбран.

### 4.6. Автоматическое распределение и явное построение — разные уровни

Ранее согласованное автоматическое распределение плоских детей построителем требует единственного полного решения с учётом типов и кратностей. Внутри каждой группы сохраняется исходный относительный порядок; распределение между разными местами не обязано сохранять их порядок во входном списке.

При нескольких решениях требуется явная привязка; произвольный жадный выбор запрещён. При отсутствии решений — ошибка совместимости.

Это не алгоритм позиционного шаблона и не алгоритм распределения выражений результата. В результате DSL выражения связываются с местами статически и в своём порядке. Конкретное согласование обоих режимов с новым Builder остаётся задачей API.

## 5. Наследование детей и порядок

### 5.1. Наследуемая схема

~~~text
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);

node Addition : BinaryExpression;
node Subtraction : BinaryExpression;
~~~

Потомки получают обоих детей без дублирования. При одной базе без собственного списка сохраняются состав и порядок базы.

### 5.2. Ссылки на унаследованные места

~~~text
node Reversed : BinaryExpression (
    @right,
    @left
);
~~~

@ отличает ссылку на место от имени типа безымянного ребёнка. Неизвестная ссылка — ошибка. Ссылка не создаёт нового ребёнка, а сохраняет тип и кратность унаследованного места.

При добавлении собственного ребёнка требуется полный список:

~~~text
node Extended : BinaryExpression (
    @left,
    extra: Expression?,
    @right
);
~~~

Новые места можно располагать между унаследованными. Перестановка унаследованных мест разрешена. Доступ по тегу сохраняет смысл; плоские индексы отражают новый порядок.

### 5.3. Множественное наследование

Совпадение мест определяется по тегу. Совместимые места одного тега объединяются в одно; разные теги обозначают разные места.

Для объединяемых мест должны точно совпадать тип и кратность. Даже отношение подтип/надтип между разными типами не разрешает конфликт. Собственное уточнение потомка не исправляет конфликт нескольких баз.

Если базы приносят разные составы или порядок, потомок явно перечисляет полную итоговую схему. Если списки полностью совпадают, список потомка можно опустить. Базы без детей не влияют на порядок.

### 5.4. Сужение типа ребёнка

~~~text
abstract AssignableExpression : Expression;

node Assignment : BinaryExpression (
    left: AssignableExpression,
    @right
);
~~~

Разрешено явно сузить тип места до объявленного подтипа, сохранив кратность. Расширение и замена несвязанным типом запрещены. Структурного сходства типов недостаточно.

Уточнение повторяющегося места также сохраняет суффикс *; необязательного — ?. Повторные теги в итоговом явном списке запрещены.

## 6. Типизированные данные

### 6.1. Datatype и тип узла

Datatype описывает значение, а не узел. Его имя нельзя использовать как тип ребёнка или шаблон узла.

Встроенный Int уже существует; для полного пользовательского примера выберем другое имя:

~~~text
datatype CounterValue {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
}

node Counter<CounterValue>;
node TaggedCounter<CounterValue>(items: Node*);
~~~

Данные и дети совместимы. Один datatype переиспользуется разными типами узлов.

### 6.2. Параметры datatype

| Параметр | Назначение |
|---|---|
| javaType | Нативный Java-тип |
| default | Java-выражение начального значения |
| serialize(value) | Преобразование нативного значения в строку |
| parse(text) | Разбор строки в нативное значение |
| parseError | Ожидаемое исключение разбора либо none |
| validate(value) | Необязательная дополнительная проверка |

Первые пять параметров обязательны в итоговом описании с учётом наследования. Отсутствующий validate эквивалентен true.

Порядок параметров свободный. Повтор одного параметра ошибочен даже при одинаковом тексте. Неизвестный параметр — ошибка. Необязательный validate не делает необязательными остальные поля.

### 6.3. Текстовое и нативное представление

Типизированный getValue() предоставляет нативное значение; общий getData() — строку serialize(value). Внутреннее хранение скрыто за интерфейсом.

Нативные значения ненулевые и неизменяемые. Аргумент setData не может быть null. String использует строковое представление непосредственно.

Для узла без datatype getData() всегда пуст. setData("") успешно ничего не меняет; непустая строка отклоняется. Такой узел не получает неявный datatype String. Параметры default и validate без datatype запрещены.

### 6.4. Наследование datatype

~~~text
datatype PositiveInt : Int {
    default = "1";
    validate(value) = "value > 0";
}

datatype MyText : String;
~~~

База только одна. Наследуются все параметры; любой можно переопределить. Краткая форма без блока объявляет новый datatype, не псевдоним.

При изменении javaType новый Java-тип должен быть подтипом базового; это ответственность автора. Числовое преобразование примитивов не считается наследованием. Циклы наследования запрещены.

### 6.5. Наследование datatype узла

Узел наследует datatype базы. Локальная привязка может сохранить его либо уточнить до потомка в иерархии datatype:

~~~text
abstract Literal<Int>;
node PositiveLiteral<PositiveInt> : Literal;
~~~

Разные datatype нескольких баз конфликтуют, даже если связаны наследованием. Уточнение потомка не исправляет конфликт.

Если новый datatype и базовый узел приносят конкурирующие переопределения default или validate, автоматического приоритета нет: это ошибка.

### 6.6. Контракт сериализации

parse(serialize(value)) восстанавливает эквивалентное значение, но не обязательно тот же объект. serialize(parse(text)) не обязан сохранять исходное написание: например, +007 превращается в 7.

Parse, serialize, validate и getData должны быть чистыми и детерминированными. Для одинаковых данных одного типа getData всегда даёт одинаковое содержимое строки. Это каноническое представление используется в равенстве и хэше.

## 7. Проверки, начальные значения и ошибки

### 7.1. Переопределение в узле

~~~text
abstract Positive<Int> {
    default = "1";
    validate(value) = "value > 0";
}

node SmallNumber : Positive {
    validate(value) = "value < 10";
}
~~~

SmallNumber наследует default = 1, но его проверка допускает отрицательные значения: локальный validate полностью заменяет прежний. Автоматического объединения через И или ИЛИ нет.

Для снятия проверки применяется validate(value) = "true". Отсутствие локальной проверки, наоборот, сохраняет унаследованную.

Соответствие default валидатору обеспечивает автор. Автоматическая проверка начального значения не введена.

### 7.2. Происхождение объявлений в ромбе

Одно объявление общего предка, пришедшее несколькими путями, не конфликтует с самим собой. Независимые объявления конфликтуют даже при одинаковом тексте.

~~~text
abstract A<Int> { default = "1"; }
abstract B<Int> { default = "1"; }
node C : A, B; // Ошибка: независимые источники default.
~~~

Собственный default или validate потомка не исправляет конфликт баз. Совместимость баз проверяется до локальных переопределений. Выбор по близости, тексту или порядку баз не выполняется.

### 7.3. Атомарность присваивания данных

setData и setValue возвращают boolean. При отрицательном результате проверки либо ожидаемой ошибке разбора setData возвращает false и сохраняет прежнее значение. Отказ не сбрасывает значение к default.

Присваивание происходит только после успешного разбора и проверки.

### 7.4. Исключения

В false переводится только ожидаемое исключение parse, указанное в parseError, включая его подклассы. При parseError = none специального перехвата нет.

Исключения validate и неожиданные исключения parse выходят наружу. Область перехвата parse не включает validate, даже если валидатор выбросил исключение того же класса.

### 7.5. Граница ответственности Java

Astranaut не реализует Java-парсер для строковых фрагментов. Их синтаксис, типы и checked-исключения проверяет Java-компилятор. Генератор не добавляет общий catch, throws или обёртки, чтобы исправить произвольный пользовательский код.

Контракты чистоты и неизменяемости документируются, но автоматического доказательства для произвольного Java-кода нет.

## 8. Встроенные типы данных

### 8.1. Набор и начальные значения

| Имя | Java-тип | Начальное значение |
|---|---|---|
| String | java.lang.String | пустая строка |
| Int | int | 0 |
| Long | long | 0L |
| Boolean | boolean | false |
| Double | double | 0.0 |
| CodePoint | int | 0 (U+0000) |

Имена заняты встроенными объявлениями. Переобъявлять, например, datatype Int нельзя.

### 8.2. Boolean

Только true и false, с точным регистром, без пробелов. TRUE, 1 и строка с пробелами отклоняются. Значение false успешно разбирается и не означает отказ setData.

### 8.3. Int и Long

Вся строка должна соответствовать:

~~~text
[+-]?[0-9]+
~~~

Разрешены ASCII-цифры, знак и ведущие нули. Пробелы, суффиксы, подчёркивания, шестнадцатеричные и двоичные префиксы запрещены. Переполнение — ошибка разбора.

Сериализация десятичная, без лишнего плюса, нулей и суффиксов: +007 даёт 7, -0 даёт 0.

### 8.4. Double

Обычная числовая запись:

~~~text
[+-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)([eE][+-]?[0-9]+)?
~~~

Допустимы 12, -0.5, .5, 1., +1.25e-3. Запрещены пробелы, запятая, суффиксы f/d и hex-форма.

Специальные значения принимаются ровно как NaN, Infinity, -Infinity. Варианты +Infinity, nan и -NaN запрещены.

Переполнение числовой строки до бесконечности отклоняется; явная строка Infinity разрешена. Округление допустимо, при равном расстоянии выбирается чётный младший бит. Слишком малое значение может округлиться до нуля с сохранением знака.

Сериализация — Double.toString(value). Знак нуля сохраняется, варианты битового представления NaN нормализуются в NaN. Это важно и для структурного сравнения через getData: 0.0 и -0.0 имеют разные строки.

### 8.5. CodePoint

Вводится встроенный datatype CodePoint. Его нативный Java-тип — int, начальное значение — 0 (U+0000). Допустимы только скалярные значения Unicode по D327: U+0000–U+10FFFF, кроме U+D800–U+DFFF.

Разбор данных принимает строку ровно с одним скалярным значением Unicode и возвращает его числовой код. Пустая строка, несколько кодовых точек и одиночные суррогаты недопустимы. Сериализация возвращает строку с соответствующим символом, а не десятичную запись его кода. Символ вне основной многоязычной плоскости может занимать две кодовые единицы UTF-16, оставаясь одним значением CodePoint.

Встроенный узел Character использует datatype CodePoint. Character — тип узла, CodePoint — тип его данных; это разные объявления. CodePoint доступен и другим типам узлов:

~~~text
node Letter<CodePoint>;
~~~

Имя CodePoint занято встроенным объявлением и не может быть переобъявлено, как и имена остальных встроенных datatype (§8.1). Сам datatype не является типом узла: его нельзя использовать вместо Character в шаблоне узла или схеме детей.

Это завершает выбор datatype для Character, ранее отложенный в D325–D331, и сохраняет принятые требования к данным Character. Конкретный класс ожидаемого исключения разбора и детали реализации API данным решением не выбираются.

Основание: D333.

## 9. Шаблоны узлов и детей

### 9.1. Проверка типа

~~~text
Expression
IntegerLiteral
_
~~~

Абстрактный тип принимает всех прямых и косвенных потомков. Конкретный — только свой тип, поскольку конкретное наследование запрещено. _ принимает любой один узел.

Имя типа без списков не ограничивает данные и детей.

### 9.2. Три разных пустых формы

| Шаблон | Смысл |
|---|---|
| Expression | Только проверка типа |
| Expression() | Только проверка типа: тегов для проверки нет |
| Expression[] | Тип и отсутствие всех фактических детей |

Ни одна из форм сама по себе не требует пустых данных.

### 9.3. Позиционный шаблон

~~~text
Addition[IntegerLiteral, Expression]
~~~

Проверяет полный плоский список фактических детей: ровно два ребёнка в указанном порядке. Перестановок или автоматического распределения по типам нет.

Позиционный шаблон узла не является поиском подфрагмента его детей. Повторения могут менять количество сопоставленных детей, но полное покрытие списка остаётся обязательным.

### 9.4. Именованный шаблон

~~~text
Addition(left: IntegerLiteral)
Addition(right: Expression, left: IntegerLiteral)
~~~

Проверяет только указанные теги. Остальные дети не ограничены. Порядок записи тегов не влияет на результат.

Тег должен быть объявлен у типа, указанного в шаблоне, включая наследование. Тег, существующий только у отдельных потомков этого типа, не подходит.

### 9.5. Одиночные места и отсутствие

~~~text
Return(value: IntegerLiteral)
Return(value: none)
~~~

Обычный шаблон требует наличия ребёнка. none требует отсутствия необязательного ребёнка. Для обязательного места none — ошибка DSL.

Список после тега одиночного места запрещён:

~~~text
Return(value: [IntegerLiteral]) // Ошибка.
Return(value: IntegerLiteral[]) // Узел-ребёнок без детей.
~~~

Во втором случае [] относится к IntegerLiteral, а не к месту value.

### 9.6. Повторяющиеся группы по тегу

~~~text
Block(items: [Return, ExpressionStatement])
Block(items: [Return])
Block(items: [])
Block(items: none)
~~~

Список проверяет всю указанную группу. Пустой список и none равнозначны. Даже для одного элемента квадратные скобки обязательны:

~~~text
Block(items: Return) // Ошибка, items — повторяющееся место.
~~~

Другие группы не проверяются, если не перечислены.

### 9.7. Сложные шаблоны внутри цепочки

~~~text
Negation[Expression as a], Plus, Expression as b
    -> Addition[Negation[$a], $b];
~~~

Первый элемент фрагмента проверяет целое поддерево. Сложные вложенные шаблоны не выделяются в отдельный язык правил и разрешены в одноэлементных и многоэлементных последовательностях.

### 9.8. Точная проверка данных

~~~text
Identifier
Identifier<"count">
Identifier<"">
~~~

Первый шаблон не ограничивает данные. Второй требует точного равенства getData() строке "count", третий — пустой строке. Сравнивается сериализованное представление данных; строковый литерал шаблона не разбирается в нативное значение datatype.

В объявлении `node Identifier<String>;` угловые скобки содержат имя типа данных; в шаблоне `Identifier<"count">` — строку для сравнения. Захват данных определён отдельно в D201 (§11.8). Константные данные создаваемого узла описаны в §11.7 (D200).

### 9.9. Общее имя данных и равенство

~~~text
Identifier<$name>, Identifier<$name> -> Identifier<$name>;
~~~

Одинаковое имя в нескольких позициях данных связывает их с одним общим значением. Все соответствующие строки getData() должны совпасть; иначе шаблон не подходит. Захват и проверка равенства не разделяются специальным знаком (D207).

Например, данные "a", "a" подходят, а "a", "b" — нет. Порядок вхождений и направление поиска не меняют требования равенства. В результате $name использует общее значение.

Это заменяет прежние примеры с `<as name>` и уточняет D203–D206. Предложенная отдельная форма `<=$name>` не принята.

Помимо ссылки на захват предусмотрены операции над данными. Их перечень, синтаксис, типизация, зависимости и правила вычисления ещё не утверждены.

### 9.9.1. Символьные литералы, диапазоны и Character

В шаблонах вводятся символьные литералы в одинарных кавычках. Одиночный символ — сокращение проверки типа Character и точного совпадения его данных:

~~~text
'a'
// Эквивалентно:
Character<"a">
~~~

Внутри одинарных кавычек разрешена запись диапазона с двумя точками. Диапазон включает обе границы и сопоставляет один символ, а не последовательность символов:

~~~text
'a..c'
// Эквивалентно:
(Character<"a"> | Character<"b"> | Character<"c">)
~~~

В этом примере a, b и c — латинские буквы. В исходном сообщении правая граница визуально похожа на кириллическую с; здесь записан латинский c в соответствии с приведённым пользователем раскрытием a, b, c. Смешанные алфавиты и общий порядок диапазонов этим примером не определяются.

Character закрепляется как предусмотренный языком тип узла, представляющий ровно один символ. Произвольная строка из нескольких символов не является допустимыми данными Character; пустая строка также не представляет символ. Это тип узла, а не новое имя datatype и не Java char.

D317 утверждает эти формы в шаблоне. D332 (§11.12) дополнительно разрешает одиночный символьный литерал в результате; диапазоны в результате запрещены. Захват данных принят в D318 (§9.9.2), участие в общих конструкциях DSL — в D319 (§9.9.3).

Единица символа определена в D320 (§9.9.4): одна кодовая точка Unicode. Порядок диапазона и равнозначность прямой и обратной записи границ определены в D321 (§9.9.5). Отдельно предстоит уточнить допустимость границ, экранирование одинарной кавычки/обратной косой черты и представление точки, а совпадающие границы разрешены без предупреждения по D322 (§9.9.6). Встроенный конкретный Character без детей и запрет его переобъявления приняты в D325 (§9.9.9). Нативный Java-тип int принят в D326 (§9.9.10). Default U+0000 принят в D331 (§9.9.15). Привязка datatype и формы создания Character в результате ещё обсуждаются. Конкретный Java API остаётся отложенным по D198.

Основание: D317.

### 9.9.2. Захват данных символьных шаблонов

После символьного литерала или диапазона разрешены обычный захват строковых данных и аккумулятор в угловых скобках:

~~~text
'a'<$letter> -> Identifier<$letter>;
'a..z'<$letter> -> Identifier<$letter>;
'a..z'<$text+>+ -> Identifier<$text>;
~~~

Обычный захват получает фактически встретившийся символ как строку getData(), а не текст записи диапазона. Например, при совпадении 'b' с диапазоном 'a..z' значение letter равно "b".

Для одиночного символа 'a'<$letter> эквивалентно Character<"a", $letter>. Диапазон 'a..c'<$letter> эквивалентен (Character<"a", $letter> | Character<"b", $letter> | Character<"c", $letter>).

В 'a..z'<$text+>+ плюс внутри угловых скобок обозначает накопление данных, а внешний плюс — одно или более повторений шаблона. Подходящая цепочка символов hello даёт Identifier<"hello">. Применяются обычные правила начального пустого значения, порядка накопления и отката неудачного кандидата.

Форма 'a..z' as x захватывает сам узел Character, а 'a..z'+ as xs — список узлов. Это не захват строковых данных. Все общие ограничения DSL сохраняются: например, обычный захват данных внутри повторения 'a..z'<$letter>+ запрещён; для накопления нужен $letter+. Повторное обычное имя данных проверяет равенство по D207.

Основание: D318.

### 9.9.3. Символьные шаблоны в общих конструкциях DSL

Символьный литерал и диапазон являются сокращёнными узловыми шаблонами Character и участвуют в обычных конструкциях DSL по их общим правилам. Они не образуют отдельный механизм сопоставления текста.

~~~text
'p', 'u', 'b', 'l', 'i', 'c' -> PublicModifier;
~~~

Это правило сопоставляет шесть соседних узлов Character с соответствующими данными в указанном порядке и заменяет их одним PublicModifier. Полная форма шаблона:

~~~text
Character<"p">, Character<"u">, Character<"b">,
Character<"l">, Character<"i">, Character<"c"> -> PublicModifier;
~~~

PublicModifier должен быть объявлен, его построение и замена должны быть допустимы в текущем контексте. Цепочка остаётся внутри одной группы; сохраняются порядок правил, направление поиска, максимальное полное совпадение и проверки неоднозначности.

К символьным шаблонам применимы группировка, альтернативы, пересечения, отрицание, кратности и захваты в тех же допустимых сочетаниях, что к соответствующим полным шаблонам Character. Новые исключения из общих ограничений не вводятся.

В частности, отрицание 'a' означает отрицание полного узлового шаблона Character<"a">: !'a' может совпасть и с узлом другого типа. Ограничение только другими символами требует проверки Character, например (Character & !'a'). Это следствие D292–D295, а не изменение семантики отрицания.

Правило для public само по себе не проверяет границы идентификатора: последовательность этих шести символов может встретиться внутри более длинной цепочки. Автоматическая проверка границ слова не вводится. D319 относится к шаблонам; создание Character одиночным символьным литералом отдельно разрешено в D332 (§11.12).

Основание: D319.

### 9.9.4. Character содержит одну кодовую точку Unicode

Один узел Character представляет ровно одну кодовую точку Unicode. Это та же единица, которая принята для длины и индексации строковых выражений DSL (D233). Символ не определяется размером Java char или количеством кодовых единиц UTF-16 и не отождествляется с графемой.

'я' и '😀' соответствуют одному Character каждый. Буква e и следующий за ней отдельный комбинируемый акцент U+0301 — две кодовые точки и, соответственно, два Character. Предсоставленная буква é (U+00E9) — одна кодовая точка. Автоматическая нормализация не выполняется по D244.

Данные Character должны содержать ровно одну кодовую точку. Пустая строка и строка из нескольких кодовых точек недопустимы. Одиночный символьный литерал подчиняется тому же требованию; запись диапазона остаётся отдельной формой шаблона из D317 и не является многосимвольными данными Character.

Решение закрывает вопрос единицы символа из D317. Порядок границ диапазона определён в D321 (§9.9.5). Экранирование, полная схема Character и обработка некорректных последовательностей кодирования остаются отдельными вопросами.

Основание: D320.

### 9.9.5. Диапазоны по Unicode с независимым порядком границ

Диапазон символьного шаблона определяется числовыми значениями кодовых точек Unicode и включает обе границы. Порядок не зависит от языка, алфавита или локали.

Порядок записи границ не влияет на множество допустимых символов: 'a..z' и 'z..a' равнозначны. Для границ с кодовыми точками u и v подходит символ с кодовой точкой c, если min(u, v) ≤ c ≤ max(u, v). Обратная запись не является ошибкой и не меняет направление поиска цепочки или порядок накопления данных.

Например, 'a..c' и 'c..a' принимают ровно латинские a, b и c. Кириллический диапазон 'а..я' не включает ё: U+0451 находится вне интервала U+0430–U+044F. Диапазон не дополняется буквами по правилам естественного языка.

Шаблон диапазона по-прежнему сопоставляет один узел Character с одной кодовой точкой по D317/D320. Захват получает фактически встретившийся символ; диапазон не создаёт последовательность символов. Направление поиска задаётся стрелкой правила по общим правилам DSL.

Это уточняет D317 и закрывает вопросы порядка диапазона и обратной записи границ. Совпадающие границы разрешены без предупреждения по D322 (§9.9.6). Экранирование и допустимость отдельных границ остаются следующими вопросами.

Основание: D321.

### 9.9.6. Диапазон с одинаковыми границами

Диапазон с одинаковыми границами разрешён и полностью эквивалентен одиночному символьному шаблону: 'a..a' означает то же, что 'a', то есть Character<"a">.

За саму запись диапазона с совпадающими границами предупреждение не выдаётся. Она не считается избыточной проверкой, требующей предупреждения по D313; строгий режим D315 не делает такую запись ошибочной.

Эквивалентность сохраняется при захватах, повторениях и использовании в других допустимых конструкциях DSL. Например, 'a..a'<$letter> эквивалентно 'a'<$letter>, а 'a..a'<$text+>+ — 'a'<$text+>+. Общие проверки окружающего шаблона остаются в силе.

Решение закрывает вопрос совпадающих границ из D317/D321. Экранирование и остальные ещё не согласованные пограничные случаи символьных литералов остаются отдельными вопросами.

Основание: D322.

### 9.9.7. Экранирование символьных литералов

В символьных литералах в одинарных кавычках приняты следующие escape-последовательности:

~~~text
'\''   // Одинарная кавычка.
'\\'   // Обратная косая черта.
'\n'   // Перевод строки LF.
'\r'   // Возврат каретки CR.
'\t'   // Горизонтальная табуляция.
'"'    // Двойная кавычка без экранирования.
~~~

Неизвестная escape-последовательность является ошибкой DSL. Буквальный перевод строки внутри символьного литерала также запрещён; для LF и CR используются соответствующие escape-последовательности.

После снятия экранирования одиночный символьный литерал должен обозначать ровно одну кодовую точку Unicode по D320. Экранирование не меняет значения символьного шаблона, правил захвата и его участия в общих конструкциях DSL.

Это решение утверждает перечисленные формы для символьных литералов. Оно не добавляет новые escape-последовательности в строки в двойных кавычках из §2.4 спецификации. Позднее D329 (§9.9.13) добавляет Unicode-экранирование для символов и строк данных.

Лексическая обработка границ диапазона, содержащих экранированные символы или точки, определена в D324 (§9.9.8).

Основание: D323.

### 9.9.8. Экранированные границы диапазонов и точки

Обе границы диапазона используют те же правила представления одного символа и экранирования, что одиночный символьный литерал (D320/D323). Внутри одинарных кавычек допустима одна из двух форм: один символ либо один символ, разделитель из двух буквальных точек .. и ещё один символ.

Каждая граница после снятия экранирования обозначает ровно одну кодовую точку Unicode. Разделитель .. является синтаксисом диапазона, а не частью данных границы. Обычная точка может быть самим символом границы, без дополнительного экранирования.

~~~text
'\t..\r'  // Диапазон U+0009–U+000D включительно.
'.'       // Одна точка.
'....'    // Точка + разделитель .. + точка: диапазон от точки до точки.
'..'      // Ошибка: два символа, не одиночный символ и не диапазон.
'.....'   // Ошибка: лишняя точка.
~~~

Диапазон '....' равнозначен '.' по D322. Порядок границ несущественен, обе границы включены по D321. В частности, '\r..\t' эквивалентен '\t..\r'.

Редакционное исправление примера из обсуждения: ассистент ошибочно написал пять точек для диапазона от точки до точки. По принятому правилу «один символ + две точки + один символ» их четыре (1 + 2 + 1). Здесь исправлен подсчёт в примере; специальное исключение для пяти точек не вводится.

Это закрывает вопрос лексического разбора диапазонов с точками и экранированными границами из D317/D323. Правила допустимых кодовых точек и полная встроенная схема Character остаются отдельными вопросами.

Основание: D324.

### 9.9.9. Встроенный конкретный Character без детей

Character является встроенным конкретным типом узла без детей. Его имя зарезервировано в общем пространстве имён типов узлов и datatype. Объявлять Character в пользовательском DSL не требуется; переобъявление запрещено.

Данные Character представляют ровно одну кодовую точку Unicode по D320. Пустая строка и несколько кодовых точек недопустимы. Как и остальные типы узлов, Character наследуется от Node. Пользовательское наследование от Character запрещено общим правилом D013: базами могут быть только абстрактные типы.

Символьные литералы и диапазоны сопоставляют этот встроенный тип по D317–D324. Отсутствие детей — часть его схемы, а не условие, которое требуется отдельно добавлять к каждому символьному шаблону.

Решение фиксирует статус, имя и дочернюю схему Character. Нативный Java-тип данных int принят в D326 (§9.9.10). Начальное значение U+0000 принято в D331 (§9.9.15). Datatype и формы построения результата ещё требуют согласования. Высказанное пользователем предположение о Java char не считается утверждённым выбором представления: char хранит одну кодовую единицу UTF-16 и не вмещает все кодовые точки, разрешённые D320.

Основание: D325.

### 9.9.10. Нативное значение Character — Java int

Нативный Java-тип данных встроенного узла Character — int. Значение содержит числовой код одной кодовой точки Unicode, а не кодовую единицу UTF-16. Например, для 😀 (U+1F600) нативное значение равно 0x1F600.

Общий getData() возвращает строку с этой кодовой точкой, а не десятичную запись её номера. Поэтому строковый захват данных Character сохраняет прежнюю семантику D318: для 😀 он получает строку "😀", не "128512". Выбор int не меняет единицу символа, правила диапазонов или накопления строк.

Нативный тип int не означает допустимость любого значения Java int. Допустимые значения определены в D327 (§9.9.11): скалярные значения Unicode. Обработка недопустимых значений на границах API требует отдельного решения. Начальное значение U+0000 определено в D331 (§9.9.15). Выбор или объявление datatype и формы построения результата ещё не определены.

Это утверждает предложение о нативном int после D325. Java char для хранения полного значения кодовой точки не используется.

Основание: D326.

### 9.9.11. Допустимые значения Character — скалярные значения Unicode

Допустимые значения данных Character — скалярные значения Unicode: кодовые точки от U+0000 до U+10FFFF включительно, кроме U+D800–U+DFFF. Исключённый диапазон используется для суррогатных кодовых единиц UTF-16 и не допускается как самостоятельное значение Character.

Для нативного int из D326 это означает условие: значение не меньше 0, не больше 0x10FFFF и не находится между 0xD800 и 0xDFFF включительно. Отрицательные значения, значения выше 0x10FFFF и отдельные суррогаты недопустимы.

Например, 😀 (U+1F600) допустим. Его представление парой кодовых единиц UTF-16 в Java String не означает два Character: пара кодирует одно допустимое скалярное значение. Одиночный суррогат в строковых данных не представляет допустимое значение Character.

Это уточняет понятие одной кодовой точки в D320 и ограничивает допустимые значения int из D326. Данные Character по-прежнему не могут быть пустой строкой или строкой из нескольких кодовых точек.

Начальное значение U+0000 принято в D331 (§9.9.15). Конкретная привязка datatype и обработка отказа на границах API ещё требуют согласования. Диапазон через область суррогатов разрешён с исключением недопустимых значений и с допустимыми границами по D328 (§9.9.12).

Основание: D327.

### 9.9.12. Диапазоны через область суррогатов

Диапазон символьного шаблона разрешён, даже если числовой интервал между его границами пересекает область суррогатов U+D800–U+DFFF. Из такого интервала принимаются только допустимые значения Character по D327; суррогатные значения исключаются.

Обе границы диапазона сами должны быть допустимыми скалярными значениями Unicode. Недопустимая граница не исправляется обрезанием, заменой или пропуском: такой символьный шаблон недопустим.

Например, интервал от U+D7FF до U+E000 включает ровно два допустимых значения: U+D7FF и U+E000. Все значения между ними относятся к суррогатам и не принимаются. Здесь обозначения U+ используются для пояснения кодов, а не как новый синтаксис литералов DSL.

Обе границы включены, их порядок несущественен по D321. Множество принимаемых значений — пересечение замкнутого числового интервала между границами с множеством скалярных значений Unicode.

Это закрывает вопрос пересечения диапазоном исключённой области, оставленный в D327. Решение не разрешает создавать Character с суррогатным значением и не требует фактически перечислять все кодовые точки при реализации проверки диапазона.

Основание: D328.

### 9.9.13. Unicode-экранирование символов и строк данных

Вводится Unicode-экранирование \u{HEX}: внутри фигурных скобок от одной до шести шестнадцатеричных цифр ASCII (0–9, a–f, A–F). Регистр цифр несущественен. Число обозначает одно скалярное значение Unicode по D327.

Форма разрешена в одиночных символьных литералах, в обеих границах символьного диапазона, а также в строковых литералах при сопоставлении и создании данных узлов. Ограничение предложения «только в символьных литералах» не принято: пользователь распространил форму на строки данных.

~~~text
'\u{0}'                       // Нулевой символ U+0000.
'\u{1F600}'                   // 😀.
'\u{D7FF}..\u{E000}'          // Диапазон через область суррогатов.
Identifier<"\u{61}"> -> Identifier<"\u{62}">;
~~~

Последнее правило эквивалентно Identifier<"a"> -> Identifier<"b">;. Escape-последовательность декодируется в содержимое литерала до сопоставления или передачи строки механизму разбора данных результата. Она не превращает строковое значение в число и не меняет контракты datatype. В строках разрешено сочетать обычный текст и несколько таких escape-последовательностей.

Суррогаты U+D800–U+DFFF и значения выше U+10FFFF являются ошибками DSL. Пустые скобки, не-шестнадцатеричные знаки и более шести цифр не соответствуют принятой форме. Одиночный символьный литерал после декодирования по-прежнему должен содержать ровно одно допустимое значение, тогда как строка данных может содержать несколько символов.

~~~text
Identifier<"\u{1F600}">       // Проверка строки с 😀.
Identifier<"a\u{0}b">         // Строка с U+0000 между a и b.
'\u{D800}'                   // Ошибка: суррогат.
"\u{110000}"                 // Ошибка: значение выше U+10FFFF.
~~~

Чтобы получить буквальный текст \u{61}, а не символ a, обратная косая черта экранируется по обычным правилам: "\\u{61}". Декодирование литерала не является рекурсивным: получившийся текст не разбирается повторно как escape-последовательность.

Решение дополняет перечень экранирования из §2.4 для строк данных и D323 для символов. D330 (§9.9.14) распространяет эту форму на все строковые контексты DSL, включая пути include и Java-фрагменты datatype.

Основание: D329.

### 9.9.14. Unicode-экранирование во всех строковых литералах DSL

Unicode-экранирование \u{HEX} из D329 разрешено во всех строковых литералах DSL, включая строки данных, пути include и строковые Java-фрагменты параметров datatype и узлов. Отдельный набор правил декодирования для этих строковых контекстов не вводится.

Сначала снимается экранирование DSL, затем полученная строка используется по назначению. Сохраняются ограничения D329: от одной до шести шестнадцатеричных цифр, независимость от регистра цифр, только допустимые скалярные значения Unicode. Декодирование не является рекурсивным.

~~~text
include "\u{63}ommon.dsl";
// Эквивалентно include "common.dsl";
~~~

Для include все ограничения пути проверяются по декодированной строке: Unicode-экранирование не позволяет обойти запрет абсолютных путей, обратной косой черты и прочих запрещённых форм по §2.5.

Для Java-фрагмента сначала получается текст Java после декодирования DSL, затем этот текст обрабатывается по обычным правилам Java. Unicode-экранирование DSL не заменяет проверки синтаксиса, типов и исключений Java-компилятором (§7.5). Если требуется буквальная обратная косая черта в передаваемом тексте, применяется обычное экранирование DSL.

Это расширяет D329 на все строковые контексты и закрывает оставленный там вопрос о путях include и Java-фрагментах. Правила символьных литералов и их диапазонов остаются прежними.

Основание: D330.

### 9.9.15. Начальное значение Character — U+0000

Начальное значение данных встроенного узла Character — U+0000. В нативном Java-представлении по D326 это int со значением 0.

Строковое представление getData() содержит ровно один нулевой символ. Это не пустая строка и не строка "0". В строковом литерале DSL такое содержимое можно записать как "\u{0}" по D329–D330.

U+0000 является допустимым скалярным значением Unicode по D327, поэтому начальное значение удовлетворяет требованию D320 о ровно одной кодовой точке. Нулевой символ не означает отсутствие данных или отсутствие узла.

Решение определяет default Character. Создание Character одиночным символьным литералом разрешено в D332 (§11.12). Character использует встроенный datatype CodePoint по D333 (§8.5).

Основание: D331.

### 9.9.16. Строковый шаблон цепочки Character с проверкой экранирования

Строковый литерал в позиции шаблона, вне фильтра данных узла, является сокращением цепочки узлов Character, соответствующих содержимому строки в исходном порядке.

~~~text
"public" -> PublicModifier;
// Эквивалентно:
'p', 'u', 'b', 'l', 'i', 'c' -> PublicModifier;
~~~

Сначала проверяются и декодируются escape-последовательности строкового литерала DSL, затем полученная строка разбивается на скалярные значения Unicode. Каждое значение задаёт один элемент цепочки Character. Используются строковые правила §2.4 и D329–D330, включая \u{HEX}; длина записи escape-последовательности не влияет на число сопоставляемых узлов.

~~~text
"a\nb" -> Marker;
// Цепочка из трёх Character: 'a', LF, 'b'.

"\u{1F600}" -> Emoji;
// Один Character с 😀, несмотря на две кодовые единицы UTF-16.

"\\n" -> Marker;
// Два Character: обратная косая черта и буква n.

"\q" -> Marker;       // Ошибка DSL: неизвестная escape-последовательность.
"\u{D800}" -> Marker; // Ошибка DSL: суррогат.
~~~

Проверка escape-последовательностей обязательна до сопоставления. Неизвестные escape-последовательности, некорректная форма Unicode-экранирования, недопустимые значения Unicode и буквальный перевод строки внутри литерала являются ошибками DSL. Декодирование не рекурсивно; автоматическая нормализация Unicode не выполняется.

Контекст определяет смысл строки: Identifier<"public"> проверяет данные одного узла Identifier, а "public" в позиции шаблона сопоставляет шесть соседних Character. Маркеры диапазона внутри двойных кавычек не вводят диапазон: "a..z" — цепочка из четырёх Character, в отличие от символьного диапазона 'a..z'.

Сохраняются правила цепочек: непрерывность, границы текущей группы, порядок правил и проверки применимости результата. Типы результата в примерах предполагаются объявленными. Автоматическая проверка границ слова не добавляется.

Решение вводит строковый литерал как сокращение цепочки в шаблоне. Пустой строковый шаблон запрещён по D335 (§9.9.17). Суффиксы кратности относятся ко всей цепочке по D336 (§9.9.18). Узловые захваты через as определены в D337 (§9.9.19). Обычный захват строковых данных определён в D338 (§9.9.20). Накопительная форма принята в D339 (§9.9.21). Строковый литерал в результате требует отдельного уточнения.

Основание: D334.

### 9.9.17. Запрет пустого строкового шаблона

Пустой строковый литерал "" запрещён в позиции шаблона цепочки Character. Это ошибка DSL независимо от расположения: запрет действует и внутри более крупного шаблона, который в целом гарантированно поглощает узлы.

~~~text
"" -> Marker;            // Ошибка DSL.
Start, "" -> Marker;     // Ошибка даже при обязательном Start.
~~~

Добавление группировки, альтернативы или суффикса кратности не делает пустой строковый шаблон допустимым. Для необязательности используется ? по общим правилам; отдельный строковый шаблон успешного совпадения без поглощения узлов не вводится. Это согласуется с запретом пустой группы () по D287.

Запрет относится именно к строковому шаблону цепочки. Пустые строки в выражениях данных и фильтрах узлов остаются допустимыми:

~~~text
Identifier<""> -> EmptyIdentifier; // Проверка пустых данных одного узла.
Token -> Identifier<"">;          // Построение узла с пустыми данными.
~~~

Типы в примерах предполагаются объявленными; результат должен допускать такие данные по своему datatype. В частности, пустая строка по-прежнему не является допустимыми данными Character/CodePoint. Решение не отменяет статическую диагностику доказанно невозможных шаблонов или результатов.

Это закрывает вопрос пустого строкового шаблона, оставленный в D334.

Основание: D335.

### 9.9.18. Кратность строкового шаблона относится ко всей цепочке

Суффиксы кратности ?, * и + после строкового шаблона относятся ко всей цепочке Character, полученной после декодирования строки, а не к последнему символу.

~~~text
"ab"+   // Эквивалентно ('a', 'b')+.
"ab"*   // Эквивалентно ('a', 'b')*.
"ab"?   // Эквивалентно ('a', 'b')?.
~~~

"ab"+ сопоставляет одну или более полных пар ab: ab, abab, ababab и так далее. "ab"* допускает ноль или более таких пар. "ab"? допускает отсутствие всей пары либо одну полную пару. Запись "ab"+ не эквивалентна 'a', 'b'+.

Сохраняются общие правила повторений, группировки и максимального полного совпадения. Пустой строковый шаблон запрещён по D335, в том числе с суффиксом; несколько суффиксов подряд запрещены по D286. Полный шаблон правила должен гарантированно поглощать хотя бы один узел, даже если отдельная строковая часть допускает отсутствие.

~~~text
Start, "ab"* -> Marker; // Обязательный Start обеспечивает непустое совпадение.
"ab"* -> Marker;        // Ошибка: полный шаблон допускает пустое совпадение.
~~~

Правила экранирования D334 применяются до определения цепочки: суффикс повторяет декодированное содержимое целиком. Узловые захваты строкового шаблона через as определены в D337 (§9.9.19); обычный захват строковых данных определён в D338 (§9.9.20), накопительная форма принята в D339 (§9.9.21).

Основание: D336.

### 9.9.19. Узловые захваты строкового шаблона

Захват as после строкового шаблона относится ко всей цепочке Character, представленной строкой. Его категория соответствует раскрытому шаблону и определяется статически после проверки и декодирования escape-последовательностей.

~~~text
"ab" as xs    // Список из двух Character: ('a', 'b') as xs.
"a" as x     // Один Character: 'a' as x.
"ab"+ as xs  // Плоский список всех совпавших Character.
"\u{1F600}" as x // Один Character с 😀.
~~~

Один декодированный символ без суффикса даёт одиночный узловой захват типа Character; несколько символов дают список узлов Character. Число кодовых единиц UTF-16 и длина записи escape-последовательности не определяют категорию.

Суффикс кратности применяется ко всей строке по D336, затем as захватывает результат этой конструкции по общим правилам. Для * и + захват списочный, даже если строка содержит один символ. Для ? одиночный символьный шаблон даёт необязательный узловой захват, а цепочка из нескольких символов — списочный захват, пустой при отсутствии цепочки.

Список содержит исходные вхождения Character в исходном порядке; повторения не создают вложенные списки и не сохраняют границы итераций в захвате. as не собирает строковые данные и не создаёт новый узел для всей строки.

Сохраняются общие ограничения размещения захватов, правила имён и проверки типа, категории и кратности в принимающем месте результата. Совпадение одного элемента списочного шаблона не превращает список в одиночный узел.

Основание: D337.

### 9.9.20. Захват всей строки данных строкового шаблона

После строкового шаблона цепочки разрешён обычный захват данных в форме <$name>. Он связывает имя со всей декодированной строкой, соответствующей сопоставленной цепочке Character, как с одним строковым значением.

~~~text
"public"<$text> -> Keyword<$text>;
"a\nb"<$text> -> Token<$text>;
~~~

В первом примере text равно "public". Во втором — строке из трёх символов: a, LF и b. Захватывается содержимое после проверки и снятия экранирования DSL, а не исходная запись литерала с обратными косыми чертами.

Это один захват всей цепочки. Он не разворачивается в повторное обычное связывание одного имени на каждом Character, которое требовало бы равенства данных отдельных символов. Сами символы цепочки по-прежнему проверяются строковым шаблоном по D334.

Захват относится к категории строковых данных. В отличие от него, as по D337 сохраняет исходные узлы или список узлов. Результат Keyword/Token в примерах должен быть объявлен и допускать переданную строку данных.

Сохраняются общее пространство имён, равенство повторных обычных захватов по D207 и ограничения на обычные захваты данных внутри ?, * и +. Исключений для постоянного содержимого строки не вводится. Накопительная форма после строкового шаблона отдельно принята в D339 (§9.9.21).

Это закрывает вопрос обычного захвата строковых данных после строкового шаблона; накопительная форма принята в D339 (§9.9.21).

Основание: D338.

### 9.9.21. Накопление данных строкового шаблона

После строкового шаблона цепочки разрешена накопительная форма <$name+>. Каждое успешное совпадение строки добавляет в аккумулятор её декодированное содержимое, соответствующее исходным узлам Character.

~~~text
"ab"<$text+>+ -> Token<$text>;
~~~

Для входной цепочки ababab три повторения добавляют по "ab", и результат получает данные "ababab". Плюс внутри угловых скобок обозначает накопление, внешний плюс — повторение всей строковой цепочки по D336. Тип Token предполагается объявленным и допускающим такие данные.

Сохраняются общие правила аккумуляторов: начальное значение — пустая строка; порядок вкладов соответствует исходным символам независимо от направления стрелки; возвращённые при сопоставлении части не оставляют вклада; накопления отвергнутого кандидата полностью отбрасываются.

~~~text
Start, "ab"<$text+>* -> Token<$text>;
~~~

Если после Start нет совпавших пар ab, text равно пустой строке. Обязательный Start обеспечивает непустое совпадение полного шаблона; допустимость пустых данных результата проверяется отдельно. Аккумулятор не снимает запрета пустого строкового шаблона D335.

Применяются общие ограничения имён и запрет смешивания обычного захвата и аккумулятора одного имени в шаблоне. Сохраняются выбор вкладов альтернатив по D268 и правила тождества источников и порядка накопления D307–D309. Это не новый вид состояния вне аккумулятора; источники строковой цепочки определены в D340 (§9.9.22) как отдельные вхождения Character.

Это утверждает накопительную форму, оставленную открытой в D338.

Основание: D339.

### 9.9.22. Источники строкового накопления — вхождения Character

Источниками вклада строкового шаблона в аккумулятор являются отдельные вхождения исходных узлов Character, а не строковый шаблон как неделимый источник. Для одного аккумулятора одно исходное вхождение учитывается один раз по D307–D309, даже если его данные захвачены и строковым шаблоном, и отдельным символьным шаблоном.

~~~text
(Box["ab"<$text+>] & Box['a'<$text+>, 'b'])
    -> Token<$text>;
~~~

Оба операнда проверяют один и тот же Box и весь список его детей. Первый добавляет данные исходных a и b, второй — данные того же исходного a. В аккумуляторе получается "ab", не "aab". Box и Token предполагаются объявленными с совместимыми схемами и данными.

Равенство определяется вхождением Character в исходном дереве, а не совпадением символов или ссылок на разделяемый объект. Разные вхождения с одинаковыми данными остаются разными источниками. После устранения повторов порядок вкладов задаётся исходным деревом по D308. Выбор вкладов альтернатив и откат неудачного кандидата сохраняются.

Пользователь принял правило с замечанием о сложности разбора такого условия. Синтаксическая композиция примера использует уже принятые пересечение одноузловых шаблонов, позиционные проверки детей и строковый аккумулятор. Практическая реализация ещё не проверена: нужен отдельный тест разбора и сопоставления этого примера. Принятие требования не означает, что существующий парсер уже поддерживает его.

Полного статического доказательства тождества источников не требуется. Если оно не установлено заранее, вхождения сравниваются при сопоставлении по D309. Следовательно, сложность статического анализа сама по себе не меняет результат накопления и не является причиной отвергать допустимый шаблон.

Это уточняет источники накопления строковой цепочки, оставленные открытыми в D339.

Основание: D340.

### 9.10. Общая форма фильтрации и захвата данных

Общая форма фильтрации и захвата данных узла в шаблоне — `Typename<condition, capture>`.

`condition` — условие с булевым результатом. Если оно равно true, данные узла захватываются согласно `capture`, и эта часть шаблона срабатывает. Если оно равно false, эта часть шаблона не совпадает и данные не захватываются и не добавляются в аккумулятор.

В позиции `capture` используются принятые формы `$name` и `$name+`: обычное связывание данных и накопление соответственно. Сохраняются требования равенства повторных обычных имён и правила аккумуляторов (D207–D212). Успех фильтра не отменяет остальные требования шаблона.

Запятая разделяет условие и захват. Конкретный синтаксис условий будет разобран отдельно. Части можно опускать по отдельности согласно D214 (§9.11). Пустая форма `Typename<>` запрещена (D215).

Основание: D213.

### 9.11. Необязательные части фильтра данных

Условие и захват в общей форме `Typename<condition, capture>` можно опускать по отдельности. Если остаётся одна часть, запятая не пишется:

~~~text
Typename<condition>
Typename<$name>
Typename<$name+>
~~~

`<condition>` только проверяет данные, не захватывая их. `<$name>` связывает данные без отдельного условия; требование равенства при повторном имени сохраняется. `<$name+>` добавляет данные в аккумулятор без отдельного условия. Совместная форма `<condition, capture>` сохраняется.

Синтаксис условий будет определён отдельно. Пустая форма `Typename<>` запрещена последующим решением D215 (§9.12).

Основание: D214.

### 9.12. Пустой фильтр данных запрещён

Пустая форма `Typename<>` запрещена и является ошибкой DSL. Если проверка и захват данных не нужны, пишется просто `Typename`. При наличии угловых скобок требуется хотя бы одна часть: условие или захват (D213–D214).

Основание: D215.

### 9.13. Отрицание условия данных

Оператор `!` отрицает условие фильтрации данных: истинное условие становится ложным, ложное — истинным. Например, `Identifier<!"count">` соответствует Identifier, строковые данные которого не равны "count". Это отрицание условия данных, а не отрицание узлового шаблона целиком.

Логические операторы, их относительные приоритеты и группировка условий определены в D224 (§9.20). Приоритеты выражений данных определены в D237 (§9.33). Проверка начала строки определена в D217 (§9.14).

Основание: D216.

### 9.14. Проверка начала строки данных

Условие `startsWith("prefix")` проверяет, начинается ли строка данных узла с указанного строкового литерала. Проверяется начало сериализованных данных, а не равенство всей строки.

~~~text
Identifier<startsWith("a"), $name>
Identifier<startsWith("get"), $name>
~~~

Первый шаблон принимает данные "a", "abc", "apple"; отвергает "bar" и пустую строку. Второй проверяет префикс из нескольких символов "get". При успешном совпадении `$name` захватывает всю строку данных, а не только проверенный префикс.

По D214 условие можно использовать без захвата: `Identifier<startsWith("get")>`. Принята форма со строковым литералом; пустой префикс всегда подходит (D234, §9.30); произвольные строковые выражения в аргументе разрешены по D235 (§9.31).

Основание: D217.

### 9.15. Проверка окончания строки данных

Условие `endsWith("suffix")` проверяет, заканчивается ли строка данных узла указанным строковым литералом. Проверяется окончание сериализованных данных, а не равенство всей строки.

~~~text
Identifier<endsWith("Count"), $name>
~~~

Шаблон принимает данные "itemCount" и "Count", отвергает "CountItems". При успешном совпадении `$name` захватывает всю строку данных, а не только проверенное окончание.

По D214 условие можно использовать без захвата: `Identifier<endsWith("Count")>`. Принята форма со строковым литералом; пустой суффикс всегда подходит (D234, §9.30); произвольные строковые выражения в аргументе разрешены по D235 (§9.31).

Основание: D218.

### 9.16. Проверка наличия подстроки

Условие `contains("text")` проверяет наличие указанного строкового литерала в любом месте сериализованных данных узла.

~~~text
Identifier<contains("Count"), $name>
~~~

Шаблон принимает данные "itemCount", "CountItems" и "totalCountValue". При успешном совпадении `$name` захватывает всю строку данных, а не найденную подстроку. По D214 условие можно использовать без захвата.

Принята форма со строковым литералом; пустая подстрока всегда находится (D234, §9.30); произвольные строковые выражения в аргументе разрешены по D235 (§9.31).

Основание: D219.

### 9.17. Преобразование регистра строковых данных

В DSL должны быть предусмотрены операции преобразования строки к верхнему и нижнему регистру. Вызов без аргументов преобразует строковые данные текущего узла. Вызов с одним аргументом преобразует захваченную строку; полученная строка используется как данные создаваемого узла и проходит предусмотренный разбор и проверку его datatype.

Это операции, возвращающие строку, а не сами по себе булевы условия. Имена методов, пример включения преобразования в условие и результат и сохранение исходной строки при захвате определены в D221 (§9.18). Преобразование регистра по Unicode независимо от локали определено в D245 (§9.40). Решение не утверждает изменение исходного дерева во время сопоставления.

Основание: D220.

### 9.18. Преобразование регистра в условии и результате

Приняты имена `toLowerCase` и `toUpperCase` и следующая форма применения:

~~~text
Identifier<toLowerCase() == "count", $name>
    -> Variable<toUpperCase($name)>;
~~~

В условии вызов без аргументов возвращает преобразованную строку данных текущего узла. Оператор `==` в этом примере проверяет точное равенство полученной строки строковому литералу. Преобразование служит только проверке: оно не меняет исходный узел или строку, которую захватывает `$name`.

Для исходных данных "Count" условие сравнивает "count" с "count", захват name получает исходное "Count", а новый Variable получает строку "COUNT" через `toUpperCase($name)`. Эта строка проходит обычный разбор и проверку datatype создаваемого узла.

`toLowerCase` преобразует строку к нижнему регистру, `toUpperCase` — к верхнему. Оба метода поддерживают форму без аргумента для данных текущего узла и форму с захваченной строкой в качестве аргумента. Преобразование регистра по Unicode независимо от локали определено в D245 (§9.40); остальные сочетания выражений уточняются отдельно. Неявный источник данных доступен только в фильтре текущего узла (D242, §11.11).

Основание: D221.

### 9.19. Цепочки вызовов методов

Разрешены цепочки вызовов методов через точку: следующий метод применяется к результату предыдущего.

~~~text
Identifier<toLowerCase().startsWith("get"), $name>
~~~

В этом примере `toLowerCase()` получает строковые данные текущего узла и возвращает строку в нижнем регистре. `startsWith("get")` проверяет начало именно этой преобразованной строки и возвращает булев результат условия. Подходят данные "getName", "GetName" и "GETNAME".

Захват `$name` по-прежнему получает исходную строку данных узла; цепочка не изменяет исходный узел или захватываемое значение (D221). Принцип цепочек требует соответствия метода типу результата предыдущего вызова; решение не вводит строковые методы для булевых значений. Полный набор допустимых методов и форм выражений согласуется отдельно.

Основание: D222.

### 9.20. Логические операторы и группировка условий

Условия фильтрации данных можно объединять операторами `&` (логическое «и») и `|` (логическое «или»), а также группировать круглыми скобками.

~~~text
Identifier<(startsWith("get") | startsWith("set"))
           & !endsWith("Internal"), $name>
~~~

Шаблон требует, чтобы данные начинались с "get" или "set" и не заканчивались на "Internal". Например, "getName" и "setName" подходят, "getInternal" и "otherName" — нет. Захват name выполняется только при истинности всего условия и сохраняет исходную строку.

Приоритеты логических операторов от высокого к низкому: `!`, `&`, `|`. Круглые скобки задают группировку и позволяют изменить порядок применения операторов. Это группировка условий данных; решение не вводит группировку других конструкций DSL.

Короткое замыкание является необязательной оптимизацией; обязательный порядок вычисления слева направо не вводится (D225–D226, §9.21–9.22). Приоритеты выражений данных определены в D237 (§9.33).

Основание: D224.

### 9.21. Чистота и полная определённость встроенных операций

Все встроенные операции выражений DSL являются чистыми: они не имеют побочных эффектов. На любых входных значениях допустимых типов они завершаются успешно и возвращают значение своего типа, не выбрасывая исключений из-за содержимого данных или недопустимых границ.

Корректно типизированное условие всегда возвращает true или false. Строковая операция при пограничном входе возвращает предусмотренный для неё строковый результат; конкретное поведение должно быть определено для каждой операции. Этот принцип действует и в условиях, и в выражениях данных результата.

В частности, получение подстроки с неверными границами возвращает пустую строку "". Оно не прерывает сопоставление или преобразование исключением. Синтаксис операции и правила границ определены в D227 (§9.23); индексация по кодовым точкам Unicode определена в D233 (§9.29).

Ошибки синтаксиса, неизвестные методы и несовместимые типы остаются ошибками DSL. Решение относится к вычислению встроенных выражений и не отменяет ранее установленные требования разбора и проверки datatype создаваемого узла.

Основание: D225.

### 9.22. Короткое замыкание как необязательная оптимизация

Благодаря чистоте и полной определённости встроенных операций (D225) короткое замыкание для `&` и `|` не является обязательной семантикой исполнения.

Для `A & B` при ложном A реализация может не вычислять B. Для `A | B` при истинном A реализация может не вычислять B. Разрешено также вычислить оба операнда: результат условия должен быть тем же. Пропуск вычисления влияет только на затраты исполнения.

Обязательный порядок вычисления слева направо не вводится. Приоритеты и группировка выражений по D224 сохраняются: они определяют смысл условия, а не обязательный порядок исполнения его независимых частей. Нельзя полагаться на короткое замыкание как на защиту от ошибки встроенной операции: её поведение на таком входе должно быть определено само по себе.

Основание: D226.

### 9.23. Получение подстроки

Принята операция `substring(start, end)`: индексы начинаются с нуля, начальная граница включается, конечная не включается. Форма `substring(start)` возвращает остаток строки от начальной позиции до конца.

~~~text
Identifier<substring(0, 3) == "get", $name>
    -> Variable<$name.substring(3)>;
~~~

В условии вызов без явного получателя применяется к данным текущего узла. В результате вызов на `$name` применяется к захваченной строке. Для исходного "getName" создаётся Variable с данными "Name"; захват name сохраняет исходную строку.

Неверные границы возвращают пустую строку без исключения (D225). Отрицательные границы, выход за длину строки и начало после конца являются неверными; диапазон не обрезается до допустимых границ. При совпадающих допустимых границах результат также пуст. Начальная позиция на конце строки в одноаргументной форме даёт пустую строку.

Единица индексации — кодовая точка Unicode (D233, §9.29).

Основание: D227.

### 9.24. Дополнительный набор строковых операций

В дополнение к ранее принятым строковым операциям утверждён следующий набор:

- `length()`: Длина строки.
- `isEmpty()`: Проверка пустоты строки.
- `charAt(index)`: Один символ как строка; неверный индекс возвращает пустую строку.
- `indexOf(text)`: Позиция первого вхождения; при отсутствии возвращается -1.
- `lastIndexOf(text)`: Позиция последнего вхождения; при отсутствии возвращается -1.
- `replace(old, new)`: Замена всех неперекрывающихся вхождений слева направо.
- `replaceFirst(old, new)`: Замена первого вхождения.
- `trim()`: Удаление пробельных символов с обоих краёв.
- `trimStart()`: Удаление пробельных символов в начале.
- `trimEnd()`: Удаление пробельных символов в конце.
- `concat(text)`: Присоединение строки справа.

Поиск и замена буквальные, без регулярных выражений. Все перечисленные операции доступны на данных текущего узла и через точку на строковом выражении. Они подчиняются требованиям чистоты и полной определённости D225.

Индексация по кодовым точкам Unicode определена в D233 (§9.29). Поведение пустой строки поиска и замены определено в D234 (§9.30). Правила регистра определены в D245 (§9.40). Набор удаляемых символов определён в D246 (§9.41). Операции length, indexOf и lastIndexOf возвращают целые числа; три типа значений выражений, сравнения чисел и передача числовых значений в аргументы методов определены в D229 (§9.25). Сложение и вычитание целых чисел определены в D230 (§9.26).

Основание: D228.

### 9.25. Типы значений выражений и использование чисел

У выражений DSL выделяются три типа значений: строка, целое число и булево значение. Они не являются объявляемыми datatype узлов. Захват данных узла по-прежнему содержит сериализованную строку; наличие целых чисел в выражениях не меняет категорию такого захвата.

Целые числа разрешены в сравнениях и в аргументах методов, ожидающих числовые значения. В частности, результат поиска подстроки можно передать как границу другой строковой операции:

~~~text
$name.substring(0, $name.indexOf(":"))
~~~

Для строки "key:value" выражение возвращает "key". При отсутствии двоеточия indexOf возвращает -1, а substring с такой границей возвращает пустую строку по D227. Результат вложенного вызова используется как аргумент внешнего вызова.

Последующее решение D230 (§9.26) вводит сложение и вычитание целых чисел. Перечень сравнений определён в D236 (§9.32), строгая типизация и явное преобразование в строку — в D231–D232. Целые числа имеют произвольную точность (D240, §9.36).

Основание: D229.

### 9.26. Сложение, вычитание и конкатенация строк

Для целочисленных выражений разрешены бинарные операторы `+` (сложение) и `-` (вычитание). Их результаты можно использовать в числовых аргументах строковых операций.

~~~text
Identifier<contains(":"), $name>
    -> Identifier<$name.substring($name.indexOf(":") + 1)>;
~~~

Для данных "key:value" правило создаёт Identifier с данными "value". Выражение `$name.charAt($name.length() - 1)` получает последний символ строки; на пустой строке индекс равен -1, поэтому charAt возвращает пустую строку по D228.

Для двух строк оператор `+` означает конкатенацию в порядке операндов и возвращает строку:

~~~text
Identifier<$name> -> Identifier<"prefix_" + $name>;
~~~

При name = "count" результат имеет данные "prefix_count". Для строк `a + b` соответствует `a.concat(b)`. Сложение чисел и конкатенация строк различаются по типам операндов. Эти операции внутри выражений данных не отменяют ранее принятый оператор объединения узлов и списков в результате и обозначение аккумулятора `$name+` в шаблоне.

Смешение строки и числа без явного преобразования запрещено; функция toString определена в D231 (§9.27). Целые числа имеют произвольную точность; переполнение фиксированной разрядности отсутствует (D240, §9.36). Приоритеты и группировка + и - слева направо определены в D237 (§9.33).

Основание: D230.

### 9.27. Строгая типизация и явное преобразование в строку

Выражения DSL имеют строгую типизацию без неявного преобразования числа в строку. Оператор `+` для двух целых чисел означает сложение, для двух строк — конкатенацию. Смешение строки и числа, например `"item" + 1`, является ошибкой типов, выявляемой до исполнения. Это не исключение при вычислении корректно типизированного выражения и не противоречит D225.

Введена функция `toString(value)`, которая принимает ровно один аргумент и возвращает его строковое представление. Она позволяет явно преобразовать числовой результат для использования в строковом выражении:

~~~text
Identifier<$name>
    -> Identifier<$name + "_" + toString($name.length())>;
~~~

Форма без аргументов данным решением не вводится. Правила представления трёх типов значений определены в D232 (§9.28); допустимость вызова через точку пока не определена; не вводится неявная сериализация захватов узлов или списков.

Основание: D231.

### 9.28. Строковое представление значений без локали

Функция `toString(value)` определена для всех трёх типов значений выражений DSL:

- Целое число преобразуется в десятичную запись без разделителей разрядов и зависимости от локали: 42 даёт "42", -7 даёт "-7".
- Булево значение преобразуется в строку "true" или "false".
- Строка возвращается без изменений.

Преобразование явно, принимает ровно один аргумент и не зависит от региональных настроек среды исполнения.

Основание: D232.

### 9.29. Индексация по кодовым точкам Unicode

Единица длины и индексации строк в DSL — кодовая точка Unicode. Это правило применяется к `length`, `charAt`, границам `substring` и позициям, возвращаемым `indexOf` и `lastIndexOf`. Индексы начинаются с нуля.

~~~text
"A😀Б".length()  → 3
"A😀Б".charAt(1) → "😀"
~~~

Примеры показывают значения операций, а не отдельно утверждённую грамматику вызовов на литералах. Символ, представленный суррогатной парой UTF-16, занимает одну позицию; строковые операции не разрезают эту пару при извлечении символа или подстроки. Единица индексации не зависит от внутреннего хранения строки.

Кодовая точка не тождественна графеме: буква и отдельный комбинируемый акцент считаются двумя кодовыми точками. Правила неверных индексов и границ сохраняются: charAt и substring возвращают пустую строку. Автоматическая нормализация не выполняется (D244, §9.39). Обработка некорректных последовательностей кодирования пока не определена.

Основание: D233.

### 9.30. Пустая строка в поиске и замене

Для пустой строки поиска установлены следующие результаты:

- `startsWith("")`, `endsWith("")` и `contains("")` возвращают true.
- `indexOf("")` возвращает 0.
- `lastIndexOf("")` возвращает длину исходной строки в кодовых точках Unicode.
- `replace("", text)` и `replaceFirst("", text)` возвращают исходную строку без изменений при любом строковом значении text.

Пустая подстрока находится на любой границе строки, включая начало и конец. Замена пустой строки определена отдельно как операция без изменений: вставок на границах не происходит. Правила действуют и для пустой исходной строки; оба метода поиска позиции в ней возвращают 0.

Основание: D234.

### 9.31. Строковые выражения в аргументах методов

Любой строковый аргумент встроенного метода принимает произвольное корректное выражение строкового типа, а не только строковый литерал. Допустимы захваты данных, цепочки вызовов, конкатенация и другие утверждённые строковые выражения.

~~~text
Identifier<$prefix>,
Identifier<startsWith($prefix.toLowerCase()), $name>
~~~

В этом фрагменте шаблона первый узел связывает prefix со своими данными. Второй проверяет, начинаются ли его исходные данные со строки, полученной преобразованием prefix в нижний регистр. Данные второго узла этим вызовом не преобразуются; name захватывает их исходное значение. Это пример фрагмента шаблона, а не полного правила.

Правило применяется к строковым аргументам startsWith, endsWith, contains, indexOf, lastIndexOf, replace, replaceFirst и concat; в замене оба аргумента могут быть строковыми выражениями. Требования области видимости и категории захватов сохраняются. Число или булево значение без явного toString не становится строковым аргументом (D231–D232).

Основание: D235.

### 9.32. Сравнения значений выражений

Для значений выражений DSL принят следующий набор сравнений:

- Целые числа: `==`, `!=`, `<`, `<=`, `>`, `>=`.
- Строки: `==` и `!=`, проверяющие точное равенство или неравенство содержимого.
- Булевы значения: `==` и `!=`.

Результат сравнения — булево значение. Оба операнда должны иметь одинаковый тип. Например, `"12" == 12` является ошибкой типов до исполнения; неявного преобразования строки в число или числа в строку нет.

Лексикографическое сравнение строк не вводится. Операторы порядка также не определены для булевых значений. Это сравнения значений выражений, а не захваченных узлов или списков узлов.

Приоритеты определены в D237 (§9.33). Сравнения порядка внутри фильтра заключаются в круглые скобки по D243 (§9.38).

Основание: D236.

### 9.33. Приоритеты и группировка выражений

Приоритеты операторов выражений данных от высокого к низкому:

1. Вызовы методов и цепочки через точку.
2. `!` и унарный `-` (D239).
3. Бинарные `+` и `-`, группируемые слева направо.
4. `<`, `<=`, `>`, `>=`.
5. `==`, `!=`.
6. `&`.
7. `|`.

Круглые скобки разрешены в любых выражениях данных и изменяют группировку:

~~~text
$name.substring(0, $name.length() - (1 + 2))
~~~

Указанная группировка слева направо для + и - определяет структуру выражения, а не обязательный порядок вычисления независимых операндов. Правила чистоты и необязательного короткого замыкания сохраняются (D225–D226).

Это таблица выражений данных; она не меняет синтаксис построения последовательностей узлов. Цепочки сравнений запрещены по D238 (§9.34). Унарный минус определён в D239 (§9.35); унарный плюс не вводится. Сравнения порядка внутри фильтра заключаются в круглые скобки по D243 (§9.38).

Основание: D237.

### 9.34. Запрет цепочек сравнений

Неявные цепочки сравнений запрещены. Несколько проверок следует записывать отдельными сравнениями, явно соединёнными логическими операторами.

~~~text
0 <= length() <= 10             // Ошибка.
length() >= 0 & length() <= 10  // Допустимо.
~~~

Запрет распространяется и на цепочки равенств: схематическая запись `a == b == c` недопустима; для требования равенства трёх значений пишется `a == b & b == c`. Здесь a, b и c обозначают выражения допустимого типа, а не вводят новый синтаксис переменных без знака доллара.

Цепочка не разворачивается автоматически в конъюнкцию и не трактуется как последовательное сравнение результата предыдущего сравнения со следующим операндом. Приоритеты из D237 не разрешают запрещённую форму цепочки.

Основание: D238.

### 9.35. Унарный минус

Введён унарный оператор `-` для целых чисел. Он меняет знак значения и имеет тот же приоритет, что логическое отрицание `!`: ниже вызовов методов, выше бинарных + и -.

~~~text
indexOf(":") == -1
-(length() + 1)
~~~

Унарный минус применим только к целочисленному выражению; применение к строке или булеву значению является ошибкой типов до исполнения. Унарный плюс не вводится.

Целые числа имеют произвольную точность; унарный минус даёт точный результат (D240, §9.36).

Основание: D239.

### 9.36. Целые числа произвольной точности

Целые числа в выражениях DSL имеют произвольную точность. Сложение, вычитание и унарная смена знака дают точный математический результат без переполнения фиксированной разрядности. Ограничение диапазоном машинного int или long не вводится.

При передаче целого числа в качестве индекса или границы строковой операции проверяется его фактическое значение. Если оно выходит за допустимые границы строки, charAt или substring возвращает пустую строку по ранее принятым правилам. Огромное значение не обрезается и не переполняется в допустимый индекс.

Сравнения целых чисел и десятичное представление через toString используют точное значение. Решение относится к типу целых чисел в выражениях DSL и не меняет отдельно объявляемые datatype узлов.

Основание: D240.

### 9.37. Явный доступ к данным текущего узла

В условии фильтрации данных функция `data()` без аргументов возвращает исходную сериализованную строку данных текущего сопоставляемого узла без изменений.

~~~text
Identifier<data() == "count", $name>
Identifier<data() == $prefix + "Count", $name>
~~~

Во втором примере prefix — захват строковых данных, связанный в том же правиле; показан фрагмент шаблона. Доступ к данным через data() не создаёт захват и не меняет значение, которое захватывается в name.

Краткая форма `Identifier<"count">` означает ту же проверку, что `Identifier<data() == "count">`. Это специальная краткая проверка точного равенства данных строковому литералу, а не неявное преобразование произвольной строки в булево значение.

Вне фильтра текущего узла data() недоступна (D242, §11.11).

Основание: D241.

### 9.38. Скобки для сравнений порядка в фильтре

Сравнения порядка `<`, `<=`, `>` и `>=` внутри фильтра данных должны быть заключены в круглые скобки. Это позволяет различать оператор сравнения и закрывающую угловую скобку фильтра.

~~~text
Identifier<(length() > 3), $name>
Identifier<(length() >= 3) & (length() <= 10), $name>
Identifier<length() > 3, $name> // Ошибка: отсутствуют круглые скобки.
~~~

Внутри круглых скобок знак > может быть оператором сравнения; на внешнем уровне фильтра он закрывает угловые скобки. Для ==, != и вызовов методов дополнительные группирующие скобки не требуются. Приоритеты операторов и запрет цепочек сравнений сохраняются (D237–D238).

Примеры выражений сравнений в предыдущих решениях описывают их смысл; при включении в фильтр данных они должны удовлетворять этому требованию.

Основание: D243.

### 9.39. Отсутствие автоматической нормализации Unicode

Автоматическая нормализация Unicode для строковых выражений DSL не выполняется. Сравнение и поиск работают с точной последовательностью кодовых точек, не приравнивая канонически эквивалентные представления.

Например, готовая буква é (U+00E9) и последовательность e (U+0065) с комбинируемым акцентом (U+0301) являются разными строками. Их длины по D233 равны соответственно одной и двум кодовым точкам.

Захват сохраняет исходную последовательность без скрытой нормализации. Явно вызванные операции преобразования строк сохраняют своё назначение; это решение не отменяет toLowerCase, toUpperCase и другие преобразования и не вводит отдельную функцию нормализации.

Основание: D244.

### 9.40. Преобразование регистра Unicode без локали

Операции toLowerCase и toUpperCase преобразуют регистр по правилам Unicode независимо от локали системы. Преобразование может менять число кодовых точек строки; соответствие один исходный символ — один результирующий символ не требуется.

~~~text
toUpperCase("straße") → "STRASSE"
~~~

В примере показано значение операции. После преобразования длина и индексы последующих операций вычисляются по полученной строке в кодовых точках Unicode (D233). Индексы исходной строки автоматически не переносятся на преобразованную.

Исходный захват остаётся неизменным (D221–D223). Автоматическая нормализация Unicode не добавляется (D244). Конкретная версия Unicode для воспроизводимости реализации ещё не выбрана.

Основание: D245.

### 9.41. Символы, удаляемые операциями trim

Операции trim, trimStart и trimEnd удаляют только обычный пробел (U+0020), горизонтальную табуляцию (U+0009) и символы перевода строки LF (U+000A) и CR (U+000D). CRLF обрабатывается как два входящих в этот набор символа. Другие символы, включая неразрывный пробел (U+00A0), сохраняются.

trim удаляет непрерывные последовательности этих символов с обоих краёв строки, trimStart — только с начала, trimEnd — только с конца. Символы внутри строки не удаляются. Пустая строка и строка, полностью состоящая из удаляемых символов, дают пустую строку.

Основание: D246.

### 9.42. Методы строковых литералов и выражений в скобках

Строковые методы разрешено вызывать непосредственно на строковом литерале и на заключённом в круглые скобки выражении строкового типа. Вызов применяется к значению получателя; после него допустима обычная цепочка методов. Правило действует в условиях фильтрации и в выражениях данных результата.

~~~text
"abc".toUpperCase()
($prefix + $name).toLowerCase()
~~~

Тип получателя должен соответствовать методу: скобки не превращают число или булево значение в строку. Действующие правила строгой типизации и явного преобразования через toString сохраняются.

Основание: D247.

### 9.43. Ссылка на захват данных того же узла

Условие фильтра данных может ссылаться на обычный захват данных, связываемый этим же узлом. Захват обозначает исходную сериализованную строку данных узла; проверка условия и связывание имени составляют единое условие совпадения.

~~~text
Identifier<$name.length() == 3, $name>
Identifier<length() == 3, $name>
~~~

Эти шаблоны равнозначны. Для проверки кандидата доступны его исходные данные; при ложном условии совпадения нет и захват не сохраняется. Это не требует выполнять захват как побочный эффект до проверки. При повторении обычного имени сохраняется требование равенства данных всех его вхождений (D207).

Решение относится к обычному захвату $name. Оно не разрешает чтение аккумулятора $name+ через $name в шаблоне: запрет D210 сохраняется.

Основание: D248.

### 9.44. Альтернатива узловых шаблонов

Принята запись альтернативы узловых шаблонов через | в круглых скобках. Она сопоставляет один узел, подходящий хотя бы под один из перечисленных шаблонов. Захват as после закрывающей скобки относится ко всей альтернативе и захватывает сопоставленный узел.

~~~text
(Identifier | IntegerLiteral) as value -> Argument[$value];
~~~

В примере value получает один Identifier либо IntegerLiteral. Объявление Argument должно допускать такой узел в соответствующем дочернем месте. Это альтернатива узловых шаблонов, а не логическое | внутри выражения данных и не выбор между результатами преобразования.

Решение фиксирует форму альтернативы и общий внешний захват. Пересечение вариантов без внутренних захватов определено в D258 (§9.45). Совместимость подстановки общего захвата определена в D259 (§9.46). Повторения альтернатив определены в D260 (§9.47). Общее имя захвата данных во всех вариантах разрешено в D261 (§9.48). Остальные случаи внутренних захватов и альтернативы последовательностей отдельно разрешены в D274 (§9.60); остальные ещё не согласованные случаи требуют уточнения.

Основание: D257.

### 9.45. Пересечение альтернатив без внутренних захватов

Для альтернатив узловых шаблонов без внутренних захватов совпадение одного узла с несколькими вариантами считается одним успешным совпадением. Оно не создаёт неоднозначности и не требует выбора победившего варианта. Общий внешний захват получает тот же единственный узел.

~~~text
(Expression | Identifier) as value
~~~

Если Identifier наследуется от Expression, узел Identifier подходит под оба варианта примера, но захватывается в value один раз. Порядок этих вариантов не меняет результат сопоставления.

Решение ограничено альтернативами без внутренних захватов, включая отсутствие накоплений данных внутри вариантов. Случаи с внутренними захватами и аккумуляторами требуют отдельного согласования. Требования однозначного распределения цепочек по частям шаблона сохраняются.

Основание: D258.

### 9.46. Подстановка общего захвата альтернативы

При подстановке общего захвата альтернативы в дочернее место результата статически проверяется совместимость каждого варианта альтернативы с типом этого места. Все варианты должны быть допустимы. Несовместимость хотя бы одного варианта является ошибкой DSL до исполнения.

~~~text
(Identifier | IntegerLiteral) as value -> Argument[$value];
~~~

Если соответствующее место Argument принимает Expression, а Identifier и IntegerLiteral наследуют Expression, подстановка допустима. Если место принимает только Identifier и IntegerLiteral не является его подтипом, правило отклоняется. Фактическое совпадение с Identifier на отдельном входе не снимает статическую ошибку.

Эта проверка не откладывается до отказа билдера. D251 о неприменимости при ожидаемом отказе построения не отменяет статическую совместимость типов результата. Решение определяет проверку подстановки, но не вводит новый именованный тип объединения и не требует выбора единственного общего предка вариантов.

Основание: D259.

### 9.47. Повторения и необязательность альтернативы

К альтернативе узловых шаблонов в круглых скобках разрешено применять суффиксы +, * и ?. Каждый сопоставляемый элемент независимо должен соответствовать хотя бы одному варианту; в одной последовательности могут чередоваться узлы разных вариантов.

~~~text
(Identifier | IntegerLiteral)+ as items -> Arguments[$items];
~~~

Суффикс + требует один или более узлов, * допускает ноль или более, ? — ноль или один. Общий as после суффикса захватывает результат всей конструкции: для + и * — список узлов в исходном порядке, для ? — необязательный одиночный узел. В примере место Arguments должно допускать список и все типы его элементов по D259.

Сохраняются обычные ограничения повторений и захватов: минимальное потребление всего фрагмента должно быть положительным, правила однозначности распределения и возврата элементов не меняются. Запрет обычных вложенных захватов под * и +, запрет обычного захвата данных внутри ? и специальный режим аккумуляторов остаются в силе. Общий внешний захват повторения разрешён. Это решение не определяет внутренние захваты отдельных вариантов и не вводит альтернативы последовательностей.

Основание: D260.

### 9.48. Общее имя захвата данных в альтернативе

Разрешён обычный захват строковых данных с одним и тем же именем в каждом варианте альтернативы. Если каждый вариант связывает это имя со строковыми данными, захват доступен после совпадения альтернативы независимо от того, какой вариант совпал.

~~~text
(Identifier<$text> | IntegerLiteral<$text>)
    -> Token<$text>;
~~~

В примере text содержит сериализованные строковые данные сопоставленного узла. Даже для IntegerLiteral захватывается строка getData(), а не нативное числовое значение. Данные передаются построению Token по обычным правилам результата.

Это решение фиксирует приведённый случай общего имени и одной категории значения во всех вариантах. Оно не отменяет запреты обычных захватов данных внутри повторений * и + и необязательного шаблона ?. Варианты с разными наборами имён, разными категориями, аккумуляторами или различными значениями захватов при одновременном совпадении нескольких вариантов требуют отдельного согласования.

Основание: D261.

### 9.49. Доступность захвата после альтернативы

Захват, используемый после альтернативы, должен быть доступен при совпадении каждого её варианта. Если совпадение одного из вариантов оставляет используемое значение отсутствующим, это ошибка компиляции DSL. Отсутствие не заменяется пустой строкой и не откладывается до построения результата.

~~~text
(Identifier<$text> | IntegerLiteral)
    -> Token<$text>; // Ошибка: второй вариант не связывает text.
~~~

Общий захват строковых данных во всех вариантах по D261 остаётся допустимым. Критерий относится к доступности значения независимо от совпавшего варианта, а не к фактически встретившимся данным конкретного запуска.

Позднейшее D269 (§9.55) запрещает обычный захват данных только в части вариантов, включая использование лишь внутри своей ветки. Правила категорий захватов и их совместимости, а также ограничения повторений и необязательных шаблонов сохраняются.

Основание: D262.

### 9.50. Совпавшие альтернативы с одинаковым захватом данных

Если несколько вариантов альтернативы совпали с одним узлом и связали общее имя захвата строковых данных с одинаковой строкой, это считается одним успешным совпадением. Само совпадение нескольких вариантов не создаёт неоднозначности; выбирать первый вариант не требуется.

~~~text
(Expression<$text> | Identifier<$text>)
    -> Token<$text>;
~~~

Если Identifier наследуется от Expression, узел Identifier подходит под оба варианта примера. В обоих случаях text содержит исходную строку getData() этого же узла, поэтому захват используется как одно значение. Порядок вариантов не меняет результат.

Решение расширяет D258 на данный случай одинакового обычного захвата строковых данных. Различающиеся значения обычных захватов данных рассматриваются в D264 (§9.51). Захваты узлов или списков и накопление данных аккумуляторами требуют отдельного согласования.

Основание: D263.

### 9.51. Разные значения данных в совпавших альтернативах

Если несколько вариантов альтернативы совпали с одним входным узлом, но дали разные строковые значения общего обычного захвата данных, совпадение неоднозначно. Текущий кандидат отвергается до построения результата; исходное дерево не изменяется.

~~~text
(Pair(left: Identifier<$text>)
 | Pair(right: Identifier<$text>))
    -> Token<$text>;
~~~

Если оба ребёнка Pair являются Identifier, слева данные "a", справа "b", оба варианта совпадают, но text получает разные значения. Кандидат отвергается. При одинаковых строковых значениях действует D263: это одно успешное совпадение.

Порядок вариантов не выбирает значение захвата. Билдер не используется для разрешения неоднозначности. Поиск того же правила продолжается со следующей позиции в направлении стрелки; к следующему правилу переходят только после отсутствия успешной замены текущим правилом во всём контексте. Неоднозначность конкретного кандидата сама по себе не останавливает преобразование.

Решение касается обычных захватов строковых данных. Критерии сравнения захватов узлов и списков, а также поведение аккумуляторов внутри альтернатив остаются отдельными вопросами.

Основание: D264.

### 9.52. Однократное накопление в пересекающихся альтернативах

Разрешено использовать один и тот же аккумулятор данных в вариантах альтернативы. Если один узел соответствует нескольким вариантам и каждый из них добавляет данные этого же узла в тот же аккумулятор, данные добавляются один раз, а не по числу совпавших вариантов.

~~~text
(Expression<$text+> | Identifier<$text+>)+
    -> Token<$text>;
~~~

Если Identifier наследуется от Expression, он может соответствовать обоим вариантам примера, но вносит в text свою строку getData() один раз. Повторение обрабатывает каждое вхождение узла исходной цепочки отдельно; разные вхождения с одинаковыми строками не объединяются. Для двух узлов с данными "a" и "a" результат накопления равен "aa".

Альтернативы являются способами сопоставить один входной узел, а не независимыми командами накопления. Сохраняются порядок накопления D209 и D250, начальная пустая строка D211, откат неудачных вариантов D212 и запрет смешивания $name и $name+ в шаблоне D210.

Решение фиксирует случай одного и того же вклада от того же узла в тот же аккумулятор. Аккумуляторы, присутствующие лишь в части вариантов, разрешены в D266 (§9.53). Вклад аккумуляторов берётся из первого совпавшего варианта при отсутствии конфликта обычных захватов (D268, §9.54).

Основание: D265.

### 9.53. Аккумулятор лишь в части вариантов

Аккумулятор данных может присутствовать только в части вариантов альтернативы. Вариант без добавления в этот аккумулятор ничего в него не добавляет. Значение аккумулятора доступно в результате даже при отсутствии добавлений и в этом случае равно пустой строке по D211.

~~~text
(Identifier<$text+> | Separator)+ -> Token<$text>;
~~~

В примере Identifier добавляет свои данные в text, Separator не добавляет ничего. Для последовательности Identifier<"ab">, Separator, Identifier<"cd"> накопленная строка равна "abcd". Если совпали только Separator, text равно "". Создаваемый Token по-прежнему должен допускать полученные данные; ожидаемый отказ его построения обрабатывается по D251–D252.

Это отличие аккумулятора от обычного захвата: у аккумулятора заранее определено начальное значение. D262 о недоступном обычном захвате не запрещает такую конструкцию. Порядок накопления и откат неудачных вариантов сохраняются. Для аккумуляторов действует приоритет первого совпавшего варианта (D268, §9.54); конфликт обычных захватов по-прежнему отвергает кандидата.

Основание: D266.

### 9.54. Приоритет вариантов для аккумуляторов

При одновременном совпадении нескольких вариантов альтернативы вклад в аккумуляторы берётся только из первого совпавшего варианта слева направо среди полных совпадений максимальной длины (D275, §9.61). Разные вклады сами по себе больше не являются неоднозначностью. Вклады остальных вариантов не добавляются; если выбранный вариант не содержит добавления в конкретный аккумулятор, его прежнее значение сохраняется.

Обычные захваты данных сохраняют прежнюю семантику: разные значения одного общего обычного захвата в совпавших вариантах означают неоднозначность. Наличие аккумулятора не скрывает этот конфликт. Только если обычные захваты согласованы, используется вклад аккумуляторов первого совпавшего варианта. Это не общий выбор первой ветки с игнорированием остальных проверок обычных захватов.

В примере (Identifier<$text+> | Expression)+ -> Token<$text>; узел Identifier, наследующий Expression, добавляет свои данные по первому варианту; прочий Expression ничего не добавляет. Если поменять варианты местами, первым совпадёт Expression и добавления не будет. Порядок вариантов теперь существенен для накопления, но направление стрелки не переставляет варианты.

Решение заменяет D267: пересечение вариантов с добавлением и без добавления разрешено и не требует доказательства пустоты строки. Сохраняются однократное добавление D265, начальное значение D211, откат неудачного кандидата D212 и порядок данных внутри выбранного варианта D250. Отказ билдера результата не служит поводом выбирать другой вариант.

Основание: D268; заменяет D267.

### 9.55. Обычные захваты во всех вариантах

Обычный захват данных внутри альтернативы должен присутствовать во всех её вариантах. Захват только в одной или в части веток, которые могут не сработать, запрещён при компиляции DSL. Это уточняет D262 и не вводит исключения для захвата, используемого только внутри своей ветки. Для проверки текущих данных без захвата доступны data() и строковые методы.

Например, (Identifier<$name> | IntegerLiteral) -> Token<$name>; запрещено, а (Identifier<$name> | IntegerLiteral<$name>) -> Token<$name>; допустимо при соблюдении остальных требований.

Аккумулятор может присутствовать только в части вариантов по D266: при отсутствии добавлений его значение равно пустой строке. Обычные захваты и аккумуляторы с разными именами разрешено сочетать в одном правиле. Для одного имени сочетание $name и $name+ в шаблоне по-прежнему запрещено D210, в том числе между ветками; чтение $name в результате для аккумулятора разрешено.

Решение относится к обычным захватам строковых данных и не вводит новый запрет захватов узлов через as. При сочетании обычных захватов и аккумуляторов действует D268: конфликт обычных значений отвергает кандидата, иначе вклад аккумуляторов определяется первым совпавшим вариантом.

Основание: D269.

### 9.56. Общий узловой захват в альтернативах

Разрешено использовать общее имя захвата узла через as в разных вариантах альтернативы. Такое использование должно проверяться статическим анализом DSL; оно не считается автоматически ошибкой повторного объявления только из-за наличия имени в нескольких альтернативных ветках.

~~~text
(Box(value: Expression as x)
 | Wrapper(value: Expression as x))
    -> Result[$x];
~~~

В этом примере каждый вариант связывает x с одним узлом Expression. Повторное объявление x внутри одной ветки по-прежнему запрещено. Принято разрешение конструкции при статической проверке; это не разрешение произвольных конфликтующих объявлений одного имени.

Проверки доступности, категории одиночного узла и совместимости типов определены в D271 (§9.57). При одновременном совпадении сравниваются вхождения узлов по D272 (§9.58). Критерий для узловых захватов уточнён D272; приоритет аккумуляторов не разрешает конфликт узловых захватов.

Основание: D270.

### 9.57. Проверки общего одиночного узлового захвата

Для общего захвата одиночного узла в альтернативах статический анализ проверяет: каждая ветка объявляет имя ровно один раз; во всех ветках захватывается одиночный узел, без смешивания с категорией списка или данных; тип узла из каждой ветки совместим с каждым местом подстановки этого захвата в результате.

~~~text
(Identifier as x | IntegerLiteral as x) -> Argument[$x];
~~~

Пример допустим, если место Argument принимает Expression, а Identifier и IntegerLiteral наследуют Expression. Если хотя бы один вариант несовместим с местом подстановки, это ошибка компиляции. Отсутствие объявления в одной из веток, повторное объявление в одной ветке или смешение категорий также являются ошибками до исполнения.

Совпадение фактически более узкого типа на конкретном входе не исправляет статическую несовместимость. Решение уточняет проверки D270 для общего одиночного узлового захвата; общий захват списков отдельно разрешён D273 (§9.59). Обязательные и необязательные одиночные захваты в ветках разрешено объединять по D290 (§9.70); общий захват тогда допускает отсутствие, что также проверяется в каждом месте подстановки. Критерий сравнения вхождений узлов при одновременном совпадении определён в D272 (§9.58).

Основание: D271.

### 9.58. Неоднозначность узловых захватов

При одновременном совпадении вариантов альтернативы на одном текущем узле присутствующие значения общего узлового захвата должны обозначать одно и то же вхождение узла в исходном дереве. Для необязательного захвата два отсутствия согласованы, а отсутствие и присутствующий узел конфликтуют (D291, §9.71). Захват разных вхождений является неоднозначностью, даже если узлы структурно равны. Одинаковая ссылка на неизменяемый объект, используемый в разных местах дерева, сама по себе не делает эти вхождения одним.

~~~text
(Pair(left: Expression as x)
 | Pair(right: Expression as x))
    -> Result[$x];
~~~

Если оба варианта совпали, первый связывает x с левым ребёнком, второй — с правым. Это разные вхождения. Если статический анализ доказывает такую неоднозначность, правило отвергается при компиляции DSL. Полнота статического выявления не требуется: невыявленная заранее неоднозначность конкретного кандидата приводит к его отклонению до построения результата и продолжению поиска того же правила.

Альтернатива проверяет один и тот же текущий узел, а не ищет разные узлы независимо. Одинаковый тег в разных типах не обязан иметь одинаковую позицию. Для разных конкретных типов Box и Wrapper одновременно совпасть обе ветки не могут, поэтому Box(value: Expression as x) и Wrapper(value: Expression as x) не требуют одинакового индекса value. Если варианты относятся к абстрактным типам и могут совпасть одновременно, сравниваются фактические вхождения захваченных узлов.

Это уточняет D270–D271. Приоритет вариантов для аккумуляторов не устраняет конфликт узлового захвата. Совпадения с одним и тем же вхождением объединяются при отсутствии иных конфликтов; структурное равенство разных поддеревьев для этого недостаточно.

Основание: D272.

### 9.59. Общий захват списка в альтернативах

Разрешён общий захват списка узлов в вариантах альтернативы. Статический анализ проверяет, что каждая ветка объявляет имя ровно один раз, во всех ветках оно обозначает список узлов, а все возможные типы элементов и кратность подстановки совместимы с местом результата. Смешение списка, одиночного узла и данных под одним именем запрещено.

~~~text
(Box(items: [Expression* as xs])
 | Wrapper(items: [Expression* as xs]))
    -> Result[$xs];
~~~

Если несколько вариантов одновременно совпадают на одном текущем узле, списки общего захвата должны содержать те же вхождения узлов исходного дерева в том же порядке. Различие длины, вхождений или порядка означает неоднозначность; структурное равенство разных узлов её не устраняет. Одинаковые списки дают одно совпадение при отсутствии иных конфликтов.

Применяется подход D272: статически доказанная неоднозначность отклоняется при компиляции; не выявленная заранее неоднозначность конкретного кандидата приводит к его отказу до построения результата и продолжению поиска того же правила. Приоритет аккумуляторов не скрывает конфликт списочного захвата.

Сохраняются обычные ограничения повторений: as xs в примере захватывает Expression* целиком, а не помещается внутрь повторяемого шаблона. Решение не разрешает обычные вложенные захваты внутри внешнего * или + и не вводит альтернативы последовательностей.

Основание: D273.

### 9.60. Альтернативы цепочек узлов

В круглых скобках разрешены альтернативы цепочек узлов, а не только одиночных узлов. Запятая соединяет последовательные элементы одного варианта, оператор | разделяет варианты. Таким образом, запятая связывает элементы внутри варианта сильнее, чем |.

~~~text
(Identifier, Colon | IntegerLiteral) -> Marker;
~~~

Первый вариант примера сопоставляет два соседних узла Identifier и Colon в указанном порядке; второй — один IntegerLiteral. Варианты могут потреблять разное число узлов. Цепочка остаётся непрерывной и ограниченной текущим контекстом; она не пересекает границы родителя или группы.

Решение фиксирует синтаксис и возможность альтернатив цепочек. Выбор максимальной длины полного совпадения определён в D275 (§9.61). Категория общего внешнего захвата и проверка принимающего места определены в D276 (§9.62). Повторение альтернатив цепочек через + с плоским захватом определено в D277 (§9.63). Допустимость пустых вариантов и остальные ещё не согласованные формы повторения требуют уточнения. Само это решение не вводит приоритет первого варианта для всех альтернатив: принятый приоритет D268 относится к вкладам аккумуляторов.

Основание: D274.

### 9.61. Максимальная длина полного совпадения

На текущей позиции выбирается максимальный фрагмент, позволяющий совпасть всему шаблону правила, включая части до и после альтернативы. Если варианты альтернативы допускают полные совпадения разной длины, преимущество имеет максимальная длина независимо от порядка вариантов.

~~~text
(Identifier | Identifier, Colon) -> Marker;
~~~

Для входной цепочки Identifier, Colon подходят оба варианта, но полное совпадение второго длиннее: поглощаются оба узла. Перестановка вариантов не меняет длину выбранного фрагмента. Выбор не является локальным жадным выбором самой длинной ветки без учёта продолжения шаблона.

Приоритет вариантов для вкладов аккумуляторов по D268 применяется только среди совпадений одинаковой максимальной длины. Он не позволяет короткому первому варианту вытеснить более длинное полное совпадение. Требования согласованности обычных захватов и однозначности распределения сохраняются.

После выбора максимального кандидата действуют прежние правила: неоднозначность не разрешается укорачиванием кандидата; ожидаемый отказ построения результата также не запускает перебор более коротких фрагментов. Поиск того же правила продолжается со следующей позиции в направлении стрелки.

Основание: D275.

### 9.62. Общий захват цепочек и принимающее место

Общий внешний захват альтернативы цепочек имеет категорию списка, если хотя бы один вариант является списочным. При совпадении одноэлементного варианта такого шаблона получается список из одного узла; категория не меняется во время исполнения. Если все варианты обязательные одиночные, захват одиночный. Если все варианты одиночные или необязательные одиночные и хотя бы один допускает отсутствие, общий захват — необязательный одиночный (уточнение D289, §9.69).

~~~text
(Identifier, Colon | IntegerLiteral) as items
    -> Container[$items];
~~~

В примере первый вариант даёт список из Identifier и Colon, второй — список из одного IntegerLiteral. Статический анализ обязан отдельно проверить, что соответствующее место схемы Container принимает список, его возможную кратность и все возможные типы элементов. Имя Container само по себе не гарантирует пригодность его схемы.

Например, node Container(Node*); допускает оба варианта. Место Expression* не подходит, если Colon не является Expression. Обязательное одиночное место не принимает этот списочный захват даже на входе, где совпал только IntegerLiteral. Каждое выражение результата по-прежнему заполняет своё место схемы: список не распределяется неявно по нескольким одиночным местам.

Несовместимость с местом результата является ошибкой DSL до исполнения, а не ожидаемым отказом кандидата. После статической проверки весь результат всё равно должен быть успешно построен билдерами по D251; статическая допустимость подстановки не отменяет проверок при создании узлов. Это уточняет D274 и распространяет проверку всех вариантов D259 на общий захват альтернативы цепочек.

Основание: D276.

### 9.63. Повторение альтернатив цепочек

Разрешено повторение альтернатив цепочек узлов через +. Каждая итерация сопоставляет одну из цепочек альтернативы. Общий внешний захват повторения получает единый плоский список всех поглощённых узлов в исходном порядке; границы итераций и выбранных цепочек в этом захвате не сохраняются.

~~~text
(Identifier, Colon | IntegerLiteral)+ as items
    -> Container[$items];
~~~

Например, для входа Identifier, Colon, IntegerLiteral, Identifier, Colon захват items содержит все пять узлов в том же порядке, а не список из трёх вложенных списков. Суффикс + требует хотя бы одну итерацию.

Принимающее место Container обязано статически допускать список, возможную кратность и типы всех его элементов по D276. Сохраняются требования максимального полного совпадения D275, однозначности распределения и ограничения внутренних захватов под повторением. Потеря границ итераций в результате захвата не отменяет проверки однозначности сопоставления.

Повторение через * с нулём или более итераций также разрешено (D280, §9.64). Тело * или + не может допускать пустое совпадение: это ошибка компиляции по D278 (§10.1.1).

Основание: D277.

### 9.64. Повторение альтернатив цепочек через *

Разрешено повторение альтернатив цепочек узлов через *. Оно выполняет ноль или более итераций. Общий внешний захват имеет категорию списка: при нуле итераций это пустой список, иначе — плоский список всех поглощённых узлов в исходном порядке, без границ итераций.

~~~text
Start, (Identifier, Colon | IntegerLiteral)* as items
    -> Container[$items];
~~~

Статический анализ отдельно проверяет, что принимающее место результата допускает список, все возможные типы элементов и его кратность, включая пустой список. Для примера ниже обязательный Start обеспечивает непустое совпадение всего правила; сам Start в items не входит.

Тело повторения не должно допускать пустое совпадение (D278). Сохраняются правила выбора максимального полного совпадения, однозначности распределения и ограничения внутренних захватов под повторением. Успешная статическая проверка не отменяет проверки результата билдерами.

Основание: D280.

### 9.65. Необязательная альтернатива цепочек

Разрешено применение ? к альтернативе цепочек узлов: группа либо отсутствует, либо совпадает один вариант альтернативы. Для альтернативы цепочек со списочным общим захватом этот захват сохраняет категорию списка: при отсутствии группы получается пустой список, при совпадении — все поглощённые узлы в исходном порядке.

~~~text
Start, (Identifier, Colon | IntegerLiteral)? as items
    -> Container[$items];
~~~

В примере items содержит ноль узлов, пару Identifier и Colon либо один IntegerLiteral. Start обеспечивает непустое совпадение полного шаблона и не входит в items. Статический анализ обязан проверить, что принимающее место Container допускает все эти варианты списка, включая пустой, их кратность и типы.

Это решение не меняет категорию захвата альтернативы, каждый вариант которой поглощает ровно один узел: под ? она остаётся необязательным одиночным захватом по D260. Сохраняются правила максимального полного совпадения и однозначности, запрет обычных захватов данных внутри ? и отдельная проверка построения результата билдерами.

Основание: D281.

### 9.66. Группировка цепочек без альтернативы

Круглые скобки разрешены для группировки цепочки шаблонов без оператора |. Суффиксы *, + и ? после закрывающей скобки относятся ко всей цепочке: * означает ноль или более повторений, + — одно или более, ? — отсутствие либо одно совпадение всей цепочки.

~~~text
Start, (Identifier, Colon)* as items
    -> Container[$items];
~~~

В примере повторяется целиком пара Identifier, Colon. Общий внешний захват items — плоский список поглощённых узлов в исходном порядке, без границ итераций; Start в него не входит. Для (Identifier, Colon)+ список содержит одну или более пар, для (Identifier, Colon)? — пустой список либо одну пару.

Группировка не создаёт узел дерева. Сохраняются проверки максимального полного совпадения и однозначности распределения, ограничения внутренних захватов и проверка принимающего места результата на все возможные типы и кратности, включая пустой список для * и ?. Тело * или + не должно допускать пустое совпадение (D278); полный шаблон правила должен гарантированно поглощать хотя бы один узел. Построение результата по-прежнему проверяется билдерами.

Основание: D282.

### 9.67. Вложенные повторения шаблонов

Вложенные повторения шаблонов разрешены при соблюдении общих проверок однозначности. Требование непустого тела по D278 проверяется отдельно для каждого * и +: каждая выполненная итерация каждого повторения должна поглощать хотя бы один узел.

~~~text
(Open, Identifier*, Close)+ as items
    -> Container[$items];
~~~

В примере внутреннее повторение Identifier* может выполнить ноль итераций, но его тело Identifier непусто. Тело внешнего + включает обязательные Open и Close и потому также не допускает пустого совпадения. Вложенность сама по себе не является основанием для запрета.

Общий внешний захват items содержит все поглощённые узлы, включая Open и Close, одним плоским списком в исходном порядке. Границы внутренних и внешних итераций не сохраняются. Плоский захват не отменяет проверки однозначности распределения.

Сохраняются ограничения обычных захватов внутри * и +, специальный режим аккумуляторов, выбор максимального полного совпадения и проверки принимающего места результата на все возможные типы и кратности. После статических проверок результат должен быть успешно построен билдерами.

Основание: D283.

### 9.68. Неоднозначность разбиения на итерации

Если статический анализ доказывает неоднозначность разбиения совпавшей цепочки на итерации вложенных повторений, шаблон отвергается при компиляции DSL. Одинаковый итоговый плоский список захвата не устраняет неоднозначность сопоставления.

~~~text
(Identifier+)+ as items -> Container[$items]; // Ошибка DSL.
~~~

В примере цепочка из двух Identifier допускает как одну внешнюю итерацию с двумя внутренними, так и две внешние итерации с одной внутренней в каждой. Этого доказуемого случая достаточно для отклонения шаблона: не требуется, чтобы неоднозначным был каждый возможный вход.

Для захвата обычного непустого списка идентификаторов следует использовать Identifier+ as items. Вложенные повторения в целом остаются разрешёнными по D283; запрет относится к доказанной неоднозначности распределения, а не к самой вложенности.

Если статический анализ не смог доказать неоднозначность разрешённого шаблона, сохраняется проверка конкретного максимального кандидата при исполнении. Неоднозначный кандидат отвергается без перебора более коротких фрагментов; поиск того же правила продолжается со следующей позиции.

Основание: D285.

### 9.69. Необязательный одиночный вариант альтернативы

Общий внешний захват альтернативы одиночного и необязательного одиночного шаблона имеет категорию необязательного одиночного узла. Если все варианты относятся к одиночным или необязательным одиночным шаблонам и хотя бы один допускает отсутствие узла, захват также допускает отсутствие. Если все варианты обязательные одиночные, захват остаётся обязательным одиночным.

~~~text
Start, (Identifier? | IntegerLiteral) as x
    -> Result[$x];
~~~

В примере x содержит Identifier, IntegerLiteral либо отсутствует. Статический анализ обязан проверить, что принимающее место Result допускает отсутствие узла и оба возможных типа. Start обеспечивает непустое совпадение всего правила и не входит в x.

Это уточняет D276: различие между нулём и одним узлом в таких одиночных вариантах само по себе не превращает общий захват в список. Решение относится к общему внешнему захвату альтернативы; оно не разрешает смешивать одноимённые внутренние захваты разных категорий и не превращает списочный шаблон в одиночный.

Сохраняются правила выбора максимального полного совпадения и проверки неоднозначности. Категория определяется статически и не меняется по конкретному входу. Если группа не даёт узла, это отсутствие одиночного значения, а не пустой список.

Основание: D289.

### 9.70. Одноимённые одиночные захваты разной обязательности

Одноимённые внутренние одиночные захваты в ветках альтернативы могут различаться обязательностью. Если хотя бы одна ветка допускает отсутствие захваченного узла, общий захват является необязательным одиночным. Имя по-прежнему должно быть объявлено ровно один раз в каждой ветке.

~~~text
(Box(value: Expression as x)
 | Wrapper(value: Expression? as x))
    -> Result[$x];
~~~

В примере Box связывает x с обязательным Expression, а Wrapper — с необязательным Expression. Общий x допускает отсутствие. Статический анализ проверяет совместимость всех возможных типов и возможности отсутствия с каждым принимающим местом результата; Result должен принимать необязательное значение.

Это уточняет D271: обязательный и необязательный одиночный узловой захват разрешено объединять под одним именем в альтернативах. Смешивание со списком или данными и отсутствие самого объявления в одной из веток остаются запрещёнными.

Сохраняются проверки согласованности захватов при одновременном совпадении веток и различение вхождений узлов по D272. Разрешение необязательности само по себе не устраняет конфликты захватов и не отменяет проверок построения результата билдерами.

Основание: D290.

### 9.71. Согласованность необязательных одиночных захватов

При одновременном совпадении веток альтернативы значения общего необязательного одиночного захвата должны быть согласованы. Два отсутствующих значения согласованы. Отсутствие в одной ветке и присутствующий узел в другой являются неоднозначностью. Два присутствующих значения согласованы только тогда, когда обозначают одно и то же вхождение узла в исходном дереве.

~~~text
(Pair(left: Expression? as x)
 | Pair(right: Expression? as x))
    -> Result[$x];
~~~

В примере, если левый ребёнок отсутствует, а правый содержит Expression, обе ветки совпадают, но первая даёт отсутствие x, а вторая — узел. Такой кандидат неоднозначен. Если оба ребёнка отсутствуют, значения x согласованы; если оба присутствуют, захваты разных вхождений конфликтуют по D272.

Отсутствие не является значением, которое разрешено автоматически заменить присутствующим узлом из другой совпавшей ветки. Порядок веток и приоритет вкладов аккумуляторов не разрешают этот конфликт.

Применяется общий порядок проверок: статически доказанная неоднозначность — ошибка компиляции DSL; не выявленная заранее неоднозначность максимального кандидата приводит к его отклонению до построения результата. Более короткие кандидаты для этой позиции не перебираются, поиск того же правила продолжается со следующей позиции. Согласованность отсутствующих значений сама по себе не отменяет других проверок сопоставления.

Основание: D291.

### 9.72. Отрицание узлового шаблона

Вводится отрицание узлового шаблона через !. Форма !T проверяет текущий узел и совпадает, если этот узел не соответствует шаблону T. При успешном совпадении поглощается ровно один узел. Если текущего узла нет, совпадения нет.

~~~text
Quote, (!Quote)*, Quote -> StringLiteral;
~~~

Например, !Quote соответствует любому текущему узлу, который не соответствует Quote. Для абстрактного Quote обычная проверка типа включает его подтипы, поэтому отрицание исключает и их. Повторение (!Quote)* поглощает ноль или более таких узлов.

В примере первая Quote открывает фрагмент, повторение не может поглотить Quote, а последняя Quote закрывает его. Пример распознаёт границы без сбора текста. Проверка допустимости и построение StringLiteral выполняются по обычным правилам.

Это поглощающий одноузловой шаблон, а не проверка соседних узлов без поглощения. Логическое отрицание внутри фильтров данных сохраняет прежний смысл. Форма !T и её использование под повторением разрешены. Отрицание одноузловых альтернатив и требование к кратности операнда определены в D293 (§9.73); захваты внутри отрицания запрещены, а внешний захват разрешён по D294 (§9.74).

Основание: D292.

### 9.73. Одноузловой операнд отрицания

Разрешено отрицание альтернативы одноузловых шаблонов: !(Quote | Newline) совпадает с текущим узлом, если тот не соответствует ни Quote, ни Newline. Успешное отрицание поглощает ровно один узел; при отсутствии текущего узла совпадения нет.

~~~text
!(Quote | Newline) // Один узел, не соответствующий ни одному варианту.
!(Identifier, Colon) // Ошибка: операнд — цепочка из двух узлов.
!(Identifier?) // Ошибка: операнд допускает отсутствие узла.
~~~

Операнд узлового отрицания должен быть шаблоном ровно одного узла. Операнды, допускающие ноль или несколько поглощённых узлов, запрещены при компиляции DSL. В частности, !(Identifier, Colon), !(Identifier?), !(Identifier*) и !(Identifier+) недопустимы.

Ограничение относится к числу узлов, сопоставляемых операндом в текущей цепочке. Внешнее повторение отрицания допустимо: (!(Quote | Newline))* повторяет одноузловую проверку. Отрицание не становится проверкой цепочки или условием без поглощения.

Это расширяет D292 на одноузловые альтернативы и определяет требование к кратности операнда. Захваты внутри отрицания запрещены по D294 (§9.74). Отрицание составных проверок типа, данных и детей разрешено по D295 (§9.75).

Основание: D293.

### 9.74. Захваты при отрицании

Внутри операнда узлового отрицания запрещены любые объявления захватов на любой глубине: захваты узлов и списков через as, обычные захваты данных и строковые аккумуляторы. Это ошибка DSL до исполнения. Успешное отрицание означает, что внутренний шаблон не совпал; значения из него не извлекаются.

~~~text
!(Identifier as x) // Ошибка: захват внутри отрицания.
!(Identifier<$text>) // Ошибка: обычный захват данных.
!(Identifier<$text+>) // Ошибка: аккумулятор внутри отрицания.
(!Identifier) as x // Внешний захват поглощённого узла, базовый тип Node.
~~~

Внешний захват отрицательного шаблона разрешён: (!Identifier) as x захватывает фактически поглощённый узел. Такой захват одиночный, его базовый статический тип — Node. Отрицание Identifier не даёт права считать захваченный узел Identifier или другим конкретным типом.

Статический анализ проверяет совместимость внешнего захвата с принимающим местом результата. Сам захват не создаёт узел типа Node: он сохраняет существующий узел с его фактическим типом. Остальные ограничения расположения захватов, в частности запрет обычных захватов внутри внешнего повторения, сохраняются.

Запрет относится к объявлениям захватов внутри операнда, включая вложенные проверки. Он не запрещает саму проверку данных без объявления захвата. Составные проверки типа, данных и детей разрешены как операнды по D295 (§9.75).

Основание: D294.

### 9.75. Отрицание составной проверки узла

Разрешено отрицание составной проверки одного узла, включающей тип, условия данных и проверки детей. Отрицается совпадение операнда целиком: существующий текущий узел подходит, если он не соответствует хотя бы одной из обязательных проверок операнда.

~~~text
!(Identifier<"if">) // Любой узел, кроме Identifier с данными "if".
Identifier<!"if"> // Только Identifier с другими данными.
!(Box[Expression]) // Отрицание всей проверки типа и детей.
~~~

Шаблон !(Identifier<"if">) поглощает любой узел, кроме Identifier с данными "if". Он допускает Identifier с другими данными и узлы других типов. В отличие от него, Identifier<!"if"> проверяет именно Identifier и отрицает только условие на его данные.

Шаблон !(Box[Expression]) отрицает всю проверку Box с полным позиционным шаблоном детей [Expression]. Подходит узел другого типа либо Box, дети которого не соответствуют этой проверке. Проверки нескольких детей внутри операнда допустимы: ограничение D293 относится к одному узлу текущей цепочки, а не к числу проверяемых потомков.

При успешном отрицании поглощается ровно один текущий узел; на пустом входе совпадения нет. Все объявления захватов внутри операнда, в том числе в проверках детей и данных, остаются запрещёнными по D294. Невалидный шаблон не становится допустимым из-за оборачивания в отрицание.

Основание: D295.

### 9.76. Приоритет отрицания и кратности

В узловых шаблонах отрицание ! связывается сильнее суффиксов кратности ?, * и +. Поэтому !Quote* означает (!Quote)*: ноль или более узлов, каждый из которых не соответствует Quote. Аналогично !Quote+ означает (!Quote)+, а !Quote? — (!Quote)?.

~~~text
Quote, !Quote*, Quote -> StringLiteral;
// То же самое: Quote, (!Quote)*, Quote -> StringLiteral;
!(Quote*) // Ошибка: операнд отрицания не одноузловой.
~~~

Скобки позволяют явно обозначить операнд отрицания. Запись !(Quote*) означает отрицание повторения и запрещена по D293, поскольку операнд не является шаблоном ровно одного узла. Аналогично запрещены !(Quote+) и !(Quote?).

Приоритет не меняет семантику операций: само отрицание поглощает один узел и не совпадает на пустом входе; внешний * или ? допускает отсутствие. Полный шаблон правила по-прежнему должен гарантированно поглощать хотя бы один узел. Это правило приоритета относится к узловым шаблонам и не меняет приоритеты выражений фильтрации данных.

Основание: D296.

### 9.77. Двойное узловое отрицание

Двойное узловое отрицание разрешено. Запись !!Identifier означает !(!Identifier) и по сопоставлению эквивалентна Identifier: совпадает с соответствующим текущим узлом и поглощает ровно один узел. При отсутствии текущего узла совпадения нет у обоих шаблонов.

~~~text
!!Identifier // По сопоставлению эквивалентно Identifier.
!!(Identifier as x) // Ошибка: захват внутри отрицания.
~~~

Для допустимого одноузлового операнда P двойное отрицание !(!P) сохраняет условие его совпадения. Каждое отрицание проверяет тот же текущий узел; два знака ! не означают поглощение двух узлов.

Запрет объявлений захватов внутри отрицания по D294 сохраняется независимо от числа отрицаний. Например, !!(Identifier as x) является ошибкой DSL. Упрощение двойного отрицания не может сделать допустимой конструкцию, нарушающую ограничения исходного шаблона.

Эквивалентность сопоставления дополняется уточнением статического типа внешнего захвата по D298 (§9.78). Требования одноузлового операнда и остальные статические проверки сохраняются.

Основание: D297.

### 9.78. Тип захвата после двойного отрицания

Статический анализ учитывает двойное узловое отрицание при определении типа внешнего захвата. Для (!!Identifier) as x тип захваченного узла уточняется до Identifier; такой захват разрешено подставлять в совместимое место типа Identifier, а не только Node.

~~~text
(!!Identifier) as x -> Result[$x];
// Допустимо, если соответствующее место Result принимает Identifier.
!!(Identifier as x) // Ошибка независимо от упрощения.
~~~

Для допустимого одноузлового шаблона P двойное отрицание сохраняет доступные статические сведения о типе захватываемого текущего узла, как при внешнем захвате P. Это уточняет базовый тип Node из D294 и дополняет эквивалентность сопоставления по D297. Проверки совместимости с каждым принимающим местом результата сохраняются.

Ограничения исходного шаблона проверяются до упрощений. В частности, !!(Identifier as x) остаётся ошибкой: объявление захвата находится внутри отрицания. Устранение двойного отрицания не может скрыть нарушение запрета захватов или других требований DSL.

Основание: D298.

### 9.79. Чтение внешнего захвата данных внутри отрицания

В условиях данных внутри узлового отрицания разрешено читать обычный захват данных, связанный вне операнда отрицания в том же правиле. Чтение значения не является объявлением захвата и не нарушает D294.

~~~text
Identifier<$name>, !(Identifier<data() == $name>)
    -> Identifier<$name>;
~~~

Первый узел в примере — Identifier, связывающий name со своими данными. Второй — любой существующий узел, кроме Identifier с теми же данными. Внутренний data() относится к проверяемому второму узлу.

Все требования доступности и типизации захвата сохраняются. Запись !(Identifier<$name>) по-прежнему запрещена: она содержит захват данных, а не выражение чтения. Решение не вводит захваты внутри отрицания и не меняет ограничения на чтение аккумуляторов.

Основание: D299.

### 9.80. Пересечение одноузловых шаблонов

Вводится пересечение одноузловых шаблонов через &. Оба операнда проверяют один и тот же текущий узел; пересечение совпадает только при выполнении обоих условий. Успешное совпадение поглощает ровно один узел. При отсутствии текущего узла совпадения нет.

~~~text
(Expression & !Identifier) as x -> Result[$x];
~~~

В примере узел должен соответствовать Expression и не соответствовать Identifier. Внешний захват x сохраняет статически известное ограничение Expression и может использоваться в совместимом месте результата. Проверка принимающего места Result остаётся обязательной.

Пересечение не является последовательностью двух узлов. Решение вводит одноузловую форму и внешний захват; пересечение цепочек этим решением не разрешается. Захват в одном операнде разрешён по D303 (§9.83), разные захваты в обоих операндах — по D304 (§9.84). Повторные имена определены в D305 (§9.85); дублирование источника общего аккумулятора определено в D307 (§9.87) и D309 (§9.89), порядок разных источников — в D308 (§9.88). Место & относительно кратности и запятой определено в D302 (§9.82). Относительный приоритет !, & и | определён в D301 (§9.81). Сохраняются общие требования статической проверки, включая диагностику доказанно невозможного совпадения.

Основание: D300.

### 9.81. Единые одинарные логические знаки и одинаковый относительный приоритет

Для условий данных и узловых шаблонов используются одинаковые знаки: & — «и», | — «или», ! — «не». В выражениях данных & и | принимают булевы значения; в шаблонах обозначают пересечение и альтернативу по ранее принятым правилам. Побитовые операции не вводятся.

~~~text
Identifier<startsWith("get") & !endsWith("Internal")>
(Expression & !Identifier)
~~~

Относительный приоритет этих трёх операций одинаков в обоих контекстах: ! выше &, & выше |. Круглые скобки позволяют изменить группировку. Полные таблицы сохраняют специфические для соответствующего контекста операции; место узлового & относительно кратности и запятой определено в D302 (§9.82).

В выражениях DSL записи && и || отменяются и не допускаются как альтернативное написание. Сравнения == и != сохраняются. Это уточняет обозначения D224, D226, D237 и связанных примеров, а также определяет относительный приоритет !, & и | для D300. Семантика чистых выражений и необязательного короткого замыкания D225–D226 сохраняется; она не переносится автоматически на сопоставление шаблонов с захватами.

Решения D274 (запятая сильнее |) и D296 (узловое ! сильнее суффиксов кратности) остаются в силе. Исторические записи журнала с двойными знаками следует читать с учётом настоящего решения; действующая спецификация и её примеры используют одинарные знаки.

Основание: D301.

### 9.82. Приоритет операций шаблонов и обязательные примеры в документации

Приоритет операций узловых шаблонов от высокого к низкому: !; суффиксы кратности ?, * и +; пересечение &; последовательность через запятую; альтернатива |. Круглые скобки изменяют группировку. Это дополняет D274, D296 и D301: & связывается слабее суффиксов кратности, но сильнее запятой. Относительный порядок !, & и | одинаков в шаблонах и выражениях данных.

Запись (A & !B, C) означает ((A & (!B)), C): сначала один узел, соответствующий A, но не B, затем соседний C. Запись (A & !B)* повторяет всё пересечение. Запись A & B* разбирается как A & (B*) и является ошибкой: пересечение требует одноузловых операндов, а B* допускает ноль или несколько узлов. Аналогично для операнда B? или B+; скобки вокруг всего пересечения позволяют применить кратность к его результату.

В пользовательской документации обязательно привести отдельные полные таблицы приоритетов выражений данных и операций шаблонов, подчеркнув одинаковый относительный порядок общих логических знаков. Для всех перечисленных уровней нужны понятные примеры; для сочетаний операторов разных уровней — исходная запись, эквивалентная запись с явными скобками и объяснение результата обычными словами.

Обязательно показать влияние скобок, различие проверки данных и проверки узла, сочетания ! с кратностями, & с кратностями и запятой, запятой с |, а также арифметики, сравнений и логических условий. Нужны положительные и отрицательные примеры с объяснением причины ошибки, включая A & B* и отменённые &&/||. В фильтрах сохраняется требование скобок для сравнений порядка (D243). Одной таблицы без разобранных примеров недостаточно.

Это обязательный критерий готовности пользовательской документации, а не необязательное пожелание. По мере утверждения оставшихся синтаксических конструкций таблицы и примеры должны дополняться; размещение as и правила внутренних захватов этим решением не определяются.

Основание: D302.

### 9.83. Захват в одном операнде пересечения

Внутри одного операнда пересечения разрешено объявить захват и использовать его в результате без повторного объявления в другом операнде. Для успешного совпадения пересечения обязательны оба операнда, поэтому отсутствие объявления имени в другом операнде само по себе не делает захват недоступным.

~~~text
(Box(value: Expression as x) & !Deprecated)
    -> Result[$x];
~~~

В примере Box связывает x с обязательным ребёнком Expression, а !Deprecated дополнительно проверяет тот же Box. При успешном совпадении x доступен в результате. Принимающее место Result должно быть совместимо со статическими типом и кратностью захвата.

Сохраняются все ограничения вложенных конструкций: в частности, запрет объявлений захватов внутри отрицания (D294), требования к альтернативам и повторениям. Обязательность совпадения операнда не превращает его внутренний необязательный захват в обязательный. Категория, тип и кратность определяются самим захватывающим шаблоном.

Повторные объявления одного узлового или списочного имени в разных операндах пересечения запрещены по D305 (§9.85). Однократное накопление общего источника определено в D307 (§9.87) и D309 (§9.89), порядок разных источников — в D308 (§9.88).

Основание: D303.

### 9.84. Разные захваты в операндах пересечения

В разных операндах пересечения разрешено объявлять захваты с разными именами. При успешном совпадении пересечения захваты обоих операндов доступны в результате; выбирать захваты только одного операнда не требуется. Оба операнда проверяют один и тот же текущий узел.

~~~text
(Pair(left: Expression as x)
 & Pair(right: Expression as y))
    -> Result[$x, $y];
~~~

В примере оба шаблона проверяют один Pair: первый захватывает его левого ребёнка как x, второй — правого как y. При успешном совпадении доступны оба обязательных одиночных захвата типа Expression. Совместимость каждого захвата с соответствующим местом Result проверяется статически.

Категория, тип и кратность каждого захвата сохраняются согласно объявляющему его шаблону. Сохраняются единое пространство имён, ограничения вложенных альтернатив, повторений и отрицаний, а также проверки построения результата. Разрешение разных имён не вводит повторного объявления одного узлового или списочного имени и не определяет накопление в один аккумулятор из нескольких операндов.

Основание: D304.

### 9.85. Повторные имена захватов в пересечении

Повторное объявление одного имени узлового или списочного захвата через as в разных операндах пересечения является ошибкой компиляции DSL. Оба операнда обязательны; исключение для общего имени в альтернативных ветках не распространяется на пересечение. Повторное объявление не вводит проверку равенства или идентичности узлов.

~~~text
(Pair(left: Expression as x)
 & Pair(right: Expression as x)) // Ошибка: два объявления x.
~~~

Пример содержит два объявления x и запрещён. Для захвата обоих детей следует использовать разные имена по D304. Само совпадение захватываемых вхождений также не разрешает повторное объявление одного имени через as.

Для обычных захватов данных сохраняется D207: повторное имя $name в операндах пересечения обозначает одну общую строку и требует равенства всех захваченных значений. Разные строки приводят к несовпадению шаблона, а не к выбору одного значения. Единое пространство имён и запрет смешения обычного захвата и аккумулятора одного имени сохраняются.

Правило относится к повторным объявлениям, а не к чтению уже объявленного захвата. Доказанное дублирование источника накопления рассматривается в D307 (§9.87).

Основание: D305.

### 9.86. Доказанное включение условий и сохранение захватов при упрощении

Шаблон Q включает требования шаблона P, если любое совпадение Q обязательно означает совпадение P на том же исходном узле и при тех же внешних значениях захватов. В терминах множеств совпадений Q является подмножеством P. Направление включения определяется этим критерием, а не сходством текста.

Упрощать P & Q до Q разрешено только при доказанном включении и сохранении всех захватов и вкладов в аккумуляторы. Одного включения условий недостаточно: удаляемый операнд может содержать нужный захват. Ограничения исходного шаблона проверяются до упрощения; запрещённое повторное объявление или захват внутри отрицания нельзя скрыть оптимизацией.

Например, Identifier<startsWith("a")> включает требования Identifier: дополнительный фильтр сужает множество подходящих узлов. Пересечение этих проверок без захватов можно упростить до проверки с фильтром. Если удаляемая проверка содержит захват, необходимо отдельно доказать его сохранение.

Статический анализ обязан обосновать включение для выполняемого упрощения. Полнота доказательства для произвольных выражений не требуется. Если доказательства нет, упрощение не выполняется; само отсутствие доказательства не является ошибкой DSL. Примеры включения и случаев, когда удаление операнда теряет захват, обязательны в документации по D302.

Основание: D306.

### 9.87. Доказанное однократное накопление общего источника в пересечении

Если операнды пересечения добавляют данные одного и того же вхождения исходного узла в один и тот же аккумулятор, такие дублирующие вклады учитываются один раз при доказанном совпадении источника и аккумулятора. Равенства строк, структурного равенства узлов или совпадения ссылки на объект в разных местах дерева недостаточно.

В примере (Identifier<$text+> & Identifier<startsWith("a"), $text+>) -> Token<$text>; оба добавления относятся к текущему узлу и аккумулятору text. Для исходных данных "abc" результат накопления равен "abc", а не "abcabc". Пример намеренно избыточен: по D306 его можно упростить до Identifier<startsWith("a"), $text+> -> Token<$text>; с сохранением однократного вклада.

Включение одного условия в другое и совпадение источников накопления — отдельные доказательства. Включение условий само по себе не позволяет объединить вклады разных вхождений. Разные исходные вхождения с одинаковой строкой остаются отдельными источниками накопления.

Без доказательства совпадения источника и аккумулятора статически объединять вклады нельзя. Если тождество источников не установлено статически, оно проверяется при сопоставлении по D309 (§9.89); один источник в одном аккумуляторе учитывается один раз. Порядок разных источников определён в D308 (§9.88): по исходному дереву. Откат отвергнутого кандидата и остальные принятые ограничения аккумуляторов сохраняются.

Основание: D307.

### 9.88. Порядок дерева определяет накопление, включая пересечения

Вклады разных исходных вхождений в один аккумулятор упорядочиваются по узлам исходного дерева, а не по расположению токенов, условий или операндов в шаблоне. Это общее правило D209 и D250 применяется и к пересечениям: сначала текущий узел, затем рекурсивно поддеревья детей слева направо в порядке итоговой схемы и элементов групп. Несколько корней фрагмента рассматриваются слева направо независимо от стрелки.

~~~text
(Pair(left: Identifier<$text+>)
 & Pair(right: Identifier<$text+>))
    -> Token<$text>;
~~~

Если в схеме Pair левый ребёнок предшествует правому, данные левого Identifier "ab" и правого "cd" дают "abcd". Перестановка двух операндов & не меняет результат накопления. Если оба ребёнка содержат "ab", получается "abab": это разные вхождения исходного дерева. Названия тегов сами по себе не задают порядок; он берётся из схемы и исходной структуры.

Вклад включается только при явном накопительном захвате соответствующего источника в успешном варианте совпадения. Дублирование одного источника в одном аккумуляторе устраняется статически по D307 либо при сопоставлении по D309 (§9.89). Правило не меняет выбор ветки альтернативы для аккумуляторов по D268: сначала определяется состав вкладов, затем их порядок задаёт дерево.

Это порядок данных при сопоставлении, а не новое расписание применения правил преобразования: обход преобразования снизу вверх по D189–D192 сохраняется. Порядок вычисления независимых условий не должен менять наблюдаемый результат накопления. В документации обязателен пример перестановки операндов пересечения с неизменным результатом (D302).

Основание: D308.

### 9.89. Проверка тождества источников накопления при сопоставлении

Если статический анализ не установил, относятся ли накопительные захваты операндов пересечения к одному исходному вхождению, это проверяется при сопоставлении конкретного кандидата. Для одного аккумулятора данные одного и того же вхождения учитываются один раз; данные разных вхождений учитываются отдельно.

Тождество определяется точным местом узла в исходном дереве, а не равенством строк, структурным равенством поддеревьев или ссылкой на объект. Один неизменяемый объект, использованный в двух местах дерева, даёт два разных вхождения. Проверка проводится отдельно для каждого аккумулятора в пределах текущего кандидата совпадения.

Статическое доказательство D307 позволяет заранее устранить дублирующее накопление, но его отсутствие не меняет семантику и само по себе не запрещает шаблон. При одинаковом входе результат накопления не зависит от возможностей статического анализатора и наличия этой оптимизации.

После определения состава вкладов и устранения повторов данные накапливаются в порядке исходного дерева по D308. Выбор веток альтернатив для аккумуляторов по D268 сохраняется: невыбранная ветка не добавляет источник. Откат неудачного варианта не оставляет ни вкладов, ни отметок об уже учтённых вхождениях; новое совпадение не наследует такие отметки.

Это закрывает оставленный в D307 вопрос об источниках, тождество которых не доказано статически. В документации следует сопоставить случаи одного вхождения, двух равных по данным вхождений и одного объекта в двух местах дерева, с одинаковым поведением при статическом и динамическом установлении тождества (D302).

Основание: D309.

### 9.90. Сохранение ограничений типов внешнего захвата пересечения

Внешний захват пересечения сохраняет все гарантированные ограничения типов его операндов. Для (Printable & Named) as x компилятор знает, что захваченный узел одновременно является Printable и Named. Сводить эти сведения к одному общему предку не требуется; новый именованный тип узла в DSL не вводится.

~~~text
(Printable & Named) as x
~~~

Если Printable и Named — абстрактные типы, а Document наследуется от обоих, шаблон может захватить Document. Захват x разрешено передать как в место Printable, так и в место Named, а также в совместимые базовые типы. При этом передать x в место Document на основании только этих двух ограничений нельзя: принадлежность конкретному потомку шаблон не гарантирует.

Для передачи захвата простого пересечения A & B в место типа T достаточно, чтобы хотя бы одно из гарантированных ограничений A или B было подтипом T по объявленной иерархии (включая равенство типов). При альтернативе A | B совместимость должна быть обеспечена для каждого возможного варианта. Проверка выполняется при компиляции DSL для каждого принимающего места; если совместимость не установлена, подстановка является ошибкой.

Фактический тип и содержимое исходного узла при подстановке сохраняются. Речь идёт о статических сведениях компилятора, а не о преобразовании узла в объект общего предка. Кратность, остальные требования принимающего места и проверки построения результата остаются в силе.

Поиск общего предка, имеющийся в core (findCommonBaseType), может использоваться там, где обобщение не теряет необходимых гарантий, но не является обязательным промежуточным шагом проверки пересечения. Варианты сведения к общему предку и произвольного выбора одного операнда отвергнуты. Конкретное представление ограничений в Java API по-прежнему отложено согласно D198.

В пользовательской документации нужны примеры передачи в Printable и Named и отказа для Document, а также сравнение с альтернативой по D302.

Основание: D310.

### 9.91. Проверка типов сочетаний пересечения и альтернативы

При проверке совместимости внешнего захвата сочетания & и | с принимающим местом компилятор рассматривает каждый возможный вариант и сохраняет все гарантированные ограничения пересечения внутри этого варианта. Подстановка разрешена только тогда, когда совместимость обеспечена для каждого варианта; фактический выбор при исполнении не заменяет статическую проверку.

~~~text
(Printable & (Named | Numbered)) as x
~~~

Для (Printable & (Named | Numbered)) as x проверяются варианты Printable & Named и Printable & Numbered. В обоих гарантирован Printable, поэтому принимающее место Printable подходит. Если ни Printable, ни Numbered не являются подтипами Named, во втором варианте принадлежность Named не гарантирована и подстановка в место Named запрещена. Если Numbered является подтипом Named, оба варианта совместимы с Named. Наследование самого Printable от Named также обеспечило бы нужную гарантию по D310.

Для вложенных сочетаний применяется тот же принцип: все возможные варианты должны удовлетворять требованию получателя; внутри каждого варианта достаточно гарантированного ограничения, обеспечивающего требуемый тип по D310. Сведения не сводятся обязательно к одному общему предку. Проверяются также кратность и остальные требования каждого принимающего места.

Рассмотрение вариантов описывает статическую проверку типов и не требует физически раскрывать шаблон или менять сопоставление. Оно не разрешает дублировать захваты, менять приоритет альтернатив для аккумуляторов или обходить проверки неоднозначности. Конкретный алгоритм и представление ограничений не фиксируются.

В документации необходимо показать успешную передачу в Printable, отказ для Named при отсутствии достаточных отношений наследования и успешный случай при Numbered : Named. Доказанно невозможный исходный вариант вызывает ошибку компиляции всего DSL по D312 (§9.92); молча исключать его ради успешной проверки типов запрещено.

Основание: D311.

### 9.92. Доказанно невозможная ветка — ошибка компиляции всего DSL

Если статический анализ доказал, что вариант шаблона не может совпасть ни с одним допустимым входом в своём контексте, компиляция всего DSL завершается с ошибкой. Требование распространяется на отдельные ветки альтернатив и вложенные варианты, даже когда другие ветки работоспособны. Это расширяет D255 с невозможного шаблона целого правила на невозможные варианты внутри него.

~~~text
((Identifier & !Identifier) | Number) as x
// Ошибка компиляции: первая ветка невозможна.
~~~

В примере первая ветка требует одновременно Identifier и !Identifier и никогда не совпадёт. Наличие рабочей ветки Number не делает конструкцию допустимой. Пользователь должен явно исправить противоречие или удалить невозможную ветку.

Молча удалить невозможную ветку, сузить тип захвата до Number и успешно завершить компиляцию запрещено. Первоначальное предложение исключать такую ветку только из проверки типа отклонено. Предупреждения недостаточно: доказанная невозможность должна приводить к отказу компиляции.

Диагностика должна указать исходную ветку (место в DSL) и объяснить доказанную причину невозможности, например несовместимые требования Identifier и !Identifier. Проверяются также синтаксис и ограничения захватов: невозможность ветки не оправдывает других нарушений.

Полнота обнаружения невозможных вариантов не требуется, как и в D255. Отсутствие доказательства не считается доказанной невозможностью; отсутствие совпадения на конкретном входном дереве само по себе не является ошибкой компиляции. Данное решение не изменяет D256 о предупреждении для корректного правила, перекрытого более ранним правилом; невозможность самого условия и перекрытие приоритетом различаются.

В документации обязателен отрицательный пример с рабочей соседней веткой, объяснение отказа всей компиляции и исправленная запись Number as x. Упрощения D306 не должны скрывать доказанно невозможные исходные ветки.

Основание: D312.

## 10. Повторения, захваты и неоднозначность

### 10.1. Суффиксы шаблонов

| Форма | Число совпавших узлов |
|---|---:|
| T | 1 |
| T? | 0 или 1 |
| T* | 0 и более |
| T+ | 1 и более |

Эти формы также применимы к универсальному шаблону _. Шаблон всего фрагмента цепочки обязан поглощать хотя бы один элемент; отдельные необязательные части разрешены.

### 10.1.1. Запрет пустой итерации

Повторение через * или + запрещено при компиляции DSL, если его тело способно совпасть с пустой цепочкой. Каждая успешная итерация должна поглощать хотя бы один узел. Это локальное требование к каждому повторению, независимо от минимального потребления всего шаблона правила.

~~~text
(Identifier? | IntegerLiteral)+ // Ошибка: тело допускает пустое совпадение.
Start, (Identifier? | IntegerLiteral)* -> Marker; // Ошибка даже при обязательном Start.
~~~

Проверка относится к телу повторения, а не к его результату: само повторение * может успешно выполнить ноль итераций. Например, Start, Identifier* -> Marker; не нарушает это требование, поскольку каждая выполненная итерация Identifier поглощает один узел, а Start обеспечивает непустое совпадение всего правила.

Сохраняется отдельное требование положительного минимального потребления полного шаблона. Наличие обязательного узла вне повторения не исправляет пустую итерацию внутри него. При анализе альтернатив и вложенных конструкций учитывается возможность пустого совпадения тела; разрешение пустых итераций с искусственным ограничением их числа не вводится.

Основание: D278.

### 10.1.2. Запрет пустых веток альтернатив

Синтаксически пустые ветки альтернатив запрещены: перед каждым | и после него должен присутствовать шаблон. Записи (Identifier | ), ( | Identifier) и (Identifier | | IntegerLiteral) являются ошибками DSL.

Необязательность выражается явно через ?. Например, вместо Start, (Identifier | ) -> Marker; следует писать Start, Identifier? -> Marker;.

Запрет относится к отсутствию шаблона в ветке, а не к возможности явно записанного шаблона совпасть с пустой цепочкой. Ветка Identifier? не является синтаксически пустой. При этом сохраняются независимые требования: полный шаблон правила обязан поглощать хотя бы один узел, а тело повторения * или + не должно допускать пустое совпадение (D278).

Основание: D279.

### 10.1.3. Один суффикс кратности на уровень шаблона

На одном уровне шаблона допускается не более одного суффикса кратности: ?, * или +. Несколько суффиксов подряд, например Identifier+?, Identifier** или Identifier?+, являются синтаксической ошибкой DSL. Пробел между суффиксами не меняет это ограничение.

~~~text
Identifier+? // Ошибка: два суффикса подряд.
Identifier** // Ошибка: два суффикса подряд.
Start, (Identifier+)? -> Marker; // Явная вложенность.
~~~

Вложенность задаётся явными круглыми скобками. Запись (Identifier+)? обозначает необязательную группу из одного или более идентификаторов. Это допустимая часть шаблона, однако полный шаблон правила по-прежнему обязан гарантированно поглощать хотя бы один узел.

Сочетания суффиксов не вводят ленивый, притяжательный или иной дополнительный режим сопоставления. Скобки не отменяют семантических проверок: пустое тело повторения запрещено по D278, доказанная неоднозначность разбиения на итерации — по D285.

Основание: D286.

### 10.1.4. Запрет пустой группы в шаблоне

Пустая группа () в шаблоне запрещена синтаксически. Запрет сохраняется при добавлении суффикса: ()?, ()* и ()+ также недопустимы. Скобки группировки должны содержать шаблон; отдельная пустая группа как конструкция успешного совпадения без поглощения узлов не вводится.

~~~text
Start, () -> Marker; // Ошибка DSL.
Start, ()? -> Marker; // Ошибка DSL.
T[] -> Marker; // Проверка узла без детей, не пустая группа.
~~~

Это ограничение отличается от проверки возможности пустого совпадения явно записанного шаблона. Например, Identifier? остаётся допустимой необязательной частью при соблюдении остальных требований. Пустые ветки альтернатив также запрещены по D279.

Запрет пустой группы не затрагивает T[]: это полный позиционный шаблон, проверяющий отсутствие детей у узла типа T. Сам узел T при совпадении поглощается. Общее требование непустого совпадения полного правила и запрет пустого тела повторения сохраняются.

Основание: D287.

### 10.2. Захват as

~~~text
Expression as x
Expression? as maybe
Statement* as items
Statement+ as nonempty
~~~

Захват сохраняет узел целиком либо список целых узлов. Тип и кратность известны статически. Повторные объявления одного имени внутри одной ветки запрещены, включая вложенные части. Исключение — общее имя в разных ветках альтернативы при проверках D270–D273/D290 (§9.56–9.59, §9.70).

Повторное as x не вводит проверку равенства. Вне указанного исключения это ошибка, в том числе между операндами пересечения (D305). В разных правилах одинаковые имена разрешены.

### 10.2.1. Категория захвата сгруппированного шаблона

Круглые скобки группировки сами по себе не меняют категорию общего внешнего захвата. Оборачивание шаблона одиночного узла в скобки не превращает его в список; необязательный одиночный шаблон остаётся необязательным одиночным, а списочный — списочным.

~~~text
(Identifier) as x       // Один узел.
(Identifier?) as x      // Необязательный узел.
(Identifier+) as items  // Список.
(Identifier, Colon) as items // Список из двух узлов.
~~~

Таким образом, (Identifier) as x захватывает один узел; (Identifier?) as x — необязательный узел; (Identifier+) as items — список. Захват (Identifier, Colon) as items содержит список из двух узлов, поскольку внутри скобок записана цепочка.

Категория определяется статически по содержимому шаблона и его суффиксам, а не по числу узлов в конкретном совпадении. Например, список из одного узла остаётся списком. Сохраняются ранее принятые правила категорий для альтернатив и проверки совместимости захвата с принимающим местом результата.

Основание: D288.

### 10.3. Где вложенные захваты запрещены

~~~text
Block[Return(value: Expression as x)*] // Ошибка.
Block[Return(value: Expression)* as returns] // Допустимо.
~~~

Внутри повторяемого через * или + шаблона обычные захваты запрещены на любой глубине. Захват самого повторения целиком разрешён. Позднее для данных принято специальное исключение: явно обозначенный строковый аккумулятор (D205, §11.9). Неявное накопление, перезапись или выбор последнего значения обычного захвата не вводятся.

Внутри ? одиночный вложенный захват узла через as разрешён и становится необязательным:

~~~text
Block[Return(value: Expression as x)?]
~~~

При отсутствии Return значение x отсутствует. Вложенный списочный захват при отсутствии содержащей его необязательной части получает пустой список (D284, §10.3.2).

### 10.3.1. Данные внутри необязательного шаблона

Обычный захват данных $name внутри необязательного шаблона ? запрещён на любой глубине вложенности. Это ошибка DSL до исполнения независимо от того, используется ли захват в результате или только в условии того же шаблона. Повторение имени, захватываемого в другом месте правила, не снимает запрет: отдельное вхождение <$name> также является обычным захватом.

Проверки данных внутри ? разрешены. Для данных текущего узла используются data() и строковые методы с неявным получателем. Ссылка в условии на данные, захваченные вне необязательного шаблона, сама по себе не является новым захватом и этим решением не запрещается.

~~~text
Start, Identifier<$name>? -> Variable<$name>; // Ошибка.
Start, Box[Identifier<$name>]? -> Marker; // Ошибка.
Start, Identifier<startsWith("get") & (length() > 3)>? -> Marker; // Допустимо.
~~~

Запрет относится к обычным захватам данных, а не к захватам узлов через as. Аккумуляторы $name+ этот запрет не затрагивает; при отсутствии добавлений сохраняется начальная пустая строка по D211. Предложение разрешить обычный захват под ? с запретом лишь его безусловного использования отклонено.

Основание: D249.

### 10.3.2. Списочный захват внутри необязательного шаблона

Списочный захват узлов через as внутри необязательного шаблона ? разрешён. Если содержащая его необязательная часть отсутствует, значение захвата — пустой список. Если она совпала, захват содержит узлы, сопоставленные непосредственно захватываемой частью, в исходном порядке.

~~~text
Start, (Identifier+ as items, Colon)?
    -> Container[$items];
~~~

В примере items содержит один или более Identifier при совпадении группы и пустой список при её отсутствии. Start и Colon в items не входят. Внутренний + не гарантирует непустоту items для всего правила: внешний ? добавляет возможность пустого списка.

Статический анализ обязан учитывать внешнюю необязательность и проверять, что принимающее место Container допускает пустой список, а также типы и кратности непустых значений. Категория захвата остаётся списочной; отдельное отсутствующее значение списка не вводится.

Сохраняются проверки однозначности и правила имён захватов. Это разрешение не снимает запрет обычных захватов внутри внешнего * или + и запрет обычных захватов данных внутри ?. Проверки построения результата билдерами также сохраняются.

Основание: D284.

### 10.4. Однозначность полного распределения

Для разрешённого шаблона на фиксированном полном входе:

- Ни одного распределения — несовпадение.
- Одно — совпадение.
- Несколько — несовпадение.

Жадность не выбирает произвольного победителя между несколькими распределениями.

~~~text
Block[Statement*, Return, Statement*]
~~~

Если Return — потомок Statement, один Return среди детей даёт единственное распределение. Два Return дают два варианта и несовпадение. Сам шаблон разрешён.

### 10.5. Запрещённые соседние повторения

~~~text
Block[Statement*, Statement*] // Запрещено.
Expression+ as prefix, Expression+ as last // Запрещено.
~~~

Во втором примере на двух элементах есть единственное распределение 1+1, но это не делает шаблон допустимым: на более длинном входе граница не определена. Поэтому старый критерий «существует хотя бы один однозначный непустой вход» не является универсально достаточным.

Общий статический критерий для всех более сложных пересекающихся шаблонов пока открыт. Нельзя самовольно заменить его запретом любой потенциальной неоднозначности: пример с Return выше явно разрешён.

### 10.6. Возврат элементов

~~~text
Expression+ as prefix, Expression as last
~~~

На цепочке a, b, c первая часть жадно пробует поглотить всё, затем возвращает c второй части. Получается единственное распределение: prefix = a, b; last = c. На двух элементах также работает; на одном — нет.

Возврат разрешён ради завершения шаблона, но не ради произвольного выбора между неоднозначными распределениями.

## 11. Построение результата

Успешно применённое правило возвращает один узел либо явный none для удаления (D341 с исключением D353). Созданный узел может содержать любое число детей, разрешённое его схемой. Список, цепочка и необязательный захват не могут быть самостоятельным результатом правила. Удаление корня даёт допустимое пустое дерево (D354). После удаления последнего ребёнка родитель остаётся листом, только если его схема допускает отсутствие детей (D355–D356). Списочные выражения и none разрешены внутри построения детей по правилам их мест. Строка как самостоятельное сокращение цепочки результата не вводится; строковое сокращение внутри детей разрешено по D342.

### 11.1. Подстановка и создание

~~~text
$x
Negation[$x]
Addition(left: $a, right: $b)
~~~

$x ссылается только на захват того же правила. Неизвестное имя — ошибка до исполнения, а не none.

Захват можно использовать несколько раз или не использовать вовсе. Подстановка не расходует его. Неиспользованный захват всё равно участвует в проверке шаблона; его отсутствие в результате не создаёт действие Delete.

### 11.2. Позиционные выражения заполняют места схемы

~~~text
node Sequence(first: Statement, middle: Statement*, last: Statement);

Sequence[$a, $body, $z]
~~~

Каждое выражение относится к своему месту: a — first, весь body — middle, z — last. Список не делится между местами. Пустой body не передвигает z в middle.

Для двух групп одного типа:

~~~text
node Parts(left: Statement*, right: Statement*);
Parts[$xs, $ys]
Parts(left: $xs, right: $ys)
~~~

Обе записи сохраняют явное разделение групп.

### 11.3. Статическая совместимость

Тип подставляемого элемента должен совпадать с типом места либо быть его потомком. Фактический более узкий тип при исполнении не исправляет слишком общий статический тип.

| Источник | Обязательное T | Необязательное T? | Группа T* |
|---|---|---|---|
| Один совместимый узел | Да | Да | Да |
| Необязательный узел | Нет | Да | Да |
| Список T* или T+ | Нет | Нет | Да |
| none | Нет | Да | Да |

Список из одного фактического элемента остаётся списком. Неявного извлечения единственного элемента нет.

### 11.4. None и пропуски

~~~text
Triple[$a, none, $c]
Parts(left: none, right: $ys)
~~~

none означает отсутствие элементов, не узел-заглушку.

В именованном построении необязательное место или группу * можно не указывать; это равнозначно none. Обязательные места должны быть заполнены.

Позиционные пропуски разрешены только при единственном статическом распределении выражений по местам с сохранением порядка. Если вариантов несколько — ошибка DSL. Фактические размеры захватов не используются для разрешения неоднозначности.

### 11.5. Объединение через +

~~~text
Block(items: $prefix + $item + $suffix)
Block[$prefix + $item + $suffix]
~~~

+ объединяет источники в одну последовательность. Порядок операндов и элементов сохраняется. Одиночный узел даёт один элемент, отсутствующий необязательный захват — ноль, список — свои элементы, none — ноль.

Можно создавать узлы внутри объединения:

~~~text
Block(items: $prefix + Return(value: $value) + $suffix)
~~~

Return создаётся даже при отсутствии value. Необязательный внутренний ребёнок не делает весь Return необязательным.

Всё выражение заполняет одно место; его части не распределяются между несколькими группами.

### 11.6. Кратность объединения и скобки

Диапазоны количества элементов суммируются:

| Выражение | Диапазон |
|---|---|
| Один + один | 2..2 |
| Необязательный + необязательный | 0..2 |
| Список * + один | 1..∞ |
| Список * + список * | 0..∞ |
| none | 0..0 |

Обязательное одиночное место требует 1..1, необязательное — диапазон внутри 0..1, группа * допускает любой неотрицательный диапазон.

Группировочные скобки вокруг выражений + не введены. Скобки после имени узла сохраняют свой обычный смысл.

### 11.7. Константные данные создаваемого узла

~~~text
Identifier<"count"> -> Identifier<"total">;
IntegerLiteral<"0"> -> IntegerLiteral<"1">;
~~~

Строковый литерал в угловых скобках результата задаёт константные данные. Строка передаётся механизму разбора данных datatype и проходит установленные проверки; для числового datatype она преобразуется в нативное числовое значение.

Это отличается от шаблона: там литерал сравнивается непосредственно с getData(), без разбора в нативное значение. Константная запись не означает захват или вычисление данных (D200).

Ожидаемый отказ разбора или проверки при построении результата означает неприменимость кандидата (D251, §12.2.1). Если анализатор установил невозможность построения результата при любых подходящих входных данных, правило отклоняется до исполнения (D254, §19.1.2).

### 11.8. Захват и перенос данных

~~~text
Identifier<$name> -> Variable<$name>;
~~~

`$name` внутри угловых скобок шаблона захватывает строку getData(); as для захвата данных не используется (D206). В результате `Variable<$name>` передаёт эту строку механизму разбора и проверки данных нового узла.

Это отдельная категория захвата — данные; она отличается от узла и списка узлов. Значение является сериализованной строкой даже при числовом datatype исходного узла. Название категории не вводит новый datatype или тип узла с именем Data (D201).

Захваты узлов, списков и данных используют единое пространство имён внутри правила (D202). Одно имя не может одновременно обозначать значения разных категорий: `Identifier<$text> as item` допустимо, а `Identifier<$x> as x` — ошибка. Повторение имени обычных данных означает равенство (§9.9, D207–D208), а повторное as для узлов и списков запрещено, кроме согласованных объявлений общего имени в разных ветках альтернативы (§9.56–9.59, §9.70). Это не запрещает многократную подстановку захваченного узла в результате. Обычные захваты данных внутри ? запрещены на любой глубине (D249, §10.3.1); проверки данных разрешены. Аккумуляторы этот запрет не затрагивает.

### 11.9. Явное накопление строковых данных

Для накопления данных внутри повторения принято специальное обозначение `$name+`: плюс после имени отмечает аккумулятор, к которому добавляются строки данных. Плюс не является частью имени. Обычный захват не становится аккумулятором автоматически (D205).

Это исключение из запрета вложенных захватов относится к явно обозначенному накоплению данных. Ключевое слово as для данных не используется (D206). Один аккумулятор может получать данные из нескольких мест (D209):

~~~text
Identifier<$text+>, Identifier<$text+> -> Identifier<$text>;
Identifier<$text> <- Identifier<$text+>, Identifier<$text+>;
~~~

В обоих правилах исходные данные "ab", "cd" дают "abcd". Порядок конкатенации — порядок узлов исходной цепочки независимо от направления поиска. Повторение имени с плюсом добавляет данные в тот же аккумулятор.

В одном шаблоне нельзя смешивать $name+ и $name для одного имени: это ошибка DSL (D210). Отклонено предложение трактовать обычное вхождение как проверку окончательной суммы. Запрет относится именно к шаблону при любой стрелке. В результате $name по-прежнему возвращает накопленную строку.

~~~text
Character<$text+>+, Identifier<$text> -> Identifier<$text>; // Ошибка.
Character<$text+>+ -> Identifier<$text>; // Допустимо.
~~~

Разные имена могут использовать разные режимы.

Начальное значение аккумулятора — пустая строка "". При отсутствии добавлений результат также равен "", а не отсутствует (D211):

~~~text
Start, Character<$text+>* -> Identifier<$text>;
~~~

Если совпал только Start, text равно "". Результирующий узел должен допускать такие данные согласно своему datatype. Нулевое число добавлений не разрешает нулевое минимальное потребление всего шаблона: здесь хотя бы один узел потребляет Start.

Накопление относится к конкретному варианту совпадения (D212). Если повторение возвращает узел следующей части шаблона, его вклад исключается. Если кандидат отвергнут целиком, его накопление отбрасывается.

~~~text
Character<$text+>+, Character<"!"> -> Identifier<$text>;
~~~

На данных "a", "b", "!" результат накопления равен "ab": завершающий символ соответствует отдельной части шаблона. Реализация может вычислять строку по окончательному совпадению; решение не требует физического изменения строки при каждой пробе.

Порядок накопления данных между уровнями дерева — обход в глубину с посещением родителя до детей: сначала данные самого узла, затем рекурсивно поддерево первого (левого) ребёнка, затем следующего ребёнка и так далее слева направо. Порядок детей соответствует итоговой схеме и порядку элементов внутри каждой группы.

В аккумулятор добавляются только данные узлов, для которых шаблон явно содержит соответствующий $name+. Неотмеченные узлы не добавляют свои данные, но не меняют порядок отмеченных потомков. Для нескольких корней сопоставленного фрагмента их поддеревья рассматриваются слева направо в исходной цепочке, независимо от направления стрелки. Учитывается только окончательный успешный вариант совпадения (D212).

~~~text
Box<$text+>[Item<$text+>[Leaf<$text+>], Item<$text+>]
    -> Result<$text>;
~~~

Если данные Box — "A", его первого Item — "B", вложенного Leaf — "C", второго Item — "D", аккумулятор получает "ABCD". Это порядок накопления данных при сопоставлении; он не меняет принятый обход преобразования дерева снизу вверх (D189–D192).

Основание: D250.

### 11.10. Методы захваченной строки и цепочки в результате

Разрешён вызов строкового метода непосредственно на захвате данных через точку. Для преобразования регистра формы `$name.toUpperCase()` и `toUpperCase($name)` равнозначны; то же относится к `$name.toLowerCase()` и `toLowerCase($name)`.

~~~text
Identifier<$name> -> Variable<$name.toUpperCase()>;
Identifier<$name> -> Variable<toUpperCase($name)>;
~~~

Оба правила создают Variable с одинаковыми данными. Захваченная исходная строка name не изменяется. Полученная строка проходит обычный разбор и проверку datatype нового узла.

Цепочки методов доступны и в выражениях данных результата:

~~~text
Identifier<$name> -> Variable<$name.toLowerCase().toUpperCase()>;
~~~

Каждый метод применяется к результату предыдущего вызова (D222). Цепочка в примере выполняет оба преобразования последовательно; решение не устанавливает её эквивалентность одному вызову toUpperCase для всех строк Unicode. Вызовы относятся к захватам строковых данных и не вводят такие методы для захватов узлов или списков.

Основание: D223.

### 11.11. Область действия неявного текущего узла

Неявный текущий узел существует только внутри собственного фильтра данных в шаблоне. Вызов data() и формы строковых методов с неявным источником данных относятся к узлу, чей фильтр вычисляется.

В выражениях данных результата неявного исходного узла нет. Источник строки должен быть указан явно:

~~~text
Identifier<$name> -> Variable<$name.toLowerCase()>; // Допустимо.
Identifier<$name> -> Variable<toLowerCase($name)>;  // Допустимо.
Identifier<$name> -> Variable<toLowerCase()>;       // Ошибка.
Identifier<$name> -> Variable<data()>;             // Ошибка.
~~~

Нельзя неявно выбрать исходный узел даже при наличии единственного узла в шаблоне. Обращение к отсутствующему неявному источнику является ошибкой DSL до исполнения. Явный получатель метода или аргумент функции, а также константные данные результата остаются допустимыми.

Основание: D242.

### 11.12. Одиночный символьный литерал в результате

Одиночный символьный литерал разрешён в выражении результата. Он создаёт встроенный узел Character с данными указанного символа и без детей.

~~~text
Comma -> ',';        // То же, что Comma -> Character<",">;
'a' -> 'b';          // То же, что Character<"a"> -> Character<"b">;
~~~

Применяются уже принятые правила экранирования и допустимых значений D320/D323/D327/D329. Созданный Character содержит ровно одно скалярное значение Unicode. Символьный литерал результата является выражением создания узла, а не строковым выражением данных или захватом.

Диапазон в результате запрещён: он задаёт множество подходящих символов и не определяет, какой узел создать. Для результата используется одиночный символ, а не запись диапазона. Эквивалентность диапазона с одинаковыми границами одиночному символу по D322 относится к шаблонам; она не вводит диапазоны как отдельную форму результата.

Сохраняются общие проверки статической совместимости типа и кратности результата с принимающим местом, построения результата, тождественных преобразований и циклов. Объявление Comma в примере предполагается существующим.

Это расширяет D317/D319: ранее символьные литералы были утверждены только в шаблонах, теперь одиночный символьный литерал разрешён и для создания результата.

Основание: D332.

### 11.13. Строковый литерал при построении детей

Строковый литерал в позиции построения детей результирующего узла разрешён как сокращение создания цепочки встроенных узлов Character.

~~~text
PublicModifier -> Text["public"];
~~~

Результат правила — один узел Text с шестью детьми Character: p, u, b, l, i, c. Типы PublicModifier и Text должны быть объявлены; принимающее место схемы Text должно допускать соответствующие тип и количество детей. Цепочка не распределяется неявно между несколькими местами схемы.

Сначала проверяются и декодируются escape-последовательности литерала DSL по уже принятым правилам, затем каждое скалярное значение Unicode создаёт один Character. Это создание новых узлов, а не захват исходных вхождений. Строка внутри угловых скобок по-прежнему задаёт данные узла, а не его детей.

D341 сохраняется: строковая цепочка не может быть самостоятельным результатом правила. D342 разрешает непустой строковый литерал внутри детей; пустая строка разрешена по D343. Односимвольная строка создаёт один Character по D344. Преобразование захваченных строковых данных в детей разрешено через chars по D346; произвольные строковые выражения разрешены в аргументе chars по D347.

Основание: D342.

### 11.14. Пустая строка при построении детей

Пустой строковый литерал "" разрешён в позиции построения детей результирующего узла. Он создаёт ноль дочерних узлов Character.

~~~text
Something -> Text[""];
~~~

В примере создаётся ровно один узел Text; строка заполняет принимающую группу пустой последовательностью. Схема Text должна допускать пустую группу. Пустая строка не создаёт Character с пустыми данными, не удаляет родительский узел и не является пустым результатом всего правила.

Запрет пустого строкового шаблона D335 сохраняется. Строковые данные в угловых скобках имеют прежний отдельный смысл. D343 уточняет D342 только в отношении пустого литерала; категория односимвольной строки определена в D344, а явное преобразование захваченных строковых данных в детей определено в D346.

Основание: D343.

### 11.15. Односимвольная строка в одиночном дочернем месте

Строковый литерал, содержащий после проверки и декодирования ровно одно скалярное значение Unicode, в позиции построения детей является выражением создания одного узла Character. Он эквивалентен одиночному символьному литералу с тем же значением и допускается в совместимом одиночном месте.

~~~text
node Letter(value: Character);
Something -> Letter["a"]; // То же, что Letter['a'].
Something -> Letter["ab"]; // Ошибка: два символа для обязательного одиночного места.
Something -> Letter[""]; // Ошибка: нет ребёнка для обязательного одиночного места.
~~~

Количество определяется по декодированным скалярным значениям Unicode, а не по длине записи escape-последовательности или числу кодовых единиц UTF-16. Например, "\u{1F600}" создаёт один Character. Проверка выполняется статически для литерала.

Это уточнение относится к строковому литералу внутри детей (D342–D343). Оно не разрешает извлекать единственный элемент произвольного списочного захвата и не вводит строку как самостоятельный результат правила: D341 сохраняется. Явное преобразование захваченных строковых данных в детей определено в D346; произвольные строковые выражения разрешены в аргументе chars по D347.

Основание: D344.

### 11.16. Объединение строковых литералов и узлов в детях

В выражении построения детей разрешено объединять строковые литералы с захваченными узлами и списками узлов через существующий оператор +. В этом контексте + объединяет последовательности детей, а не сериализует узлы и не конкатенирует их данные.

~~~text
Word[Character+ as letters]
    -> Text["(" + $letters + ")"];
~~~

В примере результатом является один Text. Его дети идут в порядке: новый Character со значением (, исходные узлы из letters в их исходном порядке, новый Character со значением ). Строковые литералы создают новые Character по D342–D344; узловой захват подставляет захваченные узлы без преобразования их в строку.

Объединённое выражение заполняет одно принимающее место схемы. Оно должно допускать типы и кратность всех элементов. Сохраняются общие правила объединения детей, включая пустой вклад литерала "" по D343, статическую проверку совместимости и запрет неявного распределения одной последовательности между несколькими местами.

D341 сохраняется: объединение детей не разрешает цепочку в качестве самостоятельного результата правила. Захват строковых данных не превращается автоматически в узлы Character; для явного преобразования захваченной строки используется chars по D346.

Основание: D345.

### 11.17. Преобразование строковых данных в детей: chars

Встроенная функция chars разрешена при построении детей результата для явного преобразования захваченных строковых данных в список новых узлов Character.

~~~text
Identifier<$name> -> Text[chars($name)];
~~~

При name = "hello" создаётся один результирующий узел Text с пятью новыми детьми Character в порядке символов строки. Пустая строка даёт пустой список детей. Принимающее место схемы должно допускать список Character и его кратность.

Результат chars имеет списочную категорию, в том числе когда фактическая строка содержит ровно один символ. Функция не подставляет исходные узлы и не меняет захваченную строку. Сохраняется единица символа, принятая для Character: одно скалярное значение Unicode.

D341 сохраняется: chars не может быть самостоятельным результатом правила. D346 утверждает форму chars($name) для захваченных строковых данных; D347 разрешает произвольное строковое выражение в аргументе. Повторное декодирование escape-последовательностей исключено по D348. Некорректный Unicode во входной строке приводит к отказу кандидата по D349.

Основание: D346.

### 11.18. Строковые выражения в аргументе chars

Функция chars принимает один аргумент — любое допустимое строковое выражение языка, а не только захват строковых данных. Сначала вычисляется значение выражения, затем из полученной строки создаётся список новых узлов Character по D346.

~~~text
Identifier<$name>
    -> Text[chars("prefix_" + $name.toLowerCase())];
~~~

Внутри аргумента chars оператор + является конкатенацией строк; снаружи, в выражении построения детей, + объединяет последовательности узлов по D345. Контекст аргумента не превращает узловые захваты в строки. Аргумент должен иметь строковый тип; остальные типы требуют уже предусмотренного языком явного преобразования в строку.

Сохраняются правила выражений данных результата: доступны константы, захваченные данные и разрешённые строковые операции; неявного текущего узла нет. Значение chars остаётся списком Character даже для константной односимвольной строки. Пустая строка даёт пустой список; принимающее место проверяется по общим правилам. При построении такого результата правило создаёт один узел; отдельное исключение для удаления через none определено в D353.

Это закрывает вопрос произвольного строкового аргумента, оставленный в D346. Интерпретация обратных косых черт определена в D348: повторного декодирования нет. Некорректный Unicode во входной строке приводит к отказу кандидата по D349.

Основание: D347.

### 11.19. Отсутствие повторного декодирования в chars

Функция chars обрабатывает готовое строковое значение и не выполняет повторного декодирования escape-последовательностей. Экранирование литералов DSL проверяется и снимается при чтении литерала до вычисления аргумента chars.

~~~text
Text[chars("\n")]   // Один Character: перевод строки.
Text[chars("\\n")]  // Два Character: обратная косая черта и n.
~~~

То же правило действует для захваченных данных и результатов строковых операций: обратная косая черта и следующие за ней символы являются обычным содержимым строки, а не командами декодирования. Содержимое не становится исходным кодом DSL и не проходит повторный лексический разбор.

Это уточняет D346–D347. Проверка допустимости самих символов Unicode сохраняется; некорректный Unicode приводит к отказу кандидата по D349.

Основание: D348.

### 11.20. Некорректный Unicode в chars

Если вычисленная строка аргумента chars содержит некорректный Unicode, в частности одиночный суррогат UTF-16, построение результата отвергает весь текущий кандидат правила. Это ожидаемый отказ построения по D251–D252, а не успешное преобразование части строки.

Частичный результат не публикуется, исходное дерево не изменяется, накопления отвергнутого кандидата отбрасываются. Недопустимые значения не пропускаются и не заменяются автоматически на U+FFFD. Корректная суррогатная пара представляет одно скалярное значение и создаёт один Character.

После отказа поиск продолжается по общим правилам D252: для того же правила со следующей позиции в направлении стрелки; отказ не передаёт управление следующему правилу немедленно и не разрешает пробовать более короткий фрагмент с той же начальной позиции.

Если статический анализ доказал невозможность построения результата при любых подходящих входных данных, применяется ранее принятое правило ошибки компиляции DSL (D254). Возможность некорректных данных лишь у некоторых кандидатов сама по себе не делает всё правило ошибочным. Некорректные escape-последовательности исходного литерала по-прежнему диагностируются при чтении DSL, а не откладываются до chars.

Это закрывает вопрос обработки некорректного Unicode, оставленный в D346–D348. Правило D348 об отсутствии повторного декодирования сохраняется.

Основание: D349.

## 12. Правила преобразования и приоритет

### 12.1. Две стрелки

~~~text
шаблон -> результат;
результат <- шаблон;
~~~

Стрелка всегда указывает на результат. -> ищет совпадение слева направо; <- — справа налево. Во второй форме шаблон расположен справа.

~~~text
Expression as a, Plus, Expression as b -> Addition[$a, $b];

Assignment[$a, $b] <-
    AssignableExpression as a, Equals, Expression as b;
~~~

Внешних квадратных скобок вокруг фрагмента нет. Запятые внутри вложенного узла относятся к его собственному списку.

### 12.2. Единый порядок правил

> **ВАЖНО: ПОРЯДОК ПРАВИЛ МЕНЯЕТ РЕЗУЛЬТАТ. ПРАВИЛА ПРОВЕРЯЮТСЯ СВЕРХУ ВНИЗ. ПОБЕЖДАЕТ ПЕРВОЕ ПОДХОДЯЩЕЕ ПРАВИЛО. БОЛЕЕ КОНКРЕТНЫЙ ШАБЛОН НЕ ПОЛУЧАЕТ АВТОМАТИЧЕСКОГО ПРЕИМУЩЕСТВА.**

Жадный выбор правила означает: текущее правило ищет совпадение по всей цепочке. Только если оно нигде не применимо, рассматривается следующее.

После одной успешной замены поиск начинается заново с первого правила на обновлённой цепочке. Продолжать с прежней позиции или следующего правила нельзя: результат и соседи могли образовать более приоритетную комбинацию.

### 12.2.1. Построение результата и отказ кандидата

Правило выполняет замену только при выполнении двух условий: весь шаблон успешно сопоставлен и весь результат успешно построен билдерами с соблюдением схем и проверок данных. Ожидаемый отказ разбора данных или отрицательный результат проверки билдера означает неприменимость данного кандидата, а не остановку преобразования.

~~~text
Token<$text> -> IntegerLiteral<$text>;
Token<$text> -> InvalidExpression<$text>;
~~~

При данных "123" первое правило создаёт целое число. При "hello" ожидаемый отказ разбора оставляет Token; если первое правило больше нигде не применимо, диагностическое правило может создать InvalidExpression.

Построение результата атомарно относительно исходного дерева. Если хотя бы один узел результата не удалось построить, весь результат кандидата отбрасывается; исходный фрагмент остаётся без изменений. Частичной замены нет. Неудачная попытка не является успешным шагом преобразования.

Сохраняется порядок поиска: текущее правило продолжает поиск других кандидатов в своём направлении. К следующему правилу переходят, если текущее нигде не выполнило замену. Отказ не останавливает обработку остальных ветвей дерева.

Автор программы на DSL должен учитывать, что исходные токены и черновые узлы могут остаться необработанными, и предусматривать диагностические правила. Несвёрнутый аргумент может препятствовать построению списка выражений и затем вызова функции; это сохраняет след ошибки в структуре. Корректность каждого созданного узла по схеме не означает завершённости разбора всей программы.

Для диагностики автор DSL может объявить общий абстрактный тип ошибки. Благодаря множественному наследованию конкретный узел ошибки может одновременно быть Expression и потомком этого типа ошибки. Затем обход дерева собирает все узлы, наследующие общий тип ошибки, для формирования сообщений. Это пользовательская модель, а не новый встроенный тип с зарезервированным именем. Наличие ожидаемого корня, например TranslationUnit, само по себе не исключает узлов ошибок внутри него.

Ожидаемые отказы отличаются от неожиданных исключений реализации: сохраняются правила §7.4 о parseError и исключениях validate. Неожиданные исключения не превращаются в неприменимость. Ошибки DSL до исполнения, обнаружение тождественного результата и циклов также не отменяются.

Основание: D251.

### 12.3. Пример арифметического приоритета

Если умножение объявлено раньше сложения, условная цепочка преобразуется так:

~~~text
a + b + c * d
a + b + Multiply[c, d]
Addition[a, b] + Multiply[c, d]
Addition[Addition[a, b], Multiply[c, d]]
~~~

Умножение побеждает, хотя находится правее. Левое направление сложения задаёт левую ассоциативность при последующих свёртках.

Для присваивания направление <- позволяет сначала свернуть правое присваивание. Само направление не устанавливает приоритет разных операторов: его устанавливает порядок правил.

## 13. Поиск фрагмента цепочки

### 13.1. Границы контекста

Цепочка — элементы одной повторяющейся группы одного родителя. Совпадение непрерывно. Оно не переходит в соседнюю группу и не пересекает границу родительского узла.

Сложный шаблон элемента может читать его детей; это не превращает вложенных детей в соседние элементы внешней цепочки.

### 13.2. Минимальная длина

Минимальная потребность во внешних элементах вычисляется заранее. Если группа или остаток в направлении поиска короче минимума, подробное сопоставление пропускается.

| Шаблон | Минимум |
|---|---:|
| A, B, C | 3 |
| Expression+, Expression | 2 |
| Comment+ | 1 |
| Box[A, B, C] | 1 |

Вложенные дети Box не увеличивают число внешних элементов. После замены длина проверяется заново. Недостаток элементов не позволяет навсегда исключить правило.

### 13.3. Непустое совпадение

~~~text
Comment* -> Marker; // Ошибка: возможно пустое совпадение.
Comment+ -> Marker; // Допустимо при совместимом типе Marker.
~~~

Весь фрагмент обязан гарантированно поглощать хотя бы один элемент. Необязательные части разрешены, если суммарный минимум положителен. Результат обязан быть ровно одним узлом (D341).

### 13.4. Максимальный кандидат и неоднозначность

На очередной позиции ищется максимальный фрагмент, допускающий полное распределение по всем частям шаблона. Если распределение единственно — успех.

Если у максимального кандидата несколько распределений, позиция отвергается. **Укорачивать этот кандидат специально ради однозначности нельзя.** Поиск продолжается со следующей позиции.

Это не означает запрета возвратов вообще: возврат для завершения обязательной следующей части разрешён. Запрещён выбор более короткого однозначного кандидата вместо более длинного неоднозначного на той же позиции.

### 13.4.1. Отказ построения результата

Если правило не применилось на текущей позиции из-за несовпадения шаблона или ожидаемого отказа построения результата, поиск продолжается для того же правила со следующей позиции в направлении его стрелки. К следующему правилу переходят только после того, как текущее не выполнило замену нигде в текущем контексте. После успешной замены поиск снова начинается с первого правила на обновлённой цепочке.

Если выбран максимальный однозначный фрагмент, удовлетворяющий шаблону, но билдер отверг результат, более короткие фрагменты с той же начальной позиции не перебираются. Размер совпадения определяет шаблон; успешность построения принимает или отвергает выбранного кандидата. Это не отменяет возврат элементов при самом сопоставлении, необходимый для завершения обязательных частей шаблона.

~~~text
Token<$text> -> IntegerLiteral<$text>;
Token<$text> -> InvalidExpression<$text>;
~~~

Для цепочки Token<"hello">, Token<"123"> первое правило сначала получает отказ на "hello", затем успешно преобразует "123". Диагностическое второе правило рассматривается лишь тогда, когда первое больше нигде не применимо. Отказ на одной позиции не передаёт управление следующему правилу немедленно.

Основание: D252.

### 13.5. Подробный пример

Шаблон: Statement*, Return, Statement*. Return — потомок Statement; A, B, C — другие Statement.

~~~text
A, Return₁, B, Return₂, C
~~~

Со старта A центральным Return может быть первый или второй — неоднозначность. Со старта Return₁ — тоже. Со старта B максимальный фрагмент B, Return₂, C однозначен и заменяется. A, Return₁ остаются перед результатом.

Индексы — пояснение разных узлов, не синтаксис DSL.

Если между частями находится Separator, не являющийся Statement:

~~~text
A, Return₁, B, Separator, C, Return₂
~~~

Со старта A максимальный кандидат заканчивается перед Separator и однозначен. Его длину ограничивает несовместимый элемент, а не попытка искусственно устранить неоднозначность.

## 14. Обход дерева и контексты применения

### 14.1. От содержимого детей к родительской цепочке

Обход идёт снизу вверх. Сначала обрабатывается внутреннее содержимое исходных элементов, затем сами элементы преобразуются в содержащем их контексте.

~~~text
A, B -> Pair;
A -> X;
~~~

Для группы A, B результат — Pair. Отдельно запускать A -> X на A перед общей обработкой цепочки нельзя. Оба правила конкурируют в одной цепочке по общему приоритету.

Если A и B имеют детей, сначала обрабатываются их дочерние контексты. Вложенные изменения могут повлиять на шаблоны, проверяющие A и B. Глобального соревнования правил на всех глубинах дерева нет.

Историческое решение о результате X, B отменено. Прежний обход сверху вниз также отменён.

### 14.2. Несколько групп

Группы одного узла обрабатываются в порядке итоговой схемы типа. Сначала группа полностью сворачивается, её история освобождается, затем начинается следующая. Направление стрелки действует внутри выбранной группы, а не переставляет группы.

Точная реализация единого обхода смешанной схемы с одиночными и повторяющимися местами должна быть согласована с новым Node.

### 14.3. Созданные поддеревья

Созданный результат считается готовым, «схлопнутым правильно». Алгоритм не запускает внутри него новый самостоятельный обход.

При этом результат немедленно участвует в дальнейшем поиске текущего контекста. Следующий шаблон может анализировать его внутреннюю структуру:

~~~text
Box[Addition[Expression as a, Expression as b]]
    -> Addition[$a, $b];
~~~

Это проверка и замена целого Box, а не самостоятельное преобразование его Addition.

### 14.4. Корень и одиночные позиции

Здесь доступен один узел. После каждой допустимой замены поиск снова начинается с первого правила до отсутствия совпадений.

~~~text
A -> X;
X -> Y;
~~~

Корень A превращается в Y, если дальше правил нет. Внутрь созданных X и Y не спускаемся, но вложенные шаблоны могут их проверять.

Отдельный такой цикл для каждого элемента повторяющейся группы не запускается: у группы уже есть общий цикл.

### 14.5. Результат в зависимости от места

| Контекст | Допустимый результат |
|---|---|
| Корень | Один узел либо none; none даёт пустое дерево (D354) |
| Обязательное одиночное место T | Один совместимый узел; none запрещён (D356) |
| Необязательное место T? | Один совместимый узел либо none |
| Фрагмент группы T* | Один совместимый узел либо none |

Список и цепочка самостоятельных результатов запрещены, даже при фактической длине один. Нужен явный контейнер. None разрешён как явное исключение для удаления по D353. Правила не запускаются на отсутствующем ребёнке. Проверки схемы родителя сохраняются; размещение действий в дифференциальном дереве описано в §16.5.

При общем обходе правило с несовместимым статическим результатом пропускается в этом контексте. Явное назначение правила несовместимому месту — ошибка DSL. Фактическая длина или более узкий тип результата запрет не снимают.

### 14.6. Удаление и запрет раскрытия в цепочку

~~~text
Comment -> none; // Удаление в совместимой группе или необязательном месте (D353).
Wrapper[Node* as body] -> $body; // Ошибка: списочный результат запрещён (D341).
~~~

В группе Node* первое правило удаляет совпавший комментарий. Остальные элементы сохраняют порядок и принадлежность группе. Удаление обязательного ребёнка запрещено по D356 независимо от наличия других детей.

Второе правило недопустимо: раскрытие обёртки в цепочку самостоятельных результатов не разрешено. Исключение для none не снимает этот запрет.

## 15. Равенство, хэширование и циклы

### 15.1. Структурное равенство

Сравниваются:

1. Имя конкретного типа.
2. Содержание строки getData().
3. Упорядоченные дети рекурсивно.
4. Принадлежность детей местам схемы и границы групп.

Координаты исходника исключены. Java-класс реализации и идентичность объектов не являются содержательной частью равенства.

Одинаковая ссылка на неизменяемый узел даёт быстрый положительный ответ. Разные ссылки не доказывают различие.

### 15.2. Хэш — фильтр

Равные структуры обязаны иметь одинаковый хэш. Разные хэши означают разные структуры. Одинаковые хэши требуют полного сравнения из-за возможной коллизии.

Имя типа и getData входят в хэш вместе с дочерней структурой и границами. Алгоритм, разрядность и кэширование пока не определены.

### 15.3. Почему сравниваются имена типов

При сериализации в JSON тип записывается строкой. При чтении по ней восстанавливается полное описание. Поэтому разные типы с одним именем нарушают контракт системы.

Сгенерированный Java-класс и универсальный адаптер могут представлять один и тот же тип и равные узлы.

### 15.4. Тождественное преобразование

~~~text
Expression as x -> $x;
Expression as a, Expression as b -> $a + $b; // Ошибка по D341: результат не является ровно одним узлом.
~~~

Если компилятор доказал, что правило всегда возвращает исходный фрагмент без изменений, это ошибка компиляции. Полнота доказательства не требуется.

Если отсутствие изменения выявлено только при конкретном применении, это ошибка исполнения с указанием правила. Молчаливый переход к следующему правилу менял бы принятую семантику.

Перестановка a, b в b, a не запрещается целиком: она тождественна только для некоторых входов с равными элементами. Такие случаи выявляются при исполнении.

### 15.5. История состояний

Исходное состояние сохраняется до первой замены. После каждой замены хэш ищется в истории; при совпадении выполняется точная проверка. Подтверждённое повторение полного состояния при том же контексте обработки означает цикл.

История локальна для текущей группы, корня или одиночной позиции. Для группы сохраняется вся цепочка, не только заменённый фрагмент: результат может взаимодействовать с соседями.

После завершения контекста история освобождается. После одного шага её удалять нельзя: A → B → A тогда не обнаружится. Неизменяемые версии могут разделять поддеревья; полные копии всего дерева не требуются.

### 15.6. Чего алгоритм не гарантирует

Лимит числа замен отклонён: размер корректного дерева не должен сам по себе приводить к отказу.

Повторные состояния обнаруживаются, но бесконечный рост без повторений — нет. Защита от такого роста остаётся открытой. История также имеет цену по памяти; локальность снижает её, но не делает нулевой.

## 16. Встроенные узлы действий

### 16.1. Схемы

Action — встроенный абстрактный тип, закрытый для пользовательского наследования. Его встроенные конкретные потомки:

~~~text
Insert(after: Node)
Delete(before: Node)
Replace(before: Node, after: Node)
~~~

Это запись схем для справки, а не требование переобъявлять встроенные типы. Дети обязательные одиночные, собственного datatype нет. Доступны именованная и позиционная формы построения.

### 16.2. Описание не равно исполнению

Построение Replace создаёт узел-описание. Оно не ищет цель во входном дереве и не выполняет замену немедленно.

Движок создаёт дерево с действиями; их исполнение выполняется отдельным проходом по D351. Подробный контракт этого прохода ещё не согласован. Имя Property не зарезервировано; вопрос этого встроенного типа отложен.

### 16.3. Описание удаления через Delete

Удаление описывается созданием встроенного узла-действия Delete с захваченным исходным узлом в обязательном одиночном ребёнке before.

~~~text
Comment as c -> Delete[$c];
~~~

Результат правила — ровно один Delete, что соответствует D341. Позиционная запись Delete[$c] соответствует именованной Delete(before: $c). Схема Delete(before: Node), отсутствие собственного datatype и остальные свойства встроенного действия сохраняются.

Построение Delete только описывает удаление захваченного комментария. Оно не выполняет удаление немедленно и не превращается в пустой результат правила. Движок создаёт дерево с действиями; применение действия выполняется отдельным проходом по D351. Подробный контракт прохода и адресация целей ещё не определены.

По D352 действие Delete допустимо в дифференциальном дереве с отдельным дифференциальным типом узла. В обычном дереве его нельзя вставить в место, не принимающее Action. Исключения из проверки схемы и отсрочка такой проверки до исполнения действий отклонены; удаление обычных узлов через none принято в D353 (§16.6).

Это описывает удаление через узел-действие. Непосредственное удаление через none отдельно разрешено в D353. Общий принцип разделения описания и исполнения из §16.2 сохраняется.

Основание: D350.

### 16.4. Построение дерева действий и отдельный проход исполнения

Движок преобразования DSL не исполняет действия. Он создаёт дерево с узлами-действиями. Выполнение действий производится отдельным проходом; создание Delete не вызывает немедленного удаления.

~~~text
Comment as c -> Delete[$c];
~~~

Обычное правило обрабатывает каждый подходящий комментарий, включая соседние комментарии. Для последовательности комментариев не требуется отдельное правило удаления всей цепочки: создаются соответствующие узлы Delete, а удаление выполняется проходом исполнения действий.

Предложения ассистента немедленно исполнять Delete при возврате из правила или передавать его вне результирующего дерева без вставки в дерево не приняты. Описание действия и его исполнение остаются разными этапами. Правило, создающее действие, возвращает один узел; исключение для непосредственного удаления через none определено в D353.

Это уточняет D350 и §16.2: форма результата — дерево с действиями, стадия исполнения — отдельный проход. Различие дифференциальных и обычных деревьев уточнено в D352 (§16.5). Подробный контракт прохода исполнения остаётся открытым. Решение не устанавливает отдельный API, автоматический запуск этого прохода или новые правила обхода внутреннего содержимого действий.

Основание: D351.

### 16.5. Дифференциальные и обычные деревья: ограничения действий

Для построения дифференциальных деревьев предусмотрен отдельный тип узла — дифференциальный узел. В дифференциальном дереве размещение узла-действия Delete для описания удаления возможно. Обычное дерево не допускает вставку такого действия в место, схема которого его не принимает.

Предложение разрешать действия в несовместимых местах обычного промежуточного дерева и откладывать проверку схемы до исполнения действий отклонено. Проверки обычного дерева сохраняются; автоматическое расширение его схем не вводится. D350–D351 не означают, что правило Comment as c -> Delete[$c]; применимо в любом обычном дереве.

Удаление при преобразовании обычного дерева разрешено через явный none по D353 (§16.6), с сохранением схемы родителя. Исполнение узлов-действий остаётся отдельным проходом; конкретный API дифференциального узла здесь не проектируется.

Основание: D352.

### 16.6. Явное удаление через none

Разрешён самостоятельный результат none для непосредственного удаления при преобразовании обычного дерева: Comment -> none;. Это исключение из D341: правило создаёт один узел либо явно не создаёт ни одного. Список и цепочка самостоятельных результатов по-прежнему запрещены; необязательный захват как самостоятельный результат этим решением не разрешается.

Удаление допустимо только при сохранении схемы родителя. Можно удалить элемент группы T* или присутствующего необязательного ребёнка T?. Удаление обязательного ребёнка и любое другое нарушение схемы запрещены по D356. Проверки обычного дерева не откладываются и не обходятся.

None не является узлом Delete и не требует отдельного прохода исполнения действий. Различие обычного и дифференциального дерева из D352 сохраняется; построение и исполнение узлов-действий остаются разными этапами.

Это отменяет запрет самостоятельного none из D341 и закрывает основной вопрос удаления обычных узлов из D352. Удаление корня разрешено в D354 (§16.7). Родитель становится листом после удаления последнего ребёнка только при допустимости этого по схеме (D356, §16.9).

Основание: D353.

### 16.7. Удаление корня и пустое дерево

Корневой узел дерева необязателен: допускается пустое дерево без узлов. Пользователь уточнил, что такая модель уже предусмотрена в Core. Поэтому правило с результатом none разрешено применять к корню; успешное применение удаляет корень и даёт пустое дерево. Например, Comment -> none; для дерева с корнем Comment оставляет дерево без узлов.

Предложение запрещать удаление корня и пропускать для него правила с none отклонено. Пустое дерево является допустимым результатом преобразования, а не ошибкой и не специальным узлом-заглушкой. Ограничение D353 на сохранение схемы родителя относится к дочерним местам и не запрещает удаление корня.

Это закрывает вопрос удаления корня из D353. Запрет списочного результата сохраняется. Удаление через none не создаёт Delete и не требует прохода исполнения действий. Правила по-прежнему не запускаются на отсутствующем узле; новое правило создания корня из пустоты этим решением не вводится.

Основание: D354.

### 16.8. Удаление последнего ребёнка

Удаление корня даёт пустое дерево (D354). Удаление некорневого узла исключает его из детей родителя; сам родитель автоматически не удаляется. Если схема допускает отсутствие детей, после удаления последнего ребёнка родитель остаётся листом.

D356 уточняет D355: удаление, нарушающее обязательность или иные ограничения схемы, не применяется. Дерево с недостающим обязательным ребёнком не является допустимым результатом. Противоречие между структурным описанием удаления и обязательностью разрешено в пользу сохранения корректности дерева.

Основание: D355–D356.

### 16.9. Преобразования сохраняют корректность дерева

Любое успешное преобразование даёт корректное дерево. Удаление обязательного ребёнка запрещено независимо от его позиции и от наличия других детей у родителя. Например, у Addition с обязательными left и right нельзя удалить ни left, ни right.

Запрет относится ко всем сочетаниям требований схемы, а не только к одиночным обязательным местам: удаление не должно нарушать типы, обязательность и кратности детей. Если отсутствие всех детей допустимо, родитель после удаления последнего ребёнка остаётся листом. Если схема требует детей, получение такого листа недопустимо. Пустое дерево после удаления необязательного корня остаётся разрешённым по D354.

Недопустимое преобразование следует выявлять при компиляции, если это возможно доказать статически. Если правило всё же запущено, кандидат, приводящий к неправильному дереву, не применяется: исходное дерево сохраняется, некорректный результат не публикуется. Это не разрешение ослабить схему или отложить исправление дерева до следующих правил.

Это разрешает вопрос D355 и уточняет D353: структурное описание родителя-листа применимо только при соблюдении схемы. Прежнее отклонение конкретного предложения в D355 не отменяет проверок корректности. По D357 (§16.10) неприменимость в отдельных контекстах не запрещает компиляцию: ошибка требуется при доказанной невозможности допустимого применения вообще. Если это не доказано, правило компилируется, но не обязано сработать.

Основание: D356.

### 16.10. Компиляция не гарантирует применение правила

Если неприменимость правила не доказана, отсутствие статического доказательства его применимости не является ошибкой: правило компилируется. Оно не обязано сработать на конкретном входном дереве и может не выполнить ни одного преобразования.

Правило Comment -> none; может удалять Comment в допустимых местах и не применяться там, где удаление нарушило бы схему. Неприменимость в отдельных контекстах не делает всё правило ошибочным. Ошибка компиляции требуется при доказанной невозможности допустимого применения правила вообще, в соответствии с D254 и D356.

При исполнении сохраняется проверка корректности результата по D356: недопустимая замена не применяется и исходное дерево не изменяется. Успешная компиляция не означает разрешения обходить схему и не требует хотя бы одного успешного применения.

Это закрывает границу между ошибкой компиляции всего правила и неприменимостью лишь в части контекстов, оставленную открытой в D356. Конкретные пределы статического анализа не расширяются до требования доказать разрешимость каждого случая.

Основание: D357.

## 17. Требования к переработке Node

### 17.1. Направление зависимости

**Node переделывается под новый DSL. DSL не ограничивается текущими методами Node.** Совместимость со старым интерфейсом и минимальный размер изменений не являются условиями проектирования.

Подтверждены именованные и безымянные группы, включая несколько соседних безымянных групп одного типа. Отказываться от них ради старого API нельзя.

### 17.2. Одиночные позиции: открытый вопрос

Пользователь поставил вопрос: можно ли считать одиночных детей вырожденными группами, каждого в своей группе? Ответ пока не согласован. Нельзя считать принятой ни единую модель групп для всех мест, ни конкретный Java-интерфейс для неё. Уже известные кратности 1 и 0..1 не решают вопрос внутреннего представления.

Синтаксическое различие одиночного шаблона и списка повторяющейся группы сохраняется, пока не принято иное решение.

### 17.3. Требуемая информация

Интерфейс должен позволять алгоритмам узнать:

- Конкретный тип и его однозначное имя.
- Данные через чистый детерминированный getData().
- Места итоговой схемы в их порядке.
- Принадлежность каждого ребёнка месту, включая безымянные места.
- Пустые места и их кратность.
- Число детей каждого места и порядок внутри него.
- Достаточную информацию для точного сравнения и хэша.

Теги не заменяют идентичность безымянных мест. Плоский список без распределения недостаточен.

### 17.4. Что есть сейчас и что не утверждено

В исследованном core есть getChildCount(), getChild(int), getChild(String), getChildTag(int) и необязательная схема Type.getChildDescriptors().

Текущий доступ по тегу возвращает один узел, а повторяющиеся места схемы не допускают тегов. Эти контракты не покрывают новый DSL.

Предложение Optional<List<Integer>> getChildCounts() **не принято**. Не приняты также обязательность старого плоского API, default-поведение для неизвестной схемы и способ хранения размеров. Нужно спроектировать интерфейс целиком, вместе с Builder, сериализацией, адаптерами и алгоритмами.

### 17.5. Последствия для остальных компонентов

Новая модель затрагивает генерацию классов, создание узлов, доступ по тегу, сравнение, хэш, клонирование, сериализацию JSON и восстановление узлов. Все эти операции обязаны сохранять границы именованных и безымянных групп.

JSON не должен терять различие [1, 1] и [2, 0] при одном плоском списке детей. Конкретный новый формат пока не утверждён.

## 18. Сквозные примеры

### 18.1. Объявления и правило свёртки

~~~text
abstract Expression;
abstract AssignableExpression : Expression;

node Identifier<String> : AssignableExpression;
node IntegerLiteral<Int> : Expression;
node Plus;
node Multiply;

node Addition : Expression(
    left: Expression,
    right: Expression
);
node Product : Expression(
    left: Expression,
    right: Expression
);
node Tokens(items: Node*);

Expression as a, Multiply, Expression as b -> Product[$a, $b];
Expression as a, Plus, Expression as b -> Addition[$a, $b];
~~~

У Tokens достаточно общий тип группы, чтобы хранить и операнды, и узлы-токены. Умножение имеет приоритет по порядку правил. После каждой свёртки поиск перезапускается; Product и Addition являются Expression и могут участвовать в следующих совпадениях.

Этот пример не задаёт лексер исходного языка: создание Identifier, IntegerLiteral и токенов остаётся внешней задачей.

### 18.2. Две группы одинакового типа

~~~text
node Split(left: Expression*, right: Expression*);
~~~

При наличии списочных захватов xs и ys:

~~~text
Split(left: $xs, right: $ys)
Split[$xs, $ys]
~~~

Обе записи однозначны. Но шаблон Split[Expression*, Expression*] запрещён. Построение знает назначения мест, а плоский позиционный шаблон пытается заново найти границу и получает неоднозначность.

### 18.3. Удаление обёртки и место замены

~~~text
abstract Statement;
node Block : Statement(items: Statement*);
node Loop(body: Statement);

Block[Statement* as body] -> $body; // Ошибка по D341: результат не является ровно одним узлом.
~~~

Этот исторический пример отклоняется статически во всех контекстах по D341: списочный захват не может быть самостоятельным результатом правила. Размещение внутри группы Statement* не снимает запрета. Дочерний список можно подставить только внутрь единственного результирующего узла.

### 18.4. Сложное правило для присваивания

Условное дерево a = a + 1 имеет Assignment с левым Identifier и правым Addition. Один вложенный шаблон может анализировать все эти позиции одновременно.

Проверка литеральных данных и равенство строковых захватов уже приняты (D199, D207): повторное имя данных проверяет одинаковое написание. Однако равенство написаний идентификаторов само по себе не доказывает, что они обозначают одну переменную с учётом областей видимости. Повторное as внутри одной ветки запрещено и не служит проверкой идентичности. Для полноценного семантически корректного преобразования нужна отдельно определённая модель разрешения имён.

Замена на a++ не сохраняет значение выражения во всех языковых контекстах; структурная допустимость правила сама по себе не доказывает семантическую корректность.

## 19. Диагностика и отклонённые конструкции

### 19.1. Ошибки до исполнения

К ним относятся повторные типы и теги, неизвестные имена и параметры, циклы наследования, несовместимые базы, неверные типы и кратности подстановок, обычные захваты внутри повторения (исключение для аккумуляторов данных — §11.9), недопустимые повторные объявления захватов узлов и списков (исключение для альтернатив — §9.56–9.59), конфликты категорий захватов, пустой минимум фрагмента и доказанное тождество.

Неизвестный тег проверяется по объявленному типу шаблона, не по возможным фактическим потомкам.

### 19.1.1. Граница ответственности билдера и статического анализа

Билдер знает о создаваемых узлах, их схемах и корректности, но не знает о шаблонах. Сопоставление шаблонов выполняется отдельным механизмом. Билдер не участвует в выборе распределения исходного фрагмента по частям шаблона и не разрешает неоднозначность сопоставления. Сохраняется требование однозначного совпадения до построения результата.

Статический анализ DSL может связывать сведения о шаблоне и результате и выявлять правила, у которых шаблон способен совпасть, но результат заведомо невозможно построить. Пользователь обозначил такую диагностику как полезное направление: заведомо неправильные программы следует выявлять до исполнения. Это задача анализатора DSL, а не расширение ответственности билдера.

Критерий ошибки компиляции определён в D254 ниже. Исчерпывающий перечень обязательных статических проверок ещё не согласован. Этот пункт не вводит запрет всех правил, построение результата которых может отказать лишь на некоторых входах: их ожидаемый отказ уже определён в D251–D252.

Основание: D253.

### 19.1.2. Заведомая невозможность построения результата

Если статический анализ установил, что правило ни при каких подходящих входных данных не сможет построить результат, это ошибка компиляции DSL. В остальных случаях возможность построения проверяется при исполнении по D251–D252. Возможный отказ на части входных данных сам по себе не является основанием отклонять правило.

Анализатор не обязан понимать произвольный Java-код разбора и валидаторов. Неполнота статического анализа не делает правило ошибочным: если заведомая невозможность не установлена, сохраняется проверка при построении результата.

~~~text
Token<$text> -> IntegerLiteral<$text>; // Допустимо: зависит от входных данных.
Token -> IntegerLiteral<"hello">; // Ошибка, если анализатор установил невозможность разбора.
~~~

В примере предполагается, что IntegerLiteral использует datatype целого числа. Для первого правила "123" допускает построение, а "hello" приводит к ожидаемому отказу кандидата. Во втором правиле данные результата постоянны; при установленной невозможности их разбора правило отклоняется до исполнения. Это уточняет критерий статической диагностики из D253; исчерпывающий перечень обязательных проверок ещё предстоит определить.

Основание: D254.

### 19.1.3. Заведомо невозможное совпадение шаблона

Если статический анализ установил, что шаблон правила не может совпасть ни с одним допустимым входным фрагментом, это ошибка компиляции DSL. Правило отклоняется независимо от возможности построения его результата.

~~~text
Identifier<startsWith("a") & startsWith("b")> -> Marker;
~~~

В примере одна строка не может одновременно начинаться с "a" и "b", поэтому условие заведомо ложно. При выявлении этого противоречия анализатор отклоняет правило.

Полнота выявления всех невозможных шаблонов не требуется. Если невозможность совпадения не установлена и других ошибок DSL нет, шаблон проверяется при исполнении. Это правило дополняет D254 о заведомо невозможном результате. Конкретный обязательный набор статических проверок остаётся отдельным вопросом.

Основание: D255.

### 19.1.4. Предупреждение о перекрытии правил

Если статический анализ установил, что правило полностью перекрыто более ранним правилом и поэтому не может сработать при принятом порядке применения, выдаётся предупреждение. Это не ошибка компиляции: само правило может быть корректным, а недостижимость обусловлена порядком правил.

Одного пересечения шаблонов недостаточно. Для полного перекрытия необходимо учитывать охват всех совпадений позднего правила, контексты применения и успешность построения результата более раннего правила. Если ранний билдер может ожидаемо отказать на соответствующем входе, такой отказ может сделать позднее правило применимым; предупреждение нельзя обосновывать только сходством шаблонов.

~~~text
Identifier<$name> -> Variable<$name>;
Identifier<"count"> -> Counter;
~~~

В этом примере предупреждение обосновано, если анализатор установил, что первое правило во всех соответствующих контекстах успешно преобразует каждый Identifier с данными "count", не оставляя возможности второму правилу сработать. Полнота обнаружения всех случаев перекрытия не требуется. Пользователь принял дополнительную работу по такой диагностике; конкретный алгоритм и объём обязательных проверок ещё не определены.

Основание: D256.

### 19.1.5. Предупреждение о доказанно избыточной проверке

Доказанно избыточная, но возможная проверка вызывает предупреждение и сама по себе не препятствует успешной компиляции. Это отличается от доказанно невозможной ветки, которая является ошибкой всего DSL по D312.

Например, в Identifier & Identifier<startsWith("a")> первый операнд не добавляет ограничений. Компилятор сообщает об избыточности и может упростить пересечение по D306, только если сохраняются все захваты и вклады в аккумуляторы. Одного сходства текста для диагностики или упрощения недостаточно.

Предупреждение должно указывать избыточную проверку и объяснять, из какого условия она следует. Возможность показать сообщение человеку не определяет его уровень; передача и вывод выполняются по D314. Пример предупреждения и отличие от ошибки невозможности обязательны в пользовательской документации.

Основание: D313.

### 19.1.6. Структурированные диагностики и вывод через вызывающую среду

Компилятор формирует ошибки и предупреждения как структурированные данные, отделённые от их отображения. Диагностика содержит уровень (ошибка или предупреждение), стабильный код, понятное объяснение и положение в исходном DSL: файл, строку и столбец для сообщений, относящихся к исходному тексту. Конкретные Java-интерфейсы и перечень кодов этим решением не задаются.

Диагностики доступны вызывающему коду программно и не требуют наличия экрана или консоли. Отдельный запуск через CLI выводит их в консоль; Maven-плагин передаёт их в журнал Maven с соответствующим уровнем. Вызов из Java получает диагностики для самостоятельной обработки. Это также позволяет будущей интеграции с IDE показывать сообщения возле исходного текста, но реализацию IDE-интеграции сейчас не вводит.

Ошибка означает неуспех компиляции независимо от того, было ли сообщение фактически отображено. Maven-плагин должен завершать соответствующую сборку ошибкой при неуспехе компиляции DSL. Предупреждение само по себе не делает компиляцию неуспешной; отсутствие канала отображения не должно приводить к потере программно доступной диагностики.

Пример представления в журнале Maven: [WARNING] rules.dsl:42:5: Избыточная проверка Identifier: она уже следует из второго операнда пересечения. Текстовая форма зависит от среды, а смысл, код, уровень и исходное место определяются компилятором.

При реализации нового компилятора необходимо обновить оба способа запуска — CLI и astranaut-maven-plugin — и проверить передачу предупреждений и ошибок, сохранение координат, успешность сборки с предупреждениями и отказ при ошибках. Пользовательская документация должна объяснять, где искать сообщения при каждом способе запуска. Нынешняя реализация плагина не считается реализацией этого нового контракта.

Строгий режим «считать предупреждения ошибками» определён в D315 (§19.1.7). Сбор независимых ошибок определён в D316 (§19.1.8); конкретные имена настроек и подавление отдельных сообщений рассматриваются отдельно.

Основание: D314.

### 19.1.7. Строгий режим предупреждений

Вводится явно включаемый режим «считать предупреждения ошибками». По умолчанию он выключен: предупреждения сами по себе не препятствуют успешной компиляции. При включённом строгом режиме наличие любого предупреждения делает компиляцию DSL неуспешной.

Семантика режима одинакова для командной строки, astranaut-maven-plugin и программного Java API. CLI сообщает неуспех завершения, Maven-плагин завершает сборку ошибкой, Java API предоставляет вызывающему коду неуспешный результат компиляции вместе с диагностиками. Конкретные имена параметров, коды завершения и сигнатуры API будут определены при проектировании интерфейсов.

Отказ в строгом режиме не зависит от того, отображены ли предупреждения на экране или в журнале: решение принимается по диагностикам компилятора. Сообщения сохраняют доступные вызывающему коду причину, стабильный код и исходное место по D314. Настоящее решение определяет влияние предупреждений на успешность, но не фиксирует способ представления их уровня в строгом режиме.

Ошибки компиляции приводят к неуспеху независимо от строгого режима. Необходимо документировать обычный и строгий режимы и проверить одинаковое поведение CLI, Maven и Java API на одном DSL с предупреждением: успех по умолчанию и отказ при включении режима.

Сбор независимых ошибок и запрет генерации при ошибках определены в D316 (§19.1.8). Подавление отдельных предупреждений и детали восстановления после ошибок остаются открытыми.

Основание: D315.

### 19.1.8. Сбор независимых ошибок и остановка до генерации

Компилятор собирает несколько независимых ошибок за один запуск, пока анализ можно надёжно продолжать. Проверки, зависящие от уже ошибочных или неизвестных сведений, пропускаются, чтобы не создавать каскад ложных сообщений.

Например, неизвестный тип в одном правиле не мешает проверить независимое правило. Проверять допустимость детей неизвестного типа бессмысленно: эта зависимая проверка не выполняется.

При наличии ошибок итог компиляции неуспешен; генерация не запускается. Сбор остальных диагностик не означает разрешение продолжать генерацию частично корректного DSL. Правило применяется совместно со структурированными диагностиками D314 и строгим режимом D315.

Решение не требует продолжать анализ после повреждения, из-за которого дальнейшие выводы ненадёжны. Точные точки восстановления после синтаксических ошибок, ограничения количества сообщений и обработка ошибок чтения файлов требуют отдельного уточнения.

Основание: D316.

### 19.2. Обычное несовпадение

Тип или вложенная структура не подошли; обязательная часть шаблона не найдена; максимальный кандидат неоднозначен. Для разрешённого шаблона неоднозначный конкретный вход не является отдельной ошибкой исполнения.

В общем обходе несовместимый контекст результата также означает пропуск правила, но явное назначение этому контексту является ошибкой DSL.

### 19.3. Ошибки исполнения

Тождественный результат конкретного применения и подтверждённый цикл останавливают обработку. Неожиданные исключения пользовательского Java-кода не скрываются общей обработкой.

### 19.4. Не следует переносить старую семантику

Не действуют: конкретные базы типов узлов; автоматическое объединение валидаторов; устранение конфликта баз локальным default; сравнение происхождения default по тексту; обход сверху вниз; предварительное отдельное преобразование элемента перед правилами его родительской цепочки; укорачивание неоднозначного максимального фрагмента на той же позиции.

## 20. Открытые вопросы и дальнейшая работа

### 20.1. Сначала конечный синтаксис DSL, затем Node

По решению D198 проектирование интерфейса Node отложено до завершения синтаксиса DSL; текущая задача — №10. Затем нужно спроектировать новую модель групп и одиночных мест, определить интерфейсы Node/Type/Builder, хранение границ, доступ по имени и индексу, работу с пустыми и безымянными местами. Требуется выбрать, что заменить, удалить или добавить, не считая существующий API обязательным.

Нужно решить судьбу узлов с неизвестной схемой, DraftNode и внешних адаптеров. Нельзя незаметно трактовать неизвестную схему как пустую.

### 20.2. Данные в шаблонах и результатах

Точная проверка литеральных данных принята (D199, §9.8), как и запись константных данных результата (D200, §11.7). Захват сериализованных данных отдельно от узла и их перенос приняты (D201, §11.8). Проверка равенства данных захваченной строке принята (D203, §9.9). Операции над данными и основные формы выражений определены в D213–D232 (§9.10–9.28, §11.10); полная грамматика и оставшиеся пограничные случаи ещё обсуждаются. Ссылки до объявления захвата разрешены (D204). Принято явное накопление строковых данных через аккумулятор $name+ из нескольких позиций в порядке исходной цепочки независимо от стрелки (D205, D209, §11.9); остальные детали ещё уточняются. Открыто сравнение захватов узлов. Обычные захваты данных внутри необязательных шаблонов запрещены (D249, §10.3.1); проверки данных разрешены, аккумуляторы запрет не затрагивает. Внешний as захватывает узел; $name внутри угловых скобок шаблона — строку getData(), а не нативное значение (D206). Повторное имя данных одновременно захватывает и требует равенства (D207); отдельный знак проверки не используется. Сочетание $name и $name+ для одного имени в шаблоне запрещено (D210); в результате $name читает накопленное значение.

Пользователь обозначил будущую потребность в счётчике с монотонно возрастающими числами для генерации уникальных имён при автоматических преобразованиях. Обсуждение отложено по его просьбе. Синтаксис, область действия, правила выдачи чисел и взаимодействие с чистыми выражениями ещё не определены; счётчик не включён в утверждённые встроенные операции.

### 20.3. Полная грамматика и неоднозначность

Нужны единая EBNF, полный перечень ключевых слов, правила всех комбинаций скобок, ограничения вложенных списочных захватов и алгоритм статического анализа пересекающихся повторений.

Нельзя считать достаточным один старый критерий D119: D178 и D179 уточняют его конкретными разрешёнными и запрещёнными примерами.

### 20.4. Пространства имён и организация правил

Не завершены языковые секции, пространства имён, именованные правила и наборы правил, явное назначение контекста, управление несколькими обходами. Определён один главный файл и include; отдельный режим нескольких равноправных входных файлов не утверждён.

### 20.5. Исполнение и инфраструктура

Требуются точный алгоритм для смешанных одиночных и повторяющихся мест, диагностика правил без допустимых контекстов, отмена работы, защита от бесконечного роста без повторений и оценка памяти истории.

При одном доступном узле также надо завершить правила применимости верхнеуровневых повторений как шаблонов: общие ограничения контекста определены, все синтаксические пограничные случаи ещё не разобраны.

### 20.6. Действия и метаданные

Механизм исполнения Insert/Delete/Replace, адреса целей и статус Property отложены. Координаты исключены из структурного сравнения; поведение прочих служебных свойств и их перенос через преобразования нужно согласовать с общей моделью.

Обязательный критерий готовности пользовательской документации (D302, §9.82): полные таблицы приоритетов данных и шаблонов с разобранными примерами всех уровней, явными скобками, положительными и отрицательными случаями. Одной таблицы недостаточно.

### 20.7. Реализация и миграция

Реализация компилятора, генератора и интерпретатора — следующие задачи. Нужны обновлённые примеры, критерии приёмки, интеграция DSL → Java → core, миграция потребителей и JSON. Объём переноса старых примеров пока не выбран.

Слияние PR №11 сохраняет пригодный для чтения промежуточный результат. Задача №10 остаётся открытой: её критерий — цельная грамматика с разрешёнными или явно отложенными вопросами. Аудит текущих пробелов приведён в §22.

## 22. Аудит пробелов и несостыковок — 30.10.2026

Это предварительный сводный аудит требований D001–D316 перед слиянием PR #11, а не новые решения языка. Задача [#10](https://github.com/kniazkov/astranaut/issues/10) остаётся открытой: слияние фиксирует материал для анализа, но не означает завершение её критерия о цельной грамматике. Вопросы ниже нужно обсуждать отдельно; возможные варианты и контрольные примеры не считаются утверждённым синтаксисом.

Область проверки: журнал README.md, действующая спецификация и её печатная версия. Исторические отменённые решения сами по себе не являются противоречием: проблема возникает, когда старое правило осталось без оговорки в действующей спецификации. Конкретный Java API Node намеренно отложен (D198); его отсутствие выделено отдельно от пробелов языка.

Обозначения: **Н** — несогласованность текста или границы правил; **П** — не определённый контракт; **О** — сознательно отложенная тема. Приоритет **P0** означает, что без решения нельзя однозначно реализовать соответствующую семантику; **P1** — нужно до завершения спецификации; **P2** — следующий этап. Нумерация A01–A34 служит для дальнейшего обсуждения и не продолжает номера утверждённых решений D.

### 22.1. Неоднозначность, логика и захваты

- **A01 · Н · P0 — Граница статически запрещённой неоднозначности.** В §10.4–10.5 и D179 разрешён `Statement*, Return, Statement*`, хотя два Return дают доказуемую неоднозначность. D272/D273/D285/D291 требуют отклонять доказанную неоднозначность захватов или разбиения на итерации; D285 явно считает достаточным один неоднозначный вход. Это не обязательно прямое противоречие, поскольку классы конструкций различаются, но общего критерия нет. Нужно определить, какие неоднозначности запрещают программу, а какие лишь отвергают конкретного кандидата, сохранив явно принятый пример D179. Нельзя молча распространить новый запрет на все распределения.

- **A02 · Н · P0 — Что считается одним распределением.** §10.4 и §13.4 говорят «несколько распределений — несовпадение», тогда как D258/D263 разрешают несколько совпавших веток с согласованными захватами, а D268 выбирает вклад аккумулятора по приоритету. Нужно формально отличить разбиение входа, выбор ветки, значения захватов и границы итераций. Контрольные случаи: `(Identifier | Identifier)`, альтернатива одинаковых цепочек и `(Identifier+)+`. Одинаковый плоский результат не должен автоматически склеивать запрещённые разбиения.

- **A03 · П · P0 — Отрицание неоднозначного внутреннего сопоставления.** D295 разрешает отрицать составной шаблон детей, а D179 допускает его динамическую неоднозначность. Для `!(Box[Statement*, Return, Statement*])` на Box с двумя Return нужно явно установить: отрицание успешно, потому что внутренний шаблон считается несовпавшим, либо неоднозначность отвергает и внешний кандидат. D297 требует эквивалентности двойного отрицания; выбранное правило должно сохранять её. Простое логическое отрицание существования распределения и отрицание успешного однозначного совпадения дают разные результаты.

- **A04 · П · P0 — Вложенные альтернативы и выбор аккумуляторов.** D268/D275 определяют первый вариант среди полных совпадений максимальной длины, но не задают общий порядок для нескольких вложенных альтернатив, пересечений и итераций. Нужно описать, когда ветка считается полностью совпавшей с учётом внешних условий, как сравниваются комбинации выборов и когда проверяется согласованность обычных захватов. Нужны примеры, где локально первая ветка не допускает полного совпадения, и где разные ветки дают одинаковую длину, но разные наборы вкладов. Нельзя свести правило к локальному жадному выбору.

- **A05 · П · P0 — Внешние ссылки и совместное решение условий.** D204 разрешает ссылку до захвата, D248 — чтение захвата в собственном фильтре, D299 — чтение внешних данных под отрицанием. Для взаимных ссылок в двух фильтрах и ссылок через альтернативы/пересечения нужно определить доступность и момент проверки для целого кандидата. Например, два обязательных Identifier могут проверять префикс по данным друг друга; это не должно зависеть от порядка вычисления. Отдельно нужны правила для комбинации внешнего связывания и повторного имени лишь в одной ветке альтернативы с учётом строгого D269.

- **A06 · П · P1 — Внутренние захваты и уточнение типов пересечением.** D310/D311 описывают внешний захват пересечения. Не определено, уточняет ли соседний операнд тип внутреннего захвата: `(Expression as x) & Identifier`. D303 говорит о типе захватывающего шаблона; из этого не следует автоматически перенос всех ограничений на x. Нужно явно решить допустимость подстановки x в место Identifier, а также уточнение необязательности/кратности внутреннего захвата другими условиями.

- **A07 · П · P1 — Проверка невозможности в контексте и под отрицанием.** D312 запрещает невозможную исходную ветку до упрощений. Нужно определить границы «ветки» и «своего контекста»: например, `Identifier & (Identifier | Number)` при разных конкретных Identifier и Number, а также отрицание заведомо ложного составного условия. Нужны правила для необязательной или нулевой итерации вокруг невозможного тела. Отдельно уточнить закрытость мира типов: отсутствие объявленного общего конкретного потомка двух абстрактных типов сейчас не обязательно равно невозможности для внешних адаптеров.

### 22.2. Грамматика и выражения

- **A08 · П · P0 — Единая грамматика и область действия as.** Полной EBNF нет (§20.3); D302 прямо оставляет размещение as открытым. Нужно определить разбор `A & B as x`, `A, B as xs`, `A | B as x`, вложенных захватов и формы `(A as x) as y`, а также обязательность скобок вокруг альтернатив/пересечений на верхнем уровне. Нужны правила совмещения фильтра данных и детей, допустимости одновременных именованных и позиционных детей, завершающих запятых в каждом контексте. Похожие формы объявления, шаблона и результата нельзя объединять по аналогии.

- **A09 · П · P1 — Лексический контракт.** §2.2 оставляет открытым окончательный список зарезервированных и контекстных слов. Требуется грамматика числовых и булевых литералов выражений: ASCII-цифры, ведущие нули, знак как оператор, недопустимые формы. Правила разбора строк datatype Int/Long из §8.3 не задают автоматически лексер выражений. Уточнить пробельные символы вне строк, одиночный CR и токенизацию соседних знаков; Unicode в строках/комментариях уже разрешён, ASCII-имена уже приняты.

- **A10 · Н/П · P0 — Строковый литерал как краткое условие.** §9.13 принимает `Identifier<!"count">`, а §9.37 допускает литерал как специальную проверку равенства без неявного string → boolean. Нужно задать точную грамматику этого сокращения: допустимы ли `<"a" | "b">`, `<("a")>`, `<!"a".isEmpty()>` и где литерал означает значение, а где проверку data(). Приоритеты и строгая типизация должны давать единственный разбор; правило «любая строка становится условием» не принято.

- **A11 · П · P1 — Полная таблица сигнатур встроенных операций.** Методы распределены по §9.14–9.42 и §11.10. Нужна единая таблица получателя, аргументов, возвращаемого типа и разрешённых форм вызова. У toLowerCase/toUpperCase приняты и метод, и функция; для остальных нельзя автоматически вводить такую же функциональную форму. Допустимость `value.toString()` прямо оставлена открытой в §9.27. Уточнить применение функционального преобразования регистра к произвольному строковому выражению, а не только к захвату.

- **A12 · П · P1 — Unicode и граница Java-строк.** Кодовые точки, отсутствие нормализации и trim уже определены. Не выбраны версия Unicode и точные правила контекстного изменения регистра; не определены одиночные суррогаты, которые может вернуть пользовательский Java datatype. Строгий UTF-8 исходника (§2.1) не решает вопрос корректности getData(). Нужны согласованные правила для длины, поиска, сравнения и сериализации таких значений, а не зависимость от случайной версии JDK.

### 22.3. Типы, построение и анализ

- **A13 · П · P1 — Минимум обязательного статического анализа.** D254/D255/D272/D285/D312 требуют ошибки при доказанном нарушении, но разрешают неполноту анализа. Без обязательного набора доказуемых случаев два компилятора могут принимать разные программы; строгий режим добавляет зависимость от найденных предупреждений. Нужен минимальный набор проверок с положительными/отрицательными тестами и политика версий. Это не требование решить общую задачу доказательства произвольного Java-кода.

- **A14 · П · P1 — Недостижимый тип из-за обязательной рекурсии.** Рекурсивные дети разрешены (§2.6), но `node Loop(child: Loop);` не имеет конечного корректного экземпляра при модели дерева. Нужно решить судьбу таких объявлений и ссылок на них: ошибка самого типа, ошибка невозможного шаблона или допустимая, но непорождаемая схема. Аналогично — абстрактные схемы без реализуемых конкретных потомков. Это отдельный вопрос от запрещённых циклов наследования.

- **A15 · Н/П · P1 — Начальное значение и гарантия корректного узла.** §7.1 возлагает соответствие default валидатору на автора и не вводит автоматической проверки default; §1.5 обещает корректность готового дерева, D251 требует успешного построения результата. Нужно описать, что происходит при неверном default и создании узла без явных данных, где проходит граница ответственности автора и какие гарантии сохраняются. Согласовать это с полной заменой validate, допускающей значения, отвергавшиеся валидатором базы.

- **A16 · П · P1 — Построение без списка детей и без данных.** Для шаблонов T, T() и T[] различия определены, но нужен столь же явный контракт результата: какие пустые/пропущенные формы равнозначны, когда применяется default, что происходит при обязательных детях. Отдельно нужны положительные/отрицательные примеры данных для узла без datatype: пустая строка принимается по §6.3, непустая отклоняется; нужно связать это с D254/D255 и фильтрами данных.

- **A17 · П · P0 — Категория результата против числового диапазона.** §11.3 запрещает список в одиночном месте независимо от фактической длины, §11.6 описывает допустимость объединения через диапазон количества. Нужна полная композиционная проверка категории и диапазона для `none + $x`, списочных выражений с доказанным максимумом один и цепочек с несколькими необязательными элементами. Нельзя разрешить обход запрета списка добавлением none или случайно запретить принятую эквивалентность `none + $x` и `$x` (D154).

- **A18 · П · P1 — Кратности и корреляции веток.** D276/D289/D290 задают категории и возможные значения, но не определяют точность анализа связанных захватов одного выбора. Например, два необязательных узловых захвата могут по веткам всегда давать суммарно ровно один узел, хотя независимые интервалы дают 0..2. Нужно решить, достаточно ли интервальной консервативной проверки или обязательны корреляции, и как это влияет на размещение результата по схеме.

- **A19 · П · P1 — Анализ пользовательских datatype без исполнения Java.** §7.5 и D254 запрещают требовать понимания произвольного Java, но нужны практические границы анализа констант для встроенных и унаследованных datatype с переопределёнными parse/validate. Следует явно определить, исполняет ли компилятор пользовательский код на стадии анализа; такое исполнение сейчас не утверждено. Также нужны диагностики нарушенного контракта serialize/getData и проверка однозначности понятия канонического представления.

### 22.4. Исполнение и контексты

- **A20 · П · P0 — Допустимость шаблона в одноузловом контексте.** §14.5 подробно ограничивает результат, но §20.5 оставляет пограничные случаи шаблонов открытыми. Нужно определить применение `T+`, `(T | T, U)` и цепочек с необязательными частями к корню и одиночному ребёнку: проверяется весь шаблон статически или разрешены варианты, совпадающие с одним узлом. Это не разрешение списочного результата в одиночном месте.

- **A21 · П · P0 — Единый порядок смешанного обхода.** D189–D192/§14 определяют обход снизу вверх, порядок групп и отсутствие спуска в новый результат. Нужен единый алгоритм для чередования обязательных детей, необязательных детей и групп: когда реконструируется родитель, что доступно следующему контексту, когда начинается история состояния. Сохраняются принятые правила: элементы группы конкурируют в общем цикле, а не преобразуются отдельно; направление стрелки не меняет порядок групп.

- **A22 · П · P1 — Правая стрелка поиска и максимальная длина.** Для <- нужны симметричные пошаговые примеры: к какой границе привязана очередная позиция, как расширяется максимальный кандидат, как сдвигается поиск после отказа. Порядок узлов внутри шаблона и накопления уже не должен переворачиваться. Проверить на асимметричной цепочке, альтернативах разной длины и отказе билдера; одних примеров ассоциативности присваивания недостаточно.

- **A23 · П · P1 — Контекстно неприменимые и перекрытые правила.** §14.5 разрешает пропуск правила с несовместимым внешним результатом; D254/D255/D312 требуют ошибки невозможности, D256 — предупреждение перекрытия. Нужно разграничить правило без единого допустимого контекста, ветку невозможную только в отдельном месте обхода и полностью перекрытое правило. Нельзя объявлять ошибкой каждую неприменимость к отдельной группе или доказывать перекрытие одним включением шаблонов без учёта отказов результата.

- **A24 · П · P1 — Ошибка исполнения после уже выполненных замен.** D251 гарантирует атомарность одного кандидата; §19.3 останавливает обработку при цикле, тождестве и неожиданном исключении. Не определён результат всего запуска при такой остановке: возвращается ли последняя корректная версия, только диагностика или иной результат; что с уже обработанными группами и файлами. Отдельно нужен контракт отмены и нехватки ресурсов без превращения их в обычное несовпадение.

- **A25 · О · P2 — Рост, память и отложенный счётчик.** Повторные состояния ловятся, бесконечный рост — нет (§15.6); лимит числа замен отклонён и не предлагается повторно. Открыты отмена и управление памятью истории. Счётчик уникальных имён (§20.2) намеренно отложен: его область, откат неудачных кандидатов, воспроизводимость и влияние на чистоту/проверку циклов нужно решить до добавления, иначе состояние дерева перестанет описывать всё состояние исполнения.

### 22.5. Диагностика и интеграция

- **A26 · П · P1 — Восстановление после ошибок.** D316 принят: независимые ошибки собираются, зависимые проверки пропускаются, генерация при ошибках не запускается. Нужно определить надёжные точки восстановления после синтаксических ошибок и ошибок include, а также судьбу связанных неизвестных имён. Формулировку §2.5 «компиляция прекращается» следует читать как неуспех; означает ли ошибка чтения немедленное прекращение всего анализа или только ветки подключения — ещё нужно уточнить. Нужны тесты независимого второго правила и отсутствия каскада по неизвестному типу.

- **A27 · П · P1 — Протокол диагностик и строгий режим.** D314/D315 определяют общий смысл, но открыты каталог стабильных кодов, диапазон исходного текста, нумерация строк/столбцов (байты, UTF-16 или кодовые точки), связанные места, детерминированный порядок и устранение повторов. Не определены представление уровня warning в строгом режиме, подавление отдельных предупреждений и граница запуска генерации при наличии только warnings в строгом режиме. Нужны единые ожидаемые результаты CLI/Maven/Java API.

- **A28 · П · P1 — Граница DSL → Java и выходные файлы.** Нужны контракт генерации, Java-имена и их конфликты с допустимыми DSL-именами, диагностики Java-фрагментов с привязкой к DSL, настройки CLI/Maven, результат при сбое записи или Java-компиляции. D316 запрещает запуск генерации при ошибках анализа, но не определяет очистку устаревших файлов, атомарность публикации и инкрементальную сборку с include. Конкретные API проектируются позже; требования к наблюдаемому результату нужны до интеграции.

### 22.6. Документация и сознательно отложенные темы

- **A29 · Н · P1 — Остатки исторического изложения в действующей спецификации.** При аудите обнаружены устаревшие дата и диапазон D001–D212, общий запрет повторного as без исключения альтернатив, §18.4 с уже решённой темой сравнения данных. Эти места редакционно исправлены в данной фиксации. Ещё нужна последовательная сверка формулировок «будет определено» в §9.9–9.11, §9.19, §9.45–9.51, §9.59–9.60 и списков §20 с последующими решениями. Например, D284 уже разрешает вложенный списочный захват под ?, а §20.3 всё ещё перечисляет ограничения обобщённо. Исторический журнал переписывать как будто старых решений не было нельзя.

- **A30 · Н · P1 — Обязательная учебная часть ещё не собрана.** D302 требует полные таблицы приоритетов и разобранные сочетания всех уровней, положительные и отрицательные примеры. Сейчас материал разнесён по подразделам, таблица шаблонов изложена словами, ряд примеров использует условные неопределённые типы. Нужны единый справочный блок и самодостаточный набор примеров с ожидаемым разбором, типами, диагностикой и результатом; Markdown и HTML должны соответствовать друг другу. Это отдельный критерий готовности документа, а не повод считать язык реализованным.

- **A31 · О · P1 — Организация программы и проходов.** Именованные правила, наборы правил, пространства имён, языковые секции, явное назначение контекста, повторные проходы и несколько равноправных входных файлов ещё не определены (§20.4). Один главный файл, канонизация include и порядок вставки правил уже приняты. Для оставшихся возможностей нужно выбрать: включить в первую законченную версию либо явно отложить; нельзя оставлять упоминание «явного назначения» без доступного способа его выполнить.

- **A32 · О · P1 — Символьный вход и демонстрационный парсер.** §1.1–1.2 задают цель разбора подмножества C, но не определяют начальное дерево символов, тип и данные символа, EOF, координаты, экранирование строк, комментарии и критерий успешного разбора без оставшихся токенов/узлов ошибок. Требуются состав подмножества C и набор положительных/отрицательных программ. Текущий пример кавычек без экранирования — только промежуточный пример, не завершённая спецификация лексера.

- **A33 · О · P2 — Node, границы групп, сериализация и метаданные.** D198/§17 сознательно откладывают конкретные Node/Type/Builder. Дальше нужны сохранение пустых и безымянных мест в JSON, идентичность вхождения при разделении объектов, структурное равенство и хэш, неизвестные схемы/адаптеры, перенос координат и прочих свойств. Не следует объявлять решение об одиночных местах как вырожденных группах принятым. Контракт неизменяемости данных Java также надо обеспечить на границах адаптеров.

- **A34 · О · P2 — Действия и критерий готовности реализации.** Схемы Insert/Delete/Replace приняты, применение дерева действий и адреса целей нет (§16); Property отложен. Нужны отдельные требования на эти механизмы, план изменений core/генератора/плагина/потребителей и матрица тестов. Существующий Java-код старого DSL и успешная сборка старого проекта не подтверждают реализацию новых D001–D316.

### 22.7. Предлагаемый порядок дальнейшего разбора

Сначала A01–A05 и A07: однозначный смысл совпадения, отрицания и выбора веток. Затем A08–A10 и A17–A23: грамматика, категории результата и контексты исполнения. После этого — остальные P1, единая EBNF и сквозные примеры, сверка всего документа и критериев задачи #10. Темы P2 обсуждаются после завершения DSL, как требует D198.

Этот порядок — предложение по итогам аудита, не новое принятое решение. Новые ответы пользователя нужно фиксировать отдельными D317 и далее, одновременно уточняя или закрывая соответствующие пункты A.
