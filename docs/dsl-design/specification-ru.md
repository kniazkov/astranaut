История обсуждения сохранена отдельно в [README.md](README.md); журнал при подготовке исходной редакции от 31 октября не изменялся; решения D373–D377 добавлены при разборе задачи #13. Примеры до §17 — независимые фрагменты, если не сказано иное: упомянутые типы и их совместимые схемы предполагаются объявленными. ## 1. Назначение и модель дерева

Astranaut предназначен для описания синтаксических деревьев, их преобразования и построения парсеров. **Объявление** задаёт допустимую структуру узла; **шаблон** проверяет существующий фрагмент; **результат** строит замену. Эти контексты могут использовать похожую запись, но имеют разные правила.

Входом может быть готовое дерево внешнего парсера, приведённое адаптером к общей модели. Для разбора текста вход имеет один корень и последовательность символьных детей; правила сворачивают их в токены и более крупные узлы. Один Character соответствует одному скалярному значению Unicode, а не Java char или графеме. Существующий преобразователь текста подлежит проверке на этот контракт.

Дерево имеет один корень либо пусто. Узлы и нативные данные неизменяемы. Успешное преобразование сохраняет корректность схемы и данных: нельзя сначала получить неправильное дерево в расчёте на исправление следующим правилом. Схема включает типы детей, их порядок, обязательность и границы повторяющихся групп.

Результат правила — один узел или явное `none` для удаления. Узел может иметь много детей. Самостоятельная цепочка результатов не допускается.

Структурная корректность не доказывает сохранение смысла программы, разрешимость имён или завершённость разбора. Эти свойства требуют соответствующих правил и анализа. Контракт предполагает корректные адаптеры и соблюдение требований пользовательскими Java-включениями.

Новый DSL не обязан быть совместимым со старым языком или интерфейсами core. Модель Node проектируется под язык. Практическая цель — демонстрационный парсер согласованного подмножества C.

## 2. Исходные файлы, имена и комментарии

### 2.1. Кодировка и окончания строк

Исходники читаются как UTF-8. BOM в начале файла разрешён. Поддерживаются LF, CRLF и одиночный CR. Некорректный UTF-8 является ошибкой: подстановка символов замены не допускается.

Unicode разрешён в строках и комментариях. Идентификаторы ограничены ASCII.

### 2.1.1. Пробелы между токенами (D383)

Между токенами DSL разрешены только обычный пробел U+0020, TAB (U+0009), LF (U+000A) и CR (U+000D). CRLF считается одним переводом строки; одиночные LF и CR также являются переводами строки. Одиночный CR завершает комментарий // так же, как LF или CRLF (D383).

Неразрывный пробел U+00A0 и прочие Unicode-пробелы вне строк и комментариев являются лексической ошибкой. В строках и комментариях Unicode сохраняется по прежним правилам. Разрешение BOM в начале файла (§2.1) сохраняется; BOM не добавляется в набор межтокенных пробелов. Переводы строк внутри литералов по-прежнему запрещены (§2.4).

```text
node⟦TAB⟧A;                     // Допустимо.
node⟦U+00A0⟧A;                  // Лексическая ошибка.
node A;⟦CR⟧node B;              // Два объявления на двух строках.
// комментарий⟦CR⟧node A;       // Комментарий окончен; A объявляется.
node A;⟦CRLF⟧node B;            // Два объявления на двух строках.
```

Обозначения ⟦TAB⟧, ⟦CR⟧, ⟦CRLF⟧ и ⟦U+00A0⟧ в примерах обозначают фактические символы входного файла, а не синтаксис DSL. Недопустимый межтокенный символ обнаруживается лексическим анализом при компиляции. Это правила исходника DSL, а не политика разбираемого пользовательского текста.

### 2.2. Идентификаторы

Форма обычного идентификатора (для имён типов узлов действует дополнительное ограничение D414, §2.2.3):

~~~text
[A-Za-z_][A-Za-z0-9_]*
~~~

Регистр значим. Одиночное имя _ занято универсальным шаблоном; имена вроде _value допустимы.

Имена типов узлов и datatype находятся в общем пространстве имён. Встроенные имена уже объявлены и не могут быть переобъявлены. Повторное объявление типа ошибочно даже при одинаковом содержимом.

В конструкциях ниже используются служебные слова `abstract`, `node`, `datatype`, `include`, `as` и `none`.

### 2.2.1. Зарезервированные слова (D391)

Слова abstract, node, datatype, include, as, none, true и false зарезервированы: их нельзя использовать как имена типов узлов, datatype, дочерних тегов и захватов узлов или данных (D391). Запрет относится к точному написанию целого имени и действует также после $ в захватах данных. Регистр значим: Include и True допустимы как имена типов узлов; includeFile допустимо как имя тега или захвата, но не типа узла по D414.

```text
node include;              // Ошибка: зарезервированное имя типа.
datatype true : String;     // Ошибка: зарезервированное имя datatype.
Identifier as true         // Ошибка: зарезервированное имя захвата узла.
Identifier<$false>         // Ошибка: зарезервированное имя захвата данных.
node Box(none: Node);      // Ошибка: зарезервированный тег.

node Include;             // Допустимое имя.
node True;                // Допустимое имя.
node includeFile;         // Ошибка: имя типа начинается со строчной буквы (D414).
```

Использование зарезервированного слова в позиции имени отвергается при компиляции, до сопоставления или построения результата. Для обычных имён правило целого токена сохраняется: includeFile — одно имя, а не ключевое слово include с остатком File. Слова внутри строк и комментариев не становятся ключевыми словами. Разрешённое имя True не является булевым литералом true.

D391 не отменяет отдельные ограничения на встроенные имена типов и универсальный шаблон _. Имена параметров datatype являются контекстными по D392 (§6.2.1). Имена встроенных функций и методов контекстны по D393 (§10.3.2); глобально они не резервируются.

### 2.2.2. Неразрывный токен ссылки на захват (D413)

$name является единым токеном: между $ и именем нельзя вставлять пробел, перевод строки или комментарий. Это относится к связыванию и использованию захватов данных и узлов. Знак + аккумулятора — отдельный токен, поэтому пробел перед ним допустим.

~~~text
Identifier<$text>       // Захват данных.
Identifier<$text+>      // Аккумулятор.
Identifier<$text +>     // Тот же аккумулятор.
Identifier<$ text>      // Лексическая ошибка.
Identifier<$/**/text>   // Лексическая ошибка.
Identifier as item -> $item; // Ссылка на захваченный узел.
~~~

Разрыв после $ отвергается лексическим анализом до сопоставления. Общие ограничения имён, включая запрет зарезервированных слов после $, сохраняются. Пробел между as и именем не относится к этому правилу: as и имя — отдельные токены.

### 2.2.3. Имена типов узлов начинаются с заглавной буквы (D414)

Имя конкретного или абстрактного типа узла имеет форму [A-Z][A-Za-z0-9_]*. Первая буква — заглавная ASCII-буква; оставшиеся символы следуют ранее согласованной лексике идентификаторов. Дополнительное требование полного стиля CamelCase не вводится. Имена datatype, дочерних тегов и захватов сохраняют прежнюю форму [A-Za-z_][A-Za-z0-9_]* и ограничения зарезервированных имён.

~~~text
node Identifier;        // Допустимо.
abstract Expression;    // Допустимо.
abstract node Value;    // Допустимо.
node identifier;        // Ошибка имени типа.
abstract _Expression;   // Ошибка имени типа.
node Box(value: Node);  // Тег может начинаться со строчной буквы.
Identifier as item      // Захват может начинаться со строчной буквы.
~~~

Недопустимое имя типа отвергается при компиляции до генерации Java.

### 2.3. Комментарии

~~~text
// Комментарий до конца строки.

/* Блочный комментарий.
   Может занимать несколько строк. */
~~~

Блочные комментарии не вкладываются. Комментарии разделяют токены. Маркеры комментариев внутри строки являются содержимым строки.

### 2.3.1. Соседние знаки и границы токенов (D384)

Лексический анализ выбирает самый длинный допустимый токен, начинающийся в текущей позиции. Соседние знаки !=, ==, <=, >=, -> и <- распознаются как цельные токены. Выбор токена не зависит от того, удобен ли он для дальнейшего синтаксического разбора; разбиение на более короткие знаки для спасения ошибочной конструкции не выполняется (D384).

Пробел, перевод строки или комментарий разделяет токены. Знаки по разные стороны такого разделителя не склеиваются в составной оператор. Это правило не меняет приоритеты выражений, требования скобок для сравнений порядка в фильтрах и правила содержимого строк, символьных литералов и комментариев.

```text
Identifier<data()!="x">       // Допустимо: единый токен !=.
Identifier<data() ! = "x">    // Ошибка синтаксиса: отдельные ! и =.
Identifier<data() !/**/="x">  // Ошибка синтаксиса: комментарий разделяет знаки.
Identifier<!"x">             // Отдельный ! перед строковым литералом.
Identifier<(length()>=1)>    // Единый >=; скобки сравнения сохранены.
Identifier -> Token;         // Единый ->.
Identifier - > Token;        // Ошибка синтаксиса: это не стрелка.
```

При данных "x" первый фильтр не совпадает, при "y" совпадает. Две разорванные записи != отвергаются при синтаксическом анализе до сопоставления. Лексер в них распознаёт отдельные знаки; он не восстанавливает подразумеваемый оператор. Пример со стрелкой предполагает совместимые объявления и допустимое построение Token.

### 2.4. Строки и экранирование

Строки заключаются в двойные кавычки. Экранирование одинаково для данных, путей include и Java-фрагментов:

| Запись | Значение |
|---|---|
| `\"` | Двойная кавычка |
| `\\` | Обратная косая черта |
| `\n` | Перевод строки |
| `\r` | Возврат каретки |
| `\t` | Табуляция |
| `\u{HEX}` | Одно скалярное значение Unicode; 1–6 шестнадцатеричных цифр |

Неизвестное экранирование и буквальный перевод строки внутри литерала — ошибки. В `\u{HEX}` допустимы цифры ASCII 0–9, a–f, A–F; значения выше U+10FFFF и U+D800–U+DFFF запрещены. Декодирование однократное: `"\\u{61}"` даёт буквальный текст `\u{61}`, а `"\u{61}"` — букву a. Сначала снимается экранирование DSL, затем строка используется по назначению. Ограничения путей include проверяются после декодирования.

~~~text
datatype MyText : String {
    default = "\"\"";
}
~~~

Здесь содержимое default после декодирования — Java-выражение пустой строки.

### 2.5. Подключение файлов

~~~text
include "../shared/common.dsl";
~~~

Директива располагается на верхнем уровне, в любом месте файла. Путь относительный, разделитель на всех ОС — /. Разрешены компоненты пути `.` и `..`. Абсолютные пути, буквы дисков, UNC-пути и обратная косая черта в декодированном пути запрещены.

Файл определяется каноническим абсолютным путём с разрешением символических ссылок. Вложенные include разрешаются относительно реального файла, а не каталога ссылки на него.

Каждый файл обрабатывается один раз. Повторные подключения и циклы include разрешены: повторно посещённый файл пропускается. Ошибка подключения делает компиляцию неуспешной. Диагностика содержит путь, причину, место директивы и цепочку подключений; общий порядок сбора независимых ошибок описан в §16.

### 2.6. Имена разрешаются независимо от порядка, правила — нет

Ссылаться на тип до объявления можно. Объявления собираются из всех подключённых файлов, затем разрешаются ссылки. Рекурсия через детей разрешена, циклы наследования запрещены.

Для правил порядок имеет значение. Просмотр начинается с главного файла, переданного на вход. Include вставляет правила подключённого файла на своём месте, рекурсивно. Если главный файл содержит правило A, include с B и C, затем D, порядок будет A, B, C, D. Повторный include ничего не добавляет.

### 2.7. Порождаемость конкретных типов

Если компилятор доказал, что конкретный тип не имеет ни одного конечного корректного экземпляра из-за требований схемы детей, объявление этого типа является ошибкой компиляции. Проверка действует даже тогда, когда тип не используется в правилах.

Например, abstract Chain(next: Chain); node Link : Chain; не допускает конечного дерева: каждый Link требует следующего Chain с тем же обязательным требованием. Взаимная обязательная рекурсия также является ошибкой, если ни один допустимый вариант не позволяет завершить дерево.

Сама рекурсия через детей не запрещается. В варианте abstract Chain(next: Chain?); node Link : Chain; цепочка может закончиться отсутствующим next, поэтому приведённая причина отказа исчезает. При анализе нужно учитывать допустимые конкретные варианты обязательных детей; наличие цикла само по себе ещё не доказывает непорождаемость.

~~~text
abstract Chain(next: Chain);
node Link : Chain; // Ошибка: нет конечного экземпляра.

// Отдельный исправленный вариант:
abstract Chain(next: Chain?);
node Link : Chain; // Цепочка может завершиться.
~~~

## 3. Объявления типов узлов

### 3.1. Абстрактные и конкретные типы

~~~text
abstract Expression;
abstract node Statement;

node Marker;
node Identifier<String> : Expression;
~~~

abstract и abstract node равнозначны. Абстрактный тип нельзя создать непосредственно. node без abstract объявляет конкретный тип.

Базами могут быть только абстрактные типы. Конкретные типы не наследуются друг от друга. Это ограничение DSL, а не зависимость от возможностей старого core.

### 3.2. Полная форма

~~~text
node TypeName<Datatype> : BaseA, BaseB (
    first: ChildType,
    second: OtherType?,
    rest: ChildType*
);
~~~

Привязка datatype, базы и список детей необязательны. Привязка данных стоит сразу после имени, до списка баз.

Вместо завершающей точки с запятой объявление с параметрами данных имеет блок:

~~~text
node PositiveLiteral<Int> : Expression {
    default = "1";
    validate(value) = "value > 0";
}
~~~

После непустого списка детей разрешена завершающая запятая. Пустой список () означает отсутствие детей, но не разрешает удалить унаследованных детей.

### 3.2.1. Запятые в списке базовых типов (D388)

В списке базовых типов завершающая запятая запрещена (D388). Запятая здесь разделяет два имени базовых типов и не может стоять после последнего имени, в том числе перед точкой с запятой, списком детей или блоком параметров данных. При наличии двоеточия требуется непустой список баз; пустой элемент и двойная запятая также запрещены. Все эти нарушения являются синтаксическими ошибками компиляции.

```text
abstract Named;
abstract Printable;

node Document : Named, Printable;  // Допустимо: две абстрактные базы.
node Document : Named, Printable,; // Ошибка: завершающая запятая.
node Document : Named, ();         // Ошибка: запятая перед списком детей.
node Document : ;                 // Ошибка: пустой список баз.
node Document : Named,, Printable; // Ошибка: пустой элемент.
```

Строки с объявлением Document — независимые альтернативы примера, а не повторные объявления в одном файле. Допустимая форма объявляет потомка Named и Printable. Неверные формы отвергаются синтаксическим анализом, до построения иерархии. Ранее разрешённые завершающие запятые в списках детей и аргументах вызовов сохраняются.

### 3.3. Встроенный Node

Node — абстрактный общий предок всех типов узлов. Наследование от него автоматическое. Он не объявляет детей и datatype, создать его нельзя.

В шаблоне Node as x и _ as x имеют одинаковый охват и статический тип захвата Node. Подстановка такого захвата в более узкое место запрещена без доказанного статического типа; фактический вид пойманного узла не даёт неявного сужения.

<a id="s4"></a>

## 4. Дочерние позиции и группы

### 4.1. Три кратности объявления

| Объявление | Допустимое число детей |
|---|---:|
| value: Expression | 1 |
| value: Expression? | 0 или 1 |
| items: Expression* | 0 и более |

Суффикс + принят для повторения шаблона, но не как новая кратность схемы объявления.

В абстрактных типах все места обязательно именованы. В конкретных типах собственные места могут не иметь тегов, включая повторяющиеся места. Все рассмотренные ниже формы разрешены.

### 4.2. Одна группа

~~~text
node AnonymousBlock(Statement*);
node NamedBlock(items: Statement*);
~~~

В обоих типах все дети относятся к одной группе. Именованный вариант позволяет обращаться по тегу items. Пустая группа допустима.

### 4.3. Одиночные позиции вокруг группы

~~~text
node Section(
    heading: Heading,
    Statement*,
    ending: Ending
);
~~~

heading и ending содержат по одному ребёнку; среднее место — произвольное число Statement. При пустой средней группе у узла два фактических ребёнка.

Размеры мест в этом примере — 1, N, 1. Это характеристика кратности. Одиночное место и повторяющаяся группа различаются в синтаксисе.

### 4.4. Несколько групп

~~~text
node Function(Parameter*, Statement*);
node AnonymousParts(Node*, Node*);
node NamedParts(left: Node*, right: Node*);
node MixedParts(prefix: Node*, Node*, Node*);
~~~

Все объявления допустимы. Разные типы групп не всегда позволяют восстановить границу: при множественном наследовании их множества допустимых узлов могут пересекаться.

Два места одинакового типа остаются разными местами. Их нельзя автоматически объединять в одну группу.

### 4.5. Границы — часть структуры

Плоские дети [A, B] могут означать размеры групп [0, 2], [1, 1] или [2, 0]. Эти узлы структурно различны.

При построении NamedParts(left: $xs, right: $ys) или AnonymousParts[$xs, $ys] назначение известно: каждое выражение заполняет своё место. Готовый узел обязан сохранить это назначение.

Теги помогают именованным группам, но не решают задачу нескольких безымянных групп. Пустые места также должны оставаться представленными. Модель должна предоставлять число детей каждого места.

### 4.6. Автоматическое распределение и явное построение — разные уровни

Автоматическое распределение плоских детей построителем требует единственного полного решения с учётом типов и кратностей. Внутри каждой группы сохраняется исходный относительный порядок; распределение между разными местами не обязано сохранять их порядок во входном списке.

При нескольких решениях требуется явная привязка; произвольный жадный выбор запрещён. При отсутствии решений — ошибка совместимости.

Для мест одного объявленного типа сначала определяются допустимые размеры, сумма которых равна числу входных детей. Единственный набор размеров разбивает вход последовательно; несколько наборов требуют явной привязки, отсутствие набора означает несовместимость.

| Схема и вход | Автоматическое распределение |
|---|---|
| `(left: T, right: T)`, два совместимых ребёнка a, b | left=a, right=b |
| `(left: T?, right: T?)`, один ребёнок | Неоднозначно: неизвестно, какое место пропущено |
| Та же схема, два ребёнка | left=a, right=b |
| `(head: T, tail: T*)`, N ≥ 1 | Размеры 1, N−1 |
| `(head: T*, tail: T)`, N ≥ 1 | Размеры N−1, 1 |
| `(head: T?, tail: T*)`, непустой вход | Неоднозначно; пустой вход однозначен |
| `(first: T, middle: T*, last: T)`, N ≥ 2 | Размеры 1, N−2, 1 |

Для двух заполненных одиночных мест с пересекающимися типами взаимозаменяемые дети назначаются по порядку входа. Если подходит только обратное назначение, выбирается оно: типовая совместимость первична. Правило размеров одного типа не заменяет общий анализ мест разных типов.

Это не алгоритм позиционного шаблона и не алгоритм распределения выражений результата. В результате DSL выражения связываются с местами статически и в своём порядке.

<a id="s5"></a>

## 5. Наследование детей и порядок

### 5.1. Наследуемая схема

~~~text
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);

node Addition : BinaryExpression;
node Subtraction : BinaryExpression;
~~~

Потомки получают обоих детей без дублирования. При одной базе без собственного списка сохраняются состав и порядок базы.

### 5.2. Ссылки на унаследованные места

~~~text
node Reversed : BinaryExpression (
    @right,
    @left
);
~~~

@ отличает ссылку на место от имени типа безымянного ребёнка. Неизвестная ссылка — ошибка. Ссылка не создаёт нового ребёнка, а сохраняет тип и кратность унаследованного места.

При добавлении собственного ребёнка требуется полный список:

~~~text
node Extended : BinaryExpression (
    @left,
    extra: Expression?,
    @right
);
~~~

Новые места можно располагать между унаследованными. Перестановка унаследованных мест разрешена. Доступ по тегу сохраняет смысл; плоские индексы отражают новый порядок.

### 5.3. Множественное наследование

Совпадение мест определяется по тегу. Совместимые места одного тега объединяются в одно; разные теги обозначают разные места.

Для объединяемых мест должны точно совпадать тип и кратность. Даже отношение подтип/надтип между разными типами не разрешает конфликт. Собственное уточнение потомка не исправляет конфликт нескольких баз.

Если базы приносят разные составы или порядок, потомок явно перечисляет полную итоговую схему. Если списки полностью совпадают, список потомка можно опустить. Базы без детей не влияют на порядок.

### 5.4. Сужение типа ребёнка

~~~text
abstract AssignableExpression : Expression;

node Assignment : BinaryExpression (
    left: AssignableExpression,
    @right
);
~~~

Разрешено явно сузить тип места до объявленного подтипа, сохранив кратность. Расширение и замена несвязанным типом запрещены. Структурного сходства типов недостаточно.

Уточнение повторяющегося места также сохраняет суффикс *; необязательного — ?. Повторные теги в итоговом явном списке запрещены.

```text
abstract HasLeft(left: Expression);
abstract HasRight(right: Expression);
node Pair : HasLeft, HasRight(@left, @right);
node ReversedPair : HasLeft, HasRight(@right, @left);
```

Обе итоговые схемы допустимы; отсутствие полного списка в этом примере ошибочно. Если одна база объявляет `value: Expression`, а другая `value: Expression?`, возникает конфликт кратностей. Если обе объявляют value с разными типами, конфликт сохраняется даже при наследовании одного типа от другого.

<a id="s6"></a>

## 6. Типизированные данные

### 6.1. Datatype и тип узла

Datatype описывает значение, а не узел. Его имя нельзя использовать как тип ребёнка или шаблон узла.

Встроенный Int уже существует; для полного пользовательского примера выберем другое имя:

~~~text
datatype CounterValue {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
}

node Counter<CounterValue>;
node TaggedCounter<CounterValue>(items: Node*);
~~~

Данные и дети совместимы. Один datatype переиспользуется разными типами узлов.

### 6.2. Параметры datatype

| Параметр | Назначение |
|---|---|
| javaType | Нативный Java-тип |
| default | Java-выражение начального значения |
| serialize(value) | Преобразование нативного значения в строку |
| parse(text) | Разбор строки в нативное значение |
| parseError | Ожидаемое исключение разбора либо none |
| validate(value) | Необязательная дополнительная проверка |

Первые пять параметров обязательны в итоговом описании с учётом наследования. Отсутствующий validate эквивалентен true.

Порядок параметров свободный. Повтор одного параметра ошибочен даже при одинаковом тексте. Неизвестный параметр — ошибка. Необязательный validate не делает необязательными остальные поля.

### 6.2.1. Контекстные имена параметров (D392)

Имена javaType, default, serialize, parse, parseError и validate являются контекстными: они обозначают параметры только в позиции имени параметра соответствующего блока описания данных. Вне этой позиции они доступны как обычные имена типов, тегов и захватов, с сохранением общих ограничений имён (D392). Глобально зарезервированными словами из D391 они не являются.

```text
node default;                 // Ошибка: имя типа начинается со строчной буквы (D414).
node Box(parse: Node);        // Допустимое имя тега.
Identifier as validate        // Допустимое имя захвата узла.
Identifier<$parse>            // Допустимое имя захвата данных.

datatype TextValue : String {
    default = "\"\"";         // Здесь default — имя параметра.
}

datatype BadText : String {
    unknown = "\"\"";         // Ошибка: неизвестный параметр.
}
```

Примеры независимы и предполагают необходимые объявления. Одноимённый тег или захват не меняет значение default в блоке параметров. Допустимость обычного имени не разрешает неизвестные параметры внутри такого блока: unknown отвергается при компиляции при проверке описания данных. Сохраняются прежние ограничения состава параметров datatype и параметров данных узла; D392 не добавляет параметры в блоки, где они ранее запрещены.

### 6.3. Текстовое и нативное представление

Типизированный getValue() предоставляет нативное значение; общий getData() — строку serialize(value). Внутреннее хранение скрыто за интерфейсом.

Нативные значения ненулевые и неизменяемые. Аргумент setData не может быть null. String использует строковое представление непосредственно.

Для узла без datatype getData() всегда пуст. setData("") успешно ничего не меняет; непустая строка отклоняется. Такой узел не получает неявный datatype String. Параметры default и validate без datatype запрещены.

### 6.4. Наследование datatype

~~~text
datatype PositiveInt : Int {
    default = "1";
    validate(value) = "value > 0";
}

datatype MyText : String;
~~~

База только одна. Наследуются все параметры; любой можно переопределить. Краткая форма без блока объявляет новый datatype, не псевдоним.

При изменении javaType новый Java-тип должен быть подтипом базового; это ответственность автора. Числовое преобразование примитивов не считается наследованием. Циклы наследования запрещены.

### 6.5. Наследование datatype узла

Узел наследует datatype базы. Локальная привязка может сохранить его либо уточнить до потомка в иерархии datatype:

~~~text
abstract Literal<Int>;
node PositiveLiteral<PositiveInt> : Literal;
~~~

Разные datatype нескольких баз конфликтуют, даже если связаны наследованием. Уточнение потомка не исправляет конфликт.

База без данных совместима с базой с данными; несколько баз с одним datatype дают одну привязку. Совпадение Java-типа у разных datatype не делает их совместимыми. Если новый datatype и базовый узел приносят конкурирующие переопределения default или validate, автоматического приоритета нет: это ошибка.

### 6.6. Контракт сериализации

parse(serialize(value)) восстанавливает эквивалентное значение, но не обязательно тот же объект. serialize(parse(text)) не обязан сохранять исходное написание: например, +007 превращается в 7.

Parse, serialize, validate и getData должны быть чистыми и детерминированными. Для одинаковых данных одного типа getData всегда даёт одинаковое содержимое строки. Это каноническое представление используется в равенстве и хэше.

<a id="s7"></a>

## 7. Проверки, начальные значения и ошибки

### 7.1. Переопределение в узле

~~~text
abstract Positive<Int> {
    default = "1";
    validate(value) = "value > 0";
}

node SmallNumber : Positive {
    validate(value) = "value < 10";
}
~~~

SmallNumber наследует default = 1, но его проверка допускает отрицательные значения: локальный validate полностью заменяет прежний. Автоматического объединения через И или ИЛИ нет.

Для снятия проверки применяется validate(value) = "true". Отсутствие локальной проверки, наоборот, сохраняет унаследованную.

Соответствие default валидатору обеспечивает автор. Автоматическая проверка начального значения не введена.

### 7.1.1. Ответственность за Java-включения

Корректность Java-включений и согласованность default с validate обеспечивает автор DSL. Сгенерированный код использует заданную валидацию. При default = "0" и validate(value) = "value > 0" билдер с начальным значением невалиден: требующее его правило не сработает. Некорректный узел не публикуется. Это обычный отказ построения, а не особая фатальная ошибка default.

### 7.2. Происхождение объявлений в ромбе

Одно объявление общего предка, пришедшее несколькими путями, не конфликтует с самим собой. Независимые объявления конфликтуют даже при одинаковом тексте.

~~~text
abstract A<Int> { default = "1"; }
abstract B<Int> { default = "1"; }
node C : A, B; // Ошибка: независимые источники default.
~~~

Собственный default или validate потомка не исправляет конфликт баз. Совместимость баз проверяется до локальных переопределений. Выбор по близости, тексту или порядку баз не выполняется.

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A { validate(value) = "value < 10"; }
abstract C : A;
node D : B, C; // Ошибка: разные объявления validate из B и A.
```

Если обе ветки без переопределений наследуют одно объявление A, такого конфликта нет.

### 7.3. Атомарность присваивания данных

setData и setValue возвращают boolean. При отрицательном результате проверки либо ожидаемой ошибке разбора setData возвращает false и сохраняет прежнее значение. Отказ не сбрасывает значение к default.

Присваивание происходит только после успешного разбора и проверки.

### 7.4. Исключения

В false переводится только ожидаемое исключение parse, указанное в parseError, включая его подклассы. При parseError = none специального перехвата нет.

Исключения validate и неожиданные исключения parse выходят наружу. Область перехвата parse не включает validate, даже если валидатор выбросил исключение того же класса.

### 7.5. Граница ответственности Java

Astranaut не реализует Java-парсер для строковых фрагментов. Их синтаксис, типы и checked-исключения проверяет Java-компилятор. Генератор не добавляет общий catch, throws или обёртки, чтобы исправить произвольный пользовательский код.

Контракты чистоты и неизменяемости документируются, но автоматического доказательства для произвольного Java-кода нет.

<a id="s8"></a>

## 8. Встроенные типы данных

### 8.1. Набор и начальные значения

| Имя | Java-тип | Начальное значение |
|---|---|---|
| String | java.lang.String | пустая строка |
| Int | int | 0 |
| Long | long | 0L |
| Boolean | boolean | false |
| Double | double | 0.0 |
| CodePoint | int | 0 (U+0000) |

Имена заняты встроенными объявлениями. Переобъявлять, например, datatype Int нельзя.

### 8.2. Boolean

Только true и false, с точным регистром, без пробелов. TRUE, 1 и строка с пробелами отклоняются. Значение false успешно разбирается и не означает отказ setData.

### 8.3. Int и Long

Вся строка должна соответствовать:

~~~text
[+-]?[0-9]+
~~~

Разрешены ASCII-цифры, знак и ведущие нули. Пробелы, суффиксы, подчёркивания, шестнадцатеричные и двоичные префиксы запрещены. Переполнение — ошибка разбора.

Сериализация десятичная, без лишнего плюса, нулей и суффиксов: +007 даёт 7, -0 даёт 0.

### 8.4. Double

Обычная числовая запись:

~~~text
[+-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)([eE][+-]?[0-9]+)?
~~~

Допустимы 12, -0.5, .5, 1., +1.25e-3. Запрещены пробелы, запятая, суффиксы f/d и hex-форма.

Специальные значения принимаются ровно как NaN, Infinity, -Infinity. Варианты +Infinity, nan и -NaN запрещены.

Переполнение числовой строки до бесконечности отклоняется; явная строка Infinity разрешена. Округление допустимо, при равном расстоянии выбирается чётный младший бит. Слишком малое значение может округлиться до нуля с сохранением знака.

Сериализация — Double.toString(value). Знак нуля сохраняется, варианты битового представления NaN нормализуются в NaN. Это важно и для структурного сравнения через getData: 0.0 и -0.0 имеют разные строки.

### 8.5. CodePoint

CodePoint — встроенный datatype. Его нативный Java-тип — int, начальное значение — 0 (U+0000). Допустимы только скалярные значения Unicode — U+0000–U+10FFFF, кроме U+D800–U+DFFF.

Разбор данных принимает строку ровно с одним скалярным значением Unicode и возвращает его числовой код. Пустая строка, несколько кодовых точек и одиночные суррогаты недопустимы. Сериализация возвращает строку с соответствующим символом, а не десятичную запись его кода. Символ вне основной многоязычной плоскости может занимать две кодовые единицы UTF-16, оставаясь одним значением CodePoint.

Встроенный узел Character использует datatype CodePoint. Character — тип узла, CodePoint — тип его данных; это разные объявления. CodePoint доступен и другим типам узлов:

~~~text
node Letter<CodePoint>;
~~~

Имя CodePoint занято встроенным объявлением и не может быть переобъявлено, как и имена остальных встроенных datatype (§8.1). Сам datatype не является типом узла: его нельзя использовать вместо Character в шаблоне узла или схеме детей.

Встроенный Character — конкретный тип без детей. Его не нужно объявлять; переобъявление и пользовательское наследование от него запрещены. Начальные данные Character — строка с U+0000, не пустая строка и не строка "0".

## 9. Шаблоны и символьный вход

### 9.1. Тип, данные и дети

Абстрактный тип в шаблоне принимает прямых и косвенных потомков. Конкретный тип принимает только себя. `_` принимает любой один узел. Имя без дополнительных ограничений не проверяет данные или детей.

| Шаблон | Проверка |
|---|---|
| `Expression` | Только тип |
| `Expression()` | Только тип: нет указанных тегов |
| `Expression[]` | Тип и отсутствие всех фактических детей |
| `Identifier<"count">` | Тип и точная строка getData() |
| `Identifier<"">` | Тип и пустые данные |
| `Identifier<$name>` | Тип и связывание строковых данных с именем |

Литерал в фильтре сравнивается с сериализованной строкой; разбор в нативный datatype не выполняется. Например, IntegerLiteral с каноническими данными `"7"` не соответствует `IntegerLiteral<"+007">`, хотя создание числа из `"+007"` может быть успешно.


### 9.1.1. Порядок фильтра и проверки детей (D378)

В узловом шаблоне фильтр данных и проверка детей могут присутствовать одновременно. Порядок фиксирован: тип → фильтр данных → проверка детей; внешние кратность и захват as применяются к полученному шаблону по §13.1. Фильтр можно опустить, проверку детей можно опустить. Совместное использование позиционной и именованной форм запрещено D379 (§9.2.1).

Identifier<$text>[] проверяет тип Identifier, связывает сериализованные данные с text и требует отсутствия всех фактических детей. Его дерево разбора: NodePattern(type=Identifier, data=Capture(text), children=Positional([])). Identifier с данными "abc" без детей совпадает и связывает text="abc"; наличие ребёнка означает несовпадение. Действуют обычные статические проверки схем и захватов.

Container<"box">[Identifier] проверяет данные и весь список детей; Container<"box">(value: Identifier) проверяет данные и указанное место. В этих примерах предполагаются совместимые объявления типов с данными.

Обратный порядок Identifier[]<$text> и Container(value: Identifier)<"box"> — синтаксическая ошибка до сопоставления. Это правило относится к шаблонам; грамматика построения результата обсуждается отдельно.

Частичная продукция EBNF для шаблона с одной формой проверки детей (D378–D379; не полная грамматика Q06):

```ebnf
typed-node-pattern = type-name, [ data-filter ], [ children-check ];
children-check = positional-children | named-children ;
```

### 9.2. Позиционная и именованная проверки

```text
Addition[IntegerLiteral, Expression]
Addition(left: IntegerLiteral)
Addition(right: Expression, left: IntegerLiteral)
```

Позиционный шаблон проверяет **весь плоский список фактических детей** в указанном порядке. Он не ищет подфрагмент и не переставляет детей по типам. Именованный шаблон проверяет только перечисленные места; остальные не ограничены, порядок записи тегов несущественен. Тег должен существовать у объявленного типа шаблона, а не только у некоторых его потомков.

Для одиночного места пишется шаблон узла; для группы — список шаблонов в квадратных скобках, даже если ожидается один элемент:

```text
Return(value: IntegerLiteral)
Return(value: none)                  // Отсутствующий необязательный ребёнок.
Block(items: [Return, ExpressionStatement])
Block(items: [Return])
Block(items: [])
Block(items: none)                   // Та же проверка пустой группы.

Return(value: [IntegerLiteral])      // Ошибка: одиночное место не список.
Block(items: Return)                 // Ошибка: группа требует списка.
Return(value: IntegerLiteral[])      // Ребёнок IntegerLiteral без детей.
```

`none` для обязательного ребёнка запрещён. Список шаблонов группы проверяет её целиком. Пропущенные теги ничего не проверяют; в частности, пропуск необязательного тега не требует отсутствия ребёнка.

### 9.2.1. Единственная форма списка детей (D379)

В одном узловом шаблоне или конструкторе результата разрешена только одна форма списка детей: позиционная либо именованная. Сочетание обеих форм в любом порядке — синтаксическая ошибка до сопоставления или построения результата (D379).

```text
Pair[Identifier, Number](left: Identifier) // Ошибка синтаксиса.
Pair(left: Identifier)[Identifier, Number] // Ошибка синтаксиса.
Pair(left: $a)[$a, $b]                    // Ошибка синтаксиса.
Pair[$a, $b](left: $a)                    // Ошибка синтаксиса.
```

В шаблоне совместные ограничения выражаются пересечением отдельных одноузловых шаблонов. Оба операнда проверяют один и тот же узел; действуют обычные правила пересечения. В результате выбирается одна форма задания детей, без смешивания назначений.

```text
Pair[Identifier, Number] & Pair(left: Identifier)
// Альтернативные формы результата:
Pair[$a, $b]
Pair(left: $a, right: $b)
```

Для схемы node Pair(left: Node, right: Node) пересечение совпадает с Pair, у которого left — Identifier, right — Number. Pair с переставленными детьми не совпадает. В результате при обязательных одиночных захватах a и b совместимых типов обе показанные формы строят Pair с left=$a и right=$b. Примеры предполагают объявленные Identifier и Number.

### 9.2.2. Завершающая запятая в списке детей (D385)

В непустом списке детей шаблона или конструктора результата разрешена одна завершающая запятая непосредственно перед закрывающей скобкой. Это относится к позиционным и именованным спискам. Запятая не добавляет элемент, отсутствие ребёнка или дополнительное место схемы; смысл совпадает с записью без неё (D385). Разрешение завершающей запятой в объявлениях сохраняется.

```text
Pair[Identifier, Number,]
Pair(left: Identifier, right: Number,)
Pair[$a, $b,]
Pair(left: $a, right: $b,)

Pair[,]        // Ошибка синтаксиса: элемент отсутствует.
Pair[$a,, $b]  // Ошибка синтаксиса: пустой элемент между запятыми.
Pair(left: $a,,) // Ошибка синтаксиса: две завершающие запятые.
```

Для схемы node Pair(left: Node, right: Node) первые два шаблона проверяют соответственно позиционный список и именованные места по прежним правилам. Pair с left типа Identifier и right типа Number проходит обе проверки; перестановка этих детей не проходит. Последние две допустимые формы результата при совместимых обязательных одиночных захватах строят тот же Pair, что и без последней запятой. Все обычные проверки типов и схем сохраняются.

В пустом списке запятая запрещена: пустые формы остаются [] и (). Недопустимые пустые элементы обнаруживаются при синтаксическом анализе до сопоставления или построения. Завершающая запятая в аргументах функций и методов отдельно разрешена D386 (§10.3.1). Завершающая запятая в фильтрах и данных результата запрещена D387 (§10.1.2). Завершающая запятая в списке базовых типов запрещена D388 (§3.2.1). Завершающая запятая в самостоятельной цепочке шаблонов запрещена D389 (§13.1.1).

### 9.2.3. Пустая именованная проверка (D402)

Пустая именованная проверка детей в шаблоне разрешена. Container() эквивалентен Container: ни одного дочернего места не проверяется. Наличие детей само по себе не мешает совпадению. Пустая позиционная проверка Container[] имеет другой смысл: она требует полного отсутствия фактических детей (D402).

```text
Container()          // Проверка типа без ограничений на детей.
Container            // Тот же смысл.
Container[]          // Проверка типа и отсутствия всех детей.
Container<"box">()    // Проверка типа и данных, без ограничений на детей.
```

Для схемы node Container(items: Node*) первые два шаблона совпадают как с пустым Container, так и с Container, содержащим детей. Третий совпадает только с пустым Container. Пример с данными предполагает отдельное совместимое объявление Container с данными; пустые круглые скобки не отменяют фильтр "box".

Если схема типа обязательно требует детей и отсутствие детей доказанно невозможно, Container[] подчиняется общему правилу статического отклонения невозможного шаблона. Container() не вводит такого требования. Запятая в пустом списке по-прежнему запрещена: Container(,) — синтаксическая ошибка по D385.

Решение относится к проверке существующего узла в шаблоне. Оно не меняет значение пустого списка детей в объявлении или правила заполнения детей при построении результата.

### 9.2.4. Дети универсального шаблона (D403)

Универсальный шаблон _ допускает позиционную проверку детей и пустую именованную проверку. Тип родителя при этом не ограничивается: проверяются существующий узел и его фактические дети по обычным правилам соответствующей формы (D403).

```text
_[]             // Любой узел без детей.
_[Identifier]   // Любой узел с единственным ребёнком Identifier.
_()             // Любой узел, без проверки детей.
```

_[] совпадает с любым листом и не совпадает с узлом, имеющим хотя бы одного ребёнка. _[Identifier] совпадает с узлом любого типа, если полный список его фактических детей состоит из одного Identifier; ноль детей, ребёнок другого несовместимого типа или дополнительный ребёнок означают несовпадение. Проверка типа ребёнка сохраняет обычные правила подтипов. _() эквивалентен _ по D402 и совпадает с любым одним существующим узлом независимо от детей.

Эти формы проверяют исходное дерево и не создают узлы. Они не снимают общие ограничения вложенных шаблонов, захватов и кратностей. Внешний захват, например _[Identifier] as parent, по-прежнему имеет статический тип Node: структура детей сама по себе не задаёт конкретный тип родителя.

D403 разрешает позиционные списки, включая пустой, и пустую именованную форму. Непустая именованная проверка у _ запрещена D404 (§9.2.5). Фильтр и захват данных у _ разрешены D405 (§9.2.6).

### 9.2.5. Именованные места у универсального шаблона (D404)

Непустая именованная проверка детей у универсального шаблона _ запрещена (D404). У _ нет объявленных дочерних тегов. Для проверки места по тегу требуется тип шаблона, у которого этот тег объявлен. Наличие такого тега у фактического узла не снимает статического ограничения.

```text
_(value: Identifier)         // Ошибка: у _ нет объявленного тега value.
_()                         // Допустимо: пустая проверка по D402–D403.
_[Identifier]               // Допустимо: позиционная проверка по D403.
Container(value: Identifier) // Допустимо, если Container объявляет value.
```

Первая форма отвергается при компиляции при проверке дочерних тегов, до сопоставления. Она не становится динамической проверкой наличия тега у любого узла. Для схемы node Container(value: Node) последняя форма совпадает с Container, чей ребёнок value имеет подходящий тип Identifier; другой несовместимый тип ребёнка означает несовпадение.

Пустая форма _() остаётся эквивалентной _, а позиционные проверки не требуют объявленных тегов. D404 не меняет правила именованных проверок у конкретных и абстрактных типов: проверяемое место должно существовать у объявленного типа шаблона, а не только у некоторых его потомков.

### 9.2.6. Данные универсального шаблона (D405)

Универсальный шаблон _ допускает фильтр и захват данных по тем же правилам, что и узловой шаблон с именем типа. Используется сериализованная строка фактического сопоставляемого узла; для узла без datatype это пустая строка по §6.3 (D405).

```text
_<"hello">          // Любой узел с данными "hello".
_<$text>           // Захват данных любого узла.
_<startsWith("a")>  // Проверка префикса данных.
_<$text>[]         // Захват данных узла без детей.
```

Первый шаблон совпадает с узлом любого типа, чьи сериализованные данные равны "hello", и не совпадает с узлом без datatype. Второй захватывает строку фактического узла, в том числе "" у узла без datatype. Третий совпадает с данными "abc", но не "xyz" или "". Четвёртый дополнительно требует полного отсутствия детей: при наличии ребёнка весь шаблон не совпадает.

Порядок частей сохраняется: _ → фильтр данных → проверка детей. Поэтому _[]<$text> — синтаксическая ошибка. Пустая именованная проверка после фильтра разрешена, например _<"hello">(); непустая именованная проверка по-прежнему запрещена D404.

Краткие строковые условия, вызов data(), неявный строковый получатель методов, условия с захватом и аккумуляторы подчиняются общим правилам фильтров. D405 не отменяет ограничений захватов под отрицанием, необязательностью и повторением и не вводит преобразование данных через datatype при сопоставлении.

### 9.2.7. Уникальность тегов в именованной проверке (D408)

В одном именованном списке проверок детей каждый тег разрешено указывать не более одного раза. Повтор тега является ошибкой DSL, даже если повторённые проверки одинаковы (D408). Повторные записи не объединяются автоматически в пересечение и не заменяют друг друга.

```text
Box(value: Expression, value: Identifier) // Ошибка: повтор тега value.
Box(value: Identifier, value: Identifier) // Ошибка и при одинаковых проверках.
Box(value: Expression & Identifier)       // Допустимая форма пересечения.
```

Ошибка обнаруживается при статической проверке тегов, до сопоставления. Примеры предполагают объявленное одиночное место value совместимого типа. В третьей форме оба ограничения проверяют одного ребёнка; обычные проверки совместимости, невозможности и избыточности сохраняются. Например, если Identifier является подтипом Expression, проверка Expression избыточна.

Уникальность проверяется отдельно для каждого именованного списка. Во вложенных узлах или отдельных операндах пересечения один и тот же тег может встречаться независимо:

```text
Box(value: Box(value: Identifier)) // Разные списки; повторного тега нет.
Box(value: Expression) & Box(value: Identifier) // Разные списки.
```

Вложенный пример предполагает схему Box с местом value типа Node. Ограничение относится к проверкам детей в шаблоне; назначение детей в результате этим решением не определяется.

### 9.3. Символьные литералы и диапазоны

```text
'a'             // Character<"a">.
'я'             // Один Character.
'😀'            // Один Character, хотя в UTF-16 две кодовые единицы.
'a..c'          // Один Character: a, b или c.
'c..a'          // То же множество.
'a..a'          // То же, что 'a'; предупреждение не требуется.
'а..я'          // Кириллические буквы этого интервала; ё не входит.
```

Диапазон включает обе границы, определяется числовыми кодами Unicode и не зависит от локали. Обе границы должны быть скалярными значениями. Интервал может пересекать суррогатную область, но её значения исключаются. `e` и отдельный комбинируемый акцент — два Character; предсоставленный `é` — один. Нормализации нет.

В одинарных кавычках допустим один символ либо символ, две буквальные точки-разделителя и второй символ. Каждая граница декодируется по правилам символьного литерала:

```text
'\''                    // Одинарная кавычка.
'\\'                    // Обратная косая черта.
'"'                     // Двойная кавычка.
'\n'                    // LF; также разрешены \r и \t.
'\u{1F600}'             // 😀.
'\t..\r'                // U+0009–U+000D включительно.
'\u{D7FF}..\u{E000}'    // Только две допустимые границы, без суррогатов.
'.'                     // Одна точка.
'....'                  // Точка + .. + точка; эквивалентно '.'.
'..'                    // Ошибка: ни символ, ни диапазон.
'.....'                 // Ошибка: лишняя точка.
'\u{D800}'              // Ошибка: суррогат.
```

Неизвестный escape, буквальный перевод строки, недопустимая Unicode-граница и лишние символы — ошибки DSL.

### 9.4. Захваты символов

```text
'a'<$letter> -> Identifier<$letter>;
'a..z'<$letter> -> Identifier<$letter>;
'a..z'<$text+>+ -> Identifier<$text>;
'a..z' as letter
'a..z'+ as letters
```

`<$letter>` получает строку фактически встретившегося символа. `as letter` захватывает сам узел, `as letters` после `+` — список. В `$text+` плюс обозначает аккумулятор; внешний `+` обозначает повторение. `'a'<$letter>` равнозначно `Character<"a", $letter>`.

Символьные шаблоны участвуют в общих операциях языка. `!'a'` может принять узел другого типа; только другие символы проверяются через `Character & !'a'`.

### 9.4.1. Фильтр после символа или диапазона (D410)

После символьного литерала или диапазона разрешён обычный фильтр данных: условие, захват или условие с захватом. Условие проверяет сериализованные данные фактического Character и дополняет ограничение литерала или диапазона, а не заменяет его.

~~~text
'a..z'<!"q", $letter> // Строчная латинская буква, кроме q; захват её строки.
'a'<$letter>         // Как Character<"a", $letter>.
'a..z'<startsWith("a")> // Совпадает только с a.
'a'<"b">             // Разбор допустим, но шаблон доказанно невозможен.
~~~

Первый шаблон совпадает с r и связывает letter="r"; q не совпадает из-за фильтра, A — из-за диапазона. Последний пример отвергается статическим анализом до сопоставления. Доступность захватов и ограничения аккумуляторов остаются общими для языка.

### 9.4.2. Без проверки детей после символа или диапазона (D411)

После символьного литерала или диапазона запрещены позиционные и именованные проверки детей, включая пустые списки и запись после фильтра данных.

~~~text
'a'[]              // Ошибка синтаксиса.
'a..z'[]           // Ошибка синтаксиса.
'a'()              // Ошибка синтаксиса.
'a'<$letter>[]     // Ошибка синтаксиса.
Character<"a">[]   // Допустимая явная форма проверки узла.
~~~

Ошибки обнаруживаются при синтаксическом анализе, до сопоставления. Последняя форма сохраняет обычный смысл проверки типа, данных и отсутствия детей. Кратность и as после символьного шаблона остаются разрешены по общим правилам.

### 9.5. Строковый шаблон цепочки

```text
"public" -> PublicModifier;
// Эквивалентная запись:
'p', 'u', 'b', 'l', 'i', 'c' -> PublicModifier;
```

Строка в позиции шаблона разворачивается в последовательность Character после проверки и снятия экранирования. Строка внутри `<...>` проверяет данные одного узла. Эти два контекста не взаимозаменяемы.

```text
"a\nb"       // Три Character: a, LF, b.
"\\n"        // Два Character: обратная косая черта и n.
"\u{1F600}"  // Один Character.
"a..z"       // Четыре Character; это не диапазон.
""           // Ошибка в позиции шаблона, даже внутри непустой цепочки.
```

Проверка границ слова не добавляется автоматически: `"public"` само по себе может найти эти символы внутри более длинной цепочки.

Кратность применяется ко всей декодированной строке:

```text
"ab"+             // ('a', 'b')+.
"ab"?             // Ноль или одна полная пара ab.
"ab" as xs        // Список двух узлов.
"a" as x          // Один узел.
"a"+ as xs        // Список даже при одном фактическом элементе.
"ab"? as xs       // Пустой список либо пара.
"a"? as x         // Необязательный одиночный узел.
"public"<$text> -> Keyword<$text>;
"ab"<$text+>+ -> Token<$text>;
```

Обычный захват строки связывает всё её содержимое как одно значение, а не требует равенства отдельных символов. Аккумулятор добавляет данные каждого исходного Character; для `ababab` последнее правило даёт `"ababab"`. Общие запреты обычных захватов под `?`, `*`, `+` сохраняются.

### 9.5.1. Запрет проверки детей после строки (D407)

Непосредственно после строкового шаблона запрещена проверка детей — как позиционная, так и именованная, включая пустые списки. Ограничение не зависит от числа символов строки (D407). Строковый шаблон обозначает цепочку Character, а не отдельный родительский узел для проверки детей.

```text
"ab"[Identifier]  // Ошибка синтаксиса.
"a"[]             // Ошибка синтаксиса даже для одного символа.
"a"()             // Ошибка синтаксиса: именованная форма тоже запрещена.
Character<"a">[]   // Допустимая явная проверка одного узла.
"ab"<$text>       // Захват данных сохраняется.
"ab"+ as xs       // Кратность и захват узлов сохраняются.
```

Недопустимые формы отвергаются при синтаксическом анализе до сопоставления. Character<"a">[] проверяет один узел Character с данными "a" и отсутствием фактических детей. Проверка детей также не разрешается после захвата данных строки: "ab"<$text>[] является синтаксической ошибкой.

Разрешённые захват данных, кратность и as после строки сохраняют смысл §9.5 и прежние статические ограничения. Решение не меняет синтаксис символьного литерала в одинарных кавычках и не разрешает пустую строку в позиции шаблона.

### 9.5.2. Только захват данных после строки (D412)

У строкового шаблона в двойных кавычках разрешены только формы захвата данных <$text> и <$text+>. Произвольный фильтр условия, в том числе условие вместе с захватом, запрещён. Ограничение действует также для строки из одного символа.

~~~text
"ab"<$text>              // Захват строки "ab" при совпадении.
"ab"<$text+>+            // Накопление данных совпавших повторений.
"ab"<startsWith("a")>    // Ошибка синтаксиса.
"ab"<true, $text>        // Ошибка синтаксиса.
"a"<!"b">               // Ошибка синтаксиса.
'a'<!"b">               // Допустимый символьный фильтр по D410.
~~~

Для входа ababab второе выражение накапливает "ababab". Обычные ограничения захватов под необязательностью и повторениями сохраняются. Двойные кавычки задают шаблон цепочки; одинарные — символьный шаблон. Условие после строки отвергается при синтаксическом анализе, а несовпадение допустимой строки — при выполнении.

## 10. Выражения данных

### 10.1. Фильтр и захват

```text
Identifier<condition, $name>
Identifier<condition, $text+>
Identifier<condition>
Identifier<$name>
Identifier<$text+>
Identifier<>                       // Ошибка: пустой фильтр.
```

`condition` — булево условие. Захват сохраняет исходную строку getData(), даже если проверка использует преобразованную строку. При ложном условии нет совпадения и вклада в захваты.

```text
Identifier<toLowerCase() == "count", $name>
    -> Variable<$name.toUpperCase()>;
```

На данных `"Count"` проверяется `"count"`, захватывается `"Count"`, создаётся Variable с `"COUNT"`.

`data()` возвращает исходную строку текущего узла и доступна только внутри его фильтра. `Identifier<"count">` — краткая проверка `Identifier<data() == "count">`; `Identifier<!"count">` проверяет неравенство. Произвольная строка не становится булевым значением автоматически.

### 10.1.1. Краткие строковые проверки (D380)

В условии фильтра отдельный строковый литерал, в том числе в группирующих скобках, является краткой проверкой равенства текущих сериализованных данных этому литералу. Сокращение разрешено в целом условии и в операндах логических !, & и |. Это синтаксическое сокращение, а не неявное преобразование строки в boolean (D380).

Сначала выражение разбирается с приоритетами §13.2: вызовы и цепочки методов связываются сильнее !. Затем в позиции условия литерал заменяется на data() == литерал; группировка сохраняет этот контекст, а !, & и | передают его своим операндам. В получателе метода, аргументе вызова, конкатенации и операндах сравнения литерал остаётся строковым значением. Прочие выражения в позиции условия должны иметь булев тип. Скобки не меняют строковый тип выражения, используемого как получатель метода или операнд сравнения.

```text
Identifier<!"x">             // !(data() == "x").
Identifier<"a" | "b">         // (data() == "a") | (data() == "b").
Identifier<("a")>             // data() == "a".
Identifier<!"a".isEmpty()>    // !("a".isEmpty()), всегда true.
Identifier<data() == "a">    // Явное сравнение строк.
Identifier<("a" | "b") & !"x"> // Логическая композиция кратких проверок.
```

Для данных "a" проверка "a" | "b" успешна; для "c" — нет. ("a") совпадает только с данными "a". !"x" совпадает с любыми данными, кроме "x". !"a".isEmpty() не зависит от данных: метод получает буквальную строку "a", возвращает false, отрицание даёт true. По-прежнему отдельно проверяется тип узла Identifier.

```text
Identifier<data() == $prefix + "a"> // Допустимо при доступном prefix.
Identifier<$prefix + "a">           // Ошибка типов: строка вместо условия.
Identifier<("a" + "b")>             // Ошибка типов, даже для константной строки.
Identifier<"a".toUpperCase()>       // Ошибка типов: результат метода — строка.
Identifier<("a").isEmpty()>         // Булево выражение, всегда false.
```

Ошибка строкового выражения вместо условия обнаруживается при компиляции, а ложный допустимый фильтр означает несовпадение при выполнении. Доказанно невозможные шаблоны дополнительно подчиняются общим статическим проверкам. Краткая форма захвата Identifier<$name> сохраняется: это захват по §10.1, а не преобразование строки в условие. В результате правила строковые выражения по-прежнему задают данные; сокращение проверки к ним не применяется.

### 10.1.2. Запрет завершающей запятой в данных (D387)

Завершающая запятая на уровне угловых скобок <…> запрещена как в фильтре шаблона, так и в данных результата (D387). Фильтр содержит одну часть — условие либо захват — или две части с фиксированными ролями: условие, затем захват. Это не произвольный список аргументов. Результат содержит одно строковое выражение данных.

```text
Identifier<"a", $name>   // Допустимо: условие и захват.
Identifier<"a">          // Допустимо: только условие.
Identifier<$name>        // Допустимо: только захват в шаблоне.
Identifier<"a",>         // Ошибка синтаксиса.
Identifier<"a", $name,>  // Ошибка синтаксиса.
Identifier<$name,>       // Ошибка синтаксиса.
// В позиции результата:
Identifier<"a",>         // Ошибка синтаксиса.
Identifier<"a">          // Допустимая форма данных результата.
```

На узле Identifier с данными "a" первый шаблон совпадает и связывает name="a"; с данными "b" он не совпадает. Все отмеченные лишние запятые отвергаются синтаксическим анализом при компиляции, до сопоставления или построения результата. Обычные требования к типам, доступности захватов и схемам сохраняются.

Запрет относится к запятой самой конструкции <…>, а не к вложенным вызовам: Identifier<startsWith("a",), $name> остаётся допустимым по D386; Identifier<startsWith("a",), $name,> ошибочен из-за последней запятой фильтра. Аналогично результат Identifier<toString(123,)> синтаксически допустим, а Identifier<toString(123,),> — нет.

### 10.2. Три типа выражений

| Тип | Операции |
|---|---|
| Строка | `+` для конкатенации, `==`, `!=`, строковые методы |
| Целое произвольной точности | Бинарные `+`, `-`, унарный `-`, все шесть сравнений |
| Булево значение | `!`, `&`, `|`, `==`, `!=` |

Это типы выражений, а не datatype узлов. Захваченные данные всегда строковые. Нет неявных преобразований, лексикографического порядка строк или побитовых операций.

```text
"item" + 1                         // Ошибка типов.
"item" + toString(1)               // "item1".
"12" == 12                         // Ошибка типов.
$name.substring(0, $name.indexOf(":"))
$name.charAt($name.length() - 1)
```

`toString(value)` принимает ровно один аргумент: строка сохраняется, число записывается десятично без локали и разделителей, булево значение — как `"true"` или `"false"`. Числовые операции не переполняются в машинный int. Унарный плюс не предусмотрен.

### 10.2.1. Ведущие нули в целых выражениях (D381)

В десятичной целочисленной записи выражений данных ведущие нули разрешены и не меняют основание счисления: 01 имеет значение 1, 010 — значение 10, 000 — значение 0. Восьмеричная интерпретация по начальному нулю не применяется (D381).

Минус остаётся отдельным унарным оператором: -01 означает отрицание числа 1. Ранее установленный запрет унарного плюса сохраняется; +1 в позиции выражения является синтаксической ошибкой. Значения целых имеют произвольную точность по §10.2.

```text
Identifier<length() == 01>  // Длина равна 1.
Identifier<length() == 010> // Длина равна 10, не 8.
Identifier<length() == 000> // Пустые данные.
Identifier<length() == +1> // Ошибка синтаксиса: унарный плюс запрещён.
```

Identifier с данными "a" соответствует первому фильтру, а с данными "ab" — нет. Данные длиной 10 соответствуют второму фильтру; длиной 8 — нет. Эти результаты определяются при сопоставлении, если программа прошла статический анализ. Запись числа в исходнике не сохраняется в значении: toString(0010) даёт "10". Правило относится к числовым выражениям DSL, а не к разбору строк пользовательским datatype.

### 10.2.2. Булевы литералы (D382)

В выражениях данных разрешены булевы литералы true и false, строго в нижнем регистре (D382). True и FALSE булевыми литералами не являются. Литерал имеет булев тип; строка в кавычках остаётся строкой и в позиции условия подчиняется правилу краткой проверки D380.

```text
Identifier<true>    // Проверка данных всегда выполнена; тип Identifier всё ещё проверяется.
Identifier<false>   // Ошибка компиляции: заведомо невозможный шаблон.
Identifier<"true">  // data() == "true", проверка строковых данных.
Identifier<True>    // Ошибка: True не булев литерал и не допустимое выражение здесь.
Identifier<FALSE>   // Та же ошибка.
```

Identifier<true> допускает любые данные узла Identifier. Identifier<"true"> совпадает с данными "true", но не с "false" или "True". Identifier<false> синтаксически разбирается как фильтр с булевым литералом false, однако отвергается статическим анализом как доказанно невозможный шаблон; это не ошибка лексики и не отложенный отказ при сопоставлении.

Слова true и false зарезервированы и не могут служить именами типов, тегов и захватов по D391 (§2.2.1).

### 10.2.3. Полная форма числового литерала (D390)

Числовой литерал выражения DSL состоит из одной или более цифр ASCII 0–9: [0-9]+. Основание всегда десятичное; ведущие нули разрешены по D381. Значение — целое произвольной точности. Знак минус является отдельным унарным оператором, а унарный плюс запрещён (D390).

```text
123     // Допустимо: 123.
00123   // Допустимо: 123.
0xFF    // Ошибка: шестнадцатеричной формы нет.
0b101   // Ошибка: двоичной формы нет.
1_000   // Ошибка: разделители цифр не разрешены.
1.5     // Ошибка: дробной формы нет.
1e3     // Ошибка: экспоненциальной формы нет.
```

Эти примеры рассматриваются как целые выражения в позиции числового значения, например справа от == в Identifier<length() == …>. При значении 00123 фильтр сравнивает длину с числом 123. Недопустимые формы отвергаются при компиляции до сопоставления; они не преобразуются молча в десятичное число и не обрезаются до начального числового токена. Лексер распознаёт допустимые токены по D384; если ошибочная запись разбивается на несколько токенов, синтаксический анализ всё равно отвергает её как выражение. Точный код диагностики относится к Q31.

Ограничение относится к числовым выражениям DSL. Содержимое строк не ограничивается этой лексемой: "0xFF", "1.5" и "1e3" являются строками, а их возможный разбор в данные узла определяется соответствующим datatype. Не-ASCII цифры не образуют числовой литерал DSL.

### 10.3. Строковые методы

Ниже сигнатуры методов на строковом получателе `s`. В фильтре его можно опустить: `length()` означает `data().length()`. В результате источник строки указывается явно. Строковые аргументы принимают любые корректные строковые выражения.

| Метод | Результат и граничные случаи |
|---|---|
| `s.length()` | Число кодовых точек Unicode |
| `s.isEmpty()` | Проверка пустой строки |
| `s.charAt(i)` | Одна кодовая точка как строка; неверный индекс даёт `""` |
| `s.substring(start, end)` | Интервал с включённым start и исключённым end |
| `s.substring(start)` | Остаток до конца строки |
| `s.startsWith(text)` | Проверка префикса |
| `s.endsWith(text)` | Проверка суффикса |
| `s.contains(text)` | Поиск подстроки |
| `s.indexOf(text)` | Первая позиция или −1 |
| `s.lastIndexOf(text)` | Последняя позиция или −1 |
| `s.replace(old, new)` | Все неперекрывающиеся буквальные вхождения слева направо |
| `s.replaceFirst(old, new)` | Первое буквальное вхождение |
| `s.trim()` | Удаление допустимых пробельных символов с обоих краёв |
| `s.trimStart()`, `s.trimEnd()` | То же только с начала или конца |
| `s.concat(text)` | Конкатенация, как `s + text` |
| `s.toLowerCase()`, `s.toUpperCase()` | Преобразование регистра Unicode без локали |

Для любого строкового выражения s также разрешены toLowerCase(s) и toUpperCase(s) (D394, §10.3.3). Цепочки методов работают на результате предыдущего вызова:

```text
Identifier<toLowerCase().startsWith("get"), $name>
    -> Variable<$name.substring(3).toLowerCase()>;
Identifier<$prefix>, Identifier<startsWith($prefix.toLowerCase())>
"abc".toUpperCase()
($prefix + $name).toLowerCase()
```

Второй пример — фрагмент шаблона, следующие два — выражения данных.

### 10.3.1. Завершающая запятая в аргументах (D386)

В непустом списке аргументов функции или метода разрешена одна завершающая запятая перед закрывающей круглой скобкой. Она не создаёт дополнительный аргумент и не меняет число или типы переданных значений (D386). Разрешение применяется к допустимым формам вызовов; оно не вводит новые функции, методы или перегрузки.

```text
toString(123,)          // "123", как toString(123).
$name.substring(0, 3,)  // Как $name.substring(0, 3).
$name.length()          // Корректный вызов без аргументов.
$name.length(,)         // Ошибка синтаксиса: нет последнего аргумента.
toString(123,,)         // Ошибка синтаксиса: двойная запятая.
$name.substring(, 3)   // Ошибка синтаксиса: отсутствует первый аргумент.
```

При $name = "abcd" вызов $name.substring(0, 3,) возвращает "abc". Пустой список аргументов записывается только как (). Пустые элементы и повторная завершающая запятая отвергаются синтаксическим анализом при компиляции. После синтаксического разбора сохраняются обычные проверки сигнатур: например, toString(123, 456,) содержит два аргумента и ошибочен по их количеству.

### 10.3.2. Контекстность имён встроенных функций и методов (D393)

Имена встроенных функций и методов (например, length, data, toString и toUpperCase) не резервируются глобально. Они доступны как обычные имена типов, тегов и захватов при соблюдении общих ограничений имён. В позиции вызова выражения данных они сохраняют встроенный смысл; одноимённое объявление или захват не переопределяет функцию или метод (D393).

```text
node length;                  // Ошибка: имя типа начинается со строчной буквы (D414).
node Box(length: Node);       // Допустимое имя тега.
Identifier<$length>           // Допустимый захват данных.
Identifier as length          // Допустимый захват узла.
Identifier<length() == 3>      // Встроенная проверка длины.
Identifier<$length>, Identifier<length() == $length.length()>
```

Примеры независимы и предполагают необходимые объявления. В последней цепочке первый Identifier захватывает строку length; у второго length() возвращает длину его собственных данных, а $length.length() — длину ранее захваченной строки. При данных "abc" и "xyz" цепочка совпадает, при "abc" и "xy" — нет.

Неизвестное имя вызова, например unknownFunction() в фильтре, остаётся ошибкой компиляции при проверке выражений: объявление одноимённого типа не создаёт функцию. Разрешение имён не добавляет новых форм вызовов и перегрузок; их таблица остаётся предметом Q09.

### 10.3.3. Строковое выражение в свободном преобразовании регистра (D394)

Свободные формы toUpperCase(s) и toLowerCase(s) принимают любое корректное строковое выражение s, а не только захват. Они эквивалентны соответственно (s).toUpperCase() и (s).toLowerCase(), возвращают строку и сохраняют ранее согласованные правила Unicode без локали (D394).

```text
toUpperCase($prefix + $name)      // Как ($prefix + $name).toUpperCase().
toLowerCase("HELLO")             // "hello".
toUpperCase("a".concat("b"))     // "AB".
toUpperCase(123)                 // Ошибка типов.
toLowerCase(true)                // Ошибка типов.
```

При доступных захватах prefix="pre" и name="fix" первый вызов возвращает "PREFIX". Числа и булевы значения не преобразуются в строку неявно: недопустимый тип аргумента обнаруживается при компиляции при проверке выражений.

Форма с одним явным строковым аргументом доступна в выражениях фильтра и данных результата при соблюдении правил доступности захватов. В фильтре строковый результат сам по себе не становится условием: Identifier<toLowerCase("HELLO")> ошибочен по типу, а Identifier<data() == toLowerCase("HELLO")> проверяет равенство данных строке "hello". Ранее разрешённые вызовы без аргументов внутри фильтра по-прежнему используют данные текущего узла. Для остальных строковых методов свободная форма с явным получателем согласована в D396 (§10.3.5).

### 10.3.4. Метод toString() (D395)

Метод toString() разрешён на строковом, числовом и булевом получателе выражения данных. Он не принимает аргументов и эквивалентен свободной функции toString(value) с тем же значением получателя (D395). Результат всегда строка. Для строки возвращается её значение без изменений; числа преобразуются без локали и разделителей, булевы значения — в "true" или "false" по ранее согласованным правилам.

```text
toString($name.length())     // Свободная функция.
$name.length().toString()    // Равнозначный метод.
"hello".toString()           // "hello".
(123).toString()             // "123".
true.toString()              // "true".
$name.length().toString(10)  // Ошибка: у метода нет аргументов.
```

При name="abc" первые два выражения возвращают "3". Метод доступен в выражениях фильтров и данных результата с обычными ограничениями доступности захватов. Вызов на захваченном узле или списке узлов ошибочен по типу: D395 не вводит сериализацию деревьев через toString(). Ненулевое число аргументов метода отвергается при компиляции при проверке сигнатуры.

Строковый результат не становится булевым условием: Identifier<true.toString()> ошибочен по типу; Identifier<data() == true.toString()> проверяет данные на равенство "true". Решение не добавляет свободную форму toString() без аргументов: ранее согласованная функция по-прежнему требует один явный аргумент.

### 10.3.5. Свободная форма строковых методов (D396)

Для всех согласованных строковых методов разрешена свободная форма с явной строкой первым аргументом: s.method(args) равнозначно method(s, args). Строка s может быть любым корректным строковым выражением; остальные аргументы, результат и граничные случаи сохраняют контракт исходного метода (D396).

```text
length($name)                    // $name.length().
startsWith($name, "get")         // $name.startsWith("get").
substring($name, 1, 3)           // $name.substring(1, 3).
substring($name, 1)              // $name.substring(1).
replace($name, "a", "b")         // $name.replace("a", "b").
trim($prefix + $name)            // ($prefix + $name).trim().
length(123)                     // Ошибка типов: получатель должен быть строкой.
```

При name="getName" length($name) возвращает 7, startsWith($name, "get") — true, substring($name, 1, 3) — "et". Неверные типы и число аргументов отвергаются при компиляции при проверке сигнатуры; неявное преобразование числа или boolean в строку не добавляется.

Правило распространяется на length, isEmpty, charAt, обе формы substring, startsWith, endsWith, contains, indexOf, lastIndexOf, replace, replaceFirst, trim, trimStart, trimEnd, concat, toLowerCase и toUpperCase из §10.3. Метод toString() и свободная функция toString(value) сохраняют отдельный контракт D395 для строки, числа и boolean. data() сохраняет прежний контракт доступа к данным текущего узла; новых форм data(s) или s.data() это решение не вводит.

Внутри фильтра сохраняются вызовы строковых методов с неявным получателем data(): startsWith("get") проверяет данные текущего узла, length() возвращает их длину. Свободная форма с явной строкой доступна также в данных результата. В результате опускать получатель нельзя.

```text
Identifier<startsWith("get"), $name>
    -> Variable<substring($name, 3)>;
Identifier<substring(1, 3) == "et">  // Неявная строка: данные текущего узла.
Identifier<substring("get", 1) == "et"> // Явная строка "get".
```

В последнем примере условие не зависит от данных, но тип Identifier всё ещё проверяется. В предпоследнем примере данные "get" проходят фильтр, а "got" — нет. При исходных данных "getName" первое правило строит Variable с данными "Name", если объявления типов и схема допускают такое построение. Различие явной и неявной формы определяется согласованными сигнатурами вызовов.

### 10.4. Unicode и полная определённость

Индексы начинаются с нуля и измеряются в кодовых точках: `"A😀Б".length()` равно 3, `charAt(1)` даёт `"😀"`. Нормализации нет: `é` и `e` с отдельным акцентом различаются. Преобразование регистра может менять длину: верхний регистр `straße` — `STRASSE`.

Отрицательная граница substring, выход за длину или start > end дают `""` без обрезания границ. Равные допустимые границы также дают `""`. Огромный целый индекс проверяется как есть, без переполнения. Поиск и замена не используют регулярные выражения.

| Вызов с пустой строкой | Значение |
|---|---|
| `startsWith("")`, `endsWith("")`, `contains("")` | true |
| `indexOf("")` | 0 |
| `lastIndexOf("")` | Длина строки |
| `replace("", text)`, `replaceFirst("", text)` | Исходная строка |

Trim удаляет только U+0020, TAB, LF и CR. Неразрывный пробел остаётся. Все встроенные операции чисты и полностью определены на допустимых значениях своих типов. Короткое замыкание `&` и `|` — возможная оптимизация; порядок вычисления независимых операндов не является наблюдаемым контрактом.

### 10.5. Область видимости данных

```text
Identifier<$name.length() == 3, $name>
Identifier<length() == 3, $name>
```

Это равнозначные фильтры: обычный захват того же узла может участвовать в условии. Ссылки на обычные данные могут предшествовать их связывающему вхождению в тексте правила; проверяется целый кандидат.

```text
Identifier<startsWith($prefix)>, Identifier<$prefix> -> Marker;
Identifier<$name> -> Variable<$name.toLowerCase()>; // Допустимо.
Identifier<$name> -> Variable<toLowerCase($name)>;  // Допустимо.
Identifier<$name> -> Variable<toLowerCase()>;       // Ошибка: нет текущего узла.
Identifier<$name> -> Variable<data()>;             // Та же ошибка.
```

Имя должно быть связано в том же правиле с соблюдением ограничений захватов. Это не разрешение читать промежуточное значение аккумулятора в шаблоне.

## 11. Захваты, логика и повторения

### 11.1. Категории захватов и область as

```text
Expression as x
Expression? as maybe
Statement* as items
Statement+ as nonempty
Identifier<$text> as item
```

`as` захватывает исходный узел целиком либо список узлов; `<$text>` — строковые данные. Имена всех категорий общие в пределах правила. `Identifier<$x> as x` — конфликт категорий. Неизвестное имя ошибочно; повторная подстановка разрешена, захват не расходуется. Неиспользуемый захват допустим и продолжает участвовать в сопоставлении.

`as` относится к ближайшему шаблону, включая его кратность. Скобки расширяют область:

```text
A | B as x       // A | (B as x), не захват всей альтернативы.
A, B as x       // A, (B as x).
A & B as x      // A & (B as x).
(A | B) as x    // Вся альтернатива.
(A, B) as xs    // Вся цепочка, список.
(A & B) as x    // Весь одноузловой шаблон.
(Identifier as x) as y // Два имени одного вхождения; допустимо.
(Identifier as x) as x // Ошибка повторного объявления.
```

Первые строки объясняют разбор; доступность захватов проверяется отдельно. Скобки не меняют категорию: `(Identifier) as x` — один узел, `(Identifier?) as x` — необязательный, `(Identifier+) as xs` — список.

### 11.2. Обычные данные и аккумуляторы

```text
Identifier<$name>, Identifier<$name> -> Token<$name>;
```

Повторное имя обычных данных требует равенства строк. `"a", "a"` подходят; `"a", "b"` — нет. Повторное объявление узла через `as` не является сравнением узлов.

Аккумулятор `$text+` начинает с `""`, собирает только явно отмеченные данные и доступен в результате как `$text`. В шаблоне одно имя нельзя одновременно накапливать и читать или связывать обычным способом. Разные имена могут использовать разные режимы.

```text
Character<$text+>+ -> Token<$text>;
Start, Character<$text+>* -> Token<$text>; // Только Start: text = "".
Character<$text+>+, '!' -> Token<$text>;   // a,b,! дают "ab".
Character<$text+>+, Identifier<$text> -> Token<$text>; // Ошибка.
```

Возвращённые при подборе части не оставляют вклада. Отвергнутый кандидат не меняет аккумуляторы другого кандидата.

Порядок накопления определяется исходным деревом: родитель перед потомками, дети слева направо в порядке схемы и элементов групп. Корни фрагмента также идут слева направо, независимо от стрелки. Это порядок данных, а не порядок преобразующего обхода.

```text
Box<$text+>[Item<$text+>[Leaf<$text+>], Item<$text+>]
    -> Token<$text>;
```

При данных Box=`A`, первого Item=`B`, Leaf=`C`, второго Item=`D` получается `ABCD`.

### 11.3. Кратности и вложенные захваты

| Форма | Смысл |
|---|---|
| `P?` | Ноль или одно совпадение P |
| `P*` | Ноль или более повторений P |
| `P+` | Одно или более повторений P |
| `(A, B)+` | Повторение всей пары |
| `(A, B)? as xs` | Пустой список либо два узла |

Каждое тело `*` или `+` должно поглощать хотя бы один узел. Полный шаблон правила также обязан иметь положительное минимальное потребление. Это независимые ограничения.

```text
Start, Identifier* -> Marker;               // Допустимо.
Identifier* -> Marker;                      // Ошибка: полный шаблон может быть пустым.
Start, (Identifier? | Number)* -> Marker;   // Ошибка: пустая итерация.
Identifier+?                               // Ошибка: два суффикса подряд.
Start, (Identifier+)? -> Marker;            // Явная вложенность допустима.
(A | )                                     // Ошибка: пустая ветка.
Start, () -> Marker;                        // Ошибка: пустая группа.
```

Под `*` и `+` обычные захваты узлов, списков и данных запрещены на любой глубине; разрешены аккумуляторы и внешний захват повторения целиком. Под `?` обычные данные запрещены, но захваты узлов и списков разрешены: отсутствующая часть даёт отсутствующий узел либо пустой список.

```text
Block[Return(value: Expression as x)*]       // Ошибка: as внутри *.
Block[Return(value: Expression)* as items]  // Захват всего повторения.
Start, Identifier<$name>? -> Token<$name>;  // Ошибка: обычные данные под ?.
Start, Identifier<startsWith("get")>? -> Marker; // Проверка разрешена.
Start, (Identifier+ as items, Colon)? -> Container[$items];
```

В последнем правиле `items` может быть пустым из-за внешнего `?`, хотя внутренний захват использует `+`. Проверки с чтением обычных данных, связанных вне необязательной части, разрешены.

Вложенные повторения допустимы при однозначном разбиении:

```text
(Open, Identifier*, Close)+ as items -> Container[$items];
(Identifier+)+ as items -> Container[$items]; // Ошибка: неоднозначные итерации.
```

Во втором примере два Identifier можно разделить на одну или две внешние итерации. Плоский одинаковый список захвата не устраняет эту неоднозначность.

### 11.4. Альтернативы

`|` допускает узловые шаблоны и цепочки разной длины. На позиции выбирается максимальное **полное** совпадение всего шаблона, с учётом частей до и после альтернативы.

```text
(Identifier | Identifier, Colon) -> Marker;
(Identifier, Colon | IntegerLiteral)+ as items -> Container[$items];
```

На входе Identifier, Colon первое правило поглощает оба узла. Короткая первая ветка не получает преимущества. Повторение во втором правиле захватывает плоский список без границ итераций.

Внешний захват имеет категорию:

| Варианты | Категория |
|---|---|
| Все обязательные одиночные | Один узел |
| Только одиночные, хотя бы один необязательный | Необязательный узел |
| Хотя бы один списочный | Список, даже при одноэлементном совпадении |

Общее внутреннее имя через `as` разрешено в разных ветках: каждая должна объявить его ровно один раз, категории должны быть совместимы, а подстановка — подходить для всех вариантов. Обязательный и необязательный одиночные захваты объединяются в необязательный. Смешивать список, узел и данные нельзя.

```text
(Identifier as x | IntegerLiteral as x) -> Argument[$x];
(Box(value: Expression as x) | Wrapper(value: Expression as x))
    -> Argument[$x];
```

`Argument` должен принимать все возможные типы. Разные конкретные Box и Wrapper не могут одновременно совпасть на одном узле; одинаковое имя тега не требует одинакового индекса ребёнка в этих типах.

Обычный захват данных должен присутствовать **во всех** ветках, даже если читается лишь внутри собственной ветки. Аккумулятор может присутствовать в части веток.

```text
(Identifier<$text> | IntegerLiteral<$text>) -> Token<$text>;
(Identifier<$text> | IntegerLiteral) -> Token<$text>; // Ошибка.
(Identifier<$text+> | Separator)+ -> Token<$text>;
```

### 11.5. Несколько совпавших веток

Само совпадение нескольких веток не является неоднозначностью. Сначала каждая ветка проверяется в составе полного варианта всего шаблона, включая фильтры и равенство повторных данных (§11.12). Для оставшихся полных совпадений одинаковой максимальной длины проверяется согласованность обычных захватов:

| Категория | Когда значения согласованы |
|---|---|
| Данные | Одинаковые строки |
| Узел | То же исходное вхождение |
| Необязательный узел | Два отсутствия либо то же присутствующее вхождение |
| Список | Те же вхождения в том же порядке и количестве |

Структурно равные узлы в разных местах — разные вхождения. Даже общий неизменяемый Java-объект в двух местах не делает места одним.

```text
(Expression | Identifier) as x
(Expression<$text> | Identifier<$text>) -> Token<$text>;
```

Для Identifier, наследующего Expression, обе ветки согласованы. Напротив, захват разных детей одного Pair конфликтует, даже если дети равны по структуре. Для обычных данных двух детей достаточно равенства строк.

При конфликте обычных захватов кандидат отвергается до построения. Статически доказанная неоднозначность узловых или списочных захватов — ошибка компиляции; недоказанная проверяется на входе.

При согласованных обычных захватах вклад **аккумуляторов** берётся из первой совпавшей ветки слева направо среди максимальных полных совпадений. Остальные ветки не добавляют данные. Отказ построения не позволяет выбрать другую ветку.

```text
(Identifier<$text+> | Expression)+ -> Token<$text>;
(Expression | Identifier<$text+>)+ -> Token<$text>;
```

Если Identifier — подтип Expression, в первом правиле его данные накапливаются, во втором — нет. Направление стрелки порядок веток не меняет.

### 11.6. Отрицание

`!P` проверяет один существующий текущий узел и поглощает его при обычном несовпадении P. Операнд обязан описывать ровно один узел. На пустом входе отрицание не срабатывает.

```text
!(Identifier<"if">)        // Любой узел, кроме Identifier с данными if.
Identifier<!"if">          // Только Identifier с другими данными.
!(Box[Expression])         // Отрицание полной проверки Box и его детей.
!(Identifier, Colon)       // Ошибка: операнд — цепочка.
!(Identifier?)             // Ошибка: операнд допускает отсутствие.
(!Identifier) as x         // Один узел; статический базовый тип Node.
(!!Identifier) as x        // Тип x уточняется до Identifier.
```

Внутри отрицания запрещены все объявления захватов на любой глубине, включая аккумуляторы. Внешний захват разрешён. В условиях можно читать обычные данные, связанные вне отрицания:

```text
Identifier<$name>, !(Identifier<data() == $name>) -> Token<$name>;
!(Identifier<$name>)       // Ошибка: это захват, не чтение.
!!(Identifier as x)        // Ошибка сохраняется под двойным отрицанием.
```

Неоднозначность операнда **не становится успехом отрицания**: она отвергает весь кандидат, в том числе при двойном отрицании. Например, `!(Box[Statement*, Return, Statement*])` на двух подходящих Return отвергается из-за неоднозначного распределения.

### 11.7. Пересечение и статические типы

`P & Q` проверяет один и тот же узел обоими одноузловыми шаблонами. Пересечение цепочек и операндов с кратностью 0 или больше 1 запрещено.

```text
(Expression & !Identifier) as x -> Argument[$x];
(Pair(left: Expression as x) & Pair(right: Expression as y))
    -> Result[$x, $y];
```

Захваты разных имён из обоих операндов доступны. Одноимённые узловые и списочные объявления в двух операндах запрещены. Для данных повторное обычное имя требует равенства строк.

Внешний захват сохраняет все гарантии пересечения. Для `(Printable & Named) as x` допустима подстановка и в Printable, и в Named, но не в конкретный Document только потому, что он наследует оба типа. Внутренний захват того же узла также уточняется:

```text
(Expression as x) & Identifier
(Expression & Identifier) as x
```

Оба шаблона гарантируют тип Identifier для x. Ограничение текущего узла нельзя автоматически переносить на другой захваченный узел, например его ребёнка. Доказанное уточнение обязательности и кратности того же дочернего места описано в §11.13.

Для `(Printable & (Named | Numbered)) as x` проверяются оба варианта. Место Printable подходит всегда; место Named подходит, если каждый вариант гарантирует Named, например при Numbered : Named. Наличие только фактического подходящего типа на конкретном входе недостаточно.

### 11.8. Источники накопления при пересечении

Одно исходное вхождение добавляет данные в конкретный аккумулятор не более одного раза. Если тождество источников не доказано статически, оно проверяется при сопоставлении. Равные строки из разных вхождений не объединяются.

```text
(Identifier<$text+> & Identifier<startsWith("a"), $text+>)
    -> Token<$text>;
(Box["ab"<$text+>] & Box['a'<$text+>, 'b'])
    -> Token<$text>;
```

В первом примере `abc` даёт `abc`, не `abcabc`. Во втором получается `ab`, не `aab`: источник строкового шаблона — каждое отдельное вхождение Character. Перестановка операндов пересечения не меняет порядок разных источников в исходном дереве.

Упрощение `P & Q` до Q допустимо лишь при доказанном включении условий и сохранении всех захватов и вкладов. Например, `Identifier & Identifier<startsWith("a")>` можно упростить; удалять `Identifier as x` из `(Identifier as x) & Identifier<startsWith("a")>` с потерей x нельзя. Статические запреты исходного шаблона проверяются до упрощения.

### 11.9. Граница статического запрета неоднозначности

Основание: D373, задача #13.

Само существование неоднозначного входа не является общим основанием для запрета шаблона. Статические запреты применяются к определённым классам: доказанно неоднозначным соседним повторениям без обязательного разделителя, неоднозначному разбиению на итерации и конфликтующим обычным захватам. Для остальных случаев неоднозначность проверяется на конкретном входе. Обязательный разделитель разрешает рассматриваемую конструкцию, но не гарантирует однозначность её совпадения и не отменяет других статических проверок. Здесь обязательность означает положительное минимальное потребление разделяющей части; допускающая пустоту часть сама по себе такой гарантии не даёт.

```text
Block[Statement*, Statement*]          // Ошибка компиляции: соседние повторения.
(Identifier+)+ as xs                   // Ошибка компиляции: границы итераций.
Block[Statement*, Return, Statement*]  // Допустимый шаблон с разделителем.
```

При Return : Statement и остальных детях Statement один Return даёт единственное распределение и успешное сопоставление. Два Return дают два выбора центрального элемента: кандидат отвергается при сопоставлении до построения результата, без ошибки исполнения. Жадность не выбирает один из Return. Ноль Return означает обычное несовпадение.

Для первых двух запрещённых форм достаточно доказанного неоднозначного входа: один Statement можно отдать любому из двух повторений; два Identifier — одной или двум внешним итерациям. Наличие у этих форм других, однозначных входов запрет не снимает.

Это граница классов проверок, а не требование статически решать все возможные случаи неоднозначности. Если неоднозначность не выявлена заранее, сохраняется проверка кандидата на входе. Решения D178, D179 и D285 сохраняются.

### 11.10. Распределение входа и выбор ветки

Основание: D374, задача #13.

Выбор разных веток альтернативы сам по себе не образует разные распределения входа. Различие границ частей или итераций образует разные распределения; одинаковый итоговый плоский захват не устраняет это различие. Согласованность обычных захватов проверяется отдельно по §11.5.

```text
(Identifier | Identifier) as x
(Identifier, Colon | Identifier, Colon) as xs
(Identifier+)+ as xs
```

В первом примере на одном Identifier есть два совпадения веток, но одно распределение: обе ветки поглощают то же вхождение, x одинаков. Шаблон допустим; неоднозначности нет.

Во втором примере на последовательности Identifier, Colon есть два совпадения веток, но одно распределение: одинаковые границы частей и тот же упорядоченный список вхождений xs. Шаблон допустим; неоднозначности нет.

В третьем примере на двух Identifier возможны одна внешняя итерация из двух элементов либо две внешние итерации по одному элементу. Это два распределения с разными границами итераций. Одинаковый список xs их не объединяет; шаблон отвергается при компиляции по D285.

Объединение совпадений одинаковых веток не отменяет проверку обычных захватов и не складывает вклады аккумуляторов разных веток. При конфликте обычных захватов сохраняются статические и динамические проверки §11.5; при согласованных захватах действует выбор вклада аккумуляторов, а не их суммирование. Порядок вложенного выбора определён в §11.11.

### 11.11. Вложенные альтернативы и выбор аккумуляторов

Основание: D375, задача #13.

Вложенные альтернативы рассматриваются в глубину, слева направо. Это порядок выбора веток в структуре шаблона, а не порядок накопления данных исходного дерева. D250 сохраняется: внутри выбранного варианта данные добавляются в порядке посещения исходного родителя до его потомков, дети слева направо.

Полный вариант совпадения удовлетворяет всему шаблону: структуре, фильтрам и требованиям равенства повторных обычных захватов внутри этого варианта (§11.12). Из таких вариантов рассматриваются совпадения максимальной длины; затем проверяется согласованность обычных захватов между ними. Отброшенная по собственным условиям ветка в этом сравнении не участвует. Только после этих проверок выбирается первый вариант в указанном порядке. Для вложенного выбора сначала рассматривается левая внешняя ветка и её вложенные варианты слева направо, затем следующая внешняя ветка. Вариант, не допускающий полного совпадения всего шаблона, в выборе не участвует.

Все аккумуляторы берутся из одного выбранного полного варианта. Полный вариант включает выбор ветки для каждого срабатывания альтернативы, в том числе внутри каждой итерации повторения; это не требование выбирать одну и ту же ветку во всех итерациях. Нельзя независимо выбирать наиболее выгодную ветку для каждого аккумулятора или суммировать вклады разных вариантов. Приоритет веток не скрывает конфликт обычных захватов, не разрешает неоднозначное распределение и не позволяет короткому совпадению вытеснить максимальное. Отказ построения результата не запускает выбор следующего варианта.

```text
((Box(left: Identifier<$a+>) | Box(right: Identifier<$b+>))
 | Box(left: Identifier<$b+>))
    -> Token<$a + ":" + $b>;
```

Для Box с Identifier в обоих местах, left="L" и right="R", есть три полных совпадения одинаковой длины:

| Вариант | a | b | Возможный результат |
|---|---|---|---|
| Левая ветка внутренней альтернативы | "L" | "" | "L:" |
| Правая ветка внутренней альтернативы | "" | "R" | ":R" |
| Правая ветка внешней альтернативы | "" | "L" | ":L" |

Выбирается первый вариант, результат — Token<"L:">. Вклад a из первого варианта и b из второго не объединяются в "L:R".

Контроль с общим обычным захватом данных:

```text
((Box(left: (Identifier<$x> & Identifier<$a+>))
  | Box(right: (Identifier<$x> & Identifier<$b+>)))
 | Box(left: (Identifier<$x> & Identifier<$b+>)))
    -> Token<$a + ":" + $b>;
```

На том же входе обычный x получает "L", "R" и "L" в трёх совпадениях. При сопоставлении кандидат отвергается до выбора аккумуляторов и построения результата. Неиспользование x в результате не отменяет проверку. Если конфликт обычных захватов доказан статически, действует соответствующий запрет компиляции; здесь значения данных конкретного входа проверяются при сопоставлении.

Контроль полноты совпадения:

```text
((Identifier<$a+> | Identifier<$b+>, Colon)
 | Identifier<$b+>), End -> Token<$a + ":" + $b>;
```

На входе Identifier<"L">, Colon, End локально подходящая первая внутренняя ветка не позволяет сопоставить следующий End. Полное совпадение даёт вторая внутренняя ветка; результат — Token<":L">. Это не безусловный выбор первой локально совпавшей ветки.

### 11.12. Связанные фильтры и взаимные ссылки

Основание: D376, задача #13.

Фильтры, читающие обычные захваты данных, проверяются по значениям, связанным всем вариантом сопоставления кандидата. Логическая модель: сначала связать обычные захваты с данными исходных узлов, затем проверить все условия этого варианта, включая равенство при повторении имени. Ссылки вперёд и взаимные ссылки допустимы и не делают результат зависимым от порядка вычисления фильтров.

Это не рекурсивное вычисление значений: захваты получают строки из входного дерева, а фильтры только проверяют их. Реализация вправе менять порядок вычислений и выполнять проверки раньше, если сохраняет тот же результат. Чтение ещё не вычисленного захвата не означает пустую строку или несовпадение.

```text
Identifier<startsWith($b), $a>,
Identifier<endsWith($a), $b>
    -> Token<$a + $b>;
```

| Входные данные | Связанные значения | Проверки | Результат |
|---|---|---|---|
| "a", "a" | a="a", b="a" | Обе истинны | Token<"aa"> |
| "ab", "b" | a="ab", b="b" | Обе ложны: "ab" не начинается с "b"; "b" не заканчивается на "ab" | Несовпадение |

В обоих случаях порядок проверки startsWith и endsWith не влияет на результат. Отказ условий — обычное несовпадение при сопоставлении, а не ошибка исполнения из-за взаимных ссылок.

Через альтернативы каждый вариант проверяется со своими связанными значениями. После проверки условий сравниваются обычные захваты совпавших вариантов по §11.5, с сохранением правил максимальной длины и D375. Значения из разных вариантов нельзя смешивать для удовлетворения условий.

```text
(Identifier<startsWith($b), $a>
 | Identifier<endsWith($b), $a>),
Identifier<endsWith($a), $b>
    -> Token<$a + $b>;
```

Обе ветки объявляют обычный a; обычный b связывается после альтернативы и доступен в её условиях. На входе "a", "a" оба полных варианта совпадают с одинаковыми a и b, результат — Token<"aa">. На входе "ab", "b" левая ветка не проходит startsWith, правая проходит endsWith($b), но общий второй Identifier не проходит endsWith($a). Ни одного полного совпадения нет.

Дополнительный контроль: конфликт между локальными ветками не проверяется до условий всего варианта.

```text
(Box(left: Identifier<$x>) | Box(right: Identifier<$x>)),
Identifier<data() == $x> -> Token<$x>;
```

Если Box содержит left="L", right="R", а следующий Identifier имеет данные "L", полное совпадение есть только через left: результат Token<"L">. Ветка right отвергнута общим последующим фильтром и не создаёт конфликт x. Если убрать следующий Identifier и его проверку, обе ветки Box совпадут с разными x и кандидат будет отвергнут по §11.5.

Сохраняются статические требования к доступности захватов: неизвестное имя и обычный захват, объявленный только в части веток, ошибочны. Взаимные ссылки сами по себе не являются такой ошибкой.

```text
(Identifier<$a> | Identifier), Identifier<endsWith($a), $b>
    -> Token<$a + $b>; // Ошибка компиляции: a объявлен не во всех ветках.
```

Решение относится к обычным данным; запрет чтения аккумулятора в шаблоне и ограничения обычных захватов под ?, * и + сохраняются.

### 11.13. Уточнение вложенных захватов пересечением

Основание: D377, задача #13.

Пересечение может статически уточнять обязательность и кратность вложенного захвата, если анализ доказывает, что ограничение другого операнда относится к тому же дочернему месту того же исходного узла и гарантирует соответствующее свойство захваченного значения при успешном совпадении всего пересечения.

```text
abstract Expression;
node Literal<Int> : Expression;
node Box(value: Expression?);
node Required(value: Expression);

(Box(value: Expression? as x) & Box(value: Expression))
    -> Required[$x];
```

Первый операнд допускает отсутствие x, но второй требует существования того же Box.value. Поэтому в успешном полном совпадении x присутствует: подстановка в обязательный Required.value разрешена при компиляции. Box с ребёнком Literal даёт Required с тем же ребёнком. Box без value не соответствует второму операнду; правило не срабатывает и не пытается построить Required без обязательного ребёнка.

Доказательство должно связывать проверку именно с захваченным местом. Совпадения имени тега у разных исходных узлов или наличия другого ребёнка недостаточно. Отдельный отрицательный пример с объявленным other:

```text
abstract Expression;
node Literal<Int> : Expression;
node Box(value: Expression?, other: Expression?);
node Required(value: Expression);

(Box(value: Expression? as x) & Box(other: Expression))
    -> Required[$x]; // Ошибка компиляции: присутствие x не гарантировано.
```

На Box с отсутствующим value и присутствующим other оба операнда могут совпасть, но x отсутствует. Проверка other не уточняет обязательность value. Без доказанной гарантии сохраняется исходная кратность захвата и обычная проверка её совместимости с местом результата; фактическое наличие value на отдельном входе не оправдывает такую подстановку.

Для групп ограничения того же места также могут уточнять доказанное количество захваченных элементов. При этом нужно доказать гарантию именно для захваченной части: количество элементов всей группы нельзя автоматически приписать захвату её подфрагмента. Уточнение числовой кратности не превращает списочный захват в одиночный узел и не отменяет запрет подстановки списка в одиночное место. Проверка другого места не переносит на захват свои ограничения количества.

Ранее принятое уточнение типа в (Expression as x) & Identifier сохраняется. Для вложенного захвата перенос гарантии требует доказательства связи с тем же местом; один только факт пересечения родительских шаблонов такого доказательства не даёт.

## 12. Построение результата и удаление

### 12.1. Форма результата

Завершающая запятая на уровне <…> данных результата запрещена (D387, §10.1.2).

```text
Identifier<$name> -> Variable<$name>;
Wrapper[Expression as x] -> $x;
Comment -> none;
Wrapper[Node* as xs] -> $xs; // Ошибка: самостоятельный список.
Wrapper(value: Expression? as x) -> $x; // Ошибка: необязательный результат.
```

Допустимы новый узел, обязательный одиночный захват или явное `none`. Узел может содержать любое число детей, разрешённое его схемой. Строка, `chars(...)`, список и объединение нескольких узлов не являются самостоятельным результатом.

Строка в `<...>` результата вычисляется и передаётся parse и validate datatype. Ожидаемый отказ построения отвергает весь кандидат. Данные результата должны быть строковым выражением; числа преобразуются через `toString`.

### 12.1.1. Порядок частей конструктора результата (D397)

В конструкторе нового узла результата установлен порядок: тип → данные → дети. После имени типа может следовать одно выражение данных в угловых скобках, затем один список детей — позиционный либо именованный. Обратный порядок является синтаксической ошибкой компиляции (D397).

```text
Container<"box">[$child]         // Допустимый порядок.
Container<"box">(value: $child)  // Допустимый порядок.
Container[$child]<"box">         // Ошибка синтаксиса.
Container(value: $child)<"box">  // Ошибка синтаксиса.
```

Примеры подразумевают объявленный Container со строковыми данными и одним обязательным местом value, а также доступный обязательный одиночный захват child совместимого типа. Обе допустимые формы строят Container с данными "box" и ребёнком $child в месте value. Обе неверные формы отвергаются до построения результата.

Данные и список детей можно опускать, если это допускает объявление типа и ранее согласованные правила построения. Само разрешение опускать синтаксические части не разрешает терять обязательных детей, не вводит автоматического переноса совпавших узлов и не меняет обработку данных по умолчанию. Сочетание позиционного и именованного списков остаётся запрещено D379.

Продукция конструктора результата (единая грамматика — §13.3):

```ebnf
node-construction = type-name, [ result-data ], [ result-children ];
result-children = positional-result-children | named-result-children ;
```

Здесь result-data содержит одно строковое выражение по правилам результата, а не фильтр шаблона. Синтаксическая допустимость отдельно проверяется на соответствие типам, схеме детей и доступности захватов.

### 12.1.2. Без группировки результата (D398)

Группирующие круглые скобки вокруг самостоятельного результата не разрешены (D398). Предложение добавить их отклонено автором как не имеющее смысла. Результат записывается непосредственно, без дополнительной группировки.

```text
A as x -> $x;       // Допустимая форма.
A -> Result;        // Допустимая форма.
Comment -> none;    // Допустимая форма.

A as x -> ($x);     // Ошибка синтаксиса.
A -> (Result);      // Ошибка синтаксиса.
Comment -> (none);  // Ошибка синтаксиса.
A -> ((Result));    // Ошибка синтаксиса.
```

Примеры независимы и предполагают совместимые объявления типов. Первое правило возвращает захваченный узел, второе строит Result, третье удаляет совпавший Comment при сохранении корректности дерева. Недопустимые формы отвергаются при синтаксическом анализе до построения результата.

Запрет согласован с ранее принятым отсутствием группирующих скобок вокруг объединения детей (§12.3, D155). Он не запрещает круглые скобки именованного конструктора Result(value: $x), аргументов функций или группировки выражений данных, например Result<($prefix + $name).toUpperCase()>. Скобки в шаблонах также сохраняются по своим правилам.

### 12.1.3. Эквивалентные пустые конструкторы (D423)

Задача #15, часть Q14. Ответ автора: «Да».

В результате правила формы T, T() и T[] эквивалентны: дети не переданы, данные при наличии datatype берутся из его default. Обязательные дети автоматически не создаются и не переносятся из совпадения.

Для node Marker; формы Marker, Marker() и Marker[] создают пустой Marker без детей и без datatype. Для node Number<Int>; формы Number, Number() и Number[] создают Number с default встроенного Int. Для node Box(value: Node); формы Box, Box() и Box[] являются ошибками компиляции: обязательный value не заполнен.

Все девять форм синтаксически допустимы. Ошибка трёх форм Box обнаруживается статической проверкой полноты заполнения детей до выполнения. Для допустимых форм создаётся узел при выполнении правила с сохранением обычных проверок билдера. Новая специальная фатальная проверка default не вводится.

Решение относится к конструкторам результата. Оно не меняет различие T(), T[] и T в шаблонах проверки существующего узла. Явно заданные данные разобраны в D424 ниже; Q14 завершён.

### 12.1.4. Явные данные и таблица конструкторов (D424)

Задача #15, завершение Q14. Ответ автора: «Да».

Для node Marker; конструктор Marker<""> допустим и создаёт обычный Marker без datatype и детей. Пустые данные не вводят неявный datatype String. Конструктор Marker<"x"> является ошибкой компиляции: непустые данные у типа без datatype запрещены, и нарушение известно статически.

Для node Number<Int>; конструктор Number<"7"> допустим и создаёт узел со значением 7. Явные данные заменяют default и передаются обычным parse/validate datatype. Пример использует встроенный Int без переопределений.

Ошибка Marker с непустой константой обнаруживается статическим анализом до выполнения правила. Допустимые конструкторы создают узлы при выполнении с обычной проверкой билдера. Это решение не вводит специальную фатальную проверку default и не требует анализа произвольного Java.

Q14 разобран решениями D423–D424. Следующая таблица объединяет все обязательные случаи; формы рассматриваются в результате правила, а не в шаблоне.

| Форма | Допустима | Данные | Результат / диагностика |
|---|---|---|---|
| `Marker` | Да | Нет datatype | Пустой Marker |
| `Marker()` | Да | Нет datatype | Пустой Marker |
| `Marker[]` | Да | Нет datatype | Пустой Marker |
| `Marker<"">` | Да | Явная пустая строка | Пустой Marker |
| `Marker<"x">` | Нет | Явная непустая строка | Ошибка статического анализа: у Marker нет datatype |
| `Number` | Да | default Int | Number со значением по умолчанию |
| `Number()` | Да | default Int | Number со значением по умолчанию |
| `Number[]` | Да | default Int | Number со значением по умолчанию |
| `Number<"7">` | Да | Явные данные вместо default | Number со значением 7 |
| `Box` | Нет | Нет datatype | Ошибка статического анализа: обязательный value не заполнен |
| `Box()` | Нет | Нет datatype | Ошибка статического анализа: обязательный value не заполнен |
| `Box[]` | Нет | Нет datatype | Ошибка статического анализа: обязательный value не заполнен |

### 12.2. Дочерние места

Одна завершающая запятая в непустом списке детей разрешена и не добавляет место или значение (D385, §9.2.2).

В одном конструкторе выбирается только одна форма списка детей. Сочетание позиционной и именованной форм в любом порядке — синтаксическая ошибка (D379, §9.2.1).

Позиционная запись результата заполняет **места схемы**, а не плоские индексы фактических детей. Каждое выражение относится к одному месту. Именованная запись задаёт место тегом.

```text
node Sequence(first: Statement, middle: Statement*, last: Statement);
// Выражения результата:
Sequence[$a, $body, $z]
Sequence(first: $a, middle: $body, last: $z)

node Parts(left: Statement*, right: Statement*);
Parts[$xs, $ys]
Parts(left: $xs, right: $ys)
```

Список не делится между местами. Пустое значение body не сдвигает z. Две группы одинакового типа сохраняют отдельные границы.

| Источник | Обязательное T | Необязательное T? | Группа T* |
|---|---|---|---|
| Один совместимый узел | Да | Да | Да |
| Необязательный совместимый узел | Нет | Да | Да |
| Список совместимых узлов | Нет | Нет | Да |
| `none` | Нет | Да | Да |

Совместимость проверяется по статическому типу: равенство или подтип требуемого типа. Список из одного фактического элемента остаётся списком; необязательный захват остаётся необязательным при фактическом наличии узла. Все возможные варианты альтернативы должны подходить.

В именованном результате необязательное место и группу можно опустить, что равнозначно none. Обязательное место заполняется обязательно. Позиционный пропуск разрешён только при единственной статической привязке с сохранением порядка; фактические длины списков не разрешают неоднозначность.

```text
Triple[$a, none, $c]
Parts(left: none, right: $ys)
```

### 12.2.1. Уникальность тегов при построении (D409)

В одном именованном конструкторе результата каждый тег разрешено указывать не более одного раза (D409). Повтор тега является ошибкой DSL даже при одинаковых выражениях. Назначения не перезаписывают друг друга и не объединяются неявно.

```text
Box(value: $a, value: $b) // Ошибка: повтор тега value.
Box(value: $a, value: $a) // Ошибка и при одинаковых значениях.
Block(items: $xs + $ys)  // Допустимое явное объединение детей.
```

Повтор обнаруживается при статической проверке назначений детей, до построения результата. Примеры предполагают доступные захваты и совместимые схемы: одиночное место value у Box и группу items у Block. В последней форме группа назначается один раз; дети xs и ys объединяются в указанном порядке по обычным правилам оператора +.

Уникальность проверяется отдельно для каждого конструктора. Один тег можно использовать в разных вложенных конструкторах; одно захваченное значение можно подставить в разные места. Требования совместимости типов и кратностей сохраняются.

### 12.3. Объединение детей

```text
Block(items: $prefix + $item + $suffix)
Block[$prefix + Return(value: $value) + $suffix]
```

`+` объединяет детей в порядке операндов: узел даёт один элемент, список — свои элементы, отсутствие и none — ноль. Всё выражение заполняет одно место. Создаваемый Return остаётся узлом, даже если его необязательный value отсутствует. `none + $x` эквивалентно `$x`.

| Состав | Возможное количество |
|---|---|
| Один узел + один узел | 2 |
| Два необязательных узла | От 0 до 2 |
| Список `*` + один узел | От 1 |
| Два списка `*` | От 0 |

Кроме количества сохраняется проверка категории: список нельзя выдать за одиночный узел. Группировочные скобки вокруг объединения детей не предусмотрены; скобки после имени узла задают именованные места.

### 12.4. Символы и строки в результате

```text
Comma -> ',';
'a' -> 'b';
PublicModifier -> Text["public"];
Something -> Text[""];
Word[Character+ as letters] -> Text["(" + $letters + ")"];
```

Одиночный символьный литерал создаёт один Character. Диапазон в результате запрещён, даже с одинаковыми границами. Строковый литерал разрешён внутри детей: после декодирования он создаёт Character для каждого скалярного значения. Пустой литерал создаёт ноль детей, но не удаляет контейнер.

Односимвольная строка внутри детей — одиночный узел и может заполнить совместимое одиночное место. Это специальное свойство литерала, длина которого известна статически:

```text
node Letter(value: Character);
Something -> Letter["a"];          // Один Character.
Something -> Letter["\u{1F600}"];  // Также один.
Something -> Letter["ab"];         // Ошибка: два ребёнка.
Something -> Letter[""];           // Ошибка: обязательный ребёнок отсутствует.
```

### 12.5. chars: строковые данные в узлы

```text
Identifier<$name> -> Text[chars($name)];
Identifier<$name> -> Text[chars("prefix_" + $name.toLowerCase())];
```

`chars` принимает ровно одно строковое выражение и возвращает список новых Character. Пустая строка даёт пустой список. Категория всегда списочная, даже для `chars("a")`; это нельзя подставить в обязательное одиночное место Character.

```text
Text[chars("\n")]     // Один Character LF.
Text[chars("\\n")]    // Два Character: обратная косая черта и n.
```

Повторного снятия экранирования нет. Непарный суррогат в вычисленной строке отвергает весь кандидат без частичного результата, пропуска символов или замены на U+FFFD. Корректная UTF-16 пара даёт один Character. Некорректный escape в самом DSL — ошибка чтения исходника, а не отложенный отказ chars.

### 12.5.1. Форма вызова chars (D401)

Операция chars, создающая список узлов Character из строки, допускается только в форме chars(s) с одним строковым выражением. Методная форма s.chars() не разрешена (D401). Правило D396 о свободных формах строковых методов не распространяется на эту операцию построения детей.

```text
Text[chars($name)]       // Допустимая форма.
Text[chars("ab")]        // Два новых Character: "a", "b".
Text[$name.chars()]      // Ошибка: методная форма chars не предусмотрена.
Text[chars(123)]         // Ошибка типов: требуется строка.
```

Примеры предполагают Text с совместимой группой детей Character и доступный строковый захват name. При name="ab" первая форма создаёт те же символы, что и вторая. Методная форма отвергается при компиляции до построения результата; точный код диагностики относится к Q31. Неверный тип аргумента проверяется статически.

Сохраняется контракт §12.5: chars возвращает список даже для строки из одного символа; самостоятельно результатом правила быть не может. Аргументом может быть любое допустимое строковое выражение с доступными захватами. Правила Unicode, обработки пустой строки и ошибок не меняются. Решение не вводит новые места применения chars.

### 12.6. Непосредственное удаление

```text
Comment -> none;
Comment+ -> none;
```

Первое правило удаляет один комментарий, второе — всю совпавшую цепочку атомарно. Удаление разрешено только при сохранении корректности дерева.

| Контекст | Результат удаления |
|---|---|
| Корень | Пустое дерево |
| Присутствующий необязательный ребёнок | Отсутствующий ребёнок |
| Элементы повторяющейся группы | Исключение совпавших элементов с сохранением порядка остальных |
| Обязательный ребёнок | Кандидат неприменим |

Родитель не удаляется автоматически вместе с последним ребёнком. Он остаётся листом, только если схема допускает отсутствие детей. Если удалить весь фрагмент нельзя, не удаляется ни одна его часть. На отсутствующем корне или ребёнке правила не запускаются.

`none` не является узлом Delete и не требует прохода исполнения действий. Неиспользование захвата само по себе также не создаёт Delete.

## 13. Приоритеты и чтение составных выражений

### 13.1. Шаблоны: от сильного связывания к слабому

| Уровень | Конструкция |
|---|---|
| 1 | Атомарный шаблон и явная группировка |
| 2 | Узловое отрицание `!` |
| 3 | Один суффикс кратности `?`, `*`, `+` |
| 4 | Захват `as` ближайшего шаблона с его кратностью |
| 5 | Одноузловое пересечение `&` |
| 6 | Цепочка через запятую |
| 7 | Альтернатива `\|` |

Строки таблицы описывают согласованные сочетания. Сложные сочетания захватов следует писать с явными скобками; единая грамматика приведена в §13.3.

| Запись | Явная группировка | Смысл |
|---|---|---|
| `!Quote*` | `(!Quote)*` | Повторение узлов, не совпавших с Quote |
| `A & !B, C` | `(A & (!B)), C` | Один узел A, не B; затем C |
| `(A & !B)*` | Повторение всего пересечения | Каждый элемент подходит A и не B |
| `A & B*` | `A & (B*)` | Ошибка: правый операнд не одноузловой |
| `A, B \| C` | `(A, B) \| C` | Пара либо один C |
| `A & B \| C` | `(A & B) \| C` | Пересечение либо C |
| `A, B as x` | `A, (B as x)` | Захватывается B |
| `(A, B) as xs` | Захват целой пары | Список двух узлов |

Группировка не отменяет проверок: `!(Quote*)` ошибочно, тогда как `(!Quote)*` допустимо. Полное правило с последним шаблоном всё равно требует непустого минимального совпадения.

### 13.1.1. Запятая в конце цепочки (D389)

Завершающая запятая в самостоятельной цепочке шаблонов запрещена, в том числе перед стрелкой правила и перед закрывающей скобкой группировки. Запятая цепочки требует следующего шаблона. Нарушение является синтаксической ошибкой компиляции (D389).

```text
Identifier, Number -> Pair;  // Допустимая цепочка.
Identifier, Number, -> Pair; // Ошибка: нет следующего шаблона.
(Identifier, Number,)        // Ошибка: запятая перед концом группировки.
Pair[Identifier, Number,]    // Допустимо по D385: список детей.
```

Первое правило предполагает отдельно объявленные Identifier и Number и допустимое построение Pair без явно заданных детей. Оно сопоставляет два соседних узла в указанном порядке. Здесь имя Pair не означает автоматический перенос совпавших узлов в результат. Последний пример — независимый шаблон для Pair с совместимой схемой детей; список детей проверяется целиком, последняя запятая не добавляет элемент.

Разрешение D385 относится к завершающей запятой самого списка детей. Оно не разрешает завершающую запятую внутри вложенной группировки цепочки: Pair[(Identifier, Number,)] ошибочен. Запятые в цепочке не создают пустых шаблонов или пустых совпадений.

### 13.1.2. Один захват на уровень шаблона (D399)

На одном уровне узлового шаблона допускается не более одного захвата as. Последовательная запись нескольких as без группировки запрещена синтаксисом. Для дополнительного захвата используется явная группировка уже захваченного шаблона (D399).

```text
Identifier as x as y       // Ошибка синтаксиса.
(Identifier as x) as y     // Допустимо: два имени одного вхождения.
((Identifier as x) as y) as z // Допустимая вложенность.
(Identifier as x) as x     // Ошибка: повторное объявление имени.
```

При совпадении с узлом Identifier во второй форме x и y обозначают одно и то же вхождение исходного дерева. В третьей форме его обозначают x, y и z. Скобки не создают дополнительного узла и не меняют кратность совпадения.

Первая форма отвергается при синтаксическом анализе до сопоставления. Последняя синтаксически имеет допустимую структуру, но отвергается статической проверкой имён захватов. Общие ограничения доступности, типов и захватов внутри повторений сохраняются. Правило не запрещает независимые захваты в разных частях составного шаблона: Pair(left: Identifier as x, right: Identifier as y) содержит по одному as в каждом дочернем шаблоне.

### 13.1.3. Кратность перед захватом (D400)

На одном уровне шаблона суффикс кратности ?, * или + ставится до захвата as: шаблон → кратность → as и имя. Суффикс непосредственно после имени захвата не разрешён. Кратность можно применять к явно сгруппированному шаблону, содержащему захват; сама такая обёртка не запрещается (D400).

```text
Identifier? as x       // Допустимый порядок.
Identifier as x?       // Ошибка синтаксиса.
(Identifier as x)?     // Допустимая группировка.
Start, (Identifier as name, Colon)? // Необязательна вся пара.
```

Первые и третья формы в составе допустимого полного шаблона связывают x с Identifier при наличии совпадения и оставляют x отсутствующим при пропуске необязательной части. Для одиночного узла первая форма проще, но это предпочтение записи, а не запрет третьей формы. Во втором примере ошибка обнаруживается при синтаксическом анализе до сопоставления.

В последнем примере Start обязателен. Если за ним совпала пара Identifier, Colon, name обозначает только Identifier; если пара пропущена, name отсутствует. Внешний захват пары обозначал бы весь фрагмент и не заменяет этот внутренний захват.

Группировка не отменяет ранее согласованных статических ограничений: обычные захваты внутри * и + по-прежнему запрещены, а полный шаблон правила обязан иметь положительное минимальное потребление. Поэтому Start, (Identifier as x)* синтаксически использует допустимый порядок, но отвергается статическим анализом из-за обычного захвата внутри повторения. Самостоятельный полный шаблон Identifier? as x также не разрешается из-за возможности пустого совпадения.

### 13.1.4. Ограничения после группировки (D406)

После группировки шаблона запрещены фильтр данных и проверка детей: ограничения записываются внутри группы (D406). Запрет относится и к группе из единственного узлового шаблона. Скобки не создают новый узловой шаблон, к которому можно приписать эти части.

```text
(Identifier)<"abc">   // Ошибка синтаксиса.
(Identifier)[]        // Ошибка синтаксиса.
(Container)(value: Identifier) // Ошибка синтаксиса.
(Identifier<"abc">)   // Допустимо.
(Identifier[])        // Допустимо.
(Identifier)? as x    // Допустимая форма в непустом полном шаблоне.
```

Ошибочные формы отвергаются при синтаксическом анализе до сопоставления. Допустимые формы внутри скобок сохраняют обычный смысл: проверку данных "abc" либо отсутствия детей. Примеры предполагают совместимые объявления типов.

Внешние кратность и захват as после группы сохраняются по D399–D400; все ограничения доступности захватов, повторений и положительного минимального потребления полного шаблона остаются в силе. Это решение касается группировки шаблона, а не скобок выражений данных.

### 13.2. Выражения данных: от сильного связывания к слабому

| Уровень | Конструкция |
|---|---|
| 1 | Скобки, вызовы, цепочки методов |
| 2 | `!`, унарный `-` |
| 3 | Бинарные `+`, `-`, группировка слева направо |
| 4 | `<`, `<=`, `>`, `>=` |
| 5 | `==`, `!=` |
| 6 | `&` |
| 7 | `\|` |

Сравнения порядка внутри фильтра данных обязательно заключаются в круглые скобки, чтобы отличить `>` от конца фильтра.

```text
Identifier<(length() >= 3) & (length() <= 10), $name>
Identifier<length() > 3, $name>             // Ошибка: нужны скобки.
Identifier<(0 <= length() <= 10)>           // Ошибка: цепочка сравнений.
Identifier<(length() > 3) & !endsWith("_")>
Identifier<(startsWith("get") | startsWith("set")) & !endsWith("Internal")>
```

Дополнительные примеры выражений:

| Запись | Группировка / результат |
|---|---|
| `10 - 3 - 2` | `(10 - 3) - 2` = 5 |
| `-(length() + 1)` | Отрицание суммы |
| `length() + 1 == 4` | `(length() + 1) == 4` |
| `!isEmpty() & contains(":")` | `(!isEmpty()) & contains(":")` |
| `isEmpty() \| startsWith("a") & endsWith("z")` | `isEmpty() \| (startsWith("a") & endsWith("z"))` |
| `"a" + "b".toUpperCase()` | `"a" + ("b".toUpperCase())` = `"aB"` |
| `("a" + "b").toUpperCase()` | `"AB"` |

Для трёх сравниваемых значений нужны отдельные проверки: `$a == $b & $b == $c`, не `$a == $b == $c`. Одинаковые знаки `!`, `&`, `|` имеют одинаковый относительный приоритет в данных и шаблонах, но оперируют разными сущностями. Используются одинарные `&` и `|`; двойные формы не входят в язык.

### 13.3. Сводная EBNF, таблица вызовов и контрольные примеры (#14)

Это редакционная сводка принятых правил спецификации и D378–D414, а не новые решения языка и не описание реализации старого компилятора. Семантические ограничения действуют поверх EBNF. Включения Java остаются строками; их содержимое проверяет Java-компилятор.

#### 13.3.1. Лексический слой

EBNF использует `,` для последовательности, `|` для выбора, `[...]` для необязательности и `{...}` для повторения. Терминалы заключены в кавычки. `identifier`, `type-name`, `capture`, `integer`, `string`, `character`, `range` — целые токены, определённые ниже; пробелы внутри них не вставляются.

| Токен / правило | Форма и ограничения |
|---|---|
| `identifier` | `[A-Za-z_][A-Za-z0-9_]*`, кроме восьми ключевых слов и отдельного `_` |
| `type-name` | `[A-Z][A-Za-z0-9_]*`, имя типа узла |
| `capture` | `$` непосредственно перед допустимым `identifier`; `$ text` и `$/**/text` ошибочны |
| `integer` | `[0-9]+`; ведущие нули допустимы, основание 10; знак — отдельный оператор |
| Булевы литералы | Только `true` и `false` |
| Ключевые слова | `abstract`, `node`, `datatype`, `include`, `as`, `none`, `true`, `false` |
| Контекстные имена | Имена параметров данных и встроенных вызовов не резервируются глобально |
| `string` | Двойные кавычки; содержимое и escape по §2.4 спецификации |
| `character` | Одинарные кавычки, внутри ровно одно скалярное значение после декодирования (§9.3) |
| `range` | Одинарные кавычки, внутри граница, две буквальные точки, граница; каждая граница — одно скалярное значение (§9.3) |
| Разделители | U+0020, TAB, LF, CR; CRLF — один перевод строки; одиночный CR завершает `//` |
| Комментарии | `//` до конца строки и невложенный `/* ... */`; разделяют токены |
| BOM | Допускается только в начале файла; не является межтокенным пробелом |
| Составные знаки | Максимальный токен: `!=`, `==`, `<=`, `>=`, `->`, `<-`; разделитель внутри запрещён |

Строковые escape: `\"`, `\\`, `\n`, `\r`, `\t`, `\u{HEX}`. В символьных литералах также используется `\'`; двойную кавычку можно записать непосредственно. HEX содержит 1–6 ASCII-цифр 0–9, a–f, A–F и задаёт скалярное значение не выше U+10FFFF, вне U+D800–U+DFFF. Неизвестный escape, буквальный перевод строки и недопустимое значение — ошибка чтения исходника. Декодирование однократное. Суррогатные значения внутри числового интервала диапазона исключаются; обратный порядок границ не меняет множество. Нормализации Unicode нет.

Имена встроенных типов уже заняты, а имена узлов и datatype находятся в общем пространстве. Это проверка объявлений, а не дополнительные ключевые слова. `type-name` — сужение `identifier` в соответствующей позиции, не конкурирующее правило выбора токена лексером.

#### 13.3.2. Объявления и правила

```ebnf
file = { include | node-declaration | datatype-declaration | rule } ;
include = "include", string, ";" ;
node-declaration = kind, type-name, [ data-binding ], [ bases ],
                   [ declared-children ], ( ";" | node-data-block ) ;
kind = "abstract", [ "node" ] | "node" ;
data-binding = "<", identifier, ">" ;
bases = ":", type-name, { ",", type-name } ;
declared-children = "(", [ declared-child, { ",", declared-child }, [ "," ] ], ")" ;
declared-child = "@", identifier
               | [ identifier, ":" ], type-name, [ "?" | "*" ] ;
datatype-declaration = "datatype", identifier, [ ":", identifier ],
                       ( ";" | datatype-block ) ;
datatype-block = "{", { datatype-field }, "}" ;
datatype-field = ( "javaType" | "default" ), "=", string, ";"
               | "parseError", "=", ( string | "none" ), ";"
               | "serialize", "(", "value", ")", "=", string, ";"
               | "parse", "(", "text", ")", "=", string, ";"
               | validation-field ;
validation-field = "validate", "(", "value", ")", "=", string, ";" ;
node-data-block = "{", { node-data-field }, "}" ;
node-data-field = "default", "=", string, ";" | validation-field ;
rule = pattern, "->", result, ";" | result, "<-", pattern, ";" ;
```

Состав параметров, их уникальность и полнота с учётом наследования проверяются отдельно. Краткая форма datatype не освобождает от обязательных итоговых параметров. Базы узлов должны быть абстрактными; детям абстрактного типа нужны теги; `@tag` должен ссылаться на унаследованное место. Блок заменяет завершающую `;`, а не дополняет её. Объявления разрешаются независимо от порядка; порядок правил и подключений сохраняет смысл §2.6 и §14.

#### 13.3.3. Шаблоны

```ebnf
pattern = sequence, { "|", sequence } ;
sequence = intersection, { ",", intersection } ;
intersection = captured-pattern, { "&", captured-pattern } ;
captured-pattern = repeated-pattern, [ "as", identifier ] ;
repeated-pattern = negated-pattern, [ "?" | "*" | "+" ] ;
negated-pattern = "!", negated-pattern | pattern-atom ;
pattern-atom = typed-pattern | wildcard-pattern
             | character-pattern | string-pattern | "(", pattern, ")" ;
typed-pattern = type-name, [ data-filter ], [ children-check ] ;
wildcard-pattern = "_", [ data-filter ], [ positional-check | "(", ")" ] ;
character-pattern = ( character | range ), [ data-filter ] ;
string-pattern = string, [ "<", data-capture, ">" ] ;
children-check = positional-check | named-check ;
positional-check = "[", [ pattern, [ "," ] ], "]" ;
named-check = "(", [ named-test, { ",", named-test }, [ "," ] ], ")" ;
named-test = identifier, ":", pattern ;
data-filter = "<", ( data-capture | expression, [ ",", data-capture ] ), ">" ;
data-capture = capture, [ "+" ] ;
```

Позиционная проверка содержит шаблон всей цепочки детей: запятая внутри него сохраняет приоритет относительно `|`. Завершающая запятая принадлежит внешнему списку детей; `Pair[(A, B,)]` запрещён. В именованной проверке запятая перед очередным `tag:` разделяет проверки; последовательность в значении тега остаётся шаблоном. Пустые `[]` и `()` имеют разный смысл: отсутствие всех детей и отсутствие дополнительных ограничений на детей соответственно.

Для фильтра точные формы `<$x>` и `<$x+>` разбираются как захват, а не как выражение-условие. В `<expression, $x>` захват относится к исходным данным. Остальные формы проходят обычную проверку типов выражений. Пустые `<>` и завершающая запятая в них запрещены.

У строкового шаблона `string` должен декодироваться в непустую цепочку; после него доступен только захват данных. После символа/диапазона допустим обычный фильтр. Проверки детей после строк, символов, диапазонов и группировок запрещены. Два списка детей, повторные суффиксы и повторные `as` на одном уровне не выводятся из грамматики.

Статический анализ отдельно проверяет одноузловость отрицания и пересечения, положительное минимальное потребление полного правила, доступность захватов, невозможность шаблонов, уникальность тегов и ограничения повторений. Например, `A & B*` разбирается, но правый операнд не одноузловой; `Start, (Identifier as x)*` разбирается, но обычный захват внутри повторения запрещён.

##### Обязательные деревья разбора Q06

| Фрагмент | Дерево разбора | Продукции и проверка |
|---|---|---|
| `A \| B as x` | `Alternative(Type(A), Capture(x, Type(B)))` | `pattern → sequence → intersection → captured-pattern`; `as` относится только к B; использование x проверяется по гарантиям всех веток |
| `(A \| B) as x` | `Capture(x, Group(Alternative(Type(A), Type(B))))` | `captured-pattern → repeated-pattern → negated-pattern → pattern-atom`; x захватывает узел любой выбранной ветки; его статический тип определяется общими правилами альтернатив |
| `(Identifier as x) as y` | `Capture(y, Group(Capture(x, Type(Identifier))))` | Внешний `captured-pattern` содержит группу с отдельным внутренним `captured-pattern`; x и y обозначают одно вхождение |
| `Identifier<$text>[]` | `NodePattern(Identifier, DataCapture(text), Positional([]))` | `typed-pattern → type-name data-filter children-check`; данные захватываются, фактических детей быть не должно |

Для третьего примера без скобок `Identifier as x as y` — ошибка синтаксиса; `(Identifier as x) as x` — ошибка статической проверки имён. Для четвёртого обратный порядок `Identifier[]<$text>` — ошибка синтаксиса. Узел Identifier с данными `abc` без детей совпадает и даёт text=`abc`; с ребёнком не совпадает. Для первых двух примеров синтаксический разбор сам по себе не разрешает подстановку x в произвольное место результата: нужны гарантии доступности, типа и кратности.

#### 13.3.4. Выражения данных

```ebnf
expression = logical-and, { "|", logical-and } ;
logical-and = equality, { "&", equality } ;
equality = ordering, [ ( "==" | "!=" ), ordering ] ;
ordering = additive, [ ( "<" | "<=" | ">" | ">=" ), additive ] ;
additive = unary, { ( "+" | "-" ), unary } ;
unary = ( "!" | "-" ), unary | postfix ;
postfix = primary, { ".", identifier, arguments } ;
primary = string | integer | "true" | "false" | capture
        | identifier, arguments | "(", expression, ")" ;
arguments = "(", [ expression, { ",", expression }, [ "," ] ], ")" ;
```

Сравнение порядка внутри фильтра должно быть защищено круглыми скобками (§13.2); незащищённый знак `>` закрывает фильтр. Это контекстное ограничение грамматики выражений, а не попытка лексера разбить токен иначе. Например, `<(length() >= 3)>` допустим, `<length() > 3>` — нет. Цепочки сравнений не допускаются: для трёх значений нужны отдельные булевы проверки, соединённые `&`.

Операции и вызовы типизируются по §10: нет преобразования строки/числа/boolean друг в друга по умолчанию. Только отдельный строковый литерал в позиции условия (в том числе в скобках, под `!`, `&`, `|`) сокращается до сравнения с `data()`. В аргументе, получателе метода, конкатенации или сравнении литерал остаётся значением. Поэтому `!"a".isEmpty()` — отрицание вызова на буквальной строке, а `!"a"` — отрицание равенства текущих данных строке `a`. Произвольная строка как условие ошибочна.

Синтаксическая форма вызова с `identifier` не разрешает произвольные функции: исчерпывающие сигнатуры перечислены ниже. `capture` в выражениях данных должен ссылаться на строковые данные, а не на узел или список.

#### 13.3.5. Результат

```ebnf
result = construction | capture | character | "none" ;
construction = type-name, [ "<", expression, ">" ], [ constructed-children ] ;
constructed-children = positional-construction | named-construction ;
positional-construction = "[", [ child-value, { ",", child-value }, [ "," ] ], "]" ;
named-construction = "(", [ assignment, { ",", assignment }, [ "," ] ], ")" ;
assignment = identifier, ":", child-value ;
child-value = child-term, { "+", child-term } ;
child-term = construction | capture | character | string | "none" | chars-call ;
chars-call = "chars", "(", expression, [ "," ], ")" ;
```

Самостоятельный `capture` должен быть обязательным одиночным узлом. Диапазон, строка, `chars` и объединение детей не являются самостоятельным результатом. Группировка результата и объединения детей запрещена. В `<expression>` конструктора требуется строка, а данные и дети всегда идут после типа именно в этом порядке. Теги уникальны внутри каждого конструктора; типы, кратности, полнота и однозначность заполнения мест проверяются статически. Группы не теряют границ.

#### 13.3.6. Исчерпывающая таблица вызовов Q09

Обозначения: S — строка, I — целое произвольной точности, B — boolean; `s:S` — любое строковое выражение. В колонках вызовов перечислены все аргументы и их типы; их число равно числу перечисленных параметров. Методная и свободная явная формы доступны в фильтрах и данных результата. Неявная форма доступна только внутри фильтра и получает `data()` текущего узла. Контракты Unicode и граничных случаев сохраняются по §10.4.

| Метод на s:S | Свободная явная форма | Неявная форма в фильтре | Результат |
|---|---|---|---|
| `s.length()` | `length(s:S)` | `length()` | I |
| `s.isEmpty()` | `isEmpty(s:S)` | `isEmpty()` | B |
| `s.charAt(i:I)` | `charAt(s:S, i:I)` | `charAt(i:I)` | S |
| `s.substring(start:I)` | `substring(s:S, start:I)` | `substring(start:I)` | S |
| `s.substring(start:I, end:I)` | `substring(s:S, start:I, end:I)` | `substring(start:I, end:I)` | S |
| `s.startsWith(text:S)` | `startsWith(s:S, text:S)` | `startsWith(text:S)` | B |
| `s.endsWith(text:S)` | `endsWith(s:S, text:S)` | `endsWith(text:S)` | B |
| `s.contains(text:S)` | `contains(s:S, text:S)` | `contains(text:S)` | B |
| `s.indexOf(text:S)` | `indexOf(s:S, text:S)` | `indexOf(text:S)` | I |
| `s.lastIndexOf(text:S)` | `lastIndexOf(s:S, text:S)` | `lastIndexOf(text:S)` | I |
| `s.replace(old:S, new:S)` | `replace(s:S, old:S, new:S)` | `replace(old:S, new:S)` | S |
| `s.replaceFirst(old:S, new:S)` | `replaceFirst(s:S, old:S, new:S)` | `replaceFirst(old:S, new:S)` | S |
| `s.trim()` | `trim(s:S)` | `trim()` | S |
| `s.trimStart()` | `trimStart(s:S)` | `trimStart()` | S |
| `s.trimEnd()` | `trimEnd(s:S)` | `trimEnd()` | S |
| `s.concat(text:S)` | `concat(s:S, text:S)` | `concat(text:S)` | S |
| `s.toLowerCase()` | `toLowerCase(s:S)` | `toLowerCase()` | S |
| `s.toUpperCase()` | `toUpperCase(s:S)` | `toUpperCase()` | S |

| Особый вызов | Получатель / аргументы | Результат | Контекст |
|---|---|---|---|
| `data()` | Текущий узел, 0 аргументов | S | Только фильтр этого узла |
| `toString(v)` | 1 аргумент S, I или B | S | Фильтр или данные результата |
| `v.toString()` | Получатель S, I или B; 0 аргументов | S | Фильтр или данные результата |
| `chars(s)` | 1 аргумент S | Список Character | Только выражение детей результата |

У `substring` две формы с двумя аргументами различаются типами: `(I, I)` — неявная строка, `(S, I)` — явная. Неявных преобразований для выбора перегрузки нет. Завершающая запятая в непустых аргументах допустима, включая `chars(s,)`; `(,)` и двойная запятая запрещены. `toString()`, `data(s)`, `s.data()` и `s.chars()` не разрешены. Число аргументов, тип получателя, типы аргументов и контекст проверяются при компиляции.

##### Обязательные примеры Q09

При доступных строковых захватах name=`ab` и prefix=`pre`:

| Выражение | Результат / разбор |
|---|---|
| `$name.toUpperCase()` | `AB`, метод строки |
| `toUpperCase($name)` | `AB`, явная свободная форма |
| `toUpperCase($prefix + $name)` | `PREAB`, аргумент — целое строковое выражение |
| `length($name)` | Число 2 |
| `toString($name.length())` | Строка `2` |
| `$name.length().toString()` | Строка `2`, метод на числовом результате |

Все шесть форм допустимы как выражения в фильтрах и данных результата; сам фильтр требует булево условие, а непосредственные данные результата — строку. Например, `Identifier<length($name) == 2>` типизирован корректно, `Identifier<length($name)>` — нет; `Result<length($name)>` требует явного `toString`. `length(123)` ошибочен по типу, а `$name.length().toString(10)` — по числу аргументов.

#### 13.3.7. Контроль лексики Q08 и композиции Q10

| Обязательный пример | Ожидаемое поведение / этап |
|---|---|
| `Identifier<length() == 01>` | Разбор допустим; совпадает с данными длины 1, не 2; десятичное 01 равно 1 |
| `Identifier<length() == +1>` | Синтаксическая ошибка: нет унарного плюса |
| `Identifier<true>` | Данные не ограничены, тип Identifier проверяется |
| `node include;` | Ошибка компиляции: ключевое слово вместо имени; также не соответствует заглавной первой букве |
| `node Box(value: Node,);` | Допустимый непустой список с завершающей запятой |
| `Box[value,]` | Ошибка: value без `$` не является ссылкой на захват и не соответствует имени типа узла; сама завершающая запятая допустима |
| `Box[$value,]` | Допустимый синтаксис результата; затем проверяются захват и схема |
| `node⟦TAB⟧A;` | Допустимое разделение токенов |
| `node⟦U+00A0⟧A;` | Лексическая ошибка |
| `// comment⟦CR⟧node A;` | CR завершает комментарий; A объявляется |
| `Identifier<!"x">` | Отрицание краткой проверки равенства |
| `Identifier<data()!="x">` | Единый токен `!=`, данные не равны x |
| `Identifier<data() !/**/= "x">` | Отдельные знаки, синтаксическая ошибка |
| `Pair[Identifier, Number](left: Identifier)` | Синтаксическая ошибка: две формы детей |
| `Pair(left: Identifier)[Identifier, Number]` | Та же ошибка при обратном порядке |
| `Pair(left: $a)[$a, $b]` | Та же ошибка в результате |

Обозначения ⟦…⟧ обозначают реальные символы тестового входа. Примеры независимы и предполагают совместимые объявления и доступные захваты там, где проверяется успешное поведение. Совместная проверка детей выражается `Pair[Identifier, Number] & Pair(left: Identifier)`; при построении выбирается одна форма списка.

Завершающая запятая разрешена только в непустых списках детей объявления/шаблона/результата и аргументов вызова. В базах, фильтрах, привязке datatype, данных результата и самостоятельной цепочке шаблонов она запрещена. Пустой элемент не появляется ни в одном списке.

## 14. Поиск и обход дерева

### 14.1. Правила и направление

```text
Expression as a, Plus, Expression as b -> Addition[$a, $b];
Assignment[$a, $b] <- AssignableExpression as a, Equals, Expression as b;
```

Стрелка указывает на результат. `->` ищет слева направо, `<-` — справа налево. Порядок узлов внутри шаблона, списков и аккумуляторов не переворачивается.

**Первое применимое правило имеет приоритет во всём текущем контексте.** Более специальный шаблон не имеет автоматического преимущества. Текущее правило ищет по всей доступной цепочке; только если нигде не применилось, проверяется следующее. После каждой успешной замены поиск начинается снова с первого правила на обновлённом контексте.

### 14.2. Максимальный полный кандидат

Цепочка непрерывна и находится внутри одной группы одного родителя. Сопоставление не пересекает границы групп или родителя. Вложенный шаблон может читать детей элемента, но не делает их его соседями.

На позиции выбирается максимальный фрагмент, позволяющий сопоставить **весь** шаблон. Возврат элементов ради обязательного продолжения разрешён:

```text
Expression+ as prefix, Expression as last -> PairOfParts[$prefix, $last];
```

На трёх элементах первые два входят в prefix, последний — в last. При одном элементе совпадения нет. Принимающая схема PairOfParts должна иметь группу и одиночное место.

Жадность не выбирает произвольное распределение при неоднозначности:

```text
Block[Statement*, Statement*]          // Ошибка: одинаковые соседние повторы.
Expression+ as a, Expression+ as b     // Ошибка: неопределённая граница.
Block[Statement*, Return, Statement*] // Допустимый шаблон.
```

В последнем примере Return — подтип Statement. Один подходящий Return даёт единственное распределение; два — неоднозначное совпадение и отказ кандидата. Это не основание запрещать сам данный шаблон.

Если максимальный кандидат неоднозначен, **укорачивать его ради однозначности нельзя**. Поиск продолжается со следующей позиции того же правила. Для шаблона `Statement*, Return, Statement*` на цепочке `A, Return₁, B, Return₂, C` позиции A и Return₁ неоднозначны; с B фрагмент `B, Return₂, C` однозначен. Здесь A, B, C — другие Statement, индексы обозначают разные вхождения.

### 14.3. Построение и отказ

Результат строится после успешного сопоставления. Если любой создаваемый узел не проходит ожидаемый разбор, валидацию или проверку схемы, **весь кандидат** отвергается. Исходное дерево сохраняется, частичного результата нет.

```text
Token<$text> -> IntegerLiteral<$text>;
Token<$text> -> InvalidExpression<$text>;
```

Для цепочки Token с данными `hello`, затем `123` первое правило сначала отказывает на `hello`, затем преобразует `123`. Второе правило получает очередь только когда первое больше нигде не применимо.

После отказа построения максимального кандидата более короткий фрагмент на той же позиции не пробуется. Не выбирается и другая альтернативная ветка ради более удобного результата. Неожиданные исключения отличаются от ожидаемых отказов и завершают запуск неуспешно (§16).

Минимальное потребление шаблона вычисляется заранее: `A, B, C` требует три внешних элемента, `Box[A, B, C]` — один. При нехватке элементов правило можно пропустить, но после изменения контекста длина проверяется заново.

### 14.4. От детей к родителю

Обход идёт снизу вверх. Сначала обрабатывается внутреннее содержимое исходных элементов, затем сами элементы конкурируют в содержащем их контексте.

```text
A, B -> Pair;
A -> X;
```

В группе A, B получается Pair. Нельзя сначала отдельно заменить сам элемент A на X и тем самым лишить первое правило его совпадения. Если A и B имеют детей, их дочерние контексты обрабатываются раньше.

Группы одного узла обрабатываются последовательно в порядке итоговой схемы. Группа полностью сворачивается до перехода к следующей. Направление стрелки не переставляет группы.

Созданный результат считается готовым: внутрь него не запускается новый самостоятельный обход. Он сразу участвует в дальнейшем поиске текущего контекста, и следующий шаблон может проверять его внутреннюю структуру.

### 14.5. Корень и одиночные места

В корне или одиночном месте доступен один узел. Подходит любой корректный шаблон, способный сопоставить именно этот доступный узел:

```text
Comment+ -> none;           // Может удалить корень Comment.
(A | B, C) -> Result;       // Корень A подходит первой ветке.
A, B? -> Result;            // Корень A подходит при отсутствии B.
```

Дети корня и соседние места не присоединяются к нему для получения цепочки. Неподходящая в данном месте двухузловая ветка не считается невозможной во всех контекстах. Списочный захват не становится одиночным от совпадения с одним элементом.

После замены снова проверяется первое правило. Например, при `A -> X; X -> Y;` корень A превращается в Y. Для элементов группы отдельный такой цикл не запускается — действует общий цикл группы.

При общем обходе правило с несовместимым статическим типом результата пропускается в конкретном месте. Успешная компиляция не обещает ни одного применения. Доказанная невозможность допустимого применения вообще — ошибка компиляции; неприменимость лишь в части контекстов такой ошибкой не является.

## 15. Равенство, циклы и действия

### 15.1. Структурное равенство

Равенство учитывает имя конкретного типа, строку getData(), упорядоченных детей рекурсивно и принадлежность детей местам схемы. Координаты исходника и Java-класс реализации не участвуют. Группы размеров `[1, 1]` и `[2, 0]` различаются при одинаковом плоском списке.

Одинаковая ссылка позволяет быстро подтвердить равенство; разные ссылки не доказывают различие. Равные структуры обязаны иметь одинаковые хэши; одинаковый хэш требует полного сравнения из-за коллизий. Имена типов должны однозначно обозначать схемы, в том числе при сериализации и адаптации.

Структурное равенство используется для проверки состояний. Согласованность узловых захватов использует другое отношение — идентичность исходного вхождения.

### 15.2. Тождество и циклы

```text
Expression as x -> $x;       // Доказанное тождество: ошибка компиляции.
A -> B;
B -> A;                     // Эти два правила образуют цикл на A или B.
```

Доказанное всегда тождественное правило отвергается при компиляции. Тождество конкретного применения — ошибка исполнения, а не повод молча перейти к следующему правилу. Например, перестановка двух детей контейнера может менять обычное дерево, но быть тождественной при равных детях.

История хранит исходное состояние и каждое последующее состояние текущего контекста. Для группы сравнивается вся цепочка, а не только заменённый фрагмент. Совпадение хэша подтверждается точным равенством. Повтор состояния в том же контексте означает цикл.

История локальна для группы, корня или одиночного места и освобождается после завершения контекста. Неизменяемые версии могут разделять поддеревья. Лимита числа замен нет. Обнаружение повторов не гарантирует завершения при бесконечном росте без повторных состояний.

### 15.3. Встроенные действия

Action — встроенный абстрактный тип, закрытый для пользовательского наследования. Встроенные конкретные типы имеют следующие схемы:

| Тип | Обязательные одиночные дети |
|---|---|
| Insert | `after: Node` |
| Delete | `before: Node` |
| Replace | `before: Node`, `after: Node` |

Собственного datatype у них нет. Переобъявлять встроенные типы нельзя. Разрешено позиционное и именованное построение:

```text
Comment as c -> Delete[$c];
Comment as c -> Delete(before: $c);
Identifier<$name> as before -> Replace[$before, Variable<$name>];
```

Каждое правило создаёт один узел-действие. **Движок DSL не исполняет действия**: результатом служит дерево с действиями; исполнение — отдельный проход. Соседние комментарии могут обрабатываться обычным одноузловым правилом по очереди.

Для дифференциального дерева предусмотрен отдельный дифференциальный тип узла. В обычном дереве действие нельзя вставить в место, схема которого не принимает его тип. Проверка схем не откладывается до исполнения действий и не ослабляется автоматически. Для непосредственного удаления обычного узла служит none.

## 16. Статические проверки и диагностика

### 16.1. Ошибки DSL

До исполнения проверяются синтаксис, имена, наследование, теги, параметры datatype, категории захватов, статические типы и кратности подстановок, ограничения повторений и отрицания. Доказанно непорождаемый конкретный тип, невозможный шаблон, невозможный результат или всегда тождественное правило — ошибки компиляции, кроме разрешённого D420 объявления промежуточной схемы: отсутствие конкретных потомков обязательного абстрактного ребёнка вызывает предупреждение.

Доказанная невозможность отдельной ветки также делает весь DSL ошибочным:

```text
((Identifier & !Identifier) | IntegerLiteral) as x -> Argument[$x];
// Ошибка: первая ветка невозможна, хотя вторая работоспособна.
```

Нельзя молча удалить ветку и объявить программу правильной. Отсутствие доказательства невозможности не означает ошибку: допускается неполный анализ и проверка кандидатов при исполнении. Анализатор не обязан понимать произвольный Java-код.

```text
Token<$text> -> IntegerLiteral<$text>; // Возможность зависит от данных.
Token -> IntegerLiteral<"hello">;     // Ошибка, если невозможность разбора доказана.
Identifier<startsWith("a") & startsWith("b")> -> Marker;
// Ошибка при установленном противоречии условий.
```

Билдер проверяет создаваемый узел, но не выбирает совпадение и не разрешает неоднозначность шаблона. Статический анализ может связывать сведения о шаблоне и результате.

### 16.1.1. Обязательные контрольные случаи (D415)

Задача #15, часть Q11. Автор подтвердил обязательность всех трёх проверок. Это обязательная часть минимума для любой реализации DSL, а не факультативные возможности анализатора.

Identifier<startsWith("a") & startsWith("b")> -> Marker; — ошибка компиляции: несовместимые префиксы данных. Ни одна строка не начинается одновременно с "a" и "b".

Token -> Number<"hello">; — ошибка компиляции: константа не разбирается встроенным Int. Здесь Number использует встроенный Int без переопределений.

Expression as x -> $x; — ошибка компиляции: правило всегда возвращает то же исходное вхождение и является тождественным.

Все три ошибки обнаруживаются статическим анализом до выполнения преобразования. Диагностика должна указывать соответствующую причину; фиксированный текст сообщения этим решением не устанавливается. Выполнение или анализ произвольного Java-кода для этих проверок не требуется.

Граничные примеры (при совместимых объявлениях типов): Identifier<startsWith("a") & startsWith("ab")> -> Marker; не содержит противоречия префиксов; Token -> Number<"7">; не содержит ошибки разбора встроенного Int; Expression as x -> Wrapper[$x]; не является прямым возвратом исходного узла. Эти примеры проходят именно перечисленные проверки, но сохраняют остальные требования DSL.

Q11 закрыт частично: зафиксированы три обязательных контрольных случая. Остальной обязательный минимум и границы более сложных доказательств требуют дальнейшего согласования. Q12 разобран решениями D416–D418; Q13–Q18 остаются открытыми. Новая семантика пока описана только в документации.

### 16.1.2. Невозможная ветка в контексте пересечения (D416)

Задача #15, часть Q12. Ответ автора: «Да».

Невозможность ветки альтернативы проверяется с учётом ограничений внешнего пересечения на тот же узел. Если ветка доказанно невозможна в этом контексте, весь DSL отвергается при компиляции, даже когда другая ветка работоспособна. Молча удалять невозможную ветку нельзя.

Обязательный отрицательный пример: Identifier & (Identifier | Number), где Identifier и Number — разные конкретные типы. Ветка Number несовместима с внешним Identifier. Статическая диагностика до сопоставления должна указать невозможную ветку Number и конфликт с внешним ограничением Identifier. Возможность совпадения через первую ветку не устраняет ошибку.

Граничный допустимый пример: Identifier & (Identifier<startsWith("a")> | Identifier<startsWith("b")>). При совместимом строковом datatype обе ветки возможны в контексте внешнего Identifier: данные "abc" подходят первой, "bcd" — второй. Этот пример не содержит невозможной ветки; обычная диагностика избыточных ограничений сохраняется.

Решение D416 определяет контекст ветки в пересечении. Отрицание противоречия разобрано в D417, нулевое повторение — в D418.

### 16.1.3. Отрицание противоречия (D417)

Задача #15, часть Q12. Ответ автора: «Давай».

Шаблон !(Identifier & !Identifier) допустим. Внутреннее пересечение заведомо ложно, но служит операндом отрицания, поэтому весь шаблон совпадает с любым одним существующим узлом. Компилятор выдаёт предупреждение о всегда истинной проверке, а не ошибку невозможного шаблона.

В этом случае внутреннее противоречие не является неработающей альтернативной веткой. Его нельзя отвергать без учёта внешнего отрицания. Упрощение приведённого шаблона до _ сохраняет смысл: потребляется ровно один узел; на пустом входе совпадения нет.

Контроль: Identifier & !Identifier без внешнего отрицания — невозможный шаблон и ошибка статического анализа до сопоставления. !(Identifier & !Identifier) проходит эту проверку с предупреждением. Требования к одноузловости отрицания и остальные ограничения DSL сохраняются.

Q12 разобран решениями D416–D418; актуальный статус остальных вопросов приведён в §18.3.

### 16.1.4. Невозможное тело нулевого повторения (D418)

Задача #15, часть Q12. Ответ автора: «Да».

Доказанно невозможное тело повторения под * является ошибкой компиляции. Возможность нулевого числа повторений не делает такое тело допустимым: компилятор не должен молча удалять его.

Обязательный пример: Start, (Identifier & !Identifier)* -> Marker; отвергается статическим анализом до сопоставления. Диагностика указывает, что тело повторения Identifier & !Identifier никогда не может совпасть. Наличие возможного совпадения всего правила за счёт нуля повторений не устраняет ошибку.

Контроль при совместимых объявлениях: Start, Identifier* -> Marker; допустим по этой проверке, поскольку тело Identifier возможно. Ноль Identifier после Start — нормальное совпадение. Если автору нужен только Start, он может явно написать Start -> Marker;.

Отличие от D417: отрицание использует ложность своего операнда для проверки узла, а * лишь допускает пропуск невозможного тела. Q12 разобран: контекст пересечения определён D416, отрицание — D417, нулевое повторение — D418. Q11 остаётся частично открытым; Q13–Q18 ещё требуют согласования.

### 16.1.5. Закрытый набор типов и роль адаптера (D419)

Задача #15, часть Q13. Автор отверг предложенную открытую модель: «Никаких внешних типов. Все типы объявляются внутри DSL. Из них получается код Java, внешний адаптер строит исходное дерево, используя узлы из этого сгенерированного кода».

Набор типов закрыт относительно внешних адаптеров: адаптер не добавляет типы узлов и отношения наследования. Пользовательские типы объявляются в DSL, из объявлений генерируется Java-код, и адаптер использует узлы этого кода для построения исходного дерева. Ранее установленные встроенные типы DSL сохраняются; они не являются расширениями адаптера.

Допустимый пример: abstract External; node Concrete : External; node Holder(value: External);. Адаптер может построить Holder с ребёнком Concrete, используя соответствующие сгенерированные узлы.

Недопустимый сценарий: объявить только abstract External; node Holder(value: External); и рассчитывать, что адаптер введёт отсутствующий в DSL конкретный тип ExternalImpl. Такой способ расширения набора типов не предусмотрен. Отсутствие объявленного конкретного потомка нельзя компенсировать предположением о типах, которые появятся во время выполнения.

Это решение фиксирует границу набора типов для статического анализа. Q13 остаётся частично открытым: отдельно согласуются диагностика абстрактной схемы без конкретных потомков, использующего её обязательного места Holder.value и пересечения Left & Right без общего конкретного потомка. Предложение о допустимости Holder за счёт внешних типов отклонено.

### 16.1.6. Непорождаемый Holder как промежуточная схема (D420)

Задача #15, часть Q13. Автор отклонил ошибку компиляции для объявления Holder: при постепенном проектировании DSL абстрактные типы могут долго оставаться без конкретных потомков. Java-код должен генерироваться; невозможность создать экземпляр не запрещает объявление.

Для abstract External; node Holder(value: External); при отсутствии конкретных потомков External объявления допустимы. Компилятор выдаёт предупреждение: обязательное место Holder.value невозможно заполнить, поэтому корректный экземпляр Holder сейчас создать нельзя. Это предупреждение статического анализа не блокирует генерацию Java.

Само объявление абстрактного External допустимо. Адаптер по D419 использует только сгенерированные типы и не может добавить недостающий конкретный тип. Билдер Holder с незаполненным обязательным value остаётся невалидным; создание некорректного узла не разрешается.

Граничный пример: после добавления node Concrete : External; обязательный value можно заполнить узлом Concrete, и указанная причина предупреждения исчезает. Пока конкретного потомка нет, сохранение схемы Holder полезно как промежуточный этап проектирования.

D420 уточняет общее правило об ошибке непорождаемого конкретного типа: для рассмотренного отсутствия конкретных потомков обязательного абстрактного ребёнка применяется предупреждение. Прежняя ошибка доказанной обязательной бесконечной рекурсии этим решением не отменяется. Допустимость объявления не означает допустимости любого шаблона или построения результата с этим типом; диагностика таких использований рассматривается отдельно.

Q13 разобран частично: D419 определяет закрытый набор типов, D420 — допустимость объявления Holder с предупреждением. Пересечение Left & Right без общего конкретного потомка разобрано в D421.

### 16.1.7. Пересечение без общего конкретного потомка (D421)

Задача #15, часть Q13. Ответ автора: «Да».

Если у абстрактных Left и Right во всём DSL нет общего конкретного потомка, используемый в правиле шаблон (Left & Right) as x является доказанно невозможным и вызывает ошибку компиляции. Закрытый набор типов D419 не допускает появления недостающего типа из адаптера.

Обязательный отрицательный пример: abstract Left; abstract Right; затем (Left & Right) as x -> Wrapper[$x];. При совместимой схеме Wrapper компиляция всё равно завершается ошибкой статического анализа до выполнения: ни один конкретный тип не удовлетворяет обоим ограничениям. Диагностика указывает пересечение Left & Right и отсутствие общего конкретного потомка.

Сами объявления abstract Left; abstract Right; допустимы. В отличие от промежуточного объявления Holder по D420, здесь невозможный типовой набор используется в шаблоне правила.

Граничный пример: добавление node Both : Left, Right; при совместимых базовых схемах даёт общий конкретный тип. Узел Both удовлетворяет Left & Right, и указанная причина ошибки исчезает. Остальные проверки шаблона, захвата x и результата Wrapper[$x] сохраняются.

Q13: закрытая модель определена D419, предупреждение для промежуточного Holder — D420, невозможное пересечение — D421. Использование непорождаемого Holder в шаблоне правила разобрано в D422. Прежняя ошибка обязательной бесконечной рекурсии сохраняется.

### 16.1.8. Непорождаемый Holder в шаблоне правила (D422)

Задача #15, завершение Q13. Ответ автора: «Да, это уже ошибка».

При объявлениях abstract External; node Holder(value: External); без конкретных потомков External объявление Holder допускается с предупреждением по D420, но правило Holder -> Marker; является ошибкой компиляции: корректного входного Holder существовать не может, и шаблон заведомо никогда не совпадёт.

Ошибка обнаруживается статическим анализом до выполнения преобразования и блокирует генерацию для DSL с таким правилом. Диагностика связывает невозможный шаблон Holder с обязательным местом value и отсутствием конкретного потомка External. Предупреждение о промежуточном объявлении не ослабляет проверку используемого шаблона.

Граничные примеры при совместимых объявлениях Marker: без правила промежуточная схема Holder допускает генерацию Java с предупреждением; после добавления node Concrete : External; корректный Holder с ребёнком Concrete возможен, и указанная причина ошибки правила исчезает. Иные проверки правила сохраняются.

Q13 разобран решениями D419–D422: внешних типов нет; адаптер строит дерево из сгенерированных узлов; промежуточный Holder допускается с предупреждением; невозможные пересечение и шаблон Holder в правиле отвергаются. Прежняя ошибка доказанной обязательной бесконечной рекурсии сохраняется. Это спецификация поведения, а не заявление о реализации нового анализатора.

### 16.2. Предупреждения

Доказанная избыточная, но возможная проверка — предупреждение. Например, в `Identifier & Identifier<startsWith("a")>` первое ограничение следует из второго. Упрощение разрешено лишь с сохранением захватов и вкладов.

Полностью перекрытое более ранним правилом корректное правило также вызывает предупреждение. Для доказательства недостаточно сравнить шаблоны: учитываются допустимые контексты и возможность отказа результата раннего правила.

```text
Identifier<$name> -> Variable<$name>;
Identifier<"count"> -> Counter;
```

Предупреждение для второго правила обосновано только если первое гарантированно успешно в соответствующих контекстах. Диапазон с одинаковыми символьными границами сам по себе предупреждения не требует.

### 16.3. Диагностики и способы запуска

Компилятор возвращает структурированные диагностики: уровень, стабильный код, объяснение и относящееся к исходнику положение — файл, строку и столбец. Отображение отделено от получения диагностики.

| Среда | Поведение |
|---|---|
| CLI | Вывод диагностик в консоль и неуспешное завершение при ошибках |
| Maven | Сообщения через журнал Maven; ошибка DSL завершает сборку неуспешно |
| Java API | Программный результат и диагностики для вызывающего кода |

Предупреждения по умолчанию не делают компиляцию неуспешной. Явный строгий режим делает любое предупреждение причиной неуспеха одинаково во всех трёх средах, независимо от фактического отображения сообщения.

Компилятор собирает независимые ошибки, пока может надёжно продолжать. Зависимые проверки пропускаются, чтобы не создавать каскад: неизвестный тип в одном правиле не мешает проверить другое, но его неизвестные дочерние места анализировать бессмысленно. При ошибках генерация не запускается.

### 16.4. Отказ кандидата и ошибка всего запуска

| Событие | Последствие |
|---|---|
| Обычное несовпадение или невыявленная заранее неоднозначность кандидата | Следующая позиция того же правила |
| Ожидаемый отказ parse/validate, невалидный билдер, недопустимое удаление | Кандидат не меняет дерево; поиск продолжается |
| Неожиданное исключение Java, тождественная замена, подтверждённый цикл | Неуспех всего запуска |

При ошибке исполнения частично преобразованное дерево не выдаётся как результат запуска, даже если уже были успешные шаги. Исходное неизменяемое дерево сохраняется. Это не обещает отката внешних побочных эффектов Java-кода, нарушающего контракт чистоты.

## 17. Сквозные примеры

Каждый подраздел — отдельный набор объявлений и правил. Показанные исходные деревья должны быть корректны относительно этих схем. Примеры задают ожидаемую семантику нового DSL, а не результаты запуска старого компилятора.

### 17.1. Из символьной цепочки в слово

```text
node Text(items: Node*);
node Word<String>;

'a..z'<$text+>+ -> Word<$text>;
```

Вход: Text с детьми h, e, l, l, o типа Character. Результат: тот же контейнер Text с одним Word и данными `hello`. Правило больше не подходит к Word. Буквы вне диапазона не входят в совпадение; правила для пробелов или других алфавитов этот пример не задаёт.

### 17.2. Строка в кавычках без escape в разбираемом тексте

```text
node Text(items: Node*);
node StringLiteral<String>;

'"', Character<!"\"", $text+>*, '"' -> StringLiteral<$text>;
```

Входные Character для `"hello"` сворачиваются в StringLiteral с данными `hello`. Для `""` получается пустая строка данных. Содержимое не поглощает закрывающую кавычку. Пример **не обрабатывает** экранирование кавычек исходного разбираемого языка: экранирование записи самого DSL и правила лексера целевого языка — разные уровни.

### 17.3. Приоритет умножения перед сложением

```text
abstract Expression;
abstract Binary : Expression(left: Expression, right: Expression);
node Number<Int> : Expression;
node Multiply : Binary;
node Addition : Binary;
node Plus;
node Star;
node Input(items: Node*);

Expression as a, Star, Expression as b -> Multiply[$a, $b];
Expression as a, Plus, Expression as b -> Addition[$a, $b];
```

Для Input с последовательностью `Number<"2">, Plus, Number<"3">, Star, Number<"4">` сначала сворачивается умножение, хотя находится правее. Итоговый единственный ребёнок Input:

```text
Addition[Number<"2">, Multiply[Number<"3">, Number<"4">]]
```

На `2 + 3 + 4` левое направление даёт `Addition[Addition[2, 3], 4]` в условной записи чисел. Порядок правил задаёт приоритет операций; стрелка — направление поиска.

### 17.4. Ожидаемый отказ данных и диагностический узел

```text
abstract Expression;
abstract ParseError;
node Token<String>;
node Number<Int> : Expression;
node InvalidExpression<String> : Expression, ParseError;
node Input(items: Node*);

Token<$text> -> Number<$text>;
Token<$text> -> InvalidExpression<$text>;
```

Для Input с Token `hello`, Token `123` первое правило обрабатывает `123`, затем второе — `hello`. Итог: InvalidExpression `hello`, Number `123`. Неудачный разбор первого токена не останавливает поиск числового правила. Узлы ParseError можно собрать отдельным анализом. Тип ParseError объявлен автором примера, не встроен в язык.

### 17.5. Сохранение двух групп

```text
node Item<String>;
node Source(left: Item*, right: Item*);
node Target(left: Item*, right: Item*);

Source(left: [Item* as xs], right: [Item* as ys])
    -> Target[$xs, $ys];
```

Если left пуста, а right содержит два Item, Target сохраняет размеры мест `[0, 2]`. Это не `[1, 1]` и не одна объединённая группа. Захваты списков подставляются без копирования их содержимого в строковые данные.

### 17.6. Необязательный ребёнок внутри обязательного результата

```text
abstract Expression;
node Number<Int> : Expression;
node Source(value: Expression?);
node Return(value: Expression?);

Source(value: Expression? as value) -> Return(value: $value);
```

Source без ребёнка даёт Return без ребёнка. Сам Return существует всегда: необязательность value не делает результат необязательным. Если заменить схему Return на обязательный value, подстановка станет статической ошибкой.

### 17.7. Удаление с сохранением схемы

```text
node Comment<String>;
node Block(items: Node*);
node Required(value: Comment);
node Optional(value: Comment?);

Comment+ -> none;
```

| Исходное дерево | Результат |
|---|---|
| Корень Comment | Пустое дерево |
| Block с двумя Comment | Block с пустой группой |
| Optional с Comment | Optional без ребёнка |
| Required с Comment | Без изменений: обязательного ребёнка удалить нельзя |

Одно правило допустимо в программе, хотя применимо не во всех контекстах.

### 17.8. Преобразование данных в символьных детей

```text
node Identifier<String>;
node Text(items: Character*);

Identifier<$name> -> Text["[" + chars($name.toUpperCase()) + "]"];
```

Identifier с данными `a😀` превращается в Text с четырьмя Character: `[`, `A`, `😀`, `]`. Здесь `+` объединяет детей, а вызов toUpperCase преобразует строковые данные. Пустые данные дают два ребёнка — открывающую и закрывающую скобки.

### 17.9. Гарантии пересечения и альтернативы

```text
abstract Printable;
abstract Named;
abstract Numbered;
node Document : Printable, Named;
node Receipt : Printable, Numbered;
node PrintBox(value: Printable);
node NameBox(value: Named);

(Printable & (Named | Numbered)) as x -> PrintBox[$x];
```

Правило допускает Document и Receipt: в обеих ветках гарантирован Printable. Замена PrintBox на NameBox — ошибка: ветка Printable & Numbered не гарантирует Named. В отдельном варианте схемы, где Numbered наследует Named, такая подстановка разрешена. Для `(Printable & Named) as x` подходят оба принимающих типа, но конкретный Document не гарантирован.

### 17.10. Ошибки, обнаруживаемые до преобразования

```text
abstract Expression;
node Number<Int> : Expression;
node Box(value: Expression);
node Bag(items: Expression*);
node Marker;

Number* -> Marker;                     // Ошибка: пустой минимум.
(Number+)+ as xs -> Bag[$xs];           // Ошибка: разбиение на итерации.
Box(value: Expression? as x) -> $x;     // Ошибка: необязательный результат.
Bag(items: [Expression+ as xs]) -> Box[$xs]; // Ошибка: список в одиночном месте.
((Number & !Number) | Marker) -> Bag;  // Ошибка: невозможная ветка.
```

Это независимые отрицательные примеры. Наличие работоспособной ветки или подходящего фактического значения не исправляет статическую ошибку программы.

### 18.8. Проверки существующего преобразователя и документа

Это задачи реализации и сверки, а не предложения нового синтаксиса:

- Найти существующий преобразователь текста и зафиксировать его точный путь.
- Проверить один Character на скалярное значение: BMP, 😀, комбинируемые последовательности без нормализации, пустой текст, LF/CRLF и порядок символов.
- Установить текущее поведение на непарных суррогатах и ошибках декодирования; согласовать политику до исправления.
- Проверить соответствие новой схеме Character/CodePoint и вход готового дерева, например через адаптер ANTLR.
- После согласования открытых пунктов завершить EBNF и превратить положительные и отрицательные примеры в исполняемые проверки нового компилятора.
