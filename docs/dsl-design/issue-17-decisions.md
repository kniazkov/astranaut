# Задача #17: состав первой версии и текстовый парсер

Рабочий журнал согласования. Зафиксированы только подтверждённые автором решения. После завершения обсуждения синхронизировать общую спецификацию Markdown и HTML, основной журнал решений и список открытых вопросов.

## Q24.1. Имена правил — согласовано

В первой версии правила не имеют имён. Именование правил отложено. Порядок применения остаётся определён существующими правилами обхода и порядком главного файла с include. Диагностика может указывать файл и позицию правила; имя для этого не требуется.

Допустимый пример при объявленном Word<String> и совместимой схеме входа:

```text
'a..z'<$text+>+ -> Word<$text>;
```

Символьная цепочка `abc` сворачивается в Word с данными `abc` по ранее согласованным правилам.

Граничный пример: желание назвать это правило `word` не добавляет ни объявления имени, ни возможности вызвать правило по имени. Конкретный синтаксис именования не согласован и в грамматику v1 не включается; попытка добавить отсутствующую в грамматике конструкцию должна быть отклонена при синтаксическом анализе DSL.

Решение касается только имён отдельных правил. Решение о наборах приведено ниже; решение о языковых секциях приведено ниже. Секции не вводят отдельных пространств имён типов. Решение о проходах приведено ниже. Q24 целиком остаётся открытым.

## Q24.2. Наборы правил — согласовано

Отдельный механизм именованных наборов правил отложен. Выбор правил по языковой секции входит в v1 согласно Q24.4; прежнее решение об общем списке уточнено этим решением автора. Разнесение правил по файлам через include сохраняется; подключение файла вставляет его правила в общий список по ранее согласованному порядку.

Основание: отдельная конструкция наборов не нужна; выбор правил при запуске задаётся языковыми секциями. Include сам по себе не создаёт наборов.

Допустимый пример:

```text
include "lexical.dsl";
include "syntax.dsl";
```

Если lexical.dsl содержит правила преобразования Character в Token, а syntax.dsl — Token в Expression (при соответствующих объявлениях типов и совместимых схемах), оба файла добавляют правила в общий список. Имена файлов не создают наборов.

Граничный пример: указанные include не означают «полностью закончить лексику, затем отдельно запустить синтаксис». Сохраняется текущая семантика: после успешной замены поиск начинается с первого правила в обновлённом контексте. Требование выбрать только набор «лексика» не поддерживается механизмом наборов в v1. Синтаксис объявления или выбора наборов не утверждён; отсутствующая в грамматике конструкция отклоняется при синтаксическом анализе DSL. Отдельное решение о явных проходах приведено ниже.

## Q24.3. Явные проходы — согласовано

В первой версии DSL нет отдельных явно задаваемых этапов преобразования дерева. Управление проходами отложено. Речь идёт о проходах по преобразуемому дереву, а не о чтении исходного текста DSL. Для выбранных при запуске правил сохраняется ранее согласованный порядок применения и обхода; языковые секции не вводят последовательных этапов.

Основание: наборы правил уже отложены; для v1 не вводится дополнительный механизм переключения между этапами.

Допустимый пример при объявленных типах и совместимой схеме:

```text
'a..z'<$text+>+ -> Word<$text>;
Word as w -> Expression[$w];
```

Оба правила участвуют в общем порядке поиска. После успешной замены поиск начинается с первого правила в обновлённом контексте, как установлено §14.1. Этот пример не задаёт отдельного завершённого этапа лексики перед этапом синтаксиса.

Граничный сценарий: «сначала применять только лексические правила до завершения, затем только синтаксические без возврата к лексическим» не выражается специальными этапами DSL v1. Разделение через include также не создаёт этапов. Синтаксис объявления этапов не утверждён и не добавляется в грамматику; отсутствующая в грамматике конструкция отклоняется при синтаксическом анализе DSL.

Это решение не меняет ранее установленного разделения построения дерева с узлами-действиями и отдельного исполнения этих действий: движок DSL по-прежнему не исполняет действия.

## Q24.4. Вложенные языковые секции — согласованная основа

Языковые секции входят в первую версию. Они нужны для выбора части правил при запуске разбора и определяют подпакеты генерируемого Java-кода. Имена типов по-прежнему уникальны во всём описании: секции не создают независимых пространств имён и не разрешают повторные объявления типов.

Предложенная автором форма секций:

```text
// Общие для всех языков узлы и правила
language Java {
  // Узлы и правила Java
  language Java11 {
    // Узлы и правила Java 11
  }
}
```

Секции допускают вложенность. Для указанного извне или в описании базового пакета (способ задания ещё не выбран) общие исходники располагаются в нём, исходники секции Java — в подпакете java, вложенной Java11 — в java.java11. Например, при базовом пакете example это example, example.java и example.java.java11. Общие правила преобразования произвольных имён секций в имена пакетов ещё предстоит согласовать.

Граничный пример: объявить node Identifier; в двух разных секциях нельзя даже при разных выходных Java-пакетах. Это повторное объявление типа, ошибка проверки объявлений DSL до генерации кода.

Не согласованы пока: способ выбора секции при запуске, правила имён секций, взаимодействие с include, способ задания базового Java-пакета. Эти вопросы не считаются решёнными данным примером.

Ключевое слово language предложено автором; альтернативного синтаксиса пока не принято. Решение об отсутствии отдельных этапов выполнения сохраняется: выбор секции при запуске не означает последовательного запуска секций как проходов.

## Q24.5. Правила выбранной секции — согласовано

При запуске разбора для выбранной языковой секции активны правила самой секции и всех её предков, включая общие правила вне секций. Правила соседних секций и потомков выбранной секции автоматически не включаются.

Контрольный пример (комментарии обозначают места правил):

```text
// Общие правила
language Java {
  // Правила Java
  language Java11 {
    // Правила Java11
    language Extension {
      // Правила Extension
    }
  }
  language Java17 {
    // Правила Java17
  }
}
language SQL {
  // Правила SQL
}
```

При выборе Java.Java11 используются общие правила, непосредственно Java и непосредственно Java11. Не используются Extension, Java17 и SQL. При выборе Java используются только общие правила и непосредственно Java, без правил вложенных секций. Обозначение пути здесь объясняет выбор; конкретный интерфейс передачи этого выбора при запуске ещё не согласован.

Это обычный выбор активных правил при запуске, а не диагностика и не последовательность этапов. Неактивное правило не применяется даже при подходящем дереве. Отсутствие его применения не является ошибкой само по себе. Порядок активных правил установлен ниже в Q24.6; правила доступности типов этим решением не устанавливаются.

## Q24.6. Порядок активных правил — согласовано

Активные правила сохраняют порядок записи в исходнике: неактивные секции пропускаются, вложенность не повышает приоритет. Подключения include сохраняют ранее установленный порядок вставки правил; допустимость include внутри секций и его контекст ещё предстоит согласовать.

Контрольный пример (буквы обозначают отдельные правила):

```text
// Общее правило A
language Java {
  // Правило B
  language Java11 {
    // Правило C
  }
  // Правило D
}
// Общее правило E
```

Для Java.Java11 порядок — A, B, C, D, E. Для Java — A, B, D, E. Это один список активных правил, а не последовательные этапы.

Граничный случай: если B и C могут примениться в одном текущем контексте, C не получает преимущества из-за большей глубины секции; действует существующая семантика приоритета первого применимого правила (§14.1). Неактивное C при выборе Java не участвует в поиске вообще. Такой выбор не является ошибкой и не требует диагностики.

## Q24.7. Видимость типов секций — согласовано

Тип, объявленный в секции, доступен только внутри этой секции и её подсекций. Из родительской или соседней секции он недоступен. Общие типы вне языковых секций доступны во всех секциях. Глобальная уникальность имён сохраняется: ограничение видимости не разрешает повторять имена в разных секциях.

Предложение о доступности любого типа из любой секции отклонено автором. Генерация классов в разные Java-пакеты не отменяет ограничений видимости DSL.

Допустимый пример (при совместимых схемах преобразуемого дерева):

```text
node CommonWord<String>;
language Java {
  node JavaIdentifier<String>;
  CommonWord<$name> -> JavaIdentifier<$name>;
  language Java11 {
    node Java11Identifier<String>;
    JavaIdentifier<$name> -> Java11Identifier<$name>;
  }
}
```

В Java виден общий CommonWord; в Java11 виден JavaIdentifier из родительской секции. Применимость правил определяется выбранной секцией и обычными проверками дерева.

Недопустимый пример:

```text
language Java {
  node JavaIdentifier<String>;
}
language SQL {
  node SqlIdentifier<String>;
  JavaIdentifier<$name> -> SqlIdentifier<$name>;
}
```

В SQL ссылка на JavaIdentifier недоступна. Это ошибка разрешения имён/проверки доступности DSL до генерации, а не отказ кандидата при выполнении. Аналогично правило непосредственно в Java не может ссылаться на Java11Identifier, объявленный только во вложенной Java11. Выбор Java11 при запуске не делает такой тип видимым для правила, объявленного в родительской секции.

Для datatype та же область видимости подтверждена в Q24.8.

## Q24.8. Видимость datatype — согласовано

На datatype распространяется та же область видимости, что и на типы узлов: объявленный в секции datatype доступен в этой секции и её подсекциях, но недоступен в родительской и соседних секциях. Общие datatype вне секций доступны всем. Глобальная уникальность имён типов узлов и datatype в общем пространстве имён сохраняется.

Контрольный пример: при корректном объявлении datatype JavaText внутри Java запись node JavaName<JavaText>; внутри Java допустима. Запись node Java11Name<JavaText>; внутри Java.Java11 также допустима. Полное объявление datatype здесь не приводится: его синтаксис и контракт остаются прежними.

Граничные примеры: node SqlName<JavaText>; внутри SQL и node CommonName<JavaText>; вне Java недопустимы. Недоступная ссылка диагностируется при разрешении имён/проверке доступности DSL до генерации кода. Выбор Java.Java11 при запуске не меняет область видимости в месте объявления. Повторное объявление JavaText в SQL не разрешается даже при отсутствии взаимной видимости.

## Q24.9. Продолжение секций в нескольких блоках и файлах — согласовано

Одну языковую секцию разрешено продолжать несколькими блоками, в том числе в разных подключённых файлах. Это относится и к вложенным секциям: их части можно разнести по файлам, сохраняя вложенность. Содержимое объединяется, правила сохраняют порядок исходника с учётом include, а не группируются заново по секциям.

Допустимый пример:

```text
// main.dsl
include "java-types.dsl";
include "java-rules.dsl";

// java-types.dsl
language Java {
  language Java11 {
    node Java11Name<String>;
  }
}

// java-rules.dsl
language Java {
  language Java11 {
    node Java11Word<String>;
    Java11Name<$text> -> Java11Word<$text>;
  }
}
```

Оба блока Java продолжают одну секцию Java, оба вложенных блока Java11 — одну Java.Java11. В правиле второго файла виден Java11Name из первого. Для выбранной Java.Java11 правило активно при обычных условиях применимости. Физический перенос части секции в другой файл не меняет её видимость или выходной пакет.

Граница: повторное открытие секции не разрешает повторно объявлять тип Java11Name. Такое повторное объявление остаётся ошибкой проверки объявлений до генерации. Сокращённая запись открытия секции через путь с точками этим примером не вводится. Допустимость include непосредственно внутри секции и контекст включаемого файла ещё не согласованы.
