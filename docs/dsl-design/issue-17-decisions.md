# Задача #17: состав первой версии и текстовый парсер

Рабочий журнал согласования. Зафиксированы только подтверждённые автором решения. После завершения обсуждения синхронизировать общую спецификацию Markdown и HTML, основной журнал решений и список открытых вопросов.

## Q24.1. Имена правил — согласовано

В первой версии правила не имеют имён. Именование правил отложено. Порядок применения остаётся определён существующими правилами обхода и порядком главного файла с include. Диагностика может указывать файл и позицию правила; имя для этого не требуется.

Допустимый пример при объявленном Word<String> и совместимой схеме входа:

```text
'a..z'<$text+>+ -> Word<$text>;
```

Символьная цепочка `abc` сворачивается в Word с данными `abc` по ранее согласованным правилам.

Граничный пример: желание назвать это правило `word` не добавляет ни объявления имени, ни возможности вызвать правило по имени. Конкретный синтаксис именования не согласован и в грамматику v1 не включается; попытка добавить отсутствующую в грамматике конструкцию должна быть отклонена при синтаксическом анализе DSL.

Решение касается только имён отдельных правил. Решение о наборах приведено ниже; языковые секции и пространства имён пока не обсуждены. Решение о проходах приведено ниже. Q24 целиком остаётся открытым.

## Q24.2. Наборы правил — согласовано

В первой версии все правила образуют один общий упорядоченный список. Именованные наборы и независимое включение или выключение групп правил отложены. Разнесение правил по файлам через include сохраняется; подключение файла вставляет его правила в общий список по ранее согласованному порядку.

Основание: для v1 достаточно существующего списка и include, отдельный механизм выбора групп не вводится.

Допустимый пример:

```text
include "lexical.dsl";
include "syntax.dsl";
```

Если lexical.dsl содержит правила преобразования Character в Token, а syntax.dsl — Token в Expression (при соответствующих объявлениях типов и совместимых схемах), оба файла добавляют правила в общий список. Имена файлов не создают наборов.

Граничный пример: указанные include не означают «полностью закончить лексику, затем отдельно запустить синтаксис». Сохраняется текущая семантика: после успешной замены поиск начинается с первого правила в обновлённом контексте. Требование выбрать только набор «лексика» не поддерживается механизмом наборов в v1. Синтаксис объявления или выбора наборов не утверждён; отсутствующая в грамматике конструкция отклоняется при синтаксическом анализе DSL. Отдельное решение о явных проходах приведено ниже.

## Q24.3. Явные проходы — согласовано

В первой версии DSL нет отдельных явно задаваемых этапов преобразования дерева. Управление проходами отложено. Речь идёт о проходах по преобразуемому дереву, а не о чтении исходного текста DSL. Сохраняется единый список правил и ранее согласованный порядок применения и обхода.

Основание: наборы правил уже отложены; для v1 не вводится дополнительный механизм переключения между этапами.

Допустимый пример при объявленных типах и совместимой схеме:

```text
'a..z'<$text+>+ -> Word<$text>;
Word as w -> Expression[$w];
```

Оба правила участвуют в общем порядке поиска. После успешной замены поиск начинается с первого правила в обновлённом контексте, как установлено §14.1. Этот пример не задаёт отдельного завершённого этапа лексики перед этапом синтаксиса.

Граничный сценарий: «сначала применять только лексические правила до завершения, затем только синтаксические без возврата к лексическим» не выражается специальными этапами DSL v1. Разделение через include также не создаёт этапов. Синтаксис объявления этапов не утверждён и не добавляется в грамматику; отсутствующая в грамматике конструкция отклоняется при синтаксическом анализе DSL.

Это решение не меняет ранее установленного разделения построения дерева с узлами-действиями и отдельного исполнения этих действий: движок DSL по-прежнему не исполняет действия.
