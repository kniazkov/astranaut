## Исходные наблюдения — не проектные решения

Изучены README, парсер, ключевые части сопоставления и тесты astranaut, примеры uast/trastformer и документы новой модели core.

- `A <- B` объявляет узел с одним ребёнком; абстрактный тип с единственным подтипом записывается `A <- B | 0`.
- Повторяющиеся дети в объявлениях представлены отдельной формой `List <- {Item}`; смешанные схемы текущий парсер не поддерживает.
- Повторное объявление одного номера узлового захвата слева запрещено; повторные записи в захват данных конкатенируются.
- Шаблон `A` требует отсутствия детей, но в интерпретаторе не требует отсутствия данных, вопреки README.
- Теги объявляются в схемах; шаблоны и результат используют позиционные списки детей.
- В uast.dsl сохранились старые формы `$...$`, `#1...` и данные после детей.
- Разбор разделителей местами не учитывает кавычки.
- Генератор ещё зависит от старого `org.cqfn:astranaut-core:1.2.13`; новая модель core требует отдельного согласования.

## Принятые решения

### D001. Новый проект без обязательств по совместимости — принято 26.10.2026

Astranaut рассматривается как новый проект. Старые синтаксис, семантика, архитектура и реализация не накладывают ограничений на проектирование. Обратная совместимость со старыми DSL-файлами не требуется; сохранять старые конструкции или вводить режим совместимости ради них не нужно. Существующий код и примеры служат материалом для анализа, а не нормативной спецификацией. Новые решения принимаются явно в ходе обсуждения; это решение само по себе не утверждает конкретный синтаксис и не поручает сейчас переписывать реализацию. Необходимость и объём переноса старых примеров определим отдельно.

### D002. Явные объявления типов и наследуемые дети — принято 26.10.2026

Абстрактные типы и конкретные узлы объявляются явно различимыми конструкциями с ключевыми словами. Абстрактный тип может объявлять детей; эти объявления наследуются потомками, без необходимости дублировать их в каждом конкретном типе. Абстрактный тип нельзя непосредственно инстанцировать.

Иллюстрация (окончательные ключевые слова и пунктуация ещё не утверждены):

```text
abstract Expression;
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);
node Addition : BinaryExpression;
node Subtraction : BinaryExpression;
```

Addition и Subtraction наследуют объявления left и right. Это декларации детей в базовом типе, а не вывод общих полей из уже описанных потомков.

Множественное наследование разрешено только от абстрактных типов (D003, D013). Совпадение и совместимость детей определены в D003–D005. Открыты: остальные правила порядка наследуемых и собственных детей и детали ромбовидного наследования. Безымянных детей в базах не бывает (D013). Конфликты типов баз нельзя устранять переобъявлением (D012). Сужение типа ребёнка в потомке разрешено в D011. Согласование с core выполняется при проектировании реализации.

### D003. Множественное наследование и точное совпадение типов детей — принято 26.10.2026

Разрешено наследование от нескольких абстрактных типов, в том числе объявляющих детей. Совпадающие унаследованные дети должны иметь строго одинаковый тип. Разные типы являются конфликтом даже при отношении подтип/надтип; автоматический выбор общего базового или более узкого типа не допускается.

Это решение фиксирует требование к типу. Кратность уточнена в D004. Совпадение по тегу и объединение объявлений определены в D005. Порядок определён в D008–D010 для рассмотренных случаев; остальные случаи и детали ромбовидного наследования требуют уточнения.

### D004. Точное совпадение кратности наследуемых детей — принято 26.10.2026

У совпадающих унаследованных детей должны строго совпадать и тип (D003), и кратность. Обязательный, необязательный и повторяющийся ребёнок — разные кратности; любое их несовпадение является ошибкой определения типа. Автоматическое усиление или ослабление кратности при объединении баз не допускается.

Пример: два совпадающих обязательных ребёнка типа Expression совместимы по типу и кратности; обязательный Expression и необязательный Expression — конфликт. Правила определения совпадения и объединения объявлений зафиксированы в D005.

### D005. Совпадение по тегу и объединение объявлений — принято 26.10.2026

Совпадение детей определяется по тегу. Совместимые объявления с одинаковым тегом из разных баз обозначают одного ребёнка потомка. Их тип и кратность должны строго совпадать (D003–D004). Разные теги обозначают разных детей, даже если тип и кратность одинаковы.

### D006. Обязательность тегов — принято 26.10.2026

Все дети в абстрактных узлах обязательно имеют теги. В конкретных (неабстрактных) узлах допускаются дети без тегов. Общее требование для абстрактных типов не содержит исключения для повторяющихся детей; старое ограничение core на теги повторяющихся позиций не является ограничением нового DSL (D001). Представление таких тегов в API предстоит согласовать отдельно.

### D007. Прежняя запись о конкретных базах — отменена D013

Запись о допустимости наследования от конкретных типов отменена уточнением пользователя: наследоваться можно только от абстрактных типов. Действующее правило явного порядка изложено в D008.

### D008. Явный порядок при объединении детей нескольких баз — принято 26.10.2026

Если потомок (конкретный или абстрактный, D032) получает разных детей от нескольких абстрактных баз, он обязан явно перечислить всех наследуемых детей, определив их итоговый порядок. Конкретные типы не могут быть базами (D013). Совместимые совпадающие объявления предварительно объединяются по тегу (D005).

Пример (синтаксис условный):

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);
node Addition : HasLeft, HasRight (left, right);
```

В этом примере ссылки left и right используют унаследованные типы и кратности; повторять их объявления для задания порядка не требуется. Перечисление (right, left) задаёт обратный порядок. Объявление Addition без явного списка в этом случае является ошибкой.

Перестановка детей внутри одной базы разрешена в D010. Окончательная грамматика ссылок ещё не утверждена.

### D009. Полный список при добавлении собственных детей — принято 26.10.2026

Если потомок (конкретный или абстрактный, D032) добавляет собственных детей, он обязан явно перечислить полный состав детей в итоговом порядке, включая всех унаследованных. Это требование действует и при единственной базе. Новых детей можно размещать между унаследованными; автоматического добавления в начало или конец нет.

Пример (синтаксис условный):

```text
abstract Binary (left: Expression, right: Expression);
node ConditionalBinary : Binary (
    left,
    condition: Expression,
    right
);
```

left и right сохраняют унаследованные типы и кратности; condition объявляется в потомке. При одной базе и отсутствии собственного списка сохраняются состав и порядок детей базы. Возможность менять взаимный порядок унаследованных детей утверждена в D010.

### D010. Окончательный порядок задаёт потомок — принято 26.10.2026

Потомок вправе явно менять взаимный порядок унаследованных детей, в том числе детей одной базы. Окончательный порядок устанавливает потомок; порядок баз не является ограничением для его явного списка. Перестановка сама по себе не меняет теги, типы или кратности детей. Доступ по тегу сохраняет смысл, а доступ по индексу отражает порядок конкретного типа.

Пример (синтаксис условный):

```text
abstract Binary (left: Expression, right: Expression);
node Reversed : Binary (right, left);
```

Правило D009 о наследовании порядка единственной базы при отсутствии собственного списка сохраняется: D010 разрешает его явно изменить.

### D011. Явное сужение типа ребёнка в потомке — принято 26.10.2026

Потомок не может менять кратность унаследованного ребёнка. Он может явно переобъявить тип ребёнка более узким типом, если новый тип наследуется от исходного в объявленной иерархии типов. Структурного сходства типов недостаточно. Расширение типа и замена несвязанным типом запрещены. Тег сохраняет идентичность ребёнка.

Пример пользователя (синтаксис условный):

```text
abstract Expression;
abstract AssignableExpression : Expression;
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);
node Assignment : BinaryExpression (
    left: AssignableExpression,
    right
);
```

Assignment сужает тип left с Expression до AssignableExpression; тип right и кратности обоих детей сохраняются. Предложение запретить любое изменение типа отклонено.

D003 описывает совпадение объявлений из разных баз, а D011 — явное переобъявление в потомке. D012 запрещает устранять конфликт нескольких баз даже явным сужением; уточнять тип разрешено последовательно в потомках.

### D012. Конфликт типов баз нельзя устранить уточнением — принято 26.10.2026

Разные типы детей с одинаковым тегом в наследуемых базах всегда означают ошибку, даже если один тип наследуется от другого. Явное переобъявление в потомке не устраняет этот конфликт. Требование точного совпадения типов при объединении баз (D003) сохраняется.

Сужение разрешено последовательно в потомках: на каждом шаге тип ребёнка можно уточнить до его подтипа при неизменной кратности (D011). Совместимость объявлений из баз проверяется до применения уточнений самого потомка.

Примеры (A и B — абстрактные типы):

- A объявляет value: Expression, B объявляет value: AssignableExpression — наследование от A и B одновременно ошибочно, даже при явном value: AssignableExpression в потомке.
- A объявляет value: Expression, B наследует A и уточняет value до AssignableExpression — допустимо. Дальнейший потомок B может снова сузить тип по объявленной иерархии.

### D013. Базами могут быть только абстрактные типы — уточнено 26.10.2026

Наследоваться от конкретного (неабстрактного) узла запрещено. Базами как абстрактного, так и конкретного типа могут быть только абстрактные типы. Все дети абстрактных типов обязательно именованы (D006), поэтому безымянных унаследованных детей не бывает.

Конкретный узел может объявлять собственных детей без тегов, но сам не может служить базой. Последовательное сужение типа ребёнка (D011–D012) выполняется через абстрактные промежуточные типы и может завершаться конкретным узлом.

Это уточнение отменяет прежнюю запись D007 о допустимости конкретных баз. Правила полного списка, порядка и сужения из D008–D012 сохраняются для допустимых абстрактных баз. Предыдущий вопрос о безымянных детях в базах снят как неприменимый.

### D014. Несколько повторяющихся групп и однозначное распределение — принято 26.10.2026

В одном типе разрешено несколько повторяющихся групп детей. Предложение P001 принято с правилами:

- При единственном допустимом распределении входных детей по группам распределение выполняется автоматически.
- При отсутствии допустимых распределений сообщается ошибка несовместимости с типами или кратностями схемы.
- При нескольких допустимых распределениях сообщается неоднозначность; группы необходимо задать явно по тегам. Неявный жадный выбор не допускается.

Теги в схеме сами по себе не разрешают неоднозначность плоского входного списка без привязок. Например, для first: Expression*, second: Expression* единственный Expression можно отнести к любой группе. Разные имена типов тоже не гарантируют непересечение: возможны общие подтипы.

Разбор текста декларации с несколькими группами однозначен; отдельная задача — распределение готовых детей. Перестановки между позициями схемы разрешены при однозначном распределении (D015); внутренний порядок повторяющихся групп определён в D016, синтаксис явного задания групп ещё не согласован. Для безымянных групп конкретного типа способ явного разрешения неоднозначности требует отдельного решения.

### D015. Автоматическое распределение не ограничено порядком входа — принято 26.10.2026

Если детей можно распределить однозначно, порядок их передачи не препятствует построению узла. Алгоритм должен пытаться найти единственное допустимое полное распределение с учётом типов, кратностей и явно заданных привязок; он не должен отклонять вход только потому, что дети переданы не в порядке схемы.

Локальная неоднозначность для отдельного ребёнка ещё не означает неоднозначность всего распределения: остальные дети и требования схемы могут оставить единственный полный вариант. Не допускается останавливаться на неудаче жадного выбора, если другое распределение решает задачу. При отсутствии полного решения или нескольких полных решениях действуют ошибки из D014.

Пример: схема (parameters: Parameter*, body: Statement*), вход [Statement, Parameter] допустим, если типы однозначно определяют группы. В результате группы располагаются в порядке схемы конкретного типа.

Предложение обязательно сохранять общий порядок позиционного входного списка отклонено. Порядок элементов внутри повторяющейся группы определён в D016. Роль входного порядка для двух обязательных одиночных позиций одинакового типа определена в D017; остальные случаи требуют согласования. Это правило построения узла; семантика сопоставления шаблонов обсуждается отдельно.

### D016. Стабильный порядок внутри повторяющейся группы — принято 26.10.2026

При автоматическом распределении внутри каждой повторяющейся группы сохраняется исходный относительный порядок попавших в неё детей. Распределение может переместить детей между позициями общего списка согласно схеме (D015), но не переставляет элементы внутри группы.

Пример при однозначной принадлежности к группам:

```text
Схема: parameters: Parameter*, body: Statement*
Вход: Statement₁, Parameter₂, Statement₂, Parameter₁
parameters: Parameter₂, Parameter₁
body: Statement₁, Statement₂
```

Итоговый плоский список в порядке схемы: Parameter₂, Parameter₁, Statement₁, Statement₂.

### D017. Обязательные одиночные позиции одинакового типа различаются порядком входа

Для двух обязательных одиночных позиций одинакового типа дети назначаются в порядке входа согласно окончательному порядку позиций в схеме потомка.

Условный пример: схема `(left: Expression, right: Expression)`, вход `[a, b]` — результат `left=a, right=b`. Перестановка `left=b, right=a` не считается вторым допустимым распределением. Явные привязки по тегам позволяют задать другое назначение.

Это уточняет критерий однозначности D014–D015: порядок различает такие обязательные одиночные позиции. Случай одного ребёнка для двух необязательных позиций определён в D018. Случай двух заполненных необязательных позиций определён в D019. Пересекающиеся типы для двух заполненных одиночных позиций рассмотрены в D020. Остальные обобщения пока не согласованы.

### D018. Один ребёнок для двух необязательных позиций — неоднозначность

Для схемы `(left: Expression?, right: Expression?)` и входа `[a]` без явных привязок существуют два допустимых распределения: заполнить только left или только right. Это неоднозначность; требуется явная привязка ребёнка по тегу.

Порядок входа не определяет, какая необязательная позиция пропущена. Автоматически выбирать первую позицию запрещено. Правило D017 не устраняет эту неоднозначность.

### D019. Две заполненные необязательные позиции одинакового типа

Для схемы `(left: Expression?, right: Expression?)` и входа `[a, b]` без явных привязок назначается `left=a, right=b` по порядку входа. Перестановка детей не считается альтернативным распределением.

Обе позиции заполнены, поэтому неопределённости о пропущенной позиции нет. Для одного входного ребёнка сохраняется неоднозначность D018. Это расширяет правило D017 на две заполненные необязательные позиции одинакового типа.

### D020. Порядок для двух заполненных одиночных позиций с пересекающимися типами

Если две одиночные позиции заполнены и оба входных ребёнка подходят обеим позициям, выбор определяется порядком входа относительно окончательного порядка позиций в схеме. Это действует и при разных объявленных типах позиций.

Условный пример: `(left: AssignableExpression, right: Expression)`, где AssignableExpression явно наследует Expression; вход `[a, b]`, оба ребёнка имеют тип AssignableExpression. Результат: `left=a, right=b`; обратное назначение не считается альтернативой.

Типовая совместимость имеет приоритет: если допустимо только обратное назначение, выбирается оно согласно D015. Порядок разрешает оставшийся выбор между взаимозаменяемыми детьми, а не запрещает единственное корректное распределение. Это решение касается двух заполненных одиночных позиций. Сочетание обязательной одиночной позиции с повторяющейся группой одного типа определено в D021; общее правило для произвольного числа позиций одного типа определено в D022.

### D021. Обязательная одиночная позиция и повторяющаяся группа одного типа

Предложение считать схему `(head: Expression, tail: Expression*)` неоднозначной для входа `[a, b]` отклонено пользователем: первый ребёнок назначается head, остальные — tail. Для обратной схемы `(head: Expression*, tail: Expression)` последние и первые дети распределяются соответственно: последний ребёнок назначается tail, все предыдущие — head.

Для N ≥ 1 совместимых входных детей кратности однозначно определяют размеры: (1, N−1) в первой схеме и (N−1, 1) во второй. Порядок входа определяет наполнение этих частей. Пустой вход не удовлетворяет обязательной позиции. Это расширяет использование порядка за пределы одиночных позиций; перестановки взаимозаменяемых детей между частями не создают дополнительную неоднозначность.

Для схемы `(head: Expression?, tail: Expression*)` непустой вход неоднозначен: допустимы размеры (0, N) и (1, N−1). Нельзя автоматически предпочитать заполнение head или его пропуск; нужна явная привязка, снимающая неоднозначность. Уточнение при разборе примера: пустой вход однозначен — обе части пусты.

Все примеры относятся к одному объявленному типу Expression и входным детям, совместимым с ним, без явных привязок. Общая формулировка для произвольного числа позиций одного типа определена в D022. Правило D015 о возможности перестановки при единственном типосовместимом распределении сохраняется.

### D022. Распределение по размерам позиций одного типа

Для произвольного числа позиций одного объявленного типа без явных привязок, когда все входные дети совместимы с этим типом, определяются допустимые наборы количеств детей по позициям. Сумма количеств равна числу входных детей; обязательная позиция получает одного ребёнка, необязательная — ноль или одного, повторяющаяся — любое неотрицательное количество.

- Если допустимый набор количеств единственный, вход последовательно разбивается по этим количествам в окончательном порядке позиций схемы.
- Если наборов несколько, сообщается неоднозначность; произвольный жадный выбор границ запрещён.
- Если наборов нет, вход несовместим со схемой.

Пример `(first: Expression, middle: Expression*, last: Expression)` при N ≥ 2 имеет единственный набор (1, N−2, 1): первый ребёнок, середина, последний ребёнок.

Пример пользователя `(first: Expression, second: Expression*, third: Expression*, fourth: Expression)`: первый и последний дети фиксированы. При N ≥ 3 середина допускает разные разделения между second и third, поэтому вход неоднозначен. Уточнение граничных случаев: при N = 2 обе группы пусты и распределение однозначно; при N < 2 обязательные позиции заполнить невозможно.

Это обобщает D017–D019 и D021 для позиций одного типа. Случаи разных типов требуют учёта типовой совместимости по D015 и D020; правило одинаковых типов не подменяет общий алгоритм.

### D023. Сначала согласовать явный синтаксис принятой модели

По просьбе пользователя дальнейшее расширение семантики приостановлено: сначала нужно определить конкретную запись уже обсуждённых конструкций. Подготовлен проект S001 ниже; его пунктуация, ключевые слова и лексические детали пока не утверждены.

Отложены без принятия решения: смешанное явное и автоматическое заполнение, закрытость явно заданной группы для добавления, а также предложенное использование `=` при создании узла. Объявления и создание узлов рассматриваются отдельно. После фиксации каждого ответа задаётся следующий вопрос, пока остаются открытые вопросы.

### D024. Основа синтаксиса объявлений и необязательное node после abstract

Принята основа S001: конкретный тип объявляется через `node`, абстрактный — через `abstract` или `abstract node`; базы записываются после `:`, дети — в `(...)`, именованный ребёнок — `tag: Type`, кратности — `?` и `*`, ссылка на унаследованного ребёнка — `@tag`, объявление завершается `;`.

По уточнению пользователя, `abstract XXX;` и `abstract node XXX;` полностью равнозначны. Слово node после abstract необязательно и подразумевается при его отсутствии. Обе формы допускают одинаковые списки баз и детей и не создают разных видов типов.

Принятие основы не утверждает дополнительные лексические предложения (набор символов идентификаторов, комментарии и прочее) и не возвращает отложенный вопрос создания узлов.

### D025. Завершающая запятая в списке детей

В непустом списке детей допускается одна завершающая запятая перед `)`, как в многострочной, так и в однострочной записи. Например, `node Pair (left: Expression, right: Expression,);`. Запятая не создаёт дополнительного ребёнка и не меняет семантику списка.

Пустой список записывается `()`, а не `(,)`. Пропущенные элементы и двойные запятые не разрешены. Это решение касается списка детей; форма списка баз им не изменяется.

### D026. Строчные и блочные комментарии

Разрешены комментарии `//` до конца строки и `/* ... */` для блока, в том числе многострочного. Блочные комментарии не поддерживают вложенность: первый `*/` завершает текущий блок. Незакрытый блочный комментарий является лексической ошибкой; строчный комментарий может завершаться концом файла.

Комментарии допустимы между токенами и служат разделителями: `abstract/* пояснение */node` разбирается как два ключевых слова, а части идентификатора через комментарий не склеиваются. Внутри комментариев другой вид комментария не открывается.

### D027. Идентификаторы и зарезервированные слова

Имена типов и теги соответствуют `[A-Za-z_][A-Za-z0-9_]*`: первая позиция — латинская буква ASCII или подчёркивание, далее также допускаются цифры ASCII. Регистр различается. Например, `BinaryExpression`, `left`, `_item2` допустимы, `2item` — нет.

Слова `abstract` и `node` зарезервированы и не могут использоваться как имена типов или теги. Unicode-идентификаторы пока не вводятся. Это ограничение идентификаторов не ограничивает текст комментариев латиницей. Квалифицированные имена и пространства имён рассматриваются отдельно.

### D028. Ссылки на типы до их объявления

В пределах одного файла разрешены ссылки на типы, объявленные ниже: как в списках баз, так и в объявлениях детей. Порядок объявлений не определяет доступность имени типа.

Сначала собираются объявления, затем разрешаются ссылки и проверяются ограничения типов. Имя, которое так и не было объявлено, является ошибкой. Это решение не определяет импорт и видимость между файлами и не разрешает циклическое наследование автоматически.

Пример:

```text
node Addition : BinaryExpression;

abstract BinaryExpression (
    left: Expression,
    right: Expression
);

abstract Expression;
```

### D029. Рекурсия через детей и запрет циклов наследования

Рекурсивные ссылки через типы детей разрешены. Например, `node Block (items: Block*);` описывает узел, содержащий вложенные узлы того же типа; пустая группа позволяет создать лист.

Граф наследования должен быть ациклическим. Запрещены как непосредственное наследование от самого себя, так и циклы через несколько баз. Например, `abstract A : B;` вместе с `abstract B : A;` является ошибкой. Наличие ссылок вперёд (D028) этого ограничения не отменяет.

Рекурсивное описание типов само по себе не означает разрешения циклов в экземплярах дерева. Проверка возможности построить конечный узел для рекурсивных схем с обязательными детьми этим решением не определена и остаётся отдельным вопросом.

### D030. Запрет повторного объявления типа

В одном файле каждый тип объявляется один раз. Повторное объявление того же имени является ошибкой, даже если текст и смысл объявлений полностью совпадают. Формы `abstract X;` и `abstract node X;` равнозначны (D024), поэтому их совместное использование для одного имени также является повторным объявлением.

`abstract Expression;` — полноценное определение типа, а не предварительная декларация и не заготовка для последующего дополнения. Расширять объявление вторым объявлением того же имени нельзя. Для ссылок вперёд предварительные декларации не нужны (D028). Правила между файлами будут определены вместе с импортом и пространствами имён.

### D031. Уникальность тегов в явном списке детей

В явном списке детей один тег может встречаться только один раз. Запрещены повторные объявления одного тега, повторные ссылки `@tag`, а также сочетание ссылки и переобъявления того же тега в одном списке. Совпадение типов и кратностей не делает такие повторы допустимыми.

Объединение совместимых одноимённых детей из разных баз по D005 сохраняется: оно выполняется до обработки явного списка, где объединённая позиция указывается один раз. Повторение типа у разных тегов или у безымянных позиций само по себе не является повторением тега.

### D032. Единые правила порядка для абстрактных и конкретных потомков

Правила D008–D010 распространяются и на абстрактные типы. При получении разных детей из нескольких баз либо добавлении собственных детей потомок обязан явно перечислить полный состав детей в окончательном порядке, включая всех унаследованных после объединения совместимых одноимённых позиций.

При одной базе и отсутствии собственного списка наследуются её состав и порядок. Потомок может явно переставить унаследованные позиции через `@tag`. Все дети абстрактного типа по-прежнему должны иметь теги (D006). Требования к сохранению кратности, сужению типа и уникальности тегов не меняются.

Пример:

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);

abstract Binary : HasLeft, HasRight (
    @left,
    @right
);
```

### D033. Разный порядок одинаковых детей в нескольких базах

Если несколько баз содержат один и тот же набор совместимых детей, но задают разный порядок, потомок обязан явно перечислить детей в выбранном окончательном порядке. Правило действует для абстрактных и конкретных потомков.

Различие порядка само по себе не делает объявления детей несовместимыми: дети объединяются по тегам согласно D005 при точном совпадении типов и кратностей. Однако без явного списка порядок не выбирается автоматически, в том числе по порядку перечисления баз.

Пример:

```text
abstract A (left: Expression, right: Expression);
abstract B (right: Expression, left: Expression);
node C : A, B (@left, @right);
```

Объявление `node C : A, B;` в этом примере ошибочно; вариант `(@right, @left)` также допустим.

## Синтаксис объявлений S001 — основа принята (D024–D027)

Основа записи объявлений принята в D024 на базе семантики D002–D022. Правила комментариев и идентификаторов приняты в D026–D027. Примеры в журнале решений выше остаются историческими условными иллюстрациями. Запись создания узлов, явного заполнения и смешивания аргументов отложена.

### Объявления и наследование

```text
abstract Expression;
abstract AssignableExpression : Expression;

abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);

node Addition : BinaryExpression;
node Assignment : BinaryExpression (
    left: AssignableExpression,
    @right
);
```

- `abstract` и `abstract node` равнозначно объявляют абстрактный тип; `node` без abstract — конкретный тип узла. Например, `abstract Expression;` и `abstract node Expression;` означают одно и то же.
- После `:` за именем типа перечисляются абстрактные базы через запятую.
- В круглых скобках записывается состав детей в итоговом порядке.
- Каждое объявление заканчивается `;`.
- Отсутствие списка при единственной базе сохраняет её детей и порядок (D009). Явный список не означает частичного добавления; для абстрактного и конкретного потомка применяются требования полноты D008–D009 и D032.
- Пустой список `()` обозначает отсутствие детей; он не разрешает удалить унаследованных детей. Конкретный тип без баз и без списка детей также не имеет детей.
- Наследование от конкретного типа запрещено.

### Дети и кратности

| Запись | Значение |
|---|---|
| `value: Expression` | Один обязательный ребёнок с тегом value |
| `value: Expression?` | Ноль или один ребёнок |
| `items: Expression*` | Ноль или больше детей |
| `Expression`, `Expression?`, `Expression*` | Собственные дети без тега, только в конкретном типе |
| `@value` | Ссылка на унаследованного ребёнка с сохранением типа и кратности |

Используется отдельный знак `@` для ссылки на унаследованный тег: иначе одиночное имя может означать и тег, и тип безымянного ребёнка. Регистр букв не используется для различения. `@` здесь не создаёт ребёнка и не задаёт его значение.

Совпадающий с унаследованным тег в записи `tag: Type` означает повторное объявление этой позиции. Допускается прежний тип либо его явное сужение согласно D011; кратность должна быть сохранена, включая суффикс `?` или `*`. Конфликт типов баз этим не исправляется (D012).

```text
abstract Sequence (
    items: Expression*
);

node AssignableSequence : Sequence (
    items: AssignableExpression*
);

node Pair (Expression, Expression);
```

### Несколько баз и переупорядочивание

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);

node Combined : HasLeft, HasRight (
    @left,
    @right
);

node Reversed : BinaryExpression (
    @right,
    @left
);

node Extended : BinaryExpression (
    @left,
    extra: Expression?,
    @right
);
```

Ссылки сохраняют объявления баз, но задают порядок потомка. Совпадающие совместимые дети нескольких баз предварительно объединяются по тегу. Неизвестная ссылка `@tag` — ошибка. Правила полного списка и порядка одинаковы для абстрактных и конкретных потомков (D032).

### Несколько повторяющихся групп

```text
node Framed (
    first: Expression,
    middle: Expression*,
    last: Expression
);

node Split (
    first: Expression,
    second: Expression*,
    third: Expression*,
    fourth: Expression
);
```

Обе декларации допустимы и разбираются однозначно. Для Framed распределение совместимых детей однозначно при количестве от двух. Для Split два ребёнка распределяются однозначно, три и более без дополнительных привязок дают неоднозначность распределения (D022). Такая неоднозначность конкретного входа не запрещает само объявление типа.

### Грамматика объявлений

В этой EBNF фигурные скобки обозначают повторение, квадратные — необязательную часть, а терминалы заключены в кавычки.

```text
declaration = kind, identifier, [bases], [children], ";" ;
kind        = "abstract", ["node"] | "node" ;
bases       = ":", identifier, {",", identifier} ;
children    = "(", [child, {",", child}, [","]], ")" ;
child       = "@", identifier
            | identifier, ":", identifier, [multiplicity]
            | identifier, [multiplicity] ;
multiplicity = "?" | "*" ;
```

Форма `identifier` перед `:` внутри списка детей — тег, после `:` — тип; одиночный identifier — тип безымянного ребёнка. Ссылка на унаследованный тег начинается с `@`. После запятой списка баз ожидается имя очередной базы, а открывающая скобка начинает список детей.

Завершающая запятая в непустом списке детей разрешена в D025. Комментарии `//` до конца строки и `/* ... */` без вложенности приняты в D026; комментарии разделяют токены.

Идентификаторы соответствуют `[A-Za-z_][A-Za-z0-9_]*`, регистр различается; слова `abstract` и `node` зарезервированы (D027). Unicode-идентификаторы пока не вводятся. Квалифицированные имена и остальные детали лексики требуют отдельного рассмотрения.

Грамматика описывает форму записи. Требования к тегам в абстрактных типах, наследованию, совместимости, полноте списка и распределению детей проверяются семантически.

Если несколько баз содержат полностью одинаковые списки детей — теги, типы, кратности и порядок совпадают — разрешаем ли потомку опустить список? Предложение: да; совместимые позиции объединяются, а общий порядок наследуется. Например, `abstract A (value: Expression); abstract B (value: Expression); node C : A, B;`.

## Критерии завершения

- Все темы рассмотрены; оставшиеся отложенные вопросы явно перечислены.
- Каждое решение отражено в задаче и документах PR.
- Спецификация отделяет синтаксис от семантики и содержит корректные и некорректные примеры.
- Определены совместимость, миграция и задачи реализации.
