## Исходные наблюдения — не проектные решения

Изучены README, парсер, ключевые части сопоставления и тесты astranaut, примеры uast/trastformer и документы новой модели core.

- `A <- B` объявляет узел с одним ребёнком; абстрактный тип с единственным подтипом записывается `A <- B | 0`.
- Повторяющиеся дети в объявлениях представлены отдельной формой `List <- {Item}`; смешанные схемы текущий парсер не поддерживает.
- Повторное объявление одного номера узлового захвата слева запрещено; повторные записи в захват данных конкатенируются.
- Шаблон `A` требует отсутствия детей, но в интерпретаторе не требует отсутствия данных, вопреки README.
- Теги объявляются в схемах; шаблоны и результат используют позиционные списки детей.
- В uast.dsl сохранились старые формы `$...$`, `#1...` и данные после детей.
- Разбор разделителей местами не учитывает кавычки.
- Генератор ещё зависит от старого `org.cqfn:astranaut-core:1.2.13`; новая модель core требует отдельного согласования.

## Принятые решения

### D001. Новый проект без обязательств по совместимости — принято 26.10.2026

Astranaut рассматривается как новый проект. Старые синтаксис, семантика, архитектура и реализация не накладывают ограничений на проектирование. Обратная совместимость со старыми DSL-файлами не требуется; сохранять старые конструкции или вводить режим совместимости ради них не нужно. Существующий код и примеры служат материалом для анализа, а не нормативной спецификацией. Новые решения принимаются явно в ходе обсуждения; это решение само по себе не утверждает конкретный синтаксис и не поручает сейчас переписывать реализацию. Необходимость и объём переноса старых примеров определим отдельно.

### D002. Явные объявления типов и наследуемые дети — принято 26.10.2026

Абстрактные типы и конкретные узлы объявляются явно различимыми конструкциями с ключевыми словами. Абстрактный тип может объявлять детей; эти объявления наследуются потомками, без необходимости дублировать их в каждом конкретном типе. Абстрактный тип нельзя непосредственно инстанцировать.

Иллюстрация (окончательные ключевые слова и пунктуация ещё не утверждены):

```text
abstract Expression;
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);
node Addition : BinaryExpression;
node Subtraction : BinaryExpression;
```

Addition и Subtraction наследуют объявления left и right. Это декларации детей в базовом типе, а не вывод общих полей из уже описанных потомков.

Множественное наследование разрешено только от абстрактных типов (D003, D013). Совпадение и совместимость детей определены в D003–D005. Открыты: остальные правила порядка наследуемых и собственных детей и детали ромбовидного наследования. Безымянных детей в базах не бывает (D013). Конфликты типов баз нельзя устранять переобъявлением (D012). Сужение типа ребёнка в потомке разрешено в D011. Согласование с core выполняется при проектировании реализации.

### D003. Множественное наследование и точное совпадение типов детей — принято 26.10.2026

Разрешено наследование от нескольких абстрактных типов, в том числе объявляющих детей. Совпадающие унаследованные дети должны иметь строго одинаковый тип. Разные типы являются конфликтом даже при отношении подтип/надтип; автоматический выбор общего базового или более узкого типа не допускается.

Это решение фиксирует требование к типу. Кратность уточнена в D004. Совпадение по тегу и объединение объявлений определены в D005. Порядок определён в D008–D010 для рассмотренных случаев; остальные случаи и детали ромбовидного наследования требуют уточнения.

### D004. Точное совпадение кратности наследуемых детей — принято 26.10.2026

У совпадающих унаследованных детей должны строго совпадать и тип (D003), и кратность. Обязательный, необязательный и повторяющийся ребёнок — разные кратности; любое их несовпадение является ошибкой определения типа. Автоматическое усиление или ослабление кратности при объединении баз не допускается.

Пример: два совпадающих обязательных ребёнка типа Expression совместимы по типу и кратности; обязательный Expression и необязательный Expression — конфликт. Правила определения совпадения и объединения объявлений зафиксированы в D005.

### D005. Совпадение по тегу и объединение объявлений — принято 26.10.2026

Совпадение детей определяется по тегу. Совместимые объявления с одинаковым тегом из разных баз обозначают одного ребёнка потомка. Их тип и кратность должны строго совпадать (D003–D004). Разные теги обозначают разных детей, даже если тип и кратность одинаковы.

### D006. Обязательность тегов — принято 26.10.2026

Все дети в абстрактных узлах обязательно имеют теги. В конкретных (неабстрактных) узлах допускаются дети без тегов. Общее требование для абстрактных типов не содержит исключения для повторяющихся детей; старое ограничение core на теги повторяющихся позиций не является ограничением нового DSL (D001). Представление таких тегов в API предстоит согласовать отдельно.

### D007. Прежняя запись о конкретных базах — отменена D013

Запись о допустимости наследования от конкретных типов отменена уточнением пользователя: наследоваться можно только от абстрактных типов. Действующее правило явного порядка изложено в D008.

### D008. Явный порядок при объединении детей нескольких баз — принято 26.10.2026

Если потомок (конкретный или абстрактный, D032) получает разных детей от нескольких абстрактных баз, он обязан явно перечислить всех наследуемых детей, определив их итоговый порядок. Конкретные типы не могут быть базами (D013). Совместимые совпадающие объявления предварительно объединяются по тегу (D005).

Пример (синтаксис условный):

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);
node Addition : HasLeft, HasRight (left, right);
```

В этом примере ссылки left и right используют унаследованные типы и кратности; повторять их объявления для задания порядка не требуется. Перечисление (right, left) задаёт обратный порядок. Объявление Addition без явного списка в этом случае является ошибкой.

Перестановка детей внутри одной базы разрешена в D010. Окончательная грамматика ссылок ещё не утверждена.

### D009. Полный список при добавлении собственных детей — принято 26.10.2026

Если потомок (конкретный или абстрактный, D032) добавляет собственных детей, он обязан явно перечислить полный состав детей в итоговом порядке, включая всех унаследованных. Это требование действует и при единственной базе. Новых детей можно размещать между унаследованными; автоматического добавления в начало или конец нет.

Пример (синтаксис условный):

```text
abstract Binary (left: Expression, right: Expression);
node ConditionalBinary : Binary (
    left,
    condition: Expression,
    right
);
```

left и right сохраняют унаследованные типы и кратности; condition объявляется в потомке. При одной базе и отсутствии собственного списка сохраняются состав и порядок детей базы. Возможность менять взаимный порядок унаследованных детей утверждена в D010.

### D010. Окончательный порядок задаёт потомок — принято 26.10.2026

Потомок вправе явно менять взаимный порядок унаследованных детей, в том числе детей одной базы. Окончательный порядок устанавливает потомок; порядок баз не является ограничением для его явного списка. Перестановка сама по себе не меняет теги, типы или кратности детей. Доступ по тегу сохраняет смысл, а доступ по индексу отражает порядок конкретного типа.

Пример (синтаксис условный):

```text
abstract Binary (left: Expression, right: Expression);
node Reversed : Binary (right, left);
```

Правило D009 о наследовании порядка единственной базы при отсутствии собственного списка сохраняется: D010 разрешает его явно изменить.

### D011. Явное сужение типа ребёнка в потомке — принято 26.10.2026

Потомок не может менять кратность унаследованного ребёнка. Он может явно переобъявить тип ребёнка более узким типом, если новый тип наследуется от исходного в объявленной иерархии типов. Структурного сходства типов недостаточно. Расширение типа и замена несвязанным типом запрещены. Тег сохраняет идентичность ребёнка.

Пример пользователя (синтаксис условный):

```text
abstract Expression;
abstract AssignableExpression : Expression;
abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);
node Assignment : BinaryExpression (
    left: AssignableExpression,
    right
);
```

Assignment сужает тип left с Expression до AssignableExpression; тип right и кратности обоих детей сохраняются. Предложение запретить любое изменение типа отклонено.

D003 описывает совпадение объявлений из разных баз, а D011 — явное переобъявление в потомке. D012 запрещает устранять конфликт нескольких баз даже явным сужением; уточнять тип разрешено последовательно в потомках.

### D012. Конфликт типов баз нельзя устранить уточнением — принято 26.10.2026

Разные типы детей с одинаковым тегом в наследуемых базах всегда означают ошибку, даже если один тип наследуется от другого. Явное переобъявление в потомке не устраняет этот конфликт. Требование точного совпадения типов при объединении баз (D003) сохраняется.

Сужение разрешено последовательно в потомках: на каждом шаге тип ребёнка можно уточнить до его подтипа при неизменной кратности (D011). Совместимость объявлений из баз проверяется до применения уточнений самого потомка.

Примеры (A и B — абстрактные типы):

- A объявляет value: Expression, B объявляет value: AssignableExpression — наследование от A и B одновременно ошибочно, даже при явном value: AssignableExpression в потомке.
- A объявляет value: Expression, B наследует A и уточняет value до AssignableExpression — допустимо. Дальнейший потомок B может снова сузить тип по объявленной иерархии.

### D013. Базами могут быть только абстрактные типы — уточнено 26.10.2026

Наследоваться от конкретного (неабстрактного) узла запрещено. Базами как абстрактного, так и конкретного типа могут быть только абстрактные типы. Все дети абстрактных типов обязательно именованы (D006), поэтому безымянных унаследованных детей не бывает.

Конкретный узел может объявлять собственных детей без тегов, но сам не может служить базой. Последовательное сужение типа ребёнка (D011–D012) выполняется через абстрактные промежуточные типы и может завершаться конкретным узлом.

Это уточнение отменяет прежнюю запись D007 о допустимости конкретных баз. Правила полного списка, порядка и сужения из D008–D012 сохраняются для допустимых абстрактных баз. Предыдущий вопрос о безымянных детях в базах снят как неприменимый.

### D014. Несколько повторяющихся групп и однозначное распределение — принято 26.10.2026

В одном типе разрешено несколько повторяющихся групп детей. Предложение P001 принято с правилами:

- При единственном допустимом распределении входных детей по группам распределение выполняется автоматически.
- При отсутствии допустимых распределений сообщается ошибка несовместимости с типами или кратностями схемы.
- При нескольких допустимых распределениях сообщается неоднозначность; группы необходимо задать явно по тегам. Неявный жадный выбор не допускается.

Теги в схеме сами по себе не разрешают неоднозначность плоского входного списка без привязок. Например, для first: Expression*, second: Expression* единственный Expression можно отнести к любой группе. Разные имена типов тоже не гарантируют непересечение: возможны общие подтипы.

Разбор текста декларации с несколькими группами однозначен; отдельная задача — распределение готовых детей. Перестановки между позициями схемы разрешены при однозначном распределении (D015); внутренний порядок повторяющихся групп определён в D016, синтаксис явного задания групп ещё не согласован. Для безымянных групп конкретного типа способ явного разрешения неоднозначности требует отдельного решения.

### D015. Автоматическое распределение не ограничено порядком входа — принято 26.10.2026

Если детей можно распределить однозначно, порядок их передачи не препятствует построению узла. Алгоритм должен пытаться найти единственное допустимое полное распределение с учётом типов, кратностей и явно заданных привязок; он не должен отклонять вход только потому, что дети переданы не в порядке схемы.

Локальная неоднозначность для отдельного ребёнка ещё не означает неоднозначность всего распределения: остальные дети и требования схемы могут оставить единственный полный вариант. Не допускается останавливаться на неудаче жадного выбора, если другое распределение решает задачу. При отсутствии полного решения или нескольких полных решениях действуют ошибки из D014.

Пример: схема (parameters: Parameter*, body: Statement*), вход [Statement, Parameter] допустим, если типы однозначно определяют группы. В результате группы располагаются в порядке схемы конкретного типа.

Предложение обязательно сохранять общий порядок позиционного входного списка отклонено. Порядок элементов внутри повторяющейся группы определён в D016. Роль входного порядка для двух обязательных одиночных позиций одинакового типа определена в D017; остальные случаи требуют согласования. Это правило построения узла; семантика сопоставления шаблонов обсуждается отдельно.

### D016. Стабильный порядок внутри повторяющейся группы — принято 26.10.2026

При автоматическом распределении внутри каждой повторяющейся группы сохраняется исходный относительный порядок попавших в неё детей. Распределение может переместить детей между позициями общего списка согласно схеме (D015), но не переставляет элементы внутри группы.

Пример при однозначной принадлежности к группам:

```text
Схема: parameters: Parameter*, body: Statement*
Вход: Statement₁, Parameter₂, Statement₂, Parameter₁
parameters: Parameter₂, Parameter₁
body: Statement₁, Statement₂
```

Итоговый плоский список в порядке схемы: Parameter₂, Parameter₁, Statement₁, Statement₂.

### D017. Обязательные одиночные позиции одинакового типа различаются порядком входа

Для двух обязательных одиночных позиций одинакового типа дети назначаются в порядке входа согласно окончательному порядку позиций в схеме потомка.

Условный пример: схема `(left: Expression, right: Expression)`, вход `[a, b]` — результат `left=a, right=b`. Перестановка `left=b, right=a` не считается вторым допустимым распределением. Явные привязки по тегам позволяют задать другое назначение.

Это уточняет критерий однозначности D014–D015: порядок различает такие обязательные одиночные позиции. Случай одного ребёнка для двух необязательных позиций определён в D018. Случай двух заполненных необязательных позиций определён в D019. Пересекающиеся типы для двух заполненных одиночных позиций рассмотрены в D020. Остальные обобщения пока не согласованы.

### D018. Один ребёнок для двух необязательных позиций — неоднозначность

Для схемы `(left: Expression?, right: Expression?)` и входа `[a]` без явных привязок существуют два допустимых распределения: заполнить только left или только right. Это неоднозначность; требуется явная привязка ребёнка по тегу.

Порядок входа не определяет, какая необязательная позиция пропущена. Автоматически выбирать первую позицию запрещено. Правило D017 не устраняет эту неоднозначность.

### D019. Две заполненные необязательные позиции одинакового типа

Для схемы `(left: Expression?, right: Expression?)` и входа `[a, b]` без явных привязок назначается `left=a, right=b` по порядку входа. Перестановка детей не считается альтернативным распределением.

Обе позиции заполнены, поэтому неопределённости о пропущенной позиции нет. Для одного входного ребёнка сохраняется неоднозначность D018. Это расширяет правило D017 на две заполненные необязательные позиции одинакового типа.

### D020. Порядок для двух заполненных одиночных позиций с пересекающимися типами

Если две одиночные позиции заполнены и оба входных ребёнка подходят обеим позициям, выбор определяется порядком входа относительно окончательного порядка позиций в схеме. Это действует и при разных объявленных типах позиций.

Условный пример: `(left: AssignableExpression, right: Expression)`, где AssignableExpression явно наследует Expression; вход `[a, b]`, оба ребёнка имеют тип AssignableExpression. Результат: `left=a, right=b`; обратное назначение не считается альтернативой.

Типовая совместимость имеет приоритет: если допустимо только обратное назначение, выбирается оно согласно D015. Порядок разрешает оставшийся выбор между взаимозаменяемыми детьми, а не запрещает единственное корректное распределение. Это решение касается двух заполненных одиночных позиций. Сочетание обязательной одиночной позиции с повторяющейся группой одного типа определено в D021; общее правило для произвольного числа позиций одного типа определено в D022.

### D021. Обязательная одиночная позиция и повторяющаяся группа одного типа

Предложение считать схему `(head: Expression, tail: Expression*)` неоднозначной для входа `[a, b]` отклонено пользователем: первый ребёнок назначается head, остальные — tail. Для обратной схемы `(head: Expression*, tail: Expression)` последние и первые дети распределяются соответственно: последний ребёнок назначается tail, все предыдущие — head.

Для N ≥ 1 совместимых входных детей кратности однозначно определяют размеры: (1, N−1) в первой схеме и (N−1, 1) во второй. Порядок входа определяет наполнение этих частей. Пустой вход не удовлетворяет обязательной позиции. Это расширяет использование порядка за пределы одиночных позиций; перестановки взаимозаменяемых детей между частями не создают дополнительную неоднозначность.

Для схемы `(head: Expression?, tail: Expression*)` непустой вход неоднозначен: допустимы размеры (0, N) и (1, N−1). Нельзя автоматически предпочитать заполнение head или его пропуск; нужна явная привязка, снимающая неоднозначность. Уточнение при разборе примера: пустой вход однозначен — обе части пусты.

Все примеры относятся к одному объявленному типу Expression и входным детям, совместимым с ним, без явных привязок. Общая формулировка для произвольного числа позиций одного типа определена в D022. Правило D015 о возможности перестановки при единственном типосовместимом распределении сохраняется.

### D022. Распределение по размерам позиций одного типа

Для произвольного числа позиций одного объявленного типа без явных привязок, когда все входные дети совместимы с этим типом, определяются допустимые наборы количеств детей по позициям. Сумма количеств равна числу входных детей; обязательная позиция получает одного ребёнка, необязательная — ноль или одного, повторяющаяся — любое неотрицательное количество.

- Если допустимый набор количеств единственный, вход последовательно разбивается по этим количествам в окончательном порядке позиций схемы.
- Если наборов несколько, сообщается неоднозначность; произвольный жадный выбор границ запрещён.
- Если наборов нет, вход несовместим со схемой.

Пример `(first: Expression, middle: Expression*, last: Expression)` при N ≥ 2 имеет единственный набор (1, N−2, 1): первый ребёнок, середина, последний ребёнок.

Пример пользователя `(first: Expression, second: Expression*, third: Expression*, fourth: Expression)`: первый и последний дети фиксированы. При N ≥ 3 середина допускает разные разделения между second и third, поэтому вход неоднозначен. Уточнение граничных случаев: при N = 2 обе группы пусты и распределение однозначно; при N < 2 обязательные позиции заполнить невозможно.

Это обобщает D017–D019 и D021 для позиций одного типа. Случаи разных типов требуют учёта типовой совместимости по D015 и D020; правило одинаковых типов не подменяет общий алгоритм.

### D023. Сначала согласовать явный синтаксис принятой модели

По просьбе пользователя дальнейшее расширение семантики приостановлено: сначала нужно определить конкретную запись уже обсуждённых конструкций. Подготовлен проект S001 ниже; его пунктуация, ключевые слова и лексические детали пока не утверждены.

Отложены без принятия решения: смешанное явное и автоматическое заполнение, закрытость явно заданной группы для добавления, а также предложенное использование `=` при создании узла. Объявления и создание узлов рассматриваются отдельно. После фиксации каждого ответа задаётся следующий вопрос, пока остаются открытые вопросы.

### D024. Основа синтаксиса объявлений и необязательное node после abstract

Принята основа S001: конкретный тип объявляется через `node`, абстрактный — через `abstract` или `abstract node`; базы записываются после `:`, дети — в `(...)`, именованный ребёнок — `tag: Type`, кратности — `?` и `*`, ссылка на унаследованного ребёнка — `@tag`, объявление завершается `;`.

По уточнению пользователя, `abstract XXX;` и `abstract node XXX;` полностью равнозначны. Слово node после abstract необязательно и подразумевается при его отсутствии. Обе формы допускают одинаковые списки баз и детей и не создают разных видов типов.

Принятие основы не утверждает дополнительные лексические предложения (набор символов идентификаторов, комментарии и прочее) и не возвращает отложенный вопрос создания узлов.

### D025. Завершающая запятая в списке детей

В непустом списке детей допускается одна завершающая запятая перед `)`, как в многострочной, так и в однострочной записи. Например, `node Pair (left: Expression, right: Expression,);`. Запятая не создаёт дополнительного ребёнка и не меняет семантику списка.

Пустой список записывается `()`, а не `(,)`. Пропущенные элементы и двойные запятые не разрешены. Это решение касается списка детей; форма списка баз им не изменяется.

### D026. Строчные и блочные комментарии

Разрешены комментарии `//` до конца строки и `/* ... */` для блока, в том числе многострочного. Блочные комментарии не поддерживают вложенность: первый `*/` завершает текущий блок. Незакрытый блочный комментарий является лексической ошибкой; строчный комментарий может завершаться концом файла.

Комментарии допустимы между токенами и служат разделителями: `abstract/* пояснение */node` разбирается как два ключевых слова, а части идентификатора через комментарий не склеиваются. Внутри комментариев другой вид комментария не открывается.

### D027. Идентификаторы и зарезервированные слова

Имена типов и теги соответствуют `[A-Za-z_][A-Za-z0-9_]*`: первая позиция — латинская буква ASCII или подчёркивание, далее также допускаются цифры ASCII. Регистр различается. Например, `BinaryExpression`, `left`, `_item2` допустимы, `2item` — нет.

Слова `abstract` и `node` зарезервированы и не могут использоваться как имена типов или теги. Unicode-идентификаторы пока не вводятся. Это ограничение идентификаторов не ограничивает текст комментариев латиницей. Квалифицированные имена и пространства имён рассматриваются отдельно.

### D028. Ссылки на типы до их объявления

> Расширено D067: порядок объявлений свободный во всех подключённых исходниках, включая ссылки между файлами.

В пределах одного файла разрешены ссылки на типы, объявленные ниже: как в списках баз, так и в объявлениях детей. Порядок объявлений не определяет доступность имени типа.

Сначала собираются объявления, затем разрешаются ссылки и проверяются ограничения типов. Имя, которое так и не было объявлено, является ошибкой. Это решение не определяет импорт и видимость между файлами и не разрешает циклическое наследование автоматически.

Пример:

```text
node Addition : BinaryExpression;

abstract BinaryExpression (
    left: Expression,
    right: Expression
);

abstract Expression;
```

### D029. Рекурсия через детей и запрет циклов наследования

Рекурсивные ссылки через типы детей разрешены. Например, `node Block (items: Block*);` описывает узел, содержащий вложенные узлы того же типа; пустая группа позволяет создать лист.

Граф наследования должен быть ациклическим. Запрещены как непосредственное наследование от самого себя, так и циклы через несколько баз. Например, `abstract A : B;` вместе с `abstract B : A;` является ошибкой. Наличие ссылок вперёд (D028) этого ограничения не отменяет.

Рекурсивное описание типов само по себе не означает разрешения циклов в экземплярах дерева. Проверка возможности построить конечный узел для рекурсивных схем с обязательными детьми этим решением не определена и остаётся отдельным вопросом.

### D030. Запрет повторного объявления типа

В одном файле каждый тип объявляется один раз. Повторное объявление того же имени является ошибкой, даже если текст и смысл объявлений полностью совпадают. Формы `abstract X;` и `abstract node X;` равнозначны (D024), поэтому их совместное использование для одного имени также является повторным объявлением.

`abstract Expression;` — полноценное определение типа, а не предварительная декларация и не заготовка для последующего дополнения. Расширять объявление вторым объявлением того же имени нельзя. Для ссылок вперёд предварительные декларации не нужны (D028). Правила между файлами будут определены вместе с импортом и пространствами имён.

### D031. Уникальность тегов в явном списке детей

В явном списке детей один тег может встречаться только один раз. Запрещены повторные объявления одного тега, повторные ссылки `@tag`, а также сочетание ссылки и переобъявления того же тега в одном списке. Совпадение типов и кратностей не делает такие повторы допустимыми.

Объединение совместимых одноимённых детей из разных баз по D005 сохраняется: оно выполняется до обработки явного списка, где объединённая позиция указывается один раз. Повторение типа у разных тегов или у безымянных позиций само по себе не является повторением тега.

### D032. Единые правила порядка для абстрактных и конкретных потомков

Правила D008–D010 распространяются и на абстрактные типы. При получении разных детей из нескольких баз либо добавлении собственных детей потомок обязан явно перечислить полный состав детей в окончательном порядке, включая всех унаследованных после объединения совместимых одноимённых позиций.

При одной базе и отсутствии собственного списка наследуются её состав и порядок. Потомок может явно переставить унаследованные позиции через `@tag`. Все дети абстрактного типа по-прежнему должны иметь теги (D006). Требования к сохранению кратности, сужению типа и уникальности тегов не меняются.

Пример:

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);

abstract Binary : HasLeft, HasRight (
    @left,
    @right
);
```

### D033. Разный порядок одинаковых детей в нескольких базах

Если несколько баз содержат один и тот же набор совместимых детей, но задают разный порядок, потомок обязан явно перечислить детей в выбранном окончательном порядке. Правило действует для абстрактных и конкретных потомков.

Различие порядка само по себе не делает объявления детей несовместимыми: дети объединяются по тегам согласно D005 при точном совпадении типов и кратностей. Однако без явного списка порядок не выбирается автоматически, в том числе по порядку перечисления баз.

Пример:

```text
abstract A (left: Expression, right: Expression);
abstract B (right: Expression, left: Expression);
node C : A, B (@left, @right);
```

Объявление `node C : A, B;` в этом примере ошибочно; вариант `(@right, @left)` также допустим.

### D034. Совпадающие списки детей нескольких баз

Если списки детей всех баз полностью совпадают по тегам, типам, кратностям и порядку, потомок может опустить собственный список детей. Совместимые позиции объединяются по тегам (D005), общий порядок наследуется. Правило одинаково для абстрактного и конкретного потомка, не добавляющего собственных детей.

Пример:

```text
abstract A (value: Expression);
abstract B (value: Expression);
node C : A, B;
```

У C один обязательный ребёнок value типа Expression. При различии порядка действует D033; при добавлении собственных детей требуется полный список по D009 и D032.

### D035. Базы без детей не влияют на порядок

Базы, у которых нет детей (включая унаследованных), не учитываются при определении состава и порядка детей потомка и необходимости явного списка. Они остаются полноценными базами в иерархии типов.

Если после исключения таких баз остаётся одна база с детьми, её список можно унаследовать без явного перечисления. Если остаётся несколько баз с полностью совпадающими списками, применяется D034. Если все базы без детей и потомок не объявляет собственных детей, его список пуст. Добавление собственных детей и объединение различных непустых списков подчиняются прежним правилам.

Пример:

```text
abstract Marker;
abstract HasValue (value: Expression);
node C : Marker, HasValue;
```

У C один ребёнок value; C является подтипом и Marker, и HasValue.

### D036. Данные узла — строка, отсутствие данных равно пустой строке

Принята модель, соответствующая приведённому пользователем контракту `String getData()`: метод getData() всегда возвращает текстовое представление строкой, `null` запрещён. Внутреннее хранение может быть нативным и не обязано быть строковым (уточнение D037). Отсутствие данных представлено `""` и не отличается от явно заданной пустой строки. Отдельное состояние отсутствия данных в DSL не вводится.

Предыдущее предложение о трёх состояниях («данных нет», «строка обязательна», «строка необязательна») не принято и заменено этим решением. В частности, прежнее утверждение, что пустая строка отличается от отсутствия данных, к принятой модели неприменимо.

Узлы с одинаковой пустой строкой данных могут различаться типами и детьми; например, пустой строковый литерал отличим от другого узла по типу. По одному результату getData() нельзя определить, была ли пустая строка задана явно.

Это решение фиксирует представление данных. Оно само по себе не устанавливает ограничения на содержимое строки для конкретных типов и не утверждает синтаксис задания или сопоставления данных. Проверка обязательности явной передачи данных при построении обсуждалась лишь как возможное будущее расширение и не принята.

### D037. Нативные данные требуют отдельного проектирования

Пользователь отклонил предложение разрешить любому типу узла произвольную строку без объявления данных. Требуется тщательно спроектировать типизированные данные, сохранив возможность нативного типа значения; существующий синтаксис его определения пользователя не устраивает.

Уточнение D036: строка является общим текстовым представлением через `getData()`, а не обязательным внутренним типом хранения. Нативное значение может иметь другой тип. Отсутствие данных возвращается как `""`; это не означает, что любое типизированное значение по умолчанию обязано сериализоваться в пустую строку или что любой парсер обязан принимать её. Правила значений по умолчанию, допустимых строк, преобразований и наследования данных ещё не согласованы.

Проверена текущая реализация (исходные наблюдения, не новые решения):

- [LiteralDescriptor.java](https://github.com/kniazkov/astranaut/blob/master/src/main/java/org/cqfn/astranaut/dsl/LiteralDescriptor.java) хранит нативный Java-тип, начальное значение, выражения сериализации и разбора и класс перехватываемого исключения.
- [literals.dsl](https://github.com/kniazkov/astranaut/blob/master/src/test/resources/dsl/literals.dsl) показывает позиционную запись: `IntegerLiteral <- 'int';`, `StringLiteral <- 'String', '""';`; для пользовательского типа используются до пяти строковых параметров с Java-кодом.
- [LiteralGenerator.java](https://github.com/kniazkov/astranaut/blob/master/src/main/java/org/cqfn/astranaut/codegen/java/LiteralGenerator.java) генерирует поле нативного типа, типизированные getValue()/setValue(), текстовый getData() через сериализатор и setData(String) через парсер. Поэтому прежний вывод о хранении любых данных как строки был неверен.
- [LiteralBuilder.java](https://github.com/kniazkov/astranaut/blob/master/src/main/java/org/cqfn/astranaut/interpreter/LiteralBuilder.java) в режиме интерпретации хранит строку и не выполняет нативный разбор: setData() принимает значение без такой проверки. Согласованность интерпретатора и генератора требует отдельного решения.
- Текущий LiteralDescriptor описывает данные без детей. Возможность сочетать нативные данные и детей в новой модели ещё нужно определить.

Проблемы текущей записи: смысл зависит от позиции строкового параметра; имя типа и Java-выражения выглядят одинаково; повторное использование одних преобразований несколькими типами узлов требует нового решения. Эти наблюдения не поручают менять реализацию в рамках обсуждения.

### D038. Переиспользуемые типы данных и привязка через угловые скобки

Принято отдельное объявление типа данных `datatype` с именованными параметрами. Пользователь утвердил camelCase для javaType и parseError и указание типа данных узла в угловых скобках после имени узла, перед списком баз:

```text
datatype Int {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
}

node IntegerLiteral<Int> : Expression;
```

Int описывает нативное значение и преобразования; IntegerLiteral — тип узла. Несколько типов узлов могут ссылаться на один datatype. Это не наследование от Int и не введение обобщённых типов узлов.

Смысл именованных параметров:

- javaType — нативный Java-тип;
- default — Java-выражение начального значения;
- serialize(value) — Java-выражение получения текстового представления;
- parse(text) — Java-выражение разбора текста в нативное значение;
- parseError — класс исключения, обозначающего ошибку разбора.

Тела Java-выражений записываются в строках; value и text в примере — именованные параметры соответствующих преобразований. Описание Int может использоваться несколькими узлами без повторения преобразований.

Предложения `java_type`, `parse_error` и `node IntegerLiteral data Int;` заменены записью пользователя. Ключевое слово datatype вводится для нового объявления. В приведённой форме поля завершаются `;`, объявление datatype заканчивается `}` без обязательного `;`.

Пока не определены: обязательность и значения по умолчанию самих параметров datatype, точные правила строк и подстановки параметров, стандартные типы данных, обработка преобразований интерпретатором, наследование данных и сочетание данных с детьми. Принятая форма конкретного узла не утверждает автоматически применение `<Int>` к абстрактным типам.

### D039. Типизированные данные совместимы с детьми

Один конкретный узел может одновременно иметь нативное значение объявленного datatype и дочерние узлы. Ограничение старого LiteralDescriptor «данные без детей» в новой модели не сохраняется.

Тип данных указывается в угловых скобках после имени узла, базы — после двоеточия, список детей — затем в круглых скобках. Данные не являются ребёнком и не занимают позицию в списке детей. Проверки данных и схемы детей выполняются независимо; для создания корректного узла должны выполняться обе.

Пример (Text — объявленный datatype, Statement — объявленный тип узла):

```text
node NamedBlock<Text> (
    statements: Statement*,
);
```

Данные могут хранить имя блока, дети — его содержимое. Наследование типизированных данных абстрактными и конкретными потомками остаётся следующим вопросом.

### D040. Наследование данных и совместимость нескольких баз

Абстрактный тип может объявлять datatype через ту же привязку `<Type>`, в формах `abstract Named<Text>;` и `abstract node Named<Text>;`. Потомки наследуют тип данных без повторного указания; правило действует и для промежуточных абстрактных потомков.

Запрещено наследоваться от двух или более абстрактных типов с разными типами данных. Учитываются и унаследованные данные баз: отсутствие локальной записи `<...>` не означает отсутствия данных, если они уже получены от предка. База без данных совместима с базой с данными и не отменяет её привязку.

Если несколько баз имеют один и тот же datatype, наследуется одна общая привязка данных. Если среди баз есть разные datatype, это конфликт; совпадение нативного Java-типа само по себе не делает разные объявления datatype одним типом данных. Явная запись в потомке не делает запрещённую комбинацию баз допустимой.

Пример (Text и Int — объявленные datatype):

```text
abstract Named<Text>;
abstract Marker;
abstract AlsoNamed<Text>;
abstract Numbered<Int>;

node NamedBlock : Named, Marker;    // Данные Text
node BothNames : Named, AlsoNamed;  // Одна привязка Text
node Invalid : Named, Numbered;     // Ошибка: разные типы данных
```

Безданная база здесь не запрещает данные в потомках. Унаследованный datatype можно сохранить или уточнить до его потомка (D077).

### D041. Прежний запрет изменения datatype — уточнён D077

> Действующее правило D077 разрешает уточнение до производного datatype. Прежний полный запрет ниже сохраняется как история обсуждения.

Потомок не может заменить унаследованный datatype другим. Отсутствие локальной привязки сохраняет унаследованный тип данных; явное повторение того же datatype допустимо и не меняет его смысл. Правило действует для абстрактных и конкретных потомков.

```text
abstract Named<Text>;
node Good : Named;
node Explicit<Text> : Named;
node Bad<Int> : Named; // Ошибка
```

Совпадение javaType у разных datatype не разрешает такую замену. Это правило не является сужением типа ребёнка по D011: тип данных узла сохраняется целиком вместе с его описанием преобразований.

### D042. Обязательное начальное значение datatype

Поле `default` обязательно в каждом объявлении datatype, включая типы с примитивным javaType. Оно задаёт явное Java-выражение начального нативного значения, например `default = "0";` для Int.

Отсутствие default — ошибка объявления datatype. Генератор не подставляет за автора неявный ноль, false или null. Проверка результата выражения, допустимости null в нативном представлении и согласованности начального значения с преобразованиями остаётся отдельным вопросом; контракт getData() из D036 сохраняется.

### D043. Обязательные поля datatype и документация

Для каждого datatype обязательны `javaType`, `default` (D042), `serialize(value)` и `parse(text)`. Правило действует и для строк, и для примитивных Java-типов. Отсутствие любого из этих полей — ошибка объявления; скрытые преобразования по имени javaType не подставляются.

Для строк тождественные преобразования задаются явно:

```text
serialize(value) = "value";
parse(text) = "text";
```

По требованию пользователя документация должна объяснять заполнение каждого поля и содержать полные примеры для строк, примитивов и пользовательских типов. Следует пояснить разницу между строкой DSL с Java-кодом и значением данных, именованные параметры преобразований, начальное значение и обработку ошибок. Примеры должны соответствовать окончательно согласованным правилам экранирования и parseError; эти детали ещё обсуждаются.

### D044. Обязательный parseError и явный none

Поле parseError обязательно в каждом пользовательском datatype. Значение — имя класса исключения в строке либо явный маркер `none`:

```text
parseError = "NumberFormatException";
parseError = none;
```

Указанное исключение и его подклассы означают ожидаемый отказ разбора. none означает отсутствие специального перехвата. Отсутствие поля — ошибка, а не неявный none. Предложение сделать поле необязательным снято.

Ошибки встроенного Java-кода, включая необработанные checked-исключения, выявляет обычный Java-компилятор после генерации. Astranaut не анализирует эти фрагменты и их исключения (D062). Общий неявный catch(Exception) не вводится.

### D045. Встроенные типы данных

По требованию пользователя вводятся встроенные datatype с уже заполненными описаниями; в набор обязательно входит String. Пользователь сможет ссылаться на такой тип без повторения блока параметров, например `node StringLiteral<String>;`.

Встроенные описания не отменяют требования к полноте пользовательских datatype: они предоставляют готовые описания. Полный набор встроенных типов, их точные определения, значения по умолчанию и правила конфликтов имён ещё предстоит согласовать.

### D046. Обязательная возможность валидации данных

По требованию пользователя DSL должен поддерживать явную валидацию задаваемых данных. Одного разбора строки в нативный тип недостаточно: например, узел может принимать только целые значения строго больше нуля.

Требование принято; синтаксис и место объявления валидатора уточнены в D047. Необходимо определить проверку всех способов задания данных (строковый разбор, нативный setter, начальное значение), момент отказа, поведение при ошибке и наследование ограничений. В частности, default = 0 у общего Int не удовлетворяет ограничению value > 0; корректность такого начального значения оставлена автору DSL в D047.

### D047. Валидатор в объявлении узла; default на ответственности автора

Принята запись валидатора нативного значения в блоке объявления узла:

```text
node PositiveInteger<Int> : Expression {
    validate(value) = "value > 0";
}
```

Int задаёт представление и преобразования, а validate(value) задаёт ограничение конкретного узла. Java-выражение должно возвращать boolean; true означает допустимое значение, false — недопустимое. Проверка явно задаваемых данных применяется как после успешного разбора setData, так и при передаче нативного значения через setValue. Конкретные сигнатуры методов и способ сообщения об отказе ещё предстоит согласовать.

По уточнению пользователя корректность default относительно валидатора остаётся на совести автора DSL. Автоматическую проверку default на соответствие валидатору не вводим; предыдущее предложение обязательно проверять default снято. Для ограничения value > 0 автор обязан обеспечить подходящее начальное значение. При ошибочном default система не гарантирует соблюдение этого ограничения для начального состояния.

Это проектное решение, а не утверждение о технической невозможности вызвать валидатор во время исполнения. В общем случае нельзя заранее доказать корректность произвольных Java-выражений default и validate. Проверка синтаксиса и типов Java-кода отличается от проверки соответствия значения предикату и этим решением не отменяется.

### D048. Валидация datatype и переопределяемые параметры узла

> Уточнено D059: объединений проверок нет, действует полная замена; конфликтующие объявления проверок в базах запрещены; общий источник разрешён (D060). Прежние формулировки ниже сохраняются только как история обсуждения.

По уточнению пользователя базовую валидацию необходимо определять в самом datatype. В узле разрешается переопределять начальное значение default и валидацию validate(value). Само переопределение default/validate не меняет datatype; явное уточнение datatype разрешено в D077.

Поддержано наследование ограничений абстрактных узлов с объединением через И: локальная проверка потомка не отменяет ограничений его баз. Отношение валидатора datatype к его переопределению в узле уточнено в D049: полная замена. Эти два уровня не следует смешивать.

Пример: datatype Int задаёт default = "0" и validate(value) = "true"; PositiveInteger<Int> указывает default = "1" и validate(value) = "value > 0". Ответственность за соответствие default проверке остаётся у автора DSL (D047). Параметр validate необязателен (D050).

По требованию пользователя создано отдельное [описание валидации и переопределений](https://github.com/kniazkov/astranaut/blob/docs/dsl-design/docs/dsl-design/data-validation.md) с примерами, правилами и открытыми вопросами.

### D049. Проверка узла полностью заменяет проверку datatype — принято 26.10.2026

> Уточнено D059: объединений проверок нет, действует полная замена; конфликтующие объявления проверок в базах запрещены; общий источник разрешён (D060). Прежние формулировки ниже сохраняются только как история обсуждения.

Локальный validate(value) узла полностью заменяет проверку datatype, а не объединяется с ней через И. Допускается как усиление, так и ослабление проверки datatype. Например, при validate(value) = "value >= 0" в datatype и validate(value) = "value > -10" в узле значение -5 допустимо, если нет дополнительных ограничений абстрактных баз.

Без локального переопределения применяется проверка datatype. Это решение отвечает на вопрос о переопределении проверки datatype; наследуемые ограничения абстрактных баз из D048 рассматриваются отдельно и сохраняются. Правило об отсутствии автоматической проверки default не меняется.

### D050. validate — необязательная настройка — принято 26.10.2026

> Уточнено D059: объединений проверок нет, действует полная замена; конфликтующие объявления проверок в базах запрещены; общий источник разрешён (D060). Прежние формулировки ниже сохраняются только как история обсуждения.

Параметр validate в datatype необязателен. Его отсутствие означает отсутствие дополнительных ограничений на значение нативного типа, то есть эквивалент validate(value) = "true". Это не отменяет разбор текста, проверку типов и ограничения абстрактных баз.

В узле validate также необязателен: отсутствие локального переопределения сохраняет действующую проверку datatype и наследуемые ограничения. Явный validate узла полностью заменяет проверку datatype по D049. Требование обязательного default и отказ от автоматической проверки начального значения сохраняются.

### D051. Наследование и переопределение default — принято 26.10.2026

Переопределённый default абстрактного узла наследуется потомками. При отсутствии локального default потомок использует начальное значение базы, а не возвращается к default datatype. Потомок может явно задать собственный default; это не меняет datatype.

```text
abstract Positive<Int> {
    default = "1";
}

node Literal : Positive;
node AnotherLiteral : Positive {
    default = "2";
}
```

Literal получает начальное значение 1, AnotherLiteral — 2. Правило действует и для абстрактных потомков. Соответствие начального значения проверкам остаётся ответственностью автора DSL, без автоматической валидации default (D047). Разные default нескольких баз запрещены; переопределение не устраняет конфликт (D079).

### D052. Прежнее разрешение конфликта default — отменено D079

Ранее разрешалось устранить разные default баз собственным default потомка. Это исключение отменено: конфликт баз делает наследование ошибочным независимо от локального default.

### D053. Прежнее сравнение default по тексту — отменено D080

Текстовое совпадение больше не устраняет конфликт независимых объявлений default. Действующее правило D080 сравнивает происхождение объявления.

### D054. Проверка общего предка при ромбовидном наследовании — принято 26.10.2026

> Уточнено D059: объединений проверок нет, действует полная замена; конфликтующие объявления проверок в базах запрещены; общий источник разрешён (D060). Прежние формулировки ниже сохраняются только как история обсуждения.

Одна и та же проверка общего предка учитывается один раз, независимо от числа путей наследования. Идентичность проверки определяется её объявлением, а не текстом выражения.

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A;
abstract C : A;
node D : B, C;
```

Проверка, объявленная в A, входит в набор проверок D один раз. Независимые объявления одинакового текста в разных базах остаются отдельными проверками и не объединяются. Это правило устраняет повторное включение одного объявления; порядок выполнения проверок и возможность короткого замыкания ещё не определены.

### D055. Невалидные данные не меняют значение построителя — принято 26.10.2026

Если validate возвращает false, присваивание отклоняется, прежнее значение построителя сохраняется. Правило одинаково для setData и setValue; пользователь отдельно подчеркнул, что setData не должен менять данные, если они невалидны.

Например, при текущем значении 5 и проверке value > 0 попытка установить -1 завершается отказом, а значение остаётся 5. В setData сначала разбирается входной текст и проверяется полученное нативное значение; новое значение сохраняется только после успешного разбора и проверки. При неуспешном разборе прежние данные также не заменяются. Отказ не сбрасывает значение к default.

Результат boolean принят в D056; исключения валидатора выходят наружу согласно D057. Проверка default автоматически не вводится (D047).

### D056. Результат setData и setValue — boolean — принято 26.10.2026

Методы setData и setValue возвращают true, если значение принято, и false, если validate вернул false. setData также возвращает false при ожидаемой ошибке разбора, указанной в parseError (D044). При false прежние данные построителя сохраняются (D055).

Ошибку разбора и отрицательный результат проверки следует различать как причины отказа, но возвращаемый boolean их не различает. Отдельный API подробной диагностики этим решением не вводится. Неожиданные исключения выходят наружу согласно D057.

### D057. Узкий перехват ошибок разбора — принято 26.10.2026

В false преобразуется только ожидаемое исключение самого parse, указанное в parseError, включая его подклассы (D044). Область перехвата не включает validate. При parseError = none специального перехвата нет.

Неожиданные исключения parse и исключения validate выходят наружу; новое значение построителя не присваивается. Например, NumberFormatException из validate не превращается в false, даже если этот класс указан в parseError. Автоматический общий перехват Exception или Throwable не вводится.

Это правило не обещает отката произвольных побочных эффектов пользовательского Java-кода. Требования к чистоте приняты в D058; корректность Java-кода оставлена Java-компилятору (D062).

### D058. Чистота и детерминированность validate — принято 26.10.2026

validate не должен изменять проверяемое значение или внешнее состояние. При одинаковом значении он должен давать одинаковый результат: проверка не должна зависеть от изменяющихся часов, случайности или внешнего состояния.

Требование действует для проверок datatype и узлов, включая наследуемые проверки. Это документированный контракт автора DSL; автоматическое доказательство чистоты произвольного Java-кода не обещается. Правило не отменяет D057: исключения валидатора выходят наружу. Вопрос порядка набора проверок снят в D059: действует одна проверка.

### D059. Полная замена проверки и строгие ограничения баз — принято 26.10.2026

Локальный validate полностью заменяет унаследованную проверку узла или проверку datatype. Никакого автоматического объединения через И или ИЛИ нет. Без локального validate сохраняется унаследованная проверка узла, а при её отсутствии используется проверка datatype.

```text
abstract Positive<Int> { validate(value) = "value > 0"; }
node SmallNumber : Positive { validate(value) = "value < 10"; }
```

SmallNumber допускает отрицательные значения: проверка Positive заменена целиком.

Запрещено наследование от баз с конфликтующими объявлениями проверок; собственный validate потомка не устраняет конфликт. По уточнению D060 несколько путей к одному объявлению общего предка разрешены. Совпадение текста независимых объявлений не устраняет конфликт. Базы без проверок могут участвовать в множественном наследовании при соблюдении остальных правил.

Общий datatype с одной проверкой разрешён для нескольких баз (D060). Правила default, чистоты, отказа и исключений сохраняются.

Часть D048 об объединении и D054 о слиянии проверок при ромбе отменены. D049–D050 уточнены. Предложение короткого замыкания набора проверок снято: действует одна проверка.

### D060. Общая проверка datatype и ромб без переопределений — принято 26.10.2026

Несколько баз, использующих один datatype с validate без собственных проверок узлов, разрешены: используется одна проверка общего datatype.

Ромбовидное наследование также разрешено, если обе ветки несут одно и то же объявление validate общего предка без переопределений:

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A;
abstract C : A;
node D : B, C;
```

D использует одну проверку из A. Сравнивается происхождение объявления, а не текст выражения. Разные независимые объявления не становятся одной проверкой из-за совпадения текста. Полная замена validate сохраняется; объединения проверок нет. Запрет D059 уточняется: несколько путей к одному объявлению сами по себе не являются конфликтом. Переопределение только в одной ветке создаёт запрещённый конфликт (D061).

### D061. Ромб с переопределением в одной ветке запрещён — принято 26.10.2026

Если в ромбе одна ветка переопределила validate, а другая сохранила объявление общего предка, наследование от обеих веток запрещено.

```text
abstract A<Int> { validate(value) = "value > 0"; }
abstract B : A { validate(value) = "value < 10"; }
abstract C : A;
node D : B, C; // Ошибка: разные объявления проверки.
```

Приходят два разных объявления — из B и из A. Автоматического выбора более нового или более близкого объявления нет; порядок баз не даёт приоритета. Собственный validate в D не устраняет конфликт баз (D059). Одна проверка, пришедшая несколькими путями без переопределений, разрешена (D060).

Мотивировка пользователя: правила должны быть простыми, легко запоминаться и реализовываться; скрытые правила приоритета переопределений усложняют работу конечного пользователя.

### D062. Проверка встроенного Java-кода — ответственность Java-компилятора — принято 26.10.2026

Встроенный в DSL Java-код переносится в генерируемую Java, после чего компилируется обычным Java-компилятором. Astranaut не реализует Java-парсер, не проверяет синтаксис и типы этих фрагментов и не анализирует выбрасываемые ими исключения. Если пользовательский код некорректен, включая необработанные checked-исключения, ошибку выдаёт Java-компилятор; исправление пользовательского кода — ответственность автора DSL.

Отдельная проверка DSL на checked-исключения validate не вводится. Генератор не выводит автоматически throws и не добавляет общий catch или оборачивание исключений для исправления пользовательского кода. Явный parseError и согласованные правила генерации сохраняются. Сам синтаксис DSL, обязательные поля и правила наследования по-прежнему проверяются: отказ от анализа касается именно встроенного Java-кода. Контракт чистоты validate остаётся документированным требованием к автору.

### D063. Снятие проверки выражением true — принято 26.10.2026

Для снятия проверки используется обычное переопределение validate(value) = "true". Это Java-выражение с булевым результатом, поэтому отдельного ключевого слова или особого режима отключения не требуется.

```text
abstract Positive<Int> { validate(value) = "value > 0"; }
node AnyInteger : Positive { validate(value) = "true"; }
```

AnyInteger принимает любое значение своего нативного типа с точки зрения validate. Отсутствие validate, напротив, сохраняет унаследованную проверку. Разбор текста и правила типа данных остаются в силе. Это обычное объявление validate: оно не устраняет конфликт проверок нескольких баз и не требует распознавания Java-выражения генератором (D059–D062).

### D064. Один параметр — одно задание в блоке — принято 26.10.2026

Каждый параметр в одном блоке datatype или узла можно задать только один раз. Повтор default, validate или другого параметра — ошибка DSL, даже если значения совпадают. Правило «последний побеждает» не применяется.

Разные параметры могут находиться в одном блоке, например default вместе с validate. Ограничение относится к повторам одного параметра, а не к общему числу параметров. Разрешённое переопределение унаследованного параметра в объявлении потомка сохраняется. Проверка дубликатов относится к структуре DSL и не требует анализа встроенного Java-кода.

### D065. Неизвестный параметр — ошибка DSL — принято 27.10.2026

Неизвестное имя параметра в блоке datatype или узла является ошибкой DSL. Например, validte(value) вместо validate(value) не игнорируется и не рассматривается как произвольная дополнительная настройка. Это проверка структуры DSL; содержимое строк с Java-кодом по-прежнему не анализируется (D062).

### D066. Свободный порядок параметров — принято 27.10.2026

Параметры внутри блока datatype, абстрактного или конкретного узла можно записывать в любом порядке. Порядок записи не влияет на смысл: default перед validate и validate перед default равнозначны. Это декларации настроек, а не последовательность выполняемых команд. Требования обязательности параметров, запрет дубликатов (D064) и неизвестных имён (D065) сохраняются.

### D067. Произвольный порядок объявлений во всех исходниках DSL — принято 27.10.2026

Во всех исходниках DSL объявления можно размещать в любом порядке. Разрешение ссылок не зависит от позиции объявления в файле или от порядка обработки файлов, входящих в одну компиляцию. Правило общее, включая datatype, абстрактные и конкретные типы узлов; предварительные декларации не требуются.

Сначала собираются объявления из подключённых исходников, затем разрешаются ссылки и проверяются семантические ограничения. Неизвестная ссылка является ошибкой после рассмотрения всего доступного набора объявлений, а не только уже прочитанной части файла. Встроенные типы также учитываются.

Это расширяет D028 за пределы одного файла. Механизм подключения файлов, импорты и области видимости ещё предстоит определить; произвольный порядок не означает автоматического подключения любых файлов. Ограничения на циклы наследования и повторные объявления сохраняются. Порядок детей в схеме остаётся значимым; это отдельное понятие от порядка объявлений.

### D068. Общее пространство имён типов — принято 27.10.2026

Datatype, абстрактные и конкретные типы узлов используют общее пространство имён. В одной области видимости имя обозначает только одну из этих сущностей: datatype Int и node Int конфликтуют; аналогично конфликтует abstract Int. Порядок объявлений или обработки файлов не разрешает конфликт.

Общее пространство имён не смешивает роли типов: в привязке данных ожидается datatype, в списке детей — тип узла, в списке баз — абстрактный тип узла. Неверная категория ссылки является ошибкой DSL. Детали областей видимости и импортов остаются отдельной темой. Мотивировка пользователя: единое правило упрощает использование и реализацию.

### D069. Встроенные типы уже объявлены — принято 27.10.2026

Встроенные datatype считаются уже объявленными и занимают имена в общем пространстве имён (D068). Пользовательское объявление с тем же именем — обычная ошибка повторного объявления, а не специальный случай замены встроенного типа.

Например, имя встроенного String нельзя занять через datatype String, node String или abstract String. Для собственного типа нужно другое имя. Отдельный механизм переопределения встроенных объявлений не вводится.

### D070. Встроенный String и ненулевой аргумент setData — принято 27.10.2026

Встроенный datatype String использует нативный тип java.lang.String. Начальное значение — пустая строка; parse(text) возвращает text, serialize(value) возвращает value без преобразований; parseError = none, validate отсутствует.

Для setData действует предусловие: аргумент text всегда не null. Обеспечение этого предусловия — ответственность вызывающего кода. Специальной обработки null не вводим: не преобразуем его в пустую строку и не задаём обязательный результат false или специальное исключение. Передача null нарушает контракт. Пустая строка при этом является допустимым входом и отличается от null.

Это уточнение относится к строковому аргументу setData. Контракт ненулевых нативных данных принят в D071.

### D071. Ненулевые нативные данные — принято 27.10.2026

Нативные данные ссылочных типов должны быть не null. Вызывающий код передаёт в setValue ненулевое значение; автор datatype обеспечивает ненулевой результат успешного parse и ненулевое начальное значение default. Требование распространяется и на default, переопределённый в узле.

Специальные проверки null генератором не добавляются. Нарушение этого контракта не получает специально установленного результата false, замены на default или обязательного исключения. Проверка произвольного Java-кода и доказательство ненулевого результата не выполняются (D062). Это дополняет контракт setData из D070 и не вводит автоматическую проверку default валидатором.

### D072. Неизменяемые нативные значения — принято 27.10.2026

Нативные значения ссылочных datatype должны быть неизменяемыми, чтобы данные уже построенного узла нельзя было изменить через сохранённую или возвращённую ссылку. Например, String подходит; изменяемый ArrayList напрямую как значение узла не допускается.

Обеспечение этого свойства — ответственность автора datatype и кода, передающего значения. Генератор не копирует произвольные объекты автоматически и не анализирует Java-код для доказательства неизменяемости. Контракт относится к значениям, полученным через setValue, parse и default, включая переопределённый default узла. Одной неизменяемости ссылки недостаточно: доступное через неё содержимое также не должно позволять изменить данные узла.

### D073. Сохранение значения при сериализации и разборе — принято 27.10.2026

Автор datatype обязан обеспечить, чтобы parse(serialize(value)) восстанавливал эквивалентное нативное значение. Требование относится к сохранению значения, а не идентичности объекта по ссылке.

Обратное преобразование serialize(parse(text)) не обязано сохранять исходное написание: например, вход "007" может сериализоваться как "7". Исходный текст не становится отдельным обязательным хранимым представлением данных из-за этого контракта.

Это документированное требование к автору datatype, без автоматического доказательства или анализа Java-кода. Оно не вводит автоматической проверки default и не меняет правила validate.

### D074. Чистота и детерминированность parse и serialize — принято 27.10.2026

parse и serialize должны быть чистыми и детерминированными: одинаковый вход даёт одинаковое значение или текст; переданные объекты и внешнее состояние не изменяются. Результат не должен зависеть от изменяющихся часов, случайности или внешнего состояния.

Создание нового неизменяемого объекта при parse допустимо: требуется одинаковое значение, а не одна и та же ссылка. Это документированный контракт автора datatype, без автоматического доказательства и анализа Java-кода. Правила обработки ошибок parse и сохранения значения при сериализации остаются в силе.

### D075. Одиночное наследование datatype — принято 27.10.2026

Вводится одиночное наследование между datatype: у производного datatype может быть одна база. Предложение полностью отказаться от наследования datatype отклонено.

Нативный Java-тип можно сохранить. Если javaType меняется, новый Java-тип должен наследоваться от базового Java-типа. За соблюдением этого требования следит программист DSL; Astranaut не анализирует Java-иерархию и не реализует Java-парсер (D062). Числовое преобразование между примитивами само по себе не является наследованием Java-типов.

Наследование и переопределение всех параметров определены в D076. Уточнение datatype в узле разрешено в D077; конфликты разных datatype нескольких баз узла запрещены (D040).

### D076. Синтаксис и параметры производного datatype — принято 27.10.2026

Принята форма одиночного наследования datatype:

```text
datatype PositiveInt : Int {
    default = "1";
    validate(value) = "value > 0";
}
```

Все параметры наследуются: javaType, default, serialize, parse, parseError и validate. В производном datatype можно указать только изменяемые параметры; любой параметр разрешено переопределить. Локальное значение полностью заменяет унаследованное, в том числе validate, без объединения проверок.

Обязательные поля должны присутствовать в итоговом описании с учётом наследования; повторять унаследованные обязательные поля не нужно. При смене javaType действует D075, а автор обеспечивает совместимость default, parse, serialize и остальных фрагментов с новым Java-типом. Astranaut не анализирует этот Java-код (D062). Правила однократного задания и свободного порядка параметров сохраняются.

### D077. Уточнение datatype в потомке узла — принято 27.10.2026

Узел-потомок может явно уточнить унаследованный datatype до его прямого или косвенного потомка в объявленной иерархии datatype. Прежний запрет D041 уточнён: сохранить datatype или повторить его разрешено, заменить несвязанным типом либо расширить до предка запрещено.

```text
datatype PositiveInt : Int {
    default = "1";
    validate(value) = "value > 0";
}
abstract Literal<Int>;
node PositiveLiteral<PositiveInt> : Literal;
```

Правило действует для абстрактных и конкретных потомков узлов. Отсутствие локальной привязки сохраняет унаследованный datatype. Совместимость определяется явным наследованием datatype в DSL, а не только совпадением javaType.

Разные datatype нескольких баз узла по-прежнему конфликтуют (D040), даже если один наследуется от другого. Локальное уточнение не устраняет конфликт баз. Конкурирующие свойства базового узла и нового datatype запрещены, приоритеты не вводятся (D078).

### D078. Конкурирующие свойства данных запрещены, приоритетов нет — принято 27.10.2026

Предложение при уточнении datatype автоматически отдавать приоритет параметрам базового узла отклонено. Конкурирующее наследование свойств данных из базового узла и нового datatype делает их неоднозначными и запрещается; скрытых правил выбора источника нет.

```text
datatype PositiveInt : Int {
    default = "1";
}
abstract Literal<Int> {
    default = "5";
}
node PositiveLiteral<PositiveInt> : Literal; // Ошибка.
```

Нельзя автоматически выбрать ни 5 из Literal, ни 1 из PositiveInt. То же основание относится к конкурирующим переопределениям validate. Последовательное переопределение по одной линии наследования остаётся отличным от получения конкурирующих свойств по разным линиям.

Уточнение datatype по D077 сохраняется для случаев без такого конфликта. Мотивировка пользователя: программист не должен помнить приоритеты источников; простые запреты предпочтительнее неочевидного выбора. Прежнее исключение D052 отменено в D079.

### D079. Локальный default не устраняет конфликт баз — принято 27.10.2026

Разные default нескольких баз делают наследование ошибочным. Явный default потомка не устраняет конфликт. Прежнее исключение D052 отменено.

```text
abstract A<Int> { default = "1"; }
abstract B<Int> { default = "2"; }
node C : A, B { default = "3"; } // Ошибка.
```

Правило действует для абстрактных и конкретных потомков. Проверка совместимости баз выполняется до применения локального переопределения. Порядок баз и локальное значение не выбирают источник конфликтующего свойства. Последовательное переопределение неконфликтующего унаследованного default по-прежнему разрешено.

Совпадение default определяется происхождением объявления (D080); текстовое сравнение D053 отменено.

### D080. Совпадение default по происхождению объявления — принято 27.10.2026

Совпадение унаследованных default определяется происхождением объявления, как для validate. Одно объявление общего предка, пришедшее несколькими путями, допустимо. Независимые объявления конфликтуют даже при одинаковом тексте или результате выражений.

```text
abstract A<Int> { default = "1"; }
abstract B<Int> { default = "1"; }
node C : A, B; // Ошибка: два независимых объявления default.
```

Если B и C наследуют один default из A без переопределений, потомок B и C получает одно объявление default без конфликта. Переобъявление того же текста в одной ветке создаёт новый источник и может привести к конфликту.

Прежнее правило текстового сравнения D053 отменено. Ни сравнение Java-выражений, ни вычисление их результатов не используются для устранения конфликтов. Локальный default потомка конфликт баз не исправляет (D079).

### D081. Циклы наследования datatype запрещены — принято 27.10.2026

Циклы наследования datatype запрещены, включая непосредственное наследование от самого себя и циклы через несколько объявлений. Например, база B у A и база A у B образуют ошибку DSL.

Проверка выполняется после сбора объявлений и разрешения ссылок во всех подключённых исходниках. Порядок объявлений и обработки файлов не влияет на результат (D067). Проверяется граф наследования datatype самого DSL; анализ Java-иерархии для этого не требуется.

### D082. Краткое объявление производного datatype — принято 27.10.2026

Разрешена запись без блока переопределений:

```text
datatype MyText : String;
```

Она равнозначна `datatype MyText : String {}`. Объявляется новый именованный datatype, наследующий все параметры базы, а не псевдоним String. Правила одиночного наследования, обязательных итоговых параметров и проверки конфликтов сохраняются.

### D083. Экранирование строк DSL — принято 27.10.2026

Строки DSL заключаются в двойные кавычки. Поддерживаются только следующие escape-последовательности:

| Запись | Результат |
|---|---|
| `\"` | Двойная кавычка |
| `\\` | Обратная косая черта |
| `\n` | Перевод строки |
| `\r` | Возврат каретки |
| `\t` | Табуляция |

Неизвестная escape-последовательность и буквальный перенос строки внутри такой строки являются ошибками DSL. Сначала снимается экранирование DSL, затем полученный Java-фрагмент передаётся генератору без анализа Java (D062).

Пример:

~~~text
datatype MyText : String {
    default = "\"\"";
}
~~~

Значение параметра default после снятия экранирования — Java-выражение `""`, задающее пустую строку. Чтобы передать в Java-фрагмент обратную косую черту, её нужно экранировать на уровне DSL.

### D084. Начальный набор встроенных datatype — принято 27.10.2026

Утверждён начальный набор встроенных datatype и их начальные значения:

| Datatype | Java-тип | Начальное значение (Java-выражение) |
|---|---|---|
| `String` | `java.lang.String` | `""` |
| `Int` | `int` | `0` |
| `Long` | `long` | `0L` |
| `Boolean` | `boolean` | `false` |
| `Double` | `double` | `0.0` |

Эти имена заняты встроенными объявлениями в общем пространстве имён (D069). Пользователь может объявлять собственные datatype и наследоваться от встроенных по общим правилам.

Решение фиксирует состав набора и начальные значения. Правила преобразования текста для String уже определены в D070; точные правила для остальных типов обсуждаются отдельно.

### D085. Строгий текстовый формат Boolean — принято 27.10.2026

Для встроенного Boolean допустимы только строки `"true"` и `"false"`. Регистр значим; пробелы не удаляются. Любой другой текст, включая `"TRUE"`, `"1"`, пустую строку и `" true "`, является ошибкой разбора.

При ошибке разбора setData возвращает false и сохраняет прежнее значение. Успешный разбор строки `"false"` даёт нативное значение false; это не ошибка и при отсутствии отклоняющего валидатора setData возвращает true.

Сериализация выдаёт только `"true"` или `"false"`. Начальное значение остаётся false (D084). Это правило текстового формата встроенного типа; детали реализации парсера не фиксируются этим решением.

### D086. Десятичный формат Int и Long — принято 27.10.2026

Для встроенных Int и Long принят десятичный текстовый формат `[+-]?[0-9]+`, которому должна соответствовать вся входная строка. Допускаются только ASCII-цифры, необязательный знак и ведущие нули.

Пробелы не удаляются и не допускаются. Префиксы `0x` и `0b`, подчёркивания, другие разделители, суффиксы (включая `L`), пустая строка и знак без цифр запрещены.

Выход за диапазон соответствующего Java-типа является ошибкой разбора. При ошибке формата или переполнении setData возвращает false, прежнее значение сохраняется. Успешно разобранное значение далее проходит действующую проверку validate, если она задана.

Сериализация выдаёт десятичную запись без плюса, лишних ведущих нулей и суффикса. Например, `"+007"` нормализуется в `"7"`, а `"-0"` — в `"0"`. Начальные значения остаются определёнными в D084. Конкретный способ реализации разбора этим решением не задаётся.

### D087. Специальные значения Double — принято 27.10.2026

Во встроенном Double разрешены NaN, положительная и отрицательная бесконечность. Их текстовые представления при разборе и сериализации: `"NaN"`, `"Infinity"`, `"-Infinity"` соответственно.

Сам встроенный тип не ограничивается конечными числами. Если такое ограничение требуется, автор DSL задаёт validate в производном datatype или узле; действуют общие правила полной замены проверки.

Это решение не определяет остальные варианты написания, формат обычных чисел, поведение при переполнении или потере точности — эти вопросы обсуждаются отдельно.

### D088. Текстовый формат Double — принято 27.10.2026

Для обычных чисел встроенного Double принят десятичный формат, которому должна соответствовать вся входная строка:

~~~text
[+-]?([0-9]+(\.[0-9]*)?|\.[0-9]+)([eE][+-]?[0-9]+)?
~~~

Допускаются только ASCII-цифры, необязательный знак, десятичная точка и экспонента e/E. В мантиссе должна быть хотя бы одна цифра; после e/E допускается знак, за которым обязательны цифры. Примеры допустимой записи: 12, -0.5, .5, 1., +1.25e-3. Ведущие нули допустимы.

Пробелы (в том числе по краям), десятичная запятая, подчёркивания, шестнадцатеричная запись и суффиксы f/d запрещены. Пустая строка, одиночная точка и незавершённая экспонента недопустимы.

Специальные строки — ровно "NaN", "Infinity", "-Infinity" (D087), с указанным регистром. Варианты вроде "nan", "+Infinity" или "-NaN" не принимаются.

Ошибка формата приводит к false из setData без изменения прежних данных. Это решение определяет лексический формат входа; округление, переполнение, потеря слишком малых значений и формат сериализации обычных чисел обсуждаются отдельно.

### D089. Переполнение Double при разборе — принято 27.10.2026

Переполнение при разборе десятичной записи Double считается ошибкой: если результатом преобразования становится положительная или отрицательная бесконечность, setData возвращает false и сохраняет прежнее значение.

Например, `"1e999"` и `"-1e999"` отклоняются. Явные строки `"Infinity"` и `"-Infinity"` остаются допустимыми согласно D087–D088; правило относится именно к переполнению при преобразовании числовой записи.

Проверка переполнения является частью разбора, а не заменяемым validate. Округление конечных результатов и потеря слишком малых значений этим решением не определяются.

### D090. Округление Double при разборе — принято 27.10.2026

При разборе Double разрешено округление до ближайшего представимого значения. При равном расстоянии до двух значений выбирается значение с чётным младшим битом значащей части.

Неточность представления сама по себе не является ошибкой. Разрешено округление слишком малых чисел до нуля с сохранением знака: `"1e-999"` преобразуется в 0.0, `"-1e-999"` — в -0.0. Успешно разобранное значение далее проходит действующий validate, если он задан.

Переполнение до бесконечности по-прежнему отклоняется согласно D089. Правило не требует сохранять исходное десятичное написание.

### D091. Сериализация Double — принято 27.10.2026

Для сериализации встроенного Double используется `java.lang.Double.toString(value)`.

Конечные значения записываются в стандартном формате этого метода, например `"12.0"`, `"0.5"`, `"-0.0"`; при необходимости используется экспонента E. Обратный разбор восстанавливает конечное значение, включая знак нуля. Исходное написание входной строки не сохраняется.

NaN сериализуется как `"NaN"`, бесконечности — как `"Infinity"` и `"-Infinity"`. Различия битовых вариантов NaN текстом не сохраняются; для контракта сохранения значения D073 такие варианты считаются эквивалентными.

Справка: [Double.toString(double), Java 21](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Double.html#toString(double)).

### D092. Параметры данных требуют datatype — принято 27.10.2026

Параметры default и validate разрешены только в узле с datatype, заданным явно или полученным по наследованию. Если datatype отсутствует, любой из этих параметров является ошибкой DSL. Неявный выбор String не выполняется.

Правило одинаково для конкретных и абстрактных узлов. Наличие datatype проверяется после разрешения наследования, поэтому повторять унаследованную привязку в заголовке не требуется.

~~~text
node Marker {
    default = "0"; // Ошибка: datatype отсутствует.
}

node NumberMarker<Int> {
    default = "0"; // Допустимо.
}
~~~

Проверяется структура объявления DSL, а не содержимое Java-выражений.

### D093. Текстовые данные узла без datatype — принято 27.10.2026

Для узла без datatype действует следующий контракт:

- getData() всегда возвращает пустую строку.
- setData("") возвращает true и ничего не меняет.
- setData с любой непустой строкой возвращает false и ничего не меняет.

Это позволяет десериализатору передавать текстовое представление данных единообразно для узлов с datatype и без него. Пустая строка не создаёт нативных данных и не означает неявной привязки String.

Предусловие ненулевого аргумента setData сохраняется (D070). Правило не меняет поведение узлов с datatype: для них действуют собственные parse и validate.

### D094. Подключение DSL-файлов через include — принято 27.10.2026

Принята директива подключения исходника DSL:

~~~text
include "common.dsl";

node Addition : BinaryExpression;
~~~

Директива располагается на верхнем уровне и заканчивается точкой с запятой. Её можно размещать в любом месте верхнего уровня файла. Путь разрешается относительно файла, содержащего эту директиву.

Объявления подключённого файла входят в общее пространство имён текущей компиляции. Порядок директив и объявлений не ограничивает доступность имён: ссылки разрешаются после сбора объявлений (D067–D069). Директива подключает исходник DSL, а не импортирует Java-классы.

Повторные подключения и циклы разрешены в D095. Идентичность файлов определена в D096.

### D095. Однократная обработка файлов и циклы include — принято 27.10.2026

Каждый исходный файл DSL обрабатывается только один раз за компиляцию. Повторные подключения разрешены, в том числе через несколько промежуточных файлов.

Циклы include также разрешены: если A подключает B, а B подключает A, повторно встреченный файл не обрабатывается. После сбора всех объявлений разрешаются ссылки независимо от порядка обхода файлов.

Повторное подключение одного общего файла не создаёт повторных объявлений. Независимые объявления с одинаковым именем в разных файлах остаются ошибкой общего пространства имён. Циклы наследования типов узлов и datatype по-прежнему запрещены: это отдельное ограничение, не относящееся к графу include.

Идентичность файлов определяется каноническим абсолютным путём (D096).

### D096. Канонические пути исходников — принято 27.10.2026

Идентичность исходного файла DSL определяется его каноническим абсолютным путём с разрешением компонентов `.`, `..` и символических ссылок.

Пути `common.dsl`, `./common.dsl` и символическая ссылка на тот же файл не вызывают повторной обработки, если приводят к одному каноническому пути (D095).

Вложенные include разрешаются относительно каталога реального файла, полученного после разрешения символических ссылок, а не каталога ссылки на него. Таким образом, результат подключения не зависит от того, по какому из путей файл был обнаружен первым.

### D097. Переносимые пути include — принято 27.10.2026

В include разрешены только относительные пути с разделителем `/` на всех поддерживаемых ОС.

~~~text
include "../shared/common.dsl";
~~~

Компоненты `.` и `..` разрешены; переход в родительский каталог сам по себе не запрещается. Абсолютные пути, пути с буквами дисков, UNC-пути и обратная косая черта в декодированном пути запрещены.

Ограничения относятся к записи путей в директивах include. Они не определяют способ передачи корневых исходников компилятору. Разрешение относительного пути и определение идентичности файла выполняются по D094–D096.

### D098. Кодировка исходников DSL — принято 27.10.2026

Все исходники DSL читаются только в UTF-8. Правило распространяется на корневые файлы и файлы, подключённые через include.

В начале файла допускается необязательный UTF-8 BOM. Поддерживаются окончания строк LF и CRLF. Некорректная последовательность UTF-8 является ошибкой; повреждённые последовательности не заменяются символами замены и другая кодировка автоматически не подбирается.

Unicode разрешён в строках и комментариях. Идентификаторы по-прежнему ограничены ASCII согласно D027. Разрешение Unicode не отменяет правила экранирования и запрет буквальных переносов строк внутри строкового литерала (D083).

### D099. Ошибки подключения исходников — принято 27.10.2026

Неудачный include является ошибкой всей компиляции: например, если файл отсутствует, недоступен для чтения или путь не удаётся разрешить.

Такой include не пропускается молча. Поиск одноимённого файла в других каталогах вместо указанного пути не выполняется.

Диагностика должна содержать место директивы (файл и строку), запрошенный путь, причину ошибки и цепочку подключений от корневого исходника. Это решение не требует остановиться на первой ошибке; оно запрещает считать компиляцию успешной при неудачном подключении.

### D100. Проверка типа в шаблоне с учётом наследования — принято 27.10.2026

Проверка типа в шаблоне сопоставления учитывает объявленную иерархию наследования.

Указание абстрактного типа Expression принимает конкретные узлы всех его прямых и косвенных потомков. При множественном наследовании достаточно принадлежности к указанной ветви иерархии.

Указание конкретного типа IntegerLiteral принимает только узлы этого типа, поскольку наследование от конкретных типов запрещено (D013). Datatype не является типом узла и не используется вместо него в этой проверке.

Решение определяет только проверку типа. Ограничения шаблона на данные и детей, а также смысл отсутствующих частей шаблона рассматриваются отдельно.

### D101. Отсутствующий и пустой список детей в шаблоне — принято 27.10.2026

Примечание D105: ниже сохранена историческая формулировка. Прежний смысл Expression() отменён: отсутствие детей проверяется через Expression[], а Expression() равнозначно Expression.

В шаблонах сопоставления отсутствие списка детей и явно пустой список имеют разный смысл:

~~~text
Expression     // Только проверка типа; дети и данные любые.
Expression()   // Проверка типа и отсутствия детей; данные любые.
~~~

Одиночное имя типа не накладывает ограничений на детей и данные. Явный пустой список требует, чтобы сопоставляемый узел не имел детей, но не требует пустых данных.

Проверка типа в обеих формах учитывает наследование по D100. Правило относится к шаблонам сопоставления; оно не меняет правила объявлений узлов и не определяет семантику построения результата.

### D102. Точное позиционное сопоставление детей — принято 27.10.2026

Обычный позиционный список детей в шаблоне сопоставляется с полным списком фактических детей узла: количество и порядок должны точно совпадать.

~~~text
Addition[IntegerLiteral, Expression]
~~~

Этот шаблон требует узел Addition ровно с двумя детьми. Первый ребёнок должен соответствовать IntegerLiteral, второй — Expression. Каждый вложенный шаблон применяется к ребёнку на своей позиции.

Автоматическая перестановка или распределение детей по совместимым типам при сопоставлении не выполняется. Правила распределения при построении узла не переносятся на позиционный шаблон.

Пропуск остальных детей, повторения и обращение по тегам рассматриваются отдельно. Пустой список сохраняет смысл D101: детей нет.

### D103. Частичное сопоставление детей по тегам — принято 27.10.2026

Принято сопоставление детей по тегам с частичным перечислением:

~~~text
Addition(left: IntegerLiteral)
~~~

Шаблон проверяет ребёнка с тегом left; на остальных детей ограничений не накладывает. Порядок тегов в шаблоне не влияет на результат, сопоставление не зависит от физических позиций этих детей:

~~~text
Addition(right: Expression, left: IntegerLiteral)
~~~

Здесь проверяются оба указанных тега. Вложенные шаблоны используют общие правила сопоставления, включая D100–D102. Само перечисление тегов не накладывает ограничений на данные родительского узла.

Смешивание тегов и позиций в одном списке, неизвестные и повторные теги, необязательные дети и повторяющиеся группы рассматриваются отдельно.

### D104. Разные скобки для позиционных и именованных шаблонов — принято 27.10.2026

По предложению пользователя способы сопоставления детей различаются видом скобок:

~~~text
Addition[IntegerLiteral, Expression] // По позициям.
Addition(right: Expression, left: IntegerLiteral) // По тегам.
Addition(left: Negation[IntegerLiteral]) // Вложенные способы независимы.
~~~

Квадратные скобки обозначают позиционный список с точным количеством и порядком детей (D102). Круглые скобки обозначают список проверок по тегам, с частичным перечислением и без зависимости от порядка записи тегов (D103).

Позиционные элементы записываются в квадратных скобках, именованные — в круглых. Прежние примеры позиционных шаблонов с круглыми скобками заменены. Это изменение синтаксиса шаблонов сопоставления; синтаксис объявлений детей не меняется.

Смысл пустых скобок согласован в D105: Expression[] требует отсутствия детей; Expression() равнозначно Expression. Возможность одновременно задавать оба списка одному узлу этим решением не определяется.

### D105. Пустые позиционные и именованные шаблоны — принято 27.10.2026

Приняты следующие формы шаблона:

~~~text
Expression     // Только тип (любые дети).
Expression[]   // Тип и обязательное отсутствие детей.
Expression()   // Только тип (любые дети, так как не указано никакого тега).
~~~

Expression и Expression() равнозначны: проверяется только тип по D100. Пустой список проверок по тегам не ограничивает детей. Expression[] требует ровно ноль фактических детей.

Данные во всех трёх формах не ограничиваются. Решение заменяет прежний смысл Expression() из D101: проверка отсутствия детей теперь записывается только пустым позиционным списком [].

### D106. Проверка тегов шаблона по объявленному типу — принято 27.10.2026

Тег в именованном шаблоне должен быть объявлен у указанного в шаблоне типа узла, включая унаследованные объявления детей. Неизвестный тег является ошибкой DSL.

Если left объявлен только у BinaryExpression, а у его предка Expression такого тега нет:

~~~text
Expression(left: IntegerLiteral)       // Ошибка: у Expression нет left.
BinaryExpression(left: IntegerLiteral) // Допустимо.
~~~

Наличие тега только у некоторых потомков указанного типа не делает обращение допустимым. Проверка выполняется по схеме указанного типа при проверке DSL, а не поиском подходящего тега у конкретного узла во время сопоставления.

### D107. Сопоставление необязательного ребёнка — принято 27.10.2026

Для необязательного одиночного ребёнка обычный вложенный шаблон по тегу требует наличия ребёнка и его соответствия шаблону. Отсутствие ребёнка означает несовпадение, а не ошибку.

Пример пользователя:

~~~text
node Return(value: Expression?); // Объявление узла.

Return(value: IntegerLiteral) // Есть ребёнок с тегом value, и он IntegerLiteral.
Return[IntegerLiteral]        // Есть ровно один ребёнок, и он IntegerLiteral.
~~~

Для данного объявления оба шаблона совпадают с одними и теми же узлами. Их общая семантика различна: именованный шаблон проверяет указанный тег, не ограничивая остальных детей (D103); позиционный шаблон проверяет полный список фактических детей (D102).

Необязательность ребёнка в схеме не делает его проверку в шаблоне необязательной. Если тег вообще не указан в именованном шаблоне, его наличие не проверяется.

### D108. Проверка отсутствия ребёнка через none — принято 27.10.2026

Принят специальный маркер none для проверки отсутствия необязательного ребёнка по тегу:

~~~text
Return(value: none)
~~~

Шаблон совпадает, если ребёнок value отсутствует. Если он присутствует, сопоставление неуспешно. Остальные дети этим условием не ограничиваются.

В отличие от Return[], проверяется отсутствие только ребёнка с указанным тегом, а не всех детей. Тег должен быть объявлен у указанного типа по D106. none здесь обозначает отсутствие ребёнка, а не пустые данные и не узел без собственных детей.

Применение none к повторяющимся группам принято в D109; для обязательного одиночного ребёнка none запрещён в D110.

### D109. Проверка пустой повторяющейся группы через none — принято 27.10.2026

Маркер none разрешён для повторяющейся группы детей и требует, чтобы эта группа была пуста:

~~~text
node Block(items: Statement*);

Block(items: none) // По тегу items нет ни одного ребёнка.
~~~

Остальные группы и дети этим условием не ограничиваются. Если в группе есть хотя бы один ребёнок, шаблон не совпадает.

Смысл none един для необязательного одиночного ребёнка (D108) и повторяющейся группы: по указанному тегу нет ни одного ребёнка. Тег должен быть объявлен в схеме указанного типа (D106).

### D110. Запрет none для обязательного ребёнка — принято 27.10.2026

Маркер none запрещён для обязательного одиночного ребёнка как заведомо невыполнимая проверка. Это ошибка DSL, выявляемая при проверке шаблона, а не обычное несовпадение во время сопоставления.

~~~text
node Negation(operand: Expression);

Negation(operand: none) // Ошибка DSL: operand обязан присутствовать.
~~~

Кратность определяется по схеме указанного в шаблоне типа, включая унаследованные объявления. Для необязательных детей и повторяющихся групп сохраняются правила D108–D109.

### D111. Список шаблонов для повторяющейся группы — принято 27.10.2026

Для проверки полного состава повторяющейся группы принят список шаблонов в квадратных скобках после тега:

~~~text
Block(items: [Return, ExpressionStatement])
~~~

Группа items должна содержать ровно двух детей в указанном порядке: первого сопоставляют с Return, второго — с ExpressionStatement. Другие дети и группы родительского узла этим условием не ограничиваются. Вложенные шаблоны из одних имён типов не ограничивают собственных детей и данные сопоставляемых узлов (D105).

Пустой список Block(items: []) равнозначен Block(items: none): группа items пуста.

Полный пример объявлений:

~~~text
abstract Statement;
abstract Expression;
node Block(items: Statement*);
node Return : Statement(value: Expression?);
node ExpressionStatement : Statement(value: Expression);
node IntegerLiteral<Int> : Expression;
~~~

Пример дерева, соответствующего шаблону:

~~~mermaid
graph TD
    B["Block"] -->|"items[0]"| R["Return"]
    B -->|"items[1]"| S["ExpressionStatement"]
    R -->|value| I["IntegerLiteral: 42"]
    S -->|value| J["IntegerLiteral: 7"]
~~~

Обозначения items[0] и items[1] на рёбрах поясняют позиции внутри группы и не вводят новый синтаксис DSL. Перестановка двух детей группы или добавление третьего приводит к несовпадению.

### D112. Явный список для повторяющейся группы — принято 27.10.2026

При проверке состава повторяющейся группы по тегу обязателен явный список в квадратных скобках, даже если требуется ровно один ребёнок.

~~~text
Block(items: [Return]) // Ровно один ребёнок, соответствующий Return.
Block(items: Return)   // Ошибка DSL.
~~~

Одиночный шаблон после тега повторяющейся группы не получает неявного смысла «ровно один», «хотя бы один» или «каждый». Маркер none остаётся допустимым сокращением пустого списка (D109–D111).

Правило относится к повторяющимся группам. Обычный шаблон одиночного обязательного или необязательного ребёнка сохраняется, например Return(value: IntegerLiteral).

### D113. Шаблон одиночного ребёнка не является списком — принято 27.10.2026

После тега одиночного ребёнка — обязательного или необязательного — используется шаблон узла, а не список шаблонов. Список в этой позиции является ошибкой DSL, включая пустой список.

~~~text
Return(value: [IntegerLiteral]) // Ошибка.
Return(value: IntegerLiteral)   // Допустимо.
Return(value: none)             // Отсутствие необязательного ребёнка.
~~~

Для отсутствия необязательного одиночного ребёнка применяется none (D108), а не []. Для обязательного ребёнка none запрещён (D110).

Вложенный шаблон может проверять собственных детей сопоставляемого узла:

~~~text
Return(value: IntegerLiteral[])
~~~

Здесь [] относится к детям IntegerLiteral: ребёнок value должен присутствовать, иметь этот тип и не иметь собственных детей. Это не список для тега value.

### D114. Повторение шаблона через * — принято 27.10.2026

Внутри позиционных списков разрешён суффикс * у шаблона. Он сопоставляет ноль или больше последовательных детей, каждый из которых соответствует этому шаблону.

~~~text
Block(items: [Return, ExpressionStatement*])
~~~

В группе items сначала должен находиться один ребёнок, соответствующий Return, затем ноль или больше детей, соответствующих ExpressionStatement. Список покрывает всю группу; непроверенных детей внутри неё не остаётся. Остальные дети узла этим именованным условием не ограничиваются.

Правило действует и для полного списка детей узла:

~~~text
Block[Statement*]
~~~

Все фактические дети должны соответствовать Statement; пустой список детей также подходит. Порядок детей сохраняется, перестановок нет. Вопрос нескольких возможных распределений между повторениями рассматривается отдельно.

Суффикс в шаблоне задаёт сопоставление последовательности и не меняет кратность в объявлении типа.

### D115. Необязательный элемент последовательности в шаблоне — принято 27.10.2026

Внутри позиционных списков принят суффикс ? у шаблона: ноль или один ребёнок, соответствующий этому шаблону.

~~~text
Block(items: [Return?, ExpressionStatement*])
~~~

Группа items допускает один Return в начале либо его отсутствие, затем ноль или больше ExpressionStatement. Список покрывает всю группу; порядок сохраняется.

Суффикс действует и в полном позиционном списке детей:

~~~text
Block[Return?, ExpressionStatement*]
~~~

При объявлении node Block(items: Statement*); эти две формы равнозначны: все дети Block входят в единственную группу items. Если схема содержит других детей или другие группы, равнозначность в общем случае исчезает: именованный шаблон проверяет только items, а полный позиционный список — всех фактических детей узла.

Суффикс ? в шаблоне относится к элементу сопоставляемой последовательности и не меняет кратность объявления. Разрешение неоднозначных распределений между элементами списка рассматривается отдельно.

### D116. Непустое повторение шаблона через + — принято 27.10.2026

В позиционных списках шаблонов принят суффикс +: один или больше последовательных детей, каждый из которых соответствует шаблону.

~~~text
Block[Statement+]         // Непустой полный список детей.
Block(items: [Statement+]) // Непустая группа items.
~~~

В отличие от *, пустая последовательность не подходит. Список шаблонов покрывает всю выбранную последовательность, сохраняя порядок. Для проверки по тегу остальные дети узла не ограничиваются.

Это решение касается шаблонов сопоставления. Кратность + в объявления детей этим решением не добавляется; там сохраняются ранее согласованные формы.

### D117. Запрет неоднозначного шаблона с одинаковыми повторениями — принято 27.10.2026

Пользователь отклонил предложение считать любое существующее полное распределение достаточным совпадением шаблона без захватов.

~~~text
Block[Statement*, Statement*] // Запрещённый шаблон.
~~~

Два соседних одинаковых повторения не задают однозначной границы между частями последовательности. Для непустого списка подходящих детей возможны несколько распределений. Отсутствие захватов не служит основанием разрешить эту конструкцию.

Зафиксирован запрет рассмотренного шаблона. Общий критерий запрета для более сложных пересекающихся шаблонов, а также выбор между статической проверкой потенциальной неоднозначности и проверкой конкретного входа требуют отдельного согласования. Автоматические приоритеты повторений этим решением не вводятся.

### D118. Допустимый шаблон с однозначными и неоднозначными входами — принято 27.10.2026

Шаблон ниже разрешён, несмотря на возможность неоднозначного распределения для некоторых входов:

~~~text
Block[Statement*, Return, Statement*]
~~~

Предполагается, что Return наследуется от Statement. Если все дети соответствуют Statement и среди них ровно один Return, распределение однозначно: этот ребёнок соответствует центральному элементу, остальные распределяются до и после него.

Мотивировка пользователя: здесь есть однозначное распределение для подходящего входа, поэтому шаблон следует оставить. При двух Return возможны два выбора центрального ребёнка; поведение на таком входе требует отдельного решения.

D118 не отменяет запрет конкретного шаблона из D117 и пока не задаёт универсальный алгоритм статической проверки. В частности, у Block[Statement*, Statement*] пустой вход тоже имеет единственное распределение (обе части пусты). Поэтому в D119 критерий уточнён: для рассматриваемых шаблонов требуется однозначный непустой вход; одного пустого недостаточно.

### D119. Непустой однозначный вход как критерий допустимости — принято 27.10.2026

Пользователь уточнил критерий, различающий D117 и D118: для рассматриваемого шаблона с потенциально неоднозначным распределением должен существовать хотя бы один непустой вход с однозначным полным распределением. Однозначность только на пустом входе не оправдывает такой шаблон: для проверки пустоты уже есть явный синтаксис.

~~~text
Block[Statement*, Statement*]         // Запрещён.
Block[Statement*, Return, Statement*] // Разрешён.
~~~

В первом случае любой непустой подходящий список допускает несколько границ между двумя одинаковыми повторениями. Единственный однозначный вход — пустой, чего недостаточно.

Во втором случае непустой список из одного Return имеет единственное распределение: оба повторения пусты, центральный шаблон сопоставлен с Return. Подходят и другие однозначные непустые входы, например последовательность Statement с единственным Return, если остальные дети не соответствуют Return.

Этот критерий не запрещает явные проверки пустоты Block[] и Block(items: none). Он уточняет допустимость шаблонов с неоднозначным распределением, а не требует непустого совпадения от любого шаблона вообще.

Поведение разрешённого шаблона на конкретном неоднозначном входе определено в D120: обычное несовпадение. Алгоритм проверки существования однозначного непустого входа предстоит определить при проектировании реализации.

### D120. Неоднозначное сопоставление означает несовпадение — принято 27.10.2026

Для разрешённого шаблона результат сопоставления с конкретным входом определяется количеством допустимых полных распределений:

- Ноль распределений — несовпадение.
- Одно распределение — совпадение.
- Несколько распределений — обычное несовпадение, без отдельной ошибки неоднозначности.

~~~text
Block[Statement*, Return, Statement*]
~~~

Если все дети соответствуют Statement и среди них один Return, шаблон совпадает. Если Return два, есть два выбора центрального ребёнка и шаблон не совпадает. Автоматический выбор первого, последнего или иного приоритетного распределения не выполняется.

Это правило выполнения сопоставления, отдельное от проверки допустимости самого шаблона (D117–D119). Оно не меняет правила распределения детей при построении узлов.

### D121. Универсальный шаблон узла _ — принято 27.10.2026

Принят шаблон _ для любого одного узла. Он не ограничивает тип, данные или детей и не создаёт захвата.

~~~text
Addition[_, IntegerLiteral] // Ровно два ребёнка; второй — IntegerLiteral.
Block[_*]                  // Любое количество любых детей.
~~~

Внутри позиционных списков применяются обычные суффиксы: _? — ноль или один узел, _* — ноль или больше, _+ — один или больше. Правила полноты списка и однозначности распределения сохраняются (D102, D114–D120).

Одиночное имя _ зарезервировано и не может использоваться как идентификатор. Имена вроде _value остаются допустимыми по общему правилу D027.

### D122. Именованный захват одиночного узла через as — принято 27.10.2026

Принят именованный захват одиночного узла через as:

~~~text
Addition(
    left: Expression as lhs,
    right: Expression as rhs
)
~~~

Шаблон перед as проверяется по обычным правилам. При успешном сопоставлении соответствующий узел целиком, включая данные и поддерево, захватывается под указанным именем для последующего построения результата.

~~~text
_ as x // Захват любого одного узла.
~~~

Это решение определяет запись и смысл захвата одиночного узла. Захваты последовательностей, область видимости, повторные имена и синтаксис обращения к захвату в результате рассматриваются отдельно.

### D123. Уникальность имён захватов в шаблоне правила — принято 27.10.2026

Имена захватов уникальны в пределах всего шаблона одного правила, включая все вложенные шаблоны.

~~~text
Addition(
    left: Expression as x,
    right: Expression as x // Ошибка DSL: повторное имя.
)
~~~

Повторное объявление захвата через as с тем же именем является ошибкой DSL. Оно не означает ни перезапись значения, ни неявную проверку равенства узлов.

В разных правилах одно и то же имя захвата разрешено. Способ явного сравнения захваченных узлов определяется отдельно.

### D124. Захват повторения целиком — принято 27.10.2026

Захват повторения записывается после суффикса и сохраняет всю сопоставленную последовательность узлов в исходном порядке:

~~~text
Block[Statement* as items]
~~~

При нуле сопоставленных детей items является пустым списком. Форма Statement+ as items также захватывает список, но непустой. Форма без суффикса Statement as item по-прежнему захватывает один узел (D122).

Захват не меняет правила сопоставления и не вводит приоритетов: требуется единственное полное распределение согласно D120. Правило одинаково для полного списка детей и списка повторяющейся группы по тегу.

Пользователь отдельно поднял вопрос о сохранении типа захвата и кратности уже на этапе проверки DSL. Модель метаданных и захват через ? приняты в D125. Вложенные захваты внутри повторения рассматриваются отдельно.

### D125. Статический тип и кратность захвата — принято 27.10.2026

При проверке DSL для каждого захвата сохраняются тип элементов и статическая кратность:

| Запись | Статическая категория | Кратность |
|---|---|---|
| T as x | Один узел T | 1 |
| T? as x | Необязательный узел T | 0..1 |
| T* as xs | Список узлов T | 0..∞ |
| T+ as xs | Непустой список узлов T | 1..∞ |

Принята форма захвата необязательного элемента T? as x: при отсутствии соответствующего элемента захват не содержит узла. Конкретное представление в Java определяется отдельно.

Для _ исходный тип элемента — «любой узел»; новый именованный тип DSL для этого не вводится. Тип элементов и кратность используются при проверке построения результата.

Фактическое число захваченных узлов не меняет статическую категорию: T* as xs остаётся списком, даже если на конкретном входе захвачен один узел. Списки сохраняют исходный порядок (D124).

### D126. Запрет вложенных захватов внутри повторения — принято 27.10.2026

Вложенные захваты внутри шаблона, повторяемого через * или +, запрещены. Ограничение проверяется статически как ошибка DSL, независимо от фактического количества повторений на конкретном входе.

~~~text
Block[Return(value: Expression as x)*] // Ошибка DSL.
~~~

Не вводятся неявное накопление вложенных захватов, перезапись или выбор последнего значения. Запрет распространяется на захваты в любой глубине внутри повторяемого шаблона.

Захват повторения целиком разрешён:

~~~text
Block[Return(value: Expression)* as returns]
~~~

returns содержит список целых узлов Return в исходном порядке (D124–D125). Это внешний захват результата повторения, а не захват внутри повторяемого шаблона. Правило одинаково для * и +. Вложенные захваты внутри необязательного шаблона с ? рассматриваются отдельно.

### D127. Вложенный захват узла внутри необязательного шаблона — принято 27.10.2026

Внутри необязательного шаблона с ? разрешён захват одиночного узла. Такой захват статически становится необязательным, с кратностью 0..1.

~~~text
Block[Return(value: Expression as x)?]
~~~

Если Return отсутствует, x не содержит узла. Если Return присутствует и соответствует вложенному шаблону, x содержит его ребёнка value. Наличие Return без подходящего value не даёт успешного совпадения этого полного списка.

Статический тип x — необязательный Expression; повторного заполнения захвата нет. Это не отменяет запрет вложенных захватов под * и + (D126). Представление списка, захваченного внутри ?, пока не определено.

Пользователь отдельно указал на необходимость проработать подстановку таких захватов при построении результата. Согласование подстановки становится следующим вопросом; автоматическая подстановка отсутствующего узла этим решением не вводится.

### D128. Подстановка необязательного захвата — предварительно согласовано 27.10.2026

Пользователь предварительно согласовал подстановку через $x, потребовав тщательно разобрать все варианты. Это рабочее решение для рассмотренных случаев, а не окончательная спецификация построения результата.

Если x — необязательный Expression (0..1):

~~~text
node Return(value: Expression?);
node Negation(operand: Expression);

// Формы построения результата:
Return(value: $x)     // Присутствующий x подставляется; отсутствующий оставляет value отсутствующим.
Negation(operand: $x) // Ошибка DSL: наличие обязательного ребёнка не гарантировано.
~~~

Типы и кратности проверяются заранее. Отсутствующий узел автоматически не заменяется дефолтным. Наличие x в отдельном запуске не снимает статического ограничения. Это правило прямой именованной подстановки без дополнительных проверок наличия.

### D129. Одиночный захват в одиночной позиции — принято 27.10.2026

Захват ровно одного узла совместимого типа разрешено подставлять как в обязательного, так и в необязательного одиночного ребёнка. В обоих случаях ребёнок присутствует.

По просьбе пользователя приведены эквивалентные примеры без тэгов, с позиционной записью:

~~~text
node Negation(operand: Expression);
node Return(value: Expression?);

// x получен через Expression as x.
Negation(operand: $x)
Negation[$x]

Return(value: $x)
Return[$x]
~~~

В этих объявлениях у каждого узла ровно одна позиция для ребёнка, поэтому позиционная запись однозначна. Квадратные скобки в выражении построения задают детей создаваемого узла; это не шаблон сопоставления. Объявления узлов сохраняют круглые скобки. Общие правила позиционного построения с несколькими позициями, необязательными захватами и списками ещё требуют обсуждения.

### D130. Прямая подстановка захвата в группу — принято 27.10.2026

Пользователь отклонил необходимость оборачивать ссылку на захват в список: категория, тип элементов и кратность захвата уже известны из шаблона. Для прямой подстановки в именованную группу используется $имя без дополнительных квадратных скобок.

~~~text
node Block(items: Statement*);

// s получен через Statement as s:
Block(items: $s) // Один ребёнок.

// statements получен через Statement+ as statements:
Block(items: $statements) // Все захваченные дети в исходном порядке.
~~~

Нужна совместимость типа элементов и кратности источника с принимающей группой, а не буквальное равенство категорий: один узел и непустой список подходят группе 0..∞. Захваченная последовательность становится детьми группы, а не отдельным узлом-контейнером. Для одиночного s позиционный пример — Block[$s].

Обязательная обёртка Block(items: [$s]) из предыдущего вопроса отклонена как избыточная. Это не отменяет явные списки в шаблонах сопоставления (D111–D113). Синтаксис составления группы из нескольких источников ещё не согласован. Случаи пустого списка и необязательного захвата рассматриваются следующим вопросом.

### D131. Пустая подстановка в группу и требование статического контроля — принято 27.10.2026

В повторяющуюся группу T* разрешена прямая подстановка всех четырёх категорий захвата совместимого типа: одиночного узла, необязательного узла, списка и непустого списка. В Block(items: $x) отсутствующий необязательный захват или пустой список дают ноль детей. Для node Block(items: Statement*) это корректный блок без детей. Непустой источник вставляется в исходном порядке.

Пользователь отдельно потребовал тщательно определить подстановку необязательного ребёнка в середине схемы и обеспечить статический контроль до исполнения на конкретных деревьях. По его описанию, прежняя реализация пропускала отсутствующую подстановку и передавала оставшиеся узлы билдеру, который пытался распределить их по ячейкам. Отсутствие предварительной проверки такого распределения неприемлемо для нового DSL.

Конкретный синтаксис и правила позиционной привязки пока не приняты. Следующее предложение: в выражении построения связывать каждое выражение подстановки с позицией схемы заранее, до удаления отсутствующих значений; отсутствие не меняет назначение соседних выражений. Это предложение не изменяет принятые правила позиционных шаблонов сопоставления и само по себе не отменяет ранее обсуждавшийся общий алгоритм распределения детей билдером.

### D132. Статическая привязка одиночных позиций — принято 27.10.2026

Пользователь принял привязку выражений построения к позициям схемы до исполнения для обязательных и необязательных одиночных детей.

~~~text
node Triple(first: Expression, middle: Expression?, last: Expression);

// a и c — ровно один Expression; b — необязательный Expression.
Triple[$a, $b, $c]
Triple(first: $a, middle: $b, last: $c)
~~~

Эти записи эквивалентны. При отсутствии b позиция middle остаётся пустой, а c заполняет last. Готовый узел имеет двух детей; отсутствующий ребёнок не превращается в узел-заглушку. Назначение подстановок не пересчитывается по оставшимся узлам. Тип и кратность каждой подстановки проверяются до исполнения; необязательный захват не допускается в обязательной позиции.

Пользователь отдельно подчеркнул необходимость гарантированной проверки совместимости типа захвата с принимающей позицией: по его описанию, в прежней реализации такой проверки нет. Следующий вопрос уточняет точное отношение совместимости (тип совпадает либо является потомком принимающего типа) и запрет неявного сужения по фактическому узлу. Обобщение позиционной привязки на группы и пропуск выражения в записи ещё не согласовано.

### D133. Статическая совместимость типов подстановок — принято 27.10.2026

Тип элемента захвата должен совпадать с типом принимающего ребёнка или наследоваться от него прямо либо косвенно. Кратность проверяется отдельно. Правило одинаково для именованных и позиционных подстановок, одиночных захватов и элементов списков. Несовместимость — ошибка DSL до исполнения правила на деревьях.

~~~text
abstract Expression;
abstract AssignableExpression : Expression;
node Identifier : AssignableExpression;
node IntegerLiteral : Expression;
node Assignment(left: AssignableExpression, right: Expression);

// lhs: Identifier, rhs: Expression — допустимо.
Assignment[$lhs, $rhs]

// lhs: Expression — ошибка DSL: тип слишком общий.
// lhs: IntegerLiteral — ошибка DSL: несовместимый тип.
~~~

Фактический более узкий тип узла при исполнении не исправляет несовместимость статического типа захвата. Например, захват Expression нельзя подставить в AssignableExpression, даже если фактически он содержит Identifier. Неявного сужения по конкретному дереву нет.

Для необязательной позиции AssignableExpression? захват Identifier? подходит, а Expression? не подходит: возможность отсутствия не отменяет проверку типа присутствующего элемента. Принятое правило задаёт гарантию проектируемого механизма преобразований; реализация пока не выполнялась.

### D134. Статическая позиционная привязка повторяющейся группы — принято 27.10.2026

~~~text
node Sequence(first: Statement, middle: Statement*, last: Statement);

// a и z — одиночные Statement; body — список Statement, возможно пустой.
Sequence[$a, $body, $z]
Sequence(first: $a, middle: $body, last: $z)
~~~

Записи эквивалентны. Каждое выражение относится к одному объявленному месту схемы: a — first, весь body — middle, z — last. Группа может получить ноль или несколько детей; её фактический размер не меняет привязку соседних выражений. Даже при одинаковом типе всех детей назначение подстановок известно до исполнения. Проверка типов и кратностей выполняется по D131–D133.

Это правило построения результата. Позиционные шаблоны сопоставления продолжают проверять последовательность фактических детей; их семантика не меняется. Пропуск выражений и объединение нескольких источников в одну группу ещё не согласованы. Следующий вопрос рассматривает две соседние повторяющиеся группы и сохранение границы между ними.

### D135. Соседние группы и сохранение принадлежности детей — принято 27.10.2026

~~~text
node Parts(left: Statement*, right: Statement*);

// xs и ys — захваченные списки Statement.
Parts[$xs, $ys]
Parts(left: $xs, right: $ys)
~~~

Обе формы построения допустимы и эквивалентны: xs целиком заполняет left, ys — right. Один или оба списка могут быть пустыми. Типы и кратности проверяются статически, назначения групп не выводятся заново из плоской последовательности.

Готовый узел должен сохранять принадлежность детей группам (либо границу между группами); одного плоского списка без этой информации недостаточно. Конкретное представление в памяти и формат сериализации этим решением не определены и потребуют отдельной проработки.

Это разрешение построения не отменяет запрета неоднозначного позиционного шаблона Parts[Statement*, Statement*]. Такой шаблон сопоставляется с последовательностью фактических детей по ранее принятым правилам.

### D136. Явное отсутствие одиночного ребёнка через none — принято 27.10.2026

Историческое уточнение: запрет сокращённой записи Triple[$a, $c] ниже отменён решением D138; остальные правила none сохраняются.

В построении результата none обозначает отсутствие необязательного одиночного ребёнка. Разрешены позиционная запись и запись по тэгу:

~~~text
node Triple(first: Expression, middle: Expression?, last: Expression);

Triple[$a, none, $c]
Triple(first: $a, middle: none, last: $c)
~~~

Записи эквивалентны: middle отсутствует, c заполняет last. none не создаёт узла-заглушки и не является значением данных узла. В обязательной позиции none — ошибка DSL, независимо от формы записи.

Для этой схемы Triple[$a, $c] запрещено: пропуск средней позиции не должен приводить к угадыванию назначения выражений. Пользователь отдельно подтвердил необходимость той же явной формы отсутствия для тэгов.

Возможность вообще не указывать необязательный тэг при построении рассматривается следующим вопросом. Пропуск завершающих позиционных выражений и применение none к повторяющимся группам пока не определены.

### D137. Пропуск необязательного тэга — принято 27.10.2026

При построении по тэгам необязательного одиночного ребёнка разрешено не указывать:

~~~text
node Triple(first: Expression, middle: Expression?, last: Expression);
Triple(first: $a, last: $c)
Triple(first: $a, middle: none, last: $c)
~~~

Записи эквивалентны. Все обязательные дети должны быть заданы; пропуск обязательного ребёнка — ошибка DSL до исполнения.

Пользователь предложил также разрешать пропуск необязательных мест в позиционной записи, когда назначение можно вывести по типам. Это пока предложение к уточнению D136, а не принятое изменение. Возможный критерий: ровно одно полное распределение выражений по местам схемы с сохранением порядка, с учётом статических типов, кратностей и обязательности всех мест. Каждое выражение связывается целиком с одним местом; фактические значения и размеры захватов при исполнении для выбора распределения не используются. Ноль распределений — несовместимость, несколько — неоднозначность и ошибка DSL; тэги или явное none позволяют уточнить намерение.

При таком критерии даже ранее запрещённое Triple[$a, $c] с двумя обязательными захватами Expression становится однозначным: first и last обязательны, значит пропустить можно только middle. Следовательно, принятие предложения потребует явно пересмотреть запрет D136, а не сохранить его одновременно с новым правилом. На этом шаге предложение рассматривается для одиночных обязательных/необязательных мест; распространение пропусков на группы отдельно не утверждено.

### D138. Однозначные позиционные пропуски одиночных мест — принято 27.10.2026

Необязательные одиночные места разрешено пропускать в позиционной записи построения, если существует ровно одно полное распределение выражений по местам схемы с сохранением порядка. Проверка учитывает статические типы, кратности захватов и обязательность мест. Каждое выражение связывается целиком с одним местом. Все обязательные места должны быть заполнены.

Ноль допустимых распределений — ошибка совместимости; несколько — ошибка неоднозначности. Фактические узлы и наличие необязательного захвата при исполнении не используются для выбора распределения. Единственное распределение фиксируется до исполнения.

~~~text
node Triple(first: Expression, middle: Expression?, last: Expression);
// a и c — обязательные одиночные Expression.
Triple[$a, $c] // Допустимо: пропущен только middle.

node Pair(first: Expression?, second: Expression?);
// x — обязательный одиночный Expression.
Pair[$x]       // Ошибка DSL: два распределения.
Pair[$x, none] // first заполнен, second отсутствует.
Pair[none, $x] // first отсутствует, second заполнен.
~~~

Решение явно отменяет запрет Triple[$a, $c] из D136. Явное none и запись по тэгам остаются средствами устранения неоднозначности. D137 в части позиционных пропусков теперь принят этим решением. Распространение пропусков на повторяющиеся группы пока не согласовано.

### D139. Явно пустая повторяющаяся группа — принято 27.10.2026

При построении результата none разрешено для повторяющейся группы с кратностью * и обозначает ноль детей. Допустимы обе формы:

~~~text
node Parts(left: Statement*, right: Statement*);
Parts[none, $ys]
Parts(left: none, right: $ys)
~~~

Записи эквивалентны: left пустая, весь захваченный список ys заполняет right. none не создаёт узла-заглушки. Принадлежность детей группам сохраняется по D135. Правило не разрешает none для обязательного одиночного ребёнка. Пропуск группы без явного none пока обсуждается отдельно.

### D140. Пропуск повторяющейся группы по тэгу — принято 27.10.2026

При построении по тэгам разрешено не указывать повторяющуюся группу с кратностью *. Неуказанная группа получает ноль детей, как при явном none.

~~~text
node Parts(left: Statement*, right: Statement*);
Parts(right: $ys)
Parts(left: none, right: $ys)
~~~

Эти записи эквивалентны. Назначение ys однозначно задано тэгом right. Требование указывать обязательных детей сохраняется. Это решение касается именованной записи; позиционный пропуск групп рассматривается следующим вопросом.

### D141. Однозначные позиционные пропуски групп — принято 27.10.2026

Правило единственного статического распределения D138 распространяется на пропуск повторяющихся групп *. Пропущенная группа пуста. Порядок выражений сохраняется; каждая подстановка целиком относится к одному месту схемы, список не делится между местами. Все обязательные места должны быть заполнены; типы и кратности проверяются до исполнения.

~~~text
node Sequence(first: Statement, middle: Statement*, last: Statement);
// a и z — обязательные одиночные Statement.
Sequence[$a, $z] // Допустимо: middle пустая.

node Parts(left: Statement*, right: Statement*);
// xs — список Statement.
Parts[$xs]       // Ошибка DSL: два допустимых назначения.
Parts[none, $xs] // Однозначно: xs заполняет right.
~~~

Ноль распределений — ошибка совместимости; несколько — ошибка неоднозначности. Фактическая длина списка при исполнении не используется для выбора назначения. При неоднозначности требуются тэги или явное none. Решение принято в рамках продолжающейся проверки всех случаев построения результата.

### D142. Список нельзя подставлять в одиночную позицию — принято 27.10.2026

Прямая подстановка захвата T* или T+ в обязательную либо необязательную одиночную позицию запрещена как ошибка DSL. Совместимого типа элементов недостаточно: список может содержать несколько узлов.

~~~text
node Negation(operand: Expression);
node Return(value: Expression?);

// xs захвачен через Expression+ as xs:
Negation(operand: $xs) // Ошибка DSL.
Return(value: $xs)    // Ошибка DSL.
~~~

Для Expression* действует тот же запрет. Фактическая длина списка, даже равная единице, не меняет его статическую категорию. Автоматического извлечения первого элемента и переноса проверки длины на исполнение нет. Правило одинаково для позиционной записи и записи по тэгам. Матрица D128 обновлена.

### D143. Встроенный Node и зарезервированные типы действий core — принято 27.10.2026

Вводится встроенный тип узла Node — общий прародитель всех узлов. Имя Node занято в общем пространстве имён типов, пользовательское переобъявление запрещено. Захват _ as x имеет статический тип Node: его можно подставлять в позицию Node, но нельзя неявно сужать до Expression или другого более узкого типа. Аналогичная проверка типа элемента применяется к спискам; правила кратностей сохраняются.

По просьбе пользователя проверены исходники astranaut-core. Action.TYPE объявлен как SimpleAbstractType("Action"); конкретные реализации Action — Insert, Delete, Replace, с одноимёнными значениями getName() и базой Action.TYPE. Эти четыре имени также резервируются в пространстве имён DSL: Action, Insert, Delete, Replace. Речь об именах типов, а не о запрете любых одноимённых тэгов или захватов.

Источники:
- https://github.com/kniazkov/astranaut-core/blob/master/src/main/java/com/kniazkov/astranaut/core/base/Action.java
- https://github.com/kniazkov/astranaut-core/blob/master/src/main/java/com/kniazkov/astranaut/core/base/Insert.java
- https://github.com/kniazkov/astranaut-core/blob/master/src/main/java/com/kniazkov/astranaut/core/base/Delete.java
- https://github.com/kniazkov/astranaut-core/blob/master/src/main/java/com/kniazkov/astranaut/core/base/Replace.java

Node как универсальный тип DSL — новое проектное решение, не утверждение о наличии такой базы в текущей иерархии core. Резервирование Action и конкретных действий само по себе ещё не определяет полный DSL-синтаксис их построения и исполнения. Остальные служебные классы core этим решением автоматически не резервируются.

### D144. Абстрактный Node и автоматическое наследование — принято 27.10.2026

Node — встроенный абстрактный тип, общий предок всех типов узлов. Создать экземпляр самого Node нельзя. Наследование от Node обеспечивается автоматически: пользователь не обязан писать : Node. При наличии явно указанных баз связь с Node сохраняется через иерархию; решение не требует добавлять избыточную прямую базу Node каждому потомку.

Node не объявляет собственных детей и datatype. Это не запрещает данные и детей у потомков и не ограничивает их при сопоставлении шаблоном Node без списка детей.

~~~text
abstract Expression; // Автоматически потомок Node.
node Box(value: Node);

// Равнозначные по охвату и статическому типу захвата шаблоны:
Node as x
_ as x

// Построение при одиночном захвате x типа Node:
Box(value: $x)
~~~

Node является типом узлов, а не datatype. Имя занято по D143. Новая иерархия DSL должна согласовываться с core при будущей реализации; в этом обсуждении код core не меняется.

### D145. Action закрыт для пользовательского наследования — принято 27.10.2026

Action — встроенная абстрактная категория, закрытая для пользовательского наследования. Её встроенные конкретные потомки: Insert, Delete, Replace. Action принадлежит общей иерархии Node.

~~~text
node CustomAction : Action;     // Ошибка DSL.
abstract CustomAction : Action; // Ошибка DSL.
~~~

Action разрешено использовать как тип ребёнка и в шаблонах сопоставления. Создавать экземпляр самого Action нельзя, поскольку тип абстрактный. Наследование от конкретных Insert, Delete, Replace также запрещено общим правилом наследования только от абстрактных узлов. Пользовательское объявление структуры не задаёт семантику исполнения нового действия; механизм расширения набора действий этим решением не вводится.

### D146. Уточнение о Property из core — 27.10.2026

Пользователь указал дополнительный служебный узел Property. Проверен исходник:
https://github.com/kniazkov/astranaut-core/blob/master/src/main/java/com/kniazkov/astranaut/core/algorithms/normalization/Property.java

Property — конкретный неизменяемый узел нормализации, реализующий Node, но не Action. У него нет детей; getData() возвращает строковое значение свойства, getName() — исходный ключ свойства. При этом getType().getName() возвращает не "Property", а "AstranautProperty" + NormalizationType.encode(ключ). Таким образом, существующая реализация создаёт семейство типов, зависящих от ключа.

Property добавлен к перечню служебных узлов, требующих согласования в DSL. Предложение резервировать имя Property отложено пользователем в D147: имя пока не резервируется. Его единую схему, представление ключа/значения и соответствие семейству типов core ещё нужно определить. Резервирование всего префикса AstranautProperty автоматически не вводится. Вопрос о схемах Insert/Delete/Replace, поставленный после D145, остаётся открытым и не считается принятым.

### D147. Property отложен, имя не резервируется — принято 27.10.2026

Пользователь отложил решение по Property, чтобы обдумать его назначение и представление. Предложение D146 о резервировании имени пока не принимается: Property не добавляется к зарезервированным именам DSL, встроенная схема не вводится. Существующая реализация core не меняется. Вопрос остаётся открытым; не возобновлять его немедленно следующим вопросом.

Согласованный набор имён встроенных узлов на этом этапе: Node, Action, Insert, Delete, Replace (помимо ранее согласованных встроенных datatype). Возвращаемся к оставшемуся открытым вопросу о структуре встроенных действий.

### D148. Схемы встроенных действий — принято 27.10.2026

Встроенные конкретные узлы действий имеют следующие схемы нового DSL:

~~~text
node Insert : Action(after: Node);
node Delete : Action(before: Node);
node Replace : Action(before: Node, after: Node);
~~~

Это описание встроенных типов, а не разрешение пользователю объявлять их заново. Все дети обязательные одиночные. Собственного datatype у действий нет. Тэги before и after приняты для нового DSL; порядок детей Replace — сначала before, затем after.

К подстановкам применяются общие статические проверки: допускается любой одиночный узел, поскольку принимающий тип Node; необязательные захваты, списки и none не подходят обязательным одиночным местам. Доступны именованная и позиционная формы построения:

~~~text
Insert(after: $x)
Insert[$x]
Delete(before: $x)
Delete[$x]
Replace(before: $old, after: $new)
Replace[$old, $new]
~~~

Условия исполнения действий этим решением не определяются. Реализация core и её адаптация к новым тэгам пока не меняются.

### D149. Построение действия не исполняет его — принято 27.10.2026

Выражения построения Insert, Delete и Replace создают обычные узлы, описывающие действия. Само построение не исполняет действие и не изменяет входное дерево.

~~~text
Replace[$old, $new]
~~~

Выражение создаёт Replace с двумя детьми: before содержит old, after содержит new. Оно само по себе не ищет old во входном дереве и не заменяет его. То же разделение построения и исполнения относится к Insert и Delete.

Применение дерева действий выполняется отдельным явно выбранным механизмом. Его синтаксис, выбор адресов и правила исполнения пока не определены. Создание узла действия не предоставляет обход статических проверок типов и кратностей в выражениях построения.

### D150. Объединение подстановок через + — принято 27.10.2026

В выражениях построения оператор + объединяет источники детей в одну последовательность.

~~~text
node Block(items: Statement*);
// prefix и suffix — списки Statement; item — одиночный Statement.
Block(items: $prefix + $item + $suffix)
Block[$prefix + $item + $suffix]
~~~

Обе записи эквивалентны. Элементы идут слева направо: prefix, затем item, затем suffix. Порядок внутри каждого списка сохраняется. Пустые списки дают ноль элементов. Подстановка одиночного узла добавляет один элемент. Объединение не создаёт промежуточного узла-контейнера.

Составное выражение целиком заполняет одну группу; его операнды не распределяются по разным местам схемы. Типы элементов проверяются статически на совместимость с принимающей группой. + здесь обозначает конкатенацию, не арифметику. Суффикс + в шаблонах по-прежнему означает повторение один или больше раз.

Необязательные операнды, none в составе выражения, построение новых узлов как операндов, группировка и точное вычисление статической кратности составных выражений ещё требуют обсуждения.

### D151. Необязательные захваты в объединении — принято 27.10.2026

В выражении объединения через + разрешены необязательные захваты.

~~~text
node Block(items: Statement*);
// prefix и suffix — списки Statement; item — необязательный Statement.
Block(items: $prefix + $item + $suffix)
Block[$prefix + $item + $suffix]
~~~

Присутствующий item добавляет один узел между prefix и suffix; отсутствующий добавляет ноль элементов. Порядок источников и элементов сохраняется, узел-заглушка не создаётся. Всё составное выражение по-прежнему заполняет одну группу.

Статический тип каждого операнда должен подходить принимающей группе. Возможность отсутствия или фактическое отсутствие захвата не разрешает несовместимый тип. Правила вычисления кратности составного выражения ещё требуют отдельного уточнения.

### D152. Построение нового узла внутри объединения — принято 27.10.2026

Операндами + могут быть выражения построения новых узлов, наряду с захватами.

~~~text
node Return : Statement(value: Expression?);
node Block(items: Statement*);

// prefix и suffix — списки Statement, value — необязательный Expression.
Block(items: $prefix + Return(value: $value) + $suffix)
Block[$prefix + Return[$value] + $suffix]
~~~

Обе формы создают один Return между списками. Даже если value отсутствует, Return создаётся без ребёнка и остаётся элементом группы items. Отсутствие вложенного необязательного захвата не делает выражение построения внешнего узла необязательным.

Выражение построения узла даёт ровно один элемент при успешном построении. Его внутренние подстановки проходят обычные статические проверки; тип созданного узла должен подходить принимающей группе. Правило не вводит автоматическое подавление ошибок построения и не заменяет невалидный узел пустотой.

### D153. Статическая кратность объединения — принято 27.10.2026

Кратность выражения + вычисляется суммированием нижних и верхних границ количества элементов операндов. Неограниченная верхняя граница при сложении остаётся неограниченной.

| Операнды | Диапазон результата |
|---|---|
| Один узел + один узел | 2..2 |
| Необязательный узел + необязательный узел | 0..2 |
| Список * + создаваемый узел | 1..∞ |
| Список * + список * | 0..∞ |

Обязательное одиночное место принимает только диапазон 1..1. Необязательное одиночное место принимает диапазон, целиком входящий в 0..1. Повторяющаяся группа * принимает любой неотрицательный диапазон. Совместимость типов проверяется отдельно.

В частности, сумма двух необязательных захватов не подходит одному необязательному месту: оба могут присутствовать. Фактическое количество элементов при исполнении не заменяет статической проверки. Диапазон относится ко всему выражению; его элементы не распределяются по нескольким местам схемы. Это правило подсчёта количества не вводит новые обозначения кратности в объявлениях.

### D154. none как пустой операнд объединения — принято 27.10.2026

В выражениях построения none разрешён как операнд +. Он обозначает пустую последовательность с кратностью 0..0, не создаёт узла и не накладывает ограничений на тип элементов результата.

~~~text
$xs + none // Эквивалентно $xs.
none + $x  // Эквивалентно $x.

// x — обязательный одиночный Expression.
Negation(operand: none + $x) // Допустимо: результат имеет кратность 1..1.
Negation(operand: none)      // Ошибка DSL: обязательный ребёнок отсутствует.
~~~

Совместимость с принимающим местом проверяется для всего выражения. Запрет пустоты в обязательной позиции сохраняется, но наличие none внутри непустого составного выражения само по себе не является ошибкой.

### D155. Группировочные скобки не вводятся — принято 27.10.2026

Предложение круглых скобок для группировки выражений построения отклонено. При единственной операции объединения + такие скобки не меняют последовательность, порядок или статические проверки и не дают полезной возможности.

~~~text
Block[$prefix + $item + $suffix]   // Допустимо.
Block[($prefix + $item) + $suffix] // Группировка не входит в принятый синтаксис.
~~~

Круглые скобки после имени типа для записи детей по тэгам сохраняются. Решение не затрагивает скобки внутри Java-фрагментов. К группировке можно вернуться при появлении других операций, но сейчас она не вводится.

### D156. Повторное использование захвата — принято 27.10.2026

Один захват разрешено использовать несколько раз в результате. Подстановка не расходует захват и не удаляет его содержимое.

~~~text
// x — одиночный Expression.
Addition[$x, $x]
Addition(left: $x, right: $x)

// xs — список Statement.
Block(items: $xs + $xs)
~~~

В Addition захваченное поддерево появляется в двух отдельных позициях. В Block последовательность xs повторяется дважды, с сохранением порядка каждого повторения. Совместимость типа и кратности проверяется для каждого использования; повторение не ослабляет статические ограничения.

Узлы неизменяемы, поэтому реализация может переиспользовать одни и те же объекты поддеревьев, без обязательного глубокого копирования. Разделение объектов не объединяет позиции результата: каждое вхождение остаётся самостоятельным вхождением в структуре.

Запрет повторного объявления имени захвата внутри одного шаблона (D123) сохраняется: повторное использование $x в результате не является повторным объявлением as x.

### D157. Неиспользуемые захваты допустимы — принято 27.10.2026

Объявленный в шаблоне захват разрешено не использовать в выражении результата. Это не ошибка DSL; преобразование не обязано сохранять все захваченные узлы.

~~~text
// Шаблон:
Addition(left: Expression as lhs, right: Expression as rhs)

// Выражение результата:
Negation[$lhs]
~~~

rhs участвует в сопоставлении, но не подставляется в результат. Это не самостоятельное действие Delete и не изменение входного дерева во время захвата. Все условия шаблона продолжают проверяться независимо от использования захватов в результате. Возможная необязательная диагностика неиспользуемых захватов этим решением не определяется.

### D158. Неизвестное имя захвата — ошибка DSL — принято 27.10.2026

Ссылка $name должна обозначать захват, объявленный в шаблоне того же правила. Неизвестное имя — ошибка DSL до исполнения.

~~~text
// Шаблон:
Expression as x

// Выражение результата:
Negation[$xx] // Ошибка DSL: захват xx не объявлен.
~~~

Имя не ищется в других правилах или среди тэгов; неизвестная ссылка не заменяется none. Отсутствующее значение объявленного необязательного захвата не является неизвестным именем: его тип и кратность известны статически, и применяются обычные правила необязательных подстановок.

### D159. Прямой возврат одиночного захвата — принято 27.10.2026

Выражение результата может состоять непосредственно из одиночного обязательного захвата $x, без создания нового узла-обёртки.

~~~text
// Шаблон:
Negation[Negation[Expression as x]]

// Выражение результата:
$x
~~~

Результатом становится захваченное поддерево целиком: сохраняются его фактический тип, данные и дети. Обязательного глубокого копирования нет, в соответствии с D156. Статический тип результата — тип захвата, кратность — 1..1.

Решение не определяет пустые и списочные результаты и не отменяет необходимость отдельно определить совместимость результата с местом замены во внешнем дереве.

### D160. Пустой результат преобразования корня — принято 28.10.2026

none разрешён как результат правила, применяемого к корню всего дерева. При успешном сопоставлении такой результат даёт пустое дерево без корня.

~~~text
// Шаблон:
Block[]

// Выражение результата:
none
~~~

Если корень — пустой Block и правило успешно применено, результирующее дерево не содержит корня. Это успешное преобразование, а не несовпадение шаблона. При несовпадении данное правило ничего не заменяет.

Не создаются узел Delete, узел-заглушка или null-узел. Пустота является состоянием дерева без корня. Решение не определяет применение пустого результата к дочерним позициям; допустимость удаления обязательных и необязательных детей и статический контроль контекста применения требуют отдельного обсуждения.

### D161. Необязательный захват как результат преобразования корня — принято 28.10.2026

Разрешён прямой возврат необязательного захвата $x при преобразовании корня всего дерева.

~~~text
node Box(value: Expression?);

// Шаблон:
Box[Expression? as x]

// Выражение результата:
$x
~~~

Если x присутствует, захваченное поддерево становится корнем результата. Если x отсутствует, результат — пустое дерево без корня. В обоих случаях правило успешно применено: отсутствие значения не означает несовпадение и не сохраняет прежний Box.

Статическая кратность такого результата — 0..1. Решение касается только корня всего дерева; применение результата к дочерним местам и списочные результаты требуют отдельного обсуждения.

### D162. Результат для корня ограничен кратностью 0..1 — принято 28.10.2026

При преобразовании корня всего дерева статический диапазон количества узлов результата должен целиком входить в 0..1. Прямой возврат списка T* или T+ запрещён как ошибка DSL, даже если при конкретном исполнении список пуст или содержит один элемент.

~~~text
// Шаблон:
Block[Statement* as items]

// Недопустимый результат для корня:
$items

// Допустимый результат:
Block(items: $items)
~~~

Для сохранения нескольких элементов нужно явно построить один узел-контейнер. Автоматическое создание контейнера, выбор первого элемента и результат в виде леса не вводятся. Ограничение также применяется к составным выражениям через + согласно их статическому диапазону D153. Применение к дочерним позициям рассматривается отдельно.

### D163. Замена обязательного одиночного ребёнка — принято 28.10.2026

При применении правила к заранее известной обязательной одиночной дочерней позиции результат должен иметь статическую кратность ровно 1..1. Статический тип результата должен совпадать с типом позиции или быть его потомком.

~~~text
node Negation(operand: Expression);
~~~

Для замены operand допустим один Expression или его потомок. Результаты none, необязательный захват и список не допускаются для этого места статически. Фактическое наличие значения необязательного захвата не снимает запрета.

Проверка выполняется до исполнения для данного известного контекста применения, по тем же требованиям типов и кратности, что и при построении. Решение не задаёт синтаксис указания контекста и не определяет поведение универсального обхода произвольного дерева: эти вопросы остаются открытыми.

## Синтаксис объявлений S001 — основа принята (D024–D027)

Основа записи объявлений принята в D024 на базе семантики D002–D022. Правила комментариев и идентификаторов приняты в D026–D027. Примеры в журнале решений выше остаются историческими условными иллюстрациями. Запись создания узлов, явного заполнения и смешивания аргументов отложена.

### Объявления и наследование

```text
abstract Expression;
abstract AssignableExpression : Expression;

abstract BinaryExpression : Expression (
    left: Expression,
    right: Expression
);

node Addition : BinaryExpression;
node Assignment : BinaryExpression (
    left: AssignableExpression,
    @right
);
```

- `abstract` и `abstract node` равнозначно объявляют абстрактный тип; `node` без abstract — конкретный тип узла. Например, `abstract Expression;` и `abstract node Expression;` означают одно и то же.
- После `:` за именем типа перечисляются абстрактные базы через запятую.
- В круглых скобках записывается состав детей в итоговом порядке.
- Каждое объявление заканчивается `;`.
- Отсутствие списка при единственной базе сохраняет её детей и порядок (D009). Если списки нескольких баз полностью совпадают, список также можно опустить (D034). Базы без детей не влияют на это решение (D035). Явный список не означает частичного добавления; для абстрактного и конкретного потомка применяются требования полноты D008–D009 и D032.
- Пустой список `()` обозначает отсутствие детей; он не разрешает удалить унаследованных детей. Конкретный тип без баз и без списка детей также не имеет детей.
- Наследование от конкретного типа запрещено.

### Дети и кратности

| Запись | Значение |
|---|---|
| `value: Expression` | Один обязательный ребёнок с тегом value |
| `value: Expression?` | Ноль или один ребёнок |
| `items: Expression*` | Ноль или больше детей |
| `Expression`, `Expression?`, `Expression*` | Собственные дети без тега, только в конкретном типе |
| `@value` | Ссылка на унаследованного ребёнка с сохранением типа и кратности |

Используется отдельный знак `@` для ссылки на унаследованный тег: иначе одиночное имя может означать и тег, и тип безымянного ребёнка. Регистр букв не используется для различения. `@` здесь не создаёт ребёнка и не задаёт его значение.

Совпадающий с унаследованным тег в записи `tag: Type` означает повторное объявление этой позиции. Допускается прежний тип либо его явное сужение согласно D011; кратность должна быть сохранена, включая суффикс `?` или `*`. Конфликт типов баз этим не исправляется (D012).

```text
abstract Sequence (
    items: Expression*
);

node AssignableSequence : Sequence (
    items: AssignableExpression*
);

node Pair (Expression, Expression);
```

### Несколько баз и переупорядочивание

```text
abstract HasLeft (left: Expression);
abstract HasRight (right: Expression);

node Combined : HasLeft, HasRight (
    @left,
    @right
);

node Reversed : BinaryExpression (
    @right,
    @left
);

node Extended : BinaryExpression (
    @left,
    extra: Expression?,
    @right
);
```

Ссылки сохраняют объявления баз, но задают порядок потомка. Совпадающие совместимые дети нескольких баз предварительно объединяются по тегу. Неизвестная ссылка `@tag` — ошибка. Правила полного списка и порядка одинаковы для абстрактных и конкретных потомков (D032).

### Несколько повторяющихся групп

```text
node Framed (
    first: Expression,
    middle: Expression*,
    last: Expression
);

node Split (
    first: Expression,
    second: Expression*,
    third: Expression*,
    fourth: Expression
);
```

Обе декларации допустимы и разбираются однозначно. Для Framed распределение совместимых детей однозначно при количестве от двух. Для Split два ребёнка распределяются однозначно, три и более без дополнительных привязок дают неоднозначность распределения (D022). Такая неоднозначность конкретного входа не запрещает само объявление типа.

### Грамматика объявлений

В этой EBNF фигурные скобки обозначают повторение, квадратные — необязательную часть, а терминалы заключены в кавычки.

```text
declaration = kind, identifier, [bases], [children], ";" ;
kind        = "abstract", ["node"] | "node" ;
bases       = ":", identifier, {",", identifier} ;
children    = "(", [child, {",", child}, [","]], ")" ;
child       = "@", identifier
            | identifier, ":", identifier, [multiplicity]
            | identifier, [multiplicity] ;
multiplicity = "?" | "*" ;
```

Форма `identifier` перед `:` внутри списка детей — тег, после `:` — тип; одиночный identifier — тип безымянного ребёнка. Ссылка на унаследованный тег начинается с `@`. После запятой списка баз ожидается имя очередной базы, а открывающая скобка начинает список детей.

Завершающая запятая в непустом списке детей разрешена в D025. Комментарии `//` до конца строки и `/* ... */` без вложенности приняты в D026; комментарии разделяют токены.

Идентификаторы соответствуют `[A-Za-z_][A-Za-z0-9_]*`, регистр различается; слова `abstract` и `node` зарезервированы (D027); ключевое слово `datatype` добавлено в D038. Unicode-идентификаторы пока не вводятся. Квалифицированные имена и остальные детали лексики требуют отдельного рассмотрения.

Грамматика описывает форму записи. Требования к тегам в абстрактных типах, наследованию, совместимости, полноте списка и распределению детей проверяются семантически.

## Синтаксис данных S002 — принятая форма (D038–D040)

Поля `javaType`, `default`, `serialize`, `parse` и `parseError` обязательны в итоговом описании пользовательского datatype с учётом наследования (D076), в том числе строковом и примитивном (D042–D044). Для parseError допускается явный маркер `none`. Встроенные datatype, включая String, предоставляют готовые описания (D045). Преобразования указываются явно. Документация должна объяснять заполнение каждого поля и содержать полные примеры.

```text
datatype Int {
    javaType = "int";
    default = "0";
    serialize(value) = "Integer.toString(value)";
    parse(text) = "Integer.parseInt(text)";
    parseError = "NumberFormatException";
}

node IntegerLiteral<Int> : Expression;
node ArraySize<Int>;
```

Ссылка `<Int>` ставится непосредственно после имени объявляемого узла, до `:` с базами. Указанные узлы различаются типом узла, но используют одно описание данных. Нативное значение доступно через типизированный getValue(), текстовое представление — через getData(); для Int начальное значение 0 представляется строкой `"0"`, а не пустой строкой.

Общая форма объявления абстрактного или конкретного типа узла с необязательной явной привязкой данных:

```text
dataBinding = "<", identifier, ">" ;
declaration = kind, identifier, [dataBinding], [bases], [children], ";" ;
```

Грамматика S002 расширяет правило declaration из S001 привязкой данных; остальные правила S001 сохраняются. Дети разрешены вместе с данными (D039). Абстрактные типы могут объявлять и наследовать данные; при отсутствии локальной привязки действует наследование по D040. Лексические правила identifier из D027 применяются к имени datatype; datatype становится зарезервированным словом. Имена параметров внутри блока не объявляются глобально зарезервированными этим решением.

## Синтаксис проверки данных S003 — принятая форма (D047)

После заголовка конкретного узла, включая базы и список детей при их наличии, вместо завершающего `;` допускается блок проверки:

```text
node PositiveInteger<Int> : Expression {
    validate(value) = "value > 0";
}
```

Параметр validate необязателен: его отсутствие в datatype эквивалентно проверке true (D050). После уточнения D048 validate разрешён в datatype и в узле; узел также может переопределить default. Переопределённый default абстрактной базы наследуется потомком, если тот не задаёт собственный (D051). Параметр validate обозначает проверяемое нативное значение. Проверка default автоматически не выполняется (D047). Локальный validate полностью заменяет любую унаследованную проверку; объединений нет. Конфликтующие объявления проверок в базах запрещены; одна проверка общего предка разрешена (D059–D060). Подробности и примеры вынесены в [отдельный документ](https://github.com/kniazkov/astranaut/blob/docs/dsl-design/docs/dsl-design/data-validation.md).

## Подключение исходников S004 — принятая форма (D094)

~~~text
includeDirective = "include", stringLiteral, ";" ;
~~~

Директива допустима на верхнем уровне в любом месте файла. Строка пути использует экранирование D083; путь разрешается относительно содержащего директиву файла. Объявления включаются в общее пространство имён компиляции и разрешаются независимо от порядка записи.

Каждый файл обрабатывается один раз за компиляцию; повторные подключения и циклы include разрешены (D095). Объявления разных файлов с одинаковым именем остаются ошибкой.

Идентичность файла определяется каноническим абсолютным путём с разрешением символических ссылок. Вложенные include разрешаются относительно каталога реального файла (D096).

Пути include — только относительные, с разделителем `/` на всех ОС. Компоненты `.` и `..` разрешены. Абсолютные пути, буквы дисков, UNC-пути и обратная косая черта в декодированном пути запрещены (D097).

Неудачный include делает компиляцию ошибочной. Диагностика указывает файл и строку директивы, запрошенный путь, причину и цепочку подключений от корневого исходника. Молчаливого пропуска и поиска замены в других каталогах нет (D099).

## Кодировка исходников S005 — принято (D098)

Корневые и подключённые файлы читаются как UTF-8 с необязательным BOM в начале файла. Поддерживаются LF и CRLF. Некорректный UTF-8 — ошибка без подстановки символов замены. Unicode разрешён в строках и комментариях; идентификаторы остаются ASCII. Правила строк D083 сохраняются.

## Шаблоны сопоставления S006 — проверка типа (D100)

Абстрактный тип в шаблоне принимает конкретные узлы всех прямых и косвенных потомков. Конкретный тип принимает только узлы этого типа.

В шаблонах `Expression` и `Expression()` проверяется только тип: дети и данные любые. Шаблон `Expression[]` дополнительно требует обязательного отсутствия детей; данные остаются любыми (D105, заменяет прежний смысл пустых круглых скобок в D101).

Обычный позиционный список требует точного количества и порядка фактических детей (D102). Например, `Addition[IntegerLiteral, Expression]` требует ровно двух детей с соответствующими шаблонами на первой и второй позициях. Автоматического распределения или перестановки при сопоставлении нет.

Именованный список проверяет только перечисленные теги, остальные дети не ограничиваются (D103). Например, `Addition(left: IntegerLiteral)` проверяет только left. Порядок тегов в шаблоне не важен и не зависит от физических позиций детей.

Позиционные списки заключаются в `[]`, именованные — в `()` (D104). Вложенные шаблоны могут использовать разные способы: `Addition(left: Negation[IntegerLiteral])`. Синтаксис объявлений детей этим не меняется.

Теги именованного шаблона должны существовать в схеме указанного типа, включая унаследованные теги (D106). Тег, объявленный только у некоторых потомков, недоступен через шаблон базового типа. Неизвестный тег — ошибка DSL.

Обычный вложенный шаблон по тегу требует присутствия необязательного ребёнка (D107). При схеме `node Return(value: Expression?);` шаблон `Return(value: IntegerLiteral)` проверяет наличие value и его тип; `Return[IntegerLiteral]` требует ровно одного фактического ребёнка указанного типа. Для этой схемы результаты совпадают, но способы проверки различны.

Шаблон `Return(value: none)` требует отсутствия необязательного ребёнка value, не ограничивая остальных детей (D108). Наличие ребёнка означает несовпадение. Тег должен существовать в схеме типа; none не означает пустые данные или отсутствие детей у вложенного узла.

Для повторяющейся группы `none` требует ноль детей по указанному тегу (D109). Например, `Block(items: none)` проверяет пустоту items, не ограничивая остальных детей.

Для обязательного одиночного ребёнка `none` запрещён: это ошибка DSL при проверке шаблона (D110).

Повторяющуюся группу можно проверить списком шаблонов: `Block(items: [Return, ExpressionStatement])` требует ровно двух детей в группе items в указанном порядке (D111). Остальные дети узла не ограничиваются. `Block(items: [])` равнозначно `Block(items: none)`.

При проверке повторяющейся группы по тегу список обязателен даже для одного ребёнка: `Block(items: [Return])`. Форма `Block(items: Return)` — ошибка DSL. `none` остаётся сокращением пустого списка (D112).

После тега одиночного ребёнка список запрещён, включая `[]` (D113). Используется шаблон узла или, для необязательного ребёнка, `none`. В `Return(value: IntegerLiteral[])` квадратные скобки проверяют собственных детей IntegerLiteral и потому допустимы.

Суффикс `*` внутри позиционного списка сопоставляет ноль или больше последовательных детей, каждый из которых соответствует шаблону (D114). Примеры: `Block(items: [Return, ExpressionStatement*])` и `Block[Statement*]`. Список покрывает всю выбранную последовательность; перестановок нет. Неоднозначность распределения между повторениями пока не определена.

Суффикс `?` внутри позиционного списка означает ноль или один соответствующий ребёнок (D115). Формы `Block(items: [Return?, ExpressionStatement*])` и `Block[Return?, ExpressionStatement*]` равнозначны для схемы с единственной группой items, содержащей всех детей. В общем случае первая проверяет только items, вторая — всех детей узла.

Суффикс `+` внутри позиционного списка сопоставляет один или больше последовательных детей, соответствующих шаблону (D116). Пустая последовательность не подходит. Примеры: `Block[Statement+]`, `Block(items: [Statement+])`. В объявлениях детей кратность `+` пока не введена.

Шаблон `Block[Statement*, Statement*]` запрещён (D117). Предложение разрешать неоднозначное распределение только потому, что нет захватов и результат булев, отклонено. Общий критерий проверки более сложных случаев уточняется.

Шаблон `Block[Statement*, Return, Statement*]` разрешён (D118): при единственном Return среди подходящих детей распределение однозначно. Возможность неоднозначного входа сама по себе не запрещает этот шаблон. Критерий разграничения с D117 уточнён в D119: должен существовать однозначный непустой вход; однозначности только на пустом недостаточно. Поведение на конкретном неоднозначном входе определено в D120: обычное несовпадение.

При сопоставлении разрешённого шаблона с конкретным входом требуется ровно одно полное распределение (D120). Ноль или несколько распределений означают обычное несовпадение. Приоритетного выбора между распределениями нет.

Шаблон `_` принимает любой один узел без ограничений и без захвата. В списках разрешены `_?`, `_*`, `_+` (D121). Одиночное имя `_` зарезервировано; идентификаторы вроде `_value` разрешены.

Именованный захват одиночного узла записывается как `Expression as x` или `_ as x` (D122). Захватывается весь соответствующий узел, включая данные и поддерево, для последующего построения результата. Пример: `Addition(left: Expression as lhs, right: Expression as rhs)`.

Имена захватов уникальны во всём шаблоне одного правила, включая вложенные шаблоны (D123). Повторное `as x` — ошибка DSL, без перезаписи и без неявного сравнения. В разных правилах имена могут повторяться.

Захват после суффикса повторения сохраняет всю последовательность в исходном порядке: `Statement* as items` — список, возможно пустой; `Statement+ as items` — непустой список. Без суффикса `Statement as item` захватывает один узел (D124).

При проверке DSL сохраняются тип элементов и кратность захвата (D125): `T as x` — один узел; `T? as x` — необязательный узел; `T* as xs` — список; `T+ as xs` — непустой список. Для `_` тип элемента — любой узел. Фактическое количество узлов не меняет статическую категорию. Метаданные используются при проверке построения результата.

Захваты на любой глубине внутри шаблона, повторяемого через `*` или `+`, запрещены как ошибка DSL (D126). Захват повторения целиком разрешён: `Block[Return(value: Expression)* as returns]`. Неявного накопления или перезаписи вложенных захватов нет.

Вложенный захват одиночного узла внутри `?` разрешён и статически становится необязательным (D127). В `Block[Return(value: Expression as x)?]` захват x имеет тип Expression с кратностью 0..1. При отсутствии Return узел в x отсутствует. Подстановка таких захватов в результат рассматривается отдельно.

## Построение результата S007 — предварительная основа (D128)

Ссылка на захват предложена в форме `$x`. Предварительно разрешена прямая подстановка необязательного узла в необязательного ребёнка совместимого типа: отсутствующий захват оставляет ребёнка отсутствующим. Прямая подстановка такого захвата в обязательного ребёнка предварительно запрещена как ошибка DSL. D129 разрешает одиночный захват в обязательной и необязательной одиночной позиции, включая позиционные примеры `Negation[$x]` и `Return[$x]` для узлов с единственным ребёнком. D130 разрешает прямую подстановку одиночного узла и непустого списка в совместимую повторяющуюся группу: `Block(items: $s)` и `Block(items: $statements)`, без обязательной обёртки ссылки в квадратные скобки. D131 также разрешает необязательный захват и список в группе `T*`: отсутствие или пустой список дают ноль детей. D132 устанавливает статическую привязку одиночных обязательных/необязательных позиций: в `Triple[$a, $b, $c]` отсутствие b не меняет назначение c. Тип и кратность проверяются до исполнения; необязательный захват не допускается в обязательной позиции. D133 определяет совместимость типов: статический тип элемента захвата совпадает с принимающим типом или является его прямым/косвенным потомком. Правило едино для тэгов, позиций и элементов списков; несовместимость — ошибка DSL до исполнения, без неявного сужения по фактическому узлу. D134 распространяет статическую привязку на повторяющуюся группу: в `Sequence[$a, $body, $z]` каждое выражение заполняет своё объявленное место схемы, весь body относится к средней группе, его размер не меняет назначение соседей. Это не изменяет позиционные шаблоны сопоставления. D135 разрешает построение двух соседних групп одинакового типа через `Parts[$xs, $ys]` или `Parts(left: $xs, right: $ys)`. Принадлежность детей группам сохраняется в готовом узле; плоской последовательности без границ недостаточно. Запрет неоднозначного позиционного шаблона остаётся в силе. D136 вводит `none` для отсутствующего необязательного одиночного ребёнка и в позиционной форме (`Triple[$a, none, $c]`), и по тэгу (`middle: none`). В обязательной позиции `none` запрещено. Запрет сокращённого `Triple[$a, $c]` из D136 отменён решением D138. D137 разрешает не указывать необязательного одиночного ребёнка при построении по тэгам; это эквивалентно явному `tag: none`. Обязательные дети должны быть заданы. D138 разрешает пропуск необязательных одиночных мест при ровно одном полном распределении выражений с сохранением порядка по статическим типам, кратностям и обязательности мест. Ноль распределений — ошибка совместимости, несколько — ошибка неоднозначности. Распределение фиксируется до исполнения без опоры на фактические узлы. Для схемы Triple из D136 запись `Triple[$a, $c]` с двумя обязательными Expression допустима. D139 разрешает `none` для пустой повторяющейся группы `*` при построении: `Parts[none, $ys]` эквивалентно `Parts(left: none, right: $ys)`. Никакого узла-заглушки не создаётся. D140 разрешает не указывать группу `*` при построении по тэгам: неуказанная группа пуста, как при явном `none`. D141 распространяет единственное статическое распределение на позиционные пропуски групп `*`. Подстановка целиком относится к одному месту, список не делится; пропущенная группа пуста. Неоднозначность — ошибка DSL независимо от фактических размеров захватов. D142 запрещает прямую подстановку списка `T*` или `T+` в одиночное место `T` или `T?`, даже если при исполнении список содержит один узел. Автоматического извлечения элемента нет. D143 вводит универсальный встроенный тип узла `Node`; захват `_ as x` имеет этот тип и может подставляться в место `Node`, без неявного сужения. Имена `Node`, `Action`, `Insert`, `Delete`, `Replace` заняты в общем пространстве имён типов. Конкретные формы использования встроенных действий ещё требуют обсуждения. D144 определяет `Node` как абстрактный общий предок всех типов узлов с автоматическим наследованием, без собственных детей и datatype. Создавать `Node` нельзя; `Node as x` и `_ as x` равнозначны по охвату и типу захвата. D145 закрывает встроенный абстрактный `Action` для пользовательского наследования. Его конкретные встроенные потомки — `Insert`, `Delete`, `Replace`; использовать `Action` в шаблонах и типах детей разрешено. D147 откладывает вопрос `Property`: имя пока не резервируется, встроенная схема не вводится. D148 задаёт встроенные схемы: `Insert(after: Node)`, `Delete(before: Node)`, `Replace(before: Node, after: Node)`, все — потомки `Action`, без собственного datatype. Дети обязательные одиночные; доступны тэги и позиционная запись. D149 устанавливает, что построение действия создаёт узел-описание без немедленного исполнения и поиска цели во входном дереве. Применение дерева действий выполняется отдельным явно выбранным механизмом, ещё требующим обсуждения. D150 вводит `+` для объединения подстановок в одну последовательность детей: `Block(items: $prefix + $item + $suffix)` эквивалентно `Block[$prefix + $item + $suffix]`. Сохраняется порядок источников и элементов, пустые списки ничего не добавляют; всё выражение заполняет одно место схемы. Суффикс `+` в шаблонах не меняется. D151 разрешает необязательные захваты внутри `+`: присутствующий захват даёт один элемент, отсутствующий — ноль. Тип каждого операнда проверяется статически независимо от фактического наличия. D152 разрешает выражения построения новых узлов как операнды `+`. Создаваемый узел даёт один элемент; отсутствие его необязательного ребёнка не удаляет сам узел из последовательности. D153 вычисляет диапазон количества элементов `+` суммированием нижних и верхних границ операндов. Принимающее одиночное обязательное место требует 1..1, необязательное — диапазон внутри 0..1, группа `*` допускает любой неотрицательный диапазон; типы проверяются отдельно. D154 разрешает `none` внутри `+` как пустую последовательность 0..0 без ограничений на тип элементов. Совместимость с местом схемы проверяется для всего выражения; `none + $x` эквивалентно `$x`. D155 отклоняет группировочные скобки вокруг выражений: при единственном операторе `+` они не вводятся. Круглые скобки после имени типа для тэгов сохраняются. D156 разрешает повторное использование одного захвата в результате: захват не расходуется, список может повторяться. Каждое использование создаёт отдельное вхождение; неизменяемые объекты можно разделять без обязательного глубокого копирования. Запрет повторных объявлений `as x` в одном шаблоне сохраняется. D157 разрешает не использовать объявленный захват в результате, без ошибки DSL. Условия шаблона продолжают проверяться; неиспользование захвата не является самостоятельным действием `Delete`. D158 требует разрешать `$name` только среди захватов шаблона того же правила. Неизвестное имя — ошибка DSL до исполнения, без подстановки `none`; отсутствие значения объявленного необязательного захвата — отдельный допустимый случай. D159 разрешает результат `$x` для одиночного обязательного захвата: возвращается всё поддерево с фактическим типом, данными и детьми, без обязательного копирования. Его статический тип — тип захвата, кратность 1..1. Совместимость с внешним местом замены обсуждается отдельно. D160 разрешает `none` как результат преобразования корня всего дерева: успешное правило даёт пустое дерево без корня. Это отличается от несовпадения и не создаёт `Delete` или заглушку. Дочерние позиции рассматриваются отдельно. D161 разрешает необязательный захват `$x` как результат преобразования корня: присутствующий узел становится корнем, отсутствующий даёт пустое дерево. Это успешное применение правила в обоих случаях; прежний корень не сохраняется. D162 ограничивает результат преобразования корня статическим диапазоном внутри 0..1. Прямой возврат списка `T*` или `T+` запрещён независимо от фактической длины; для нескольких элементов нужен явный узел-контейнер. Ограничение действует и для составных выражений. D163 требует для замены ребёнка в заранее известной обязательной одиночной позиции результат 1..1 совместимого статического типа. `none`, необязательные захваты и списки для такого места запрещены до исполнения. Контекст применения и универсальный обход ещё обсуждаются отдельно. Остальные варианты не согласованы; матрица и план разбора приведены в D128. Пользователь потребовал тщательно рассмотреть все случаи до окончательного утверждения.

## Текущий вопрос

При замене существующего ребёнка в заранее известной необязательной позиции T? разрешаем результат с диапазоном внутри 0..1 и совместимым типом элементов? Для node Return(value: Expression?) результат none удаляет value, но сохраняет сам Return; одиночный Expression заменяет ребёнка; необязательный Expression даёт замену или удаление в зависимости от наличия. Списки запрещены статически. Речь только о замене уже существующего ребёнка; запуск правила на отсутствующем ребёнке этим решением не вводится.
