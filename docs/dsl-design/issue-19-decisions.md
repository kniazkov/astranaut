# Задача #19: проектирование core и отложенных механизмов

Статус: обсуждение; реализация новой модели не начата. Связь: #19, Q35–Q40.

## Принятые исходные положения

1. Текущие Fragment, Builder, Type, Node и связанные классы astranaut-core можно менять так, как требуется согласованной спецификации DSL. Существующий API не является ограничением проектирования. Допускается пересмотр фундаментальных решений, включая плоское представление детей.
2. Автор подтвердил три вида по кратности: обязательный, необязательный и повторяющийся. В терминологии спецификации это дочерние места: ровно один, ноль или один, ноль или более узлов соответственно.
3. Способ представления этих мест обсуждается отдельно. Предложение считать каждое место списком, включая одиночные, пока не записывается как принятое решение: автор предложил сначала изучить core и обсудить представление.

Допустимые размеры мест: обязательное — 1; необязательное — 0 или 1; повторяющееся — 0 и более. Пустое обязательное место или два ребёнка в необязательном месте недопустимы в готовом узле. Конкретный контракт Builder и момент диагностики предстоит согласовать.

## Исходная реализация для сравнения

Изучен astranaut-core на коммите b263c06e4f30418df6f63584607d55a1ce33abae. Пути ниже относительно src/main/java/com/kniazkov/astranaut/core/base/.

- Fragment.java: неизменяемый полуоткрытый диапазон исходного текста; не контейнер детей. fromNodes объединяет диапазоны узлов одного источника; при разных источниках возвращает отсутствие происхождения.
- Node.java: getChildCount(), getChild(int), getChildrenList() предоставляют плоский список фактических детей. getChild(String) возвращает Optional<Node>; getChildTag(int) описывает тег отдельного вхождения. Общего API размеров и границ мест нет.
- Builder.java: setChildren(List<Node>) принимает полное однозначное распределение; setChild(int, Node) использует текущий индекс ребёнка, а не индекс места схемы. Частичные изменения могут оставлять обязательные места незаполненными; build() должен создать валидный узел либо бросить ConstructionException.
- AbstractType.java: имя, базовые типы, свойства и операции иерархии. Type.java добавляет необязательную схему ChildDescriptor и создание Builder.
- ChildDescriptor.java: тип, необязательный тег, Cardinality; тег у REPEATED прямо запрещён. Это расходится с разрешёнными именованными группами нового DSL.
- DraftNode.java: неизменяемые плоские дети и параллельный список тегов; произвольное имя типа, без проверки схемы. Это описание существующего кода, а не разрешение внешних типов в новом DSL.

## Q35: логическая модель мест — принято; детали API открыты

Обязательный пример:

```text
node Mixed(head: Node, optional: Node?, Node*, tail: Node*);
```

При одинаковых плоских детях [A, B, C] размеры мест [1, 0, 0, 2] и [1, 0, 1, 1] обозначают разные структуры по уже принятой спецификации. Один плоский список без дополнительного описания границ их не различает.

Автор принял дочернее место как отдельную сущность API. У узла есть упорядоченные дочерние места; каждое место имеет своё содержимое и существует даже пустым. Место — служебная часть структуры, не дополнительный AST-узел.

Три кратности места:
- обязательное: ровно один узел;
- необязательное: ноль или один узел;
- повторяющееся: ноль или более узлов.

Пример:

```text
node Addition(Expression, Expression);
```

Здесь два обязательных места: место 0 содержит левое выражение, место 1 — правое. Повторяющихся групп в DSL нет. Термин «место» используется для общей сущности; название «группа» для любого места не утверждено.

В примере Mixed всегда четыре места. При размерах [1, 0, 0, 2] необязательное и безымянное повторяющееся места пусты, но сохраняются. При [1, 0, 1, 1] узел B принадлежит безымянному месту, а C — tail; это другая структура, чем tail=[B,C]. Объединение этих структур только из-за одинакового плоского списка недопустимо.

Основание: требуется сохранять назначение детей и границы мест, включая пустые и безымянные. Это контракт представления готового дерева; конкретные методы, проверки Builder и момент диагностики ещё обсуждаются.

Физическое хранение (отдельные списки или общий массив с границами) и имена методов не выбраны. Java-тип доступа к содержимому места согласован ниже. Плоский доступ, доступ по тегу/индексу и Builder предстоит обсудить отдельно.

### Единый доступ к содержимому места — принято

Содержимое любого места предоставляется как неизменяемый `List<Node>`. Для обязательного места список содержит ровно один узел; для необязательного — ноль или один; для повторяющегося — ноль или более. Узлы сохраняют порядок, сами узлы также неизменяемы по общему контракту.

Условный пример API (имена методов не утверждены):

```java
node.getSlot(0).getNodes(); // Addition: [левое выражение]
node.getSlot(1).getNodes(); // Addition: [правое выражение]
```

Для Mixed с размерами [1, 0, 0, 2] содержимое мест соответственно [A], [], [], [B, C]. Пустой список не означает отсутствия места. Изменение возвращённого списка вызывающим кодом не допускается; попытки модификации через операции List должны отклоняться как операции над неизменяемым списком. Список из двух узлов для обязательного места недопустим в готовом узле; проверки построения обсуждаются отдельно.

Основание: алгоритмы получают единый способ чтения всех мест, а кратность ограничивает размер. Это контракт публичного доступа, а не требование хранить отдельный физический список для каждого места.
