# Задача #19: проектирование core и отложенных механизмов

Актуальный срез согласованного API без отменённых вариантов: [core-api-snapshot.md](core-api-snapshot.md). История решений ниже сохраняется; позднейшие решения заменяют ранние предложения.

Статус: обсуждение; реализация новой модели не начата. Связь: #19, Q35–Q40.

## Принятые исходные положения

1. Текущие Fragment, Builder, Type, Node и связанные классы astranaut-core можно менять так, как требуется согласованной спецификации DSL. Существующий API не является ограничением проектирования. Допускается пересмотр фундаментальных решений, включая плоское представление детей.
2. Автор подтвердил три вида по кратности: обязательный, необязательный и повторяющийся. В терминологии спецификации это дочерние места: ровно один, ноль или один, ноль или более узлов соответственно.
3. Способ представления этих мест обсуждается отдельно. Предложение считать каждое место списком, включая одиночные, пока не записывается как принятое решение: автор предложил сначала изучить core и обсудить представление.

Допустимые размеры мест: обязательное — 1; необязательное — 0 или 1; повторяющееся — 0 и более. Пустое обязательное место или два ребёнка в необязательном месте недопустимы в готовом узле. Конкретный контракт Builder и момент диагностики предстоит согласовать.

## Исходная реализация для сравнения

Изучен astranaut-core на коммите b263c06e4f30418df6f63584607d55a1ce33abae. Пути ниже относительно src/main/java/com/kniazkov/astranaut/core/base/.

- Fragment.java: неизменяемый полуоткрытый диапазон исходного текста; не контейнер детей. fromNodes объединяет диапазоны узлов одного источника; при разных источниках возвращает отсутствие происхождения.

- Builder.java: setChildren(List<Node>) принимает полное однозначное распределение; setChild(int, Node) использует текущий индекс ребёнка, а не индекс места схемы. Частичные изменения могут оставлять обязательные места незаполненными; build() должен создать валидный узел либо бросить ConstructionException.

- DraftNode.java: неизменяемые плоские дети и параллельный список тегов; произвольное имя типа, без проверки схемы. Это описание существующего кода, а не разрешение внешних типов в новом DSL.

## Q35: логическая модель мест — принято; детали API открыты

Обязательный пример:

```text
node Mixed(head: Node, optional: Node?, Node*, tail: Node*);
```

При одинаковых плоских детях [A, B, C] размеры мест [1, 0, 0, 2] и [1, 0, 1, 1] обозначают разные структуры по уже принятой спецификации. Один плоский список без дополнительного описания границ их не различает.

Автор принял дочернее место как отдельную сущность API. У узла есть упорядоченные дочерние места; каждое место имеет своё содержимое и существует даже пустым. Место — служебная часть структуры, не дополнительный AST-узел.

Три кратности места:
- обязательное: ровно один узел;
- необязательное: ноль или один узел;
- повторяющееся: ноль или более узлов.

Пример:

```text
node Addition(Expression, Expression);
```

Здесь два обязательных места: место 0 содержит левое выражение, место 1 — правое. Повторяющихся групп в DSL нет. Термин «место» используется для общей сущности; название «группа» для любого места не утверждено.

В примере Mixed всегда четыре места. При размерах [1, 0, 0, 2] необязательное и безымянное повторяющееся места пусты, но сохраняются. При [1, 0, 1, 1] узел B принадлежит безымянному месту, а C — tail; это другая структура, чем tail=[B,C]. Объединение этих структур только из-за одинакового плоского списка недопустимо.

Основание: требуется сохранять назначение детей и границы мест, включая пустые и безымянные. Это контракт представления готового дерева; конкретные методы, проверки Builder и момент диагностики ещё обсуждаются.

Физическое хранение (отдельные списки или общий массив с границами) и имена методов не выбраны. Java-тип доступа к содержимому места согласован ниже. Плоский доступ, доступ по тегу/индексу и Builder предстоит обсудить отдельно.

### Единый доступ к содержимому места — принято

Содержимое любого места предоставляется как неизменяемый `List<Node>`. Для обязательного места список содержит ровно один узел; для необязательного — ноль или один; для повторяющегося — ноль или более. Узлы сохраняют порядок, сами узлы также неизменяемы по общему контракту.

Условный пример API (имена методов не утверждены):

```java
node.getSlot(0).getNodes(); // Addition: [левое выражение]
node.getSlot(1).getNodes(); // Addition: [правое выражение]
```

Для Mixed с размерами [1, 0, 0, 2] содержимое мест соответственно [A], [], [], [B, C]. Пустой список не означает отсутствия места. Изменение возвращённого списка вызывающим кодом не допускается; попытки модификации через операции List должны отклоняться как операции над неизменяемым списком. Список из двух узлов для обязательного места недопустим в готовом узле; проверки построения обсуждаются отдельно.

Основание: алгоритмы получают единый способ чтения всех мест, а кратность ограничивает размер. Это контракт публичного доступа, а не требование хранить отдельный физический список для каждого места.

### Плоское представление детей — принято

Дополнительно сохраняется плоский доступ к фактическим детям: сначала порядок мест, затем порядок узлов внутри каждого места; пустые места не добавляют элементов. Например, [A], [], [B, C] даёт [A, B, C]. Автор отдельно подтвердил пригодность такого представления для визуализации.

Плоский список не является достаточным представлением для сериализации. Сериализация обязана сохранять отдельные места и их границы, включая пустые и безымянные. Конкретный формат ещё не выбран в Q36.

Граничный пример: для Parts(Node*, Node*) содержимое [[A], [B]] и [[A, B], []] даёт одинаковый плоский список, но разные структуры. Восстановление обеих структур в один и тот же вариант недопустимо; round trip должен сохранить исходное распределение. Это требование к сериализации и восстановлению, а не новое ограничение визуализации.

### Тег принадлежит месту — принято

Тег именует дочернее место, а не отдельного ребёнка. Доступ по тегу возвращает место со всем его содержимым. Пустое именованное место по-прежнему существует и доступно по своему тегу. Безымянное место доступно по индексу в схеме.

```text
node Block(items: Statement*);
```

Тег items обозначает одно повторяющееся место. При содержимом [S1, S2] доступ по items даёт место с обоими узлами; при [] — то же место с пустым списком. Нельзя трактовать items как имя только первого ребёнка или считать тег отсутствующим из-за пустого содержимого.

Для Mixed(head: Node, optional: Node?, Node*, tail: Node*) безымянное место имеет индекс 2 (нумерация с нуля в примерах), независимо от количества узлов в предыдущих местах. Именованные head, optional и tail обозначают соответствующие места, включая пустые optional и tail.

Основание: единообразный доступ ко всем кратностям и сохранение пустых мест. Имена методов пока условные; поведение при неизвестном теге либо неверном индексе согласовано ниже.

### Неизвестный тег и неверный индекс — принято

Доступ к месту по тегу возвращает Optional места. Известный тег даёт присутствующее место, даже если его содержимое — пустой список. Неизвестный тег даёт Optional.empty(). Доступ по индексу за пределами списка мест бросает IndexOutOfBoundsException непосредственно при обращении.

Условные имена методов:

```java
node.getSlot("items");   // Optional с местом, в том числе при содержимом [].
node.getSlot("unknown"); // Optional.empty().
```

Для Addition с двумя местами индексы 0 и 1 допустимы; -1 и 2 приводят к IndexOutOfBoundsException. Индекс относится к месту схемы, а не к плоскому списку детей.

Основание: отсутствие тега необходимо отличать от существующего пустого места; индексный доступ следует обычному контракту списка Java. Это поведение API исполнения, не правило диагностики исходника DSL.

### Схема места и содержимое; оптимизация генератора — принято

Type хранит схему мест: допустимый тип ребёнка, кратность и необязательный тег. Node предоставляет соответствующие места с содержимым; каждое место позволяет получить своё описание из схемы. Общее описание схемы не требуется копировать в каждый экземпляр узла.

Автор дополнительно потребовал от генератора производить наиболее оптимальный код. Единый публичный доступ через неизменяемый List<Node> не диктует физическое хранение детей списками и не требует отдельного хранимого объекта для каждого места.

Для объявления:

```text
node Addition(Expression, Expression);
```

оба обязательных места могут храниться непосредственно в двух полях final типа Expression. Условный эскиз полей (имена не утверждены):

```java
private final Expression left;
private final Expression right;
```

Публичный API каждого места по-прежнему предоставляет неизменяемый одноэлементный List<Node>, а описание берётся из общей схемы. Два разных Addition могут использовать одну схему, сохраняя собственные значения left и right. Доступ через список является представлением полей, а не требованием к их типу.

Недопустимо обосновывать обязательное хранение отдельных списков для одиночных мест единым API. Оптимизации не должны менять кратность, порядок, границы мест или неизменяемость готовых узлов. Проверки валидности при построении ещё обсуждаются. Стратегия создания/кэширования представлений и физическое хранение необязательных и повторяющихся мест пока не выбраны.

### Хранение необязательного ребёнка — принято

Генератору разрешено хранить необязательного ребёнка в final-поле соответствующего Java-типа, допускающем null. Внутреннее значение null означает отсутствие ребёнка; хранить Optional или список для этого не требуется.

```java
private final Expression value; // Может быть null для необязательного места.
```

Публичное содержимое места остаётся неизменяемым List<Node>: при отсутствии ребёнка возвращается [], при наличии E — [E]. Список [null] недопустим. Само место существует в обоих случаях. Разрешение относится к внутреннему представлению необязательного места и не разрешает null как ребёнка готового дерева или как значение обязательного места.

Основание: исключение ненужных объектов-обёрток при сохранении единого API и семантики кратности. Способ создания представлений списка и хранение повторяющихся мест ещё не выбраны.

### Хранение повторяющегося места — принято

Генератор выбирает физическое хранение повторяющегося места: неизменяемый список либо закрытый массив. В обоих случаях сохраняются порядок узлов, запрет null среди детей и неизменяемость содержимого после создания узла. Публичный доступ остаётся неизменяемым List<Node>; изменяемый массив не выдаётся вызывающему коду.

Готовый узел не зависит от последующих изменений изменяемого списка, переданного Builder. Например, если из входного списка [A, B] построен узел, последующие очистка списка или замена B на C не меняют содержимое места построенного узла: оно остаётся [A, B]. Список [A, null] недопустим как содержимое места готового узла. Конкретный момент отказа в Builder ещё обсуждается.

Основание: свобода оптимизации без нарушения неизменяемости. Требование касается результата построения; стратегия копирования и поведение Builder до build() этим решением не определяются.

### Явное заполнение места в Builder — принято

Builder позволяет заменить содержимое одного места целиком, явно указав индекс места в схеме либо его тег. Автор выбрал название setChildren вместо предложенного условного setSlot.

```java
builder.setChildren(0, List.of(left));
builder.setChildren(1, List.of(right));
builder.setChildren("items", statements);
```

Список заполняет ровно указанное место; автоматического распределения между местами здесь нет. Индекс означает индекс места схемы, а не ребёнка в плоском списке. Для Addition первые два вызова заполняют соответственно левое и правое обязательные места. Передача двух узлов в одно обязательное место не означает заполнения двух соседних мест.

Пустой список означает запрос очистки указанного места. Допустимость очистки обязательного места в промежуточном состоянии Builder, проверки типов и кратности, возвращаемое значение и поведение при отказе ещё предстоит согласовать. Контракт существующего setChildren(List<Node>) без адреса места обсуждается отдельно; он не переопределяется этим решением.

### Очистка обязательного места в Builder — принято

В промежуточном состоянии Builder разрешено пустое обязательное место, в том числе после явной очистки через setChildren(index/tag, пустой список). После такой очистки isValid() возвращает false, а build() бросает исключение: готовый некорректный узел не создаётся.

Пример для Addition: при заполненных двух обязательных местах очистка места 0 оставляет место 1 без изменений, но делает Builder невалидным. После заполнения места 0 одним совместимым Expression построение снова возможно, если остальные проверки проходят.

Основание: Builder допускает поэтапное заполнение. Это не разрешает пустое обязательное место в готовом Node и не меняет запрет удаления обязательного ребёнка при преобразовании дерева. Конкретный тип исключения build() и обработка других недопустимых входов setter обсуждаются отдельно.

### Проверки содержимого места при setChildren — принято

setChildren(index/tag, list) сразу отклоняет несовместимый тип ребёнка или превышение максимальной кратности места: возвращает false и сохраняет всё состояние Builder без изменений. При совместимости учитываются допустимые подтипы. Успешное заполнение или разрешённая очистка возвращает true.

Для Addition(Expression, Expression), где a и b совместимы с Expression, а stmt несовместим:

```java
builder.setChildren(0, List.of(a, b)); // false: превышена кратность.
builder.setChildren(0, List.of(stmt)); // false: несовместимый тип.
builder.setChildren(0, List.of()); // true: разрешённая очистка.
```

Первый и второй вызовы не заменяют прежнего содержимого места и не меняют другие места или данные Builder. Последний очищает место и делает Builder невалидным для build() до заполнения обязательного места.

Автор отметил асимметрию и принял её: пустое обязательное место — допустимая незавершённость Builder (в том числе после его создания), а несовместимое содержимое — недопустимое изменение. Аналогично два узла не принимаются в необязательное место. Поведение при null, неизвестном теге и неверном индексе setter ещё предстоит согласовать.

### Неизвестное место при записи — принято

setChildren с неизвестным тегом либо индексом вне схемы возвращает false, не изменяя состояние Builder. Например, для Addition из двух мест setChildren(-1, list), setChildren(2, list) и обращение по отсутствующему тегу отклоняются. Это контракт setter; ранее принятое исключение при индексном чтении места Node сохраняется. Правило не определяет пока поведение при null-аргументах.

### Согласованный интерфейс Builder

По просьбе автора интерфейс фиксировался в PR и показывался после каждого ответа. Автор завершил обсуждение состава Builder, оставив интерфейс в приведённом ниже виде.

Ниже согласованный состав нового интерфейса. Это проект контракта, не реализованный Java-файл. Данные, Fragment и единичные дети включены; плоское распределение и отдельные методы удаления отклонены.

```java
public interface Builder {
    // Конкретный тип создаваемых узлов; неизменен для этого Builder.
    Type getType();

    // null отвергается с IllegalArgumentException.
    void setFragment(Fragment fragment);

    // Разбирает и проверяет сериализованное значение согласно datatype.
    boolean setData(String data);

    // Полностью заменяет содержимое места по индексу схемы.
    boolean setChildren(int slotIndex, List<? extends Node> children);

    // Полностью заменяет содержимое места по тегу.
    boolean setChildren(String tag, List<? extends Node> children);

    // Заменяет всё содержимое места одним ребёнком.
    default boolean setChild(int slotIndex, Node child) {
        return child != null && setChildren(slotIndex, List.of(child));
    }

    default boolean setChild(String tag, Node child) {
        return child != null && setChildren(tag, List.of(child));
    }

    // Проверяет готовность к построению корректного узла.
    boolean isValid();

    // Не меняет Builder; при невалидности — ConstructionException.
    Node build() throws ConstructionException;
}
```

List — java.util.List. Успешная запись возвращает true. Несовместимый тип, превышение максимальной кратности, неизвестный тег и неверный индекс дают false без изменения состояния. Очистка обязательного места разрешена, но после неё isValid() == false и build() завершается исключением. null вместо списка, тега или элемент null внутри списка приводят к false без изменения состояния. Для очистки используется пустой список. Входные списки обеих перегрузок имеют тип List<? extends Node>, как согласовано ниже.

### null в setChildren — принято

В обеих перегрузках setChildren null вместо списка, а также null внутри списка приводят к false без изменения состояния Builder. В перегрузке с тегом null вместо тега также даёт false. null не означает очистку; для очистки передаётся пустой список.

Примеры: setChildren(0, null), setChildren((String) null, List.of()) и setChildren(0, Arrays.asList(a, null)) возвращают false. Используется Arrays.asList для отрицательного примера: List.of сам отвергает null ещё до вызова Builder. При любом из этих отказов прежние дети и остальные данные Builder сохраняются.

Сигнатуры рабочего интерфейса выше не меняются. Это контракт setter, не изменение правил getter или внутреннего nullable-хранения необязательного ребёнка.

### Ковариантный входной список — принято

Обе перегрузки setChildren принимают List<? extends Node>. Это позволяет непосредственно передавать List<Expression> и списки других подтипов Node без перекладывания в List<Node>. Рабочий интерфейс выше обновлён.

Например, List<Expression> expressions можно передать в setChildren("items", expressions), если схема места допускает соответствующие выражения и их количество. List<String> не подходит по Java-типу и отвергается компилятором Java. Совместимость конкретных узлов со схемой, ограничения кратности, обработка null и атомарность отказа остаются прежними. Тип публичного чтения содержимого места остаётся List<Node>.

### Снимок списка при setChildren — принято

Успешный setChildren сразу фиксирует содержимое переданного списка. Последующие изменения исходного списка не влияют на Builder, в том числе до первого build(). Для гарантированно неизменяемого списка допускается избежать копирования. Неизменяемая обёртка над изменяемым извне списком сама по себе такой гарантией не является.

Пример: после успешного setChildren("items", source), где source содержит [A, B], очистка source или замена B на C не меняет содержимое места Builder: оно остаётся [A, B]. Последующий build() использует зафиксированное содержимое при условии прохождения остальных проверок. Узлы не требуется глубоко копировать: действует их контракт неизменяемости.

Основание: внешнее изменение коллекции не должно менять состояние между проверкой и построением. Это дополняет ранее принятое требование независимости готового узла от входного списка. При отказе setter прежнее состояние по-прежнему сохраняется; сигнатуры рабочего интерфейса не меняются.

### Повторное использование Builder после build() — принято

build() не изменяет и не очищает состояние Builder ни при успехе, ни при отказе из-за невалидности. После построения можно изменить Builder и построить другой узел. Уже построенный узел остаётся неизменным и не зависит от последующих изменений Builder.

```java
Node first = builder.build();
builder.setChildren(0, List.of(other)); // Предполагается успешная совместимая замена.
Node second = builder.build();
```

first сохраняет прежнего ребёнка; second содержит other. Если build() вызван при пустом обязательном месте, он бросает исключение, сохраняя остальные заполненные места; после заполнения отсутствующего места можно повторить build().

Основание: повторное использование Builder и возможность исправления незавершённого состояния без потери уже заданных данных. Решение не требует создавать различные по ссылке объекты при повторном build() без изменений; политика идентичности результатов пока не определена. Сигнатуры рабочего интерфейса не меняются.

### Ошибка построения — принято

При невалидном состоянии build() бросает существующее ConstructionException. Для незаполненного обязательного места сообщение указывает, какое место не заполнено: например, индекс 0 для первого операнда Addition. Точный формат сообщения не задаётся.

Валидный Builder возвращает неизменяемый Node. Невалидный не возвращает частичный узел и не меняет состояние; его можно исправить и повторить построение. Рабочий интерфейс выше обновлён с указанием ConstructionException.

### Заполнение места одним ребёнком — принято

Добавлены setChild(int slotIndex, Node child) и setChild(String tag, Node child). Для ненулевого child это сокращения setChildren с одноэлементным списком: заменяется всё содержимое указанного места. Индекс относится к месту схемы, не к плоскому списку фактических детей.

Операция разрешена для всех трёх кратностей при совместимом типе. Например, если повторяющееся items содержит [A, B], успешный setChild("items", C) заменяет его на [C], а не добавляет C и не заменяет только A.

null вместо ребёнка даёт false без изменения состояния и не означает очистку. Проверка null должна выполняться до создания List.of, чтобы не получить исключение от фабрики списка. Неизвестный тег, неверный индекс, null-тег и несовместимый тип также дают false без изменений по общему контракту setter.

Рабочий интерфейс выше обновлён; обе перегрузки имеют согласованные default-реализации, приведённые выше.

### Default-реализации setChild — принято

Обе перегрузки setChild реализованы в интерфейсе через default: сначала проверяется child != null, затем вызывается соответствующий setChildren с List.of(child). Это исключает дублирование сокращения в реализациях Builder.

При null-ребёнке возвращается false без вызова setChildren. При ненулевом ребёнке результат и проверки адреса места и совместимости делегируются setChildren. Например, совместимая замена в известном месте успешна; неизвестный тег даёт false по контракту setChildren. Рабочий интерфейс выше обновлён.

### Очистка без отдельных методов — принято

В проектируемый Builder не добавляются отдельные removeChild или другие методы очистки места. Очистка выполняется через setChildren(index/tag, List.of()) для любой кратности.

Например, setChildren("items", List.of()) очищает известное повторяющееся место и возвращает true. Очистка обязательного места также возвращает true, но делает Builder невалидным до заполнения. Неизвестное место возвращает false без изменений. null не заменяет пустой список.

Основание: отдельный метод дублировал бы уже согласованную операцию. Старые перегрузки removeChild не переносятся в новый общий интерфейс. Рабочий интерфейс выше остаётся без изменений.

### Отказ от автоматического распределения плоских детей — принято

Автор отклонил сохранение setChildren(list) без указания места: с введением слотов такая перегрузка не нужна. В новом Builder её нет; содержимое задаётся явно по индексу слота или тегу. Алгоритмы преобразования работают через слоты и сохраняют их границы.

Для Addition два операнда записываются в места 0 и 1. Для Parts(Node*, Node*) распределение [A]/[B] или [A,B]/[] задаётся явно; Builder не угадывает его из плоского [A,B]. Это исключение старого механизма из нового API, а не отказ только в неоднозначном случае.

Плоский доступ готового Node остаётся вспомогательным представлением для чтения, в том числе визуализации. Ранее согласованная семантика позиционных шаблонов DSL, проверяющих плоский список фактических детей, этим решением не отменяется; такой просмотр не является автоматическим распределением детей при построении.

При итоговой синхронизации нужно пересмотреть §4.6 спецификации об автоматическом распределении и связанные описания старого Builder, чтобы они не оставались требованиями к новому API. Рабочий интерфейс выше остаётся без перегрузки setChildren(list).

### Установка сериализованных данных — принято

В Builder сохраняется boolean setData(String data). Метод принимает сериализованное значение, разбирает его согласно datatype и проверяет полученное значение. Успех возвращает true; ожидаемая ошибка разбора или проверки возвращает false и сохраняет прежнее значение данных без изменения остального состояния Builder.

Например, для стандартного Int строка "42" принимается; "hello" не разбирается и даёт false, сохраняя ранее принятое 42. Если datatype допускает разбор числа, но его validate отвергает это значение, результат также false без изменений.

Решение касается ожидаемого отказа parse/validate; оно не вводит перехват любых исключений пользовательского Java-кода. Поведение при null, данные типов без datatype и начальное значение Builder ещё предстоит уточнить. Рабочий интерфейс выше дополнен setData.

### null и пустая строка в setData — принято

setData(null) возвращает false без изменения состояния Builder. Пустая строка является обычным сериализованным входным значением и проходит правила parse/validate соответствующего datatype.

Для стандартного String пустая строка допустима. Для стандартного Int она не разбирается и даёт false. Для строкового datatype с требованием непустого значения она отвергается проверкой и также даёт false. При отказе прежнее значение данных Builder и всё остальное состояние сохраняются; ранее построенные узлы неизменяемы.

Пустая строка не является универсальной командой очистки или сброса к значению по умолчанию. Рабочий интерфейс выше остаётся без изменения сигнатур. Поведение типов без datatype обсуждается отдельно.

### setData для узла без datatype — принято

Если у типа узла нет datatype (в том числе унаследованного), setData("") возвращает true без изменения состояния. Непустая строка и null возвращают false без изменения состояния.

Например, для Addition(Expression, Expression) без datatype setData("") успешно ничего не меняет, setData("42") и setData(null) отклоняются. Успех пустой записи не означает, что Builder в целом валиден: обязательные дети по-прежнему должны быть заполнены.

Основание: единый интерфейс Builder сохраняется и для узлов без данных, но произвольные данные им не присваиваются. Сигнатуры рабочего интерфейса не меняются.

### Начальные данные Builder — принято

Новый Builder получает начальное нативное значение default своего datatype. Для стандартного Int это 0, для стандартного String — пустая строка.

Если validate отвергает default, создание Builder разрешено, но isValid() возвращает false, а build() бросает ConstructionException. Успешный setData с подходящим значением исправляет данные; общая валидность дополнительно требует заполнения обязательных мест и прохождения остальных проверок.

Пример: у datatype с default=0 и проверкой положительного числа новый Builder невалиден; setData("1") принимает значение, после чего при корректности остальных частей build() возможен. setData("0") возвращает false и не меняет предыдущее состояние, даже если текущее значение уже равно невалидному default.

Основание: начальное значение и валидность разделены; отклонение default проверкой не запрещает сам незавершённый Builder. Это решение касается результата validate, а не произвольных исключений при выполнении Java-включений. Сигнатуры рабочего интерфейса не меняются.

### Установка Fragment — принято

В Builder добавлен void setFragment(Fragment fragment). Ненулевой фрагмент устанавливается; null отвергается с IllegalArgumentException без изменения прежнего состояния. Автор уточнил оговорку «ненулевой не принимается»: запрещён именно null.

Предложенный ранее boolean setFragment с false при null отклонён. Контракты остальных setter, возвращающих false при null, этим не изменяются.

Например, передача корректного Fragment связывает его с будущим узлом; последующий setFragment(null) бросает IllegalArgumentException и сохраняет прежний фрагмент. EmptyFragment.INSTANCE является ненулевым обозначением отсутствующего происхождения и может передаваться в setter. Детали переноса происхождения при преобразованиях остаются предметом Q37. Рабочий интерфейс выше обновлён.

### Начальный Fragment — принято

Новый Builder имеет Fragment, равный EmptyFragment.INSTANCE. Отсутствие исходного диапазона само по себе не делает Builder невалидным и не препятствует build(): вручную созданный узел может не происходить из исходного текста.

Например, Addition с двумя корректными Expression можно построить без вызова setFragment, если остальные проверки проходят. Результат имеет отсутствующее происхождение. Незаполненное обязательное место по-прежнему препятствует построению независимо от наличия или отсутствия координат.

Основание: происхождение является дополнительной информацией, а не обязательной частью структурной корректности узла. null по-прежнему не является допустимым Fragment. Сигнатуры рабочего интерфейса не меняются.

### Тип, известный Builder — принято

В интерфейс добавлен Type getType(). Builder связан с одним конкретным типом создаваемых узлов; этот тип не меняется. Метод доступен и в незаполненном состоянии, позволяя общим алгоритмам получить схему мест.

Автор уточнил: Builder обычно создаётся специально под свой тип и просто «знает» его. Хранить Type в поле каждого экземпляра не требуется. Сгенерированная реализация может возвращать общий дескриптор своего типа непосредственно. Это контракт доступа, а не требование физического хранения или передачи типа конструктору.

Например, Builder для Addition возвращает тип Addition как до заполнения операндов, так и после build(). Переход этого же Builder к построению другого типа не предусмотрен. Рабочий интерфейс выше дополнен getType().

### Начальное содержимое слотов Builder — принято

У нового Builder все слоты схемы существуют, но изначально пусты. Обязательные дети автоматически не создаются. Необязательные и повторяющиеся слоты уже имеют допустимый размер 0; обязательные необходимо заполнить.

Например, новый Builder Addition имеет два пустых обязательных слота: isValid() == false, build() бросает ConstructionException. Builder типа только с повторяющимся местом допускает пустое содержимое по кратности; общая валидность дополнительно зависит от данных и остальных проверок.

Это правило логического начального состояния, а не требование создавать отдельные пустые списки для хранения каждого места. Ранее согласованные оптимизированные поля и представления сохраняются. Сигнатуры рабочего интерфейса не меняются.

### Завершение обсуждения состава Builder — принято

Автор отклонил добавление геттеров текущего содержимого Builder и предложил оставить интерфейс ровно в виде последнего согласованного варианта. Дополнительные методы чтения детей, данных или Fragment не вводятся. Уже согласованный Type getType() сохраняется.

Основание автора: до сих пор алгоритмы обходились без геттеров содержимого; ожидается, что интересующие проект алгоритмы смогут работать с этим интерфейсом. Это проектное решение, а не заявление о проверенной реализации всех алгоритмов.

Предложение возвращать неизменяемые снимки текущих детей Builder не принято. Состав Builder на этом согласован; реализация остаётся будущей работой. Q35 в целом ещё требует завершения обсуждения Node, Type и связанных сущностей.

### Разделение AbstractType и Type — принято

Автор сохраняет разделение: AbstractType — общий интерфейс описания типа (как абстрактного, так и конкретного), Type extends AbstractType — конкретный тип, способный создавать Builder. При этом наполнение обоих интерфейсов пересматривается; существующие методы не считаются автоматически подтверждёнными.

Например, абстрактный Expression описывается через AbstractType без возможности напрямую создать его узел; конкретный Addition имеет Type и создаёт Builder. Сохранение разделения не требует хранить дескриптор типа в каждом Builder.

По указанию автора обсуждение Type проводится до интерфейса места. Предложенные имя Slot и состав getDescriptor()/getNodes() пока не утверждены. Перенос описания мест в общий интерфейс и конкретный контракт схемы предстоит согласовать отдельно.

### Два представления схемы слотов — принято

Вместо переноса единого упорядоченного списка в AbstractType согласовано разделение:
- AbstractType предоставляет неизменяемый Set описаний именованных слотов. У каждого описания обязательный тег, допустимый тип ребёнка и кратность. Порядок элементов набора не имеет значения.
- Type дополнительно предоставляет неизменяемый List описаний всех слотов в конечном порядке. Здесь тег необязателен; индекс списка задаёт позицию слота.
- Конкретный Type предоставляет оба представления.

Рабочие названия из обсуждения: NamedSlotDescriptor и SlotDescriptor, getNamedSlots() и getSlots(). Точная Java-иерархия дескрипторов ещё обсуждается.

Тип обязуется возвращать корректные и взаимно согласованные представления. Именованная часть полного списка точно соответствует набору: совпадают теги, допустимые типы и кратности. В наборе и списке нет повторяющихся тегов. Безымянные слоты входят только в полный список; несколько безымянных слотов допустимы. Сам Java Set не гарантирует уникальность тегов при различающихся остальных полях — это отдельный инвариант типа.

Для Mixed(head: Expression, Expression*, tail: Expression?) набор содержит head и tail, а список — head, безымянное повторяющееся место, tail. Набор с иным типом или кратностью tail, пропущенным head либо лишним именованным местом нарушает контракт. Повтор одного тега в двух местах также нарушает контракт. Это ошибка описания типа, а не допустимая неоднозначность для потребителя API; конкретный механизм проверки ещё не выбран.

Так доступны полные сведения о требованиях к именованным слотам через AbstractType и о конечной раскладке всех слотов через Type. Состояние «схема неизвестна» этим представлением не вводится. Дублирование объектов дескрипторов не требуется; возможность разделения объектов зависит от будущей иерархии.

### Полная самостоятельная схема каждого типа и наследование — принято

Автор уточнил и подтвердил: каждый тип самостоятельно предоставляет полную структуру своих детей без необходимости обхода родителей. AbstractType возвращает полный неупорядоченный набор именованных слотов текущего типа; конкретный Type дополнительно возвращает полный упорядоченный список всех своих слотов, включая безымянные. Связи наследования сохраняются отдельно. Родитель предоставляет свою собственную полную схему требований, а не недостающий фрагмент схемы потомка.

Предложение ограничить набор собственными объявлениями и собирать структуру текущего типа обходом родителей снято. Ранее принятое точное соответствие именованной части списка набору текущего типа сохраняется.

Набор потомка включает все именованные слоты каждого родителя по тегам; допустимый тип ребёнка может уточняться до подтипа, кратность сохраняется по правилам DSL. Потомок может добавлять слоты. Это не буквальное включение объектов дескрипторов через Set.containsAll: после уточнения типа дескриптор отличается, но требование родителя выполняется.

Например, родитель требует value: Expression, потомок уточняет value: Identifier (Identifier — подтип Expression) и добавляет другое место. У потомка и в наборе, и в списке value имеет тип Identifier; у родителя остаётся Expression. Пропуск value или расширение его допустимого типа вместо разрешённого уточнения нарушает наследование. Увеличение числа мест не разрешает произвольно менять кратность унаследованного места.

Последнее упоминание автором «набора неименованных детей родителя» трактуется как оговорка в контексте явно подтверждённого набора именованных слотов: абстрактные типы DSL объявляют именованные места. Правила наследования от конкретных типов этим решением не отменяются.

### Непосредственные базовые типы — принято

Сохраняется Set<AbstractType> getBaseTypes(): неизменяемый набор только непосредственных родителей. Всех предков при необходимости получают обходом связей наследования. Автор подтвердил пригодность существующей схемы наследования и базовых типов.

Для цепочки A <- B <- C метод у C возвращает только B, у B — только A. A не добавляется в набор непосредственных родителей C лишь из-за транзитивного наследования; сам C также в свой набор не входит. Пустой набор допустим только у корневого типа — согласно последующему уточнению контракта.

Это не меняет самостоятельность полной схемы слотов текущего типа. Контракты вспомогательных методов проверки подтипов и поиска общего базового типа ещё рассматриваются отдельно.

### Проверка подтипов и ацикличность наследования — принято

Сохраняется isSubtypeOf(AbstractType other): тип является подтипом самого себя и каждого транзитивного предка. Для Expression <- BinaryExpression <- Addition проверка Addition относительно Expression и самого Addition даёт true, обратная проверка Expression относительно Addition — false.

Граф наследования по контракту не содержит циклов, включая прямое наследование от самого себя. Ромбовидное наследование допустимо: несколько путей к одному предку не являются циклом. Например, D имеет родителей B и C, а оба они наследуют A — допустимый ромб. Цепочка A -> B -> A недопустима как описание типов.

Автор не требует сохранять текущий алгоритм и считает возможным более эффективный обход связей родителей. Допускаются общая default-реализация и оптимизированное переопределение генератором с тем же результатом. Конкретный алгоритм и стратегия кэширования ещё не выбраны; неизменность текущего TypeHierarchy не является требованием.

Единый корень и явные связи с ним определены последующим решением ниже.

### Явные родители и единственный корневой тип — принято

В core getBaseTypes() возвращает явные связи с непосредственными родителями. Только дескриптор корневого типа Node имеет пустой набор родителей. Все остальные типы обязаны возвращать непустой Set<AbstractType>. Граф конечен и ацикличен; все пути по родителям в конечном счёте достигают единственного корневого типа.

Пустой набор у некорневого типа является нарушением контракта, а не сокращением неявного наследования от Node. Если тип непосредственно наследует корневой тип, он явно возвращает набор с его дескриптором. Речь о дескрипторе типа, не об экземпляре AST-узла.

Например: Node -> {}; Expression -> {Node}; Addition -> {Expression}. Expression -> {} недопустимо. Ромбы сохраняются, циклы запрещены. Это уточняет ранее принятую формулировку пустого набора при отсутствии родителей.

В DSL отсутствие явного списка базовых типов может по-прежнему подразумевать Node; в API core эта связь должна быть представлена явно. Решение не требует писать корневой тип в каждом объявлении DSL.

Основание автора: контракт можно изменить; обязательный непустой набор у всех некорневых типов устраняет неявные особые случаи обхода. Конкретный алгоритм isSubtypeOf по-прежнему не закреплён.

### Общий применимый тип без Optional — принято

findCommonBaseType(AbstractType other) возвращает AbstractType, без Optional. Для корректных типов одной согласованной иерархии общий тип существует всегда, как минимум корневой Node. Возвращать отсутствие результата из-за нескольких несравнимых ближайших общих предков нельзя.

Назначение — получить общий применимый тип, например для результата дизъюнкции шаблонов X | Y. Результат T обязан удовлетворять X.isSubtypeOf(T) и Y.isSubtypeOf(T).

Принятое правило:
1. Найти наиболее конкретные общие типы, считая сам тип кандидатом наряду с предками.
2. Если кандидат единственный, вернуть его.
3. Если кандидатов несколько и они несравнимы, искать общий тип для всех этих кандидатов, поднимаясь выше по тому же правилу.
4. В предельном случае вернуть Node.

Это не произвольный выбор одного кандидата и не выбор по порядку обхода. При нескольких кандидатах следующий шаг учитывает всех одновременно; порядок попарной свёртки не должен подменять согласованную семантику.

Примеры:
- X и Y непосредственно наследуют A, а A наследует Node: результат A.
- X и Y каждый наследуют A и B; A и B несравнимы и непосредственно наследуют Node: результат Node, не Optional.empty().
- В предыдущем примере A и B имеют единственного наиболее конкретного общего родителя C: результат C.
- Для типа с самим собой результат сам тип; для потомка и его предка — этот предок.

Подъём может терять точность, но сохраняет применимость к обеим ветвям. Это согласованное изменение прежнего контракта поиска единственного наиболее конкретного предка. Конкретная реализация алгоритма пока не закреплена; поведение null и некорректных графов этим решением не определяется.

```java
AbstractType findCommonBaseType(AbstractType other);
```

### Имя как идентичность типа и восстановление фабрикой — принято

Сохраняется String getName(). В рамках одной DSL имена типов уникальны: одинаковое имя обозначает один и тот же тип независимо от идентичности Java-объекта дескриптора. Равенство типов определяется именем; hashCode должен быть согласован с этим равенством. Дескрипторы одного имени обязаны иметь согласованные определения, включая схему и родителей.

Автор подчеркнул, что это принципиальное свойство для простой сериализации и десериализации: фабрика соответствующей DSL по строке имени предоставляет полное описание типа. Схему не требуется восстанавливать из плоского списка детей или выводить из имени; она известна фабрике и описанию DSL.

Например, имя Addition позволяет фабрике получить тип Addition с его полной схемой и связями наследования; отдельные дескрипторы этого имени равны. Разные определения под одним именем в одной DSL недопустимы. Точная сигнатура фабрики и обработка неизвестного имени ещё не согласованы.

Уникальность здесь относится к одной DSL; решение не вводит глобальный реестр имён для всех независимых DSL. Восстановление типа по имени не заменяет восстановление данных и содержимого слотов конкретного узла.

### Properties типа и узла — принято

Сохраняется Map<String, String> getProperties() у типа для необязательных дополнительных метаданных, например language и color. Эти сведения не требуют отдельных методов getLanguage()/getColor() в интерфейсе узла. Карта типа неизменяема и задаёт значения по умолчанию для его узлов.

Конкретный узел может переопределять отдельные свойства типа по ключам. Node.getProperties() возвращает итоговую неизменяемую карту: свойства типа плюс собственные свойства узла, имеющие приоритет при совпадении ключа. Собственная карта узла не заменяет всю карту типа.

Пример: тип имеет {language: "Java", color: "green"}, узел задаёт {color: "red"}. Итог — {language: "Java", color: "red"}. Терять language из-за переопределения color нельзя. Если собственных свойств нет, узел может непосредственно возвращать карту типа; отдельное хранение карты в каждом узле не требуется.

Основание автора: дополнительные необязательные свойства используются для языка и визуализации; единая карта позволяет не перегружать Node специальными методами. Предложение удалить getProperties снято, внешняя таблица метаданных не выбрана.

Наследование свойств между типами, способ задания собственных свойств узла, подавление ключа типа и участие метаданных в сериализации рассматриваются отдельно. Согласованный Builder этим решением не расширяется.

### Properties не наследуются между типами — принято

getProperties() каждого типа возвращает только его собственные свойства. Автоматического наследования или объединения карт родителей нет. Отсутствующий у текущего типа ключ не ищется у предков.

Например, родители A и B задают color=red и color=green, а их потомок C не задаёт color. В свойствах C ключ color отсутствует; конфликта наследования свойств нет. Если C явно задаёт color=blue, его узлы по умолчанию получают blue.

Ранее согласованное переопределение свойств типа конкретным узлом по ключам сохраняется: оно применяется к карте фактического типа узла и не обходит родителей этого типа. Собственная пустая карта типа допустима.

Основание автора: у каждого типа свои свойства. Наследование структурных требований и связи базовых типов этим не меняются.

### Контракт карты properties и default — принято

В AbstractType сохраняется default-реализация:

```java
default Map<String, String> getProperties() {
    return Map.of();
}
```

Возвращаемая карта неизменяема и никогда не равна null; ключи и значения также не могут быть null. Тип без дополнительных свойств не обязан переопределять метод.

Пустая карта допустима. Карта {color: "green"} допустима при соблюдении неизменяемости. Возврат null, карты с null-ключом или null-значением нарушает контракт реализации. Это не вводит наследование properties от родителей. Конкретные ограничения на пустые строки этим решением не задаются.

### Создание независимого Builder конкретного типа — принято

В Type сохраняется Builder createBuilder(). Каждый вызов возвращает новый независимый Builder именно этого конкретного типа. Его getType() соответствует типу, на котором вызван createBuilder().

Начальное состояние соответствует принятым контрактам: все слоты пусты, данные имеют default datatype (если он есть), Fragment равен EmptyFragment.INSTANCE. Начальная валидность определяется обязательными слотами и проверками данных; метод не обещает сразу валидный Builder.

Пример: b1 = type.createBuilder() и b2 = type.createBuilder() дают независимые изменяемые построители. Установка ребёнка или данных в b1 не меняет b2. Общий неизменяемый дескриптор типа и другие безопасно разделяемые неизменяемые значения дублировать не требуется.

Абстрактный тип не предоставляет создание Builder для непосредственного построения своего узла. Сигнатура:

```java
Builder createBuilder();
```

### Явная реализация схем слотов — принято

Методы получения набора именованных слотов AbstractType и полного списка слотов Type не имеют default-реализации, возвращающей пустую коллекцию. Тип обязан предоставить свою схему, в том числе явно пустую для типа без соответствующих мест.

Рабочие сигнатуры:

```java
Set<NamedSlotDescriptor> getNamedSlots();
List<SlotDescriptor> getSlots();
```

Названия методов и дескрипторов остаются рабочими. Допустимы явно возвращённые Set.of() и List.of() для действительно пустых схем. Отсутствие требуемой реализации в конкретном Java-классе должно обнаруживаться компилятором Java, а не молча означать отсутствие слотов. Реализация может быть унаследована по обычным правилам Java, но обязана предоставлять корректную схему текущего типа.

Основание: отсутствие реализации не должно скрывать ошибку описания структуры. Это не меняет default пустой карты properties. Схемы остаются полными, неизменяемыми и взаимно согласованными по принятым выше правилам.

### Явная реализация getBaseTypes — принято

У getBaseTypes() убирается default-реализация, возвращающая пустой набор. В AbstractType это обязательный метод:

```java
Set<AbstractType> getBaseTypes();
```

Корневой тип явно возвращает пустой набор; все остальные — непустой неизменяемый набор непосредственных родителей. Например, корневой Node возвращает Set.of(), Expression непосредственно под ним — набор с дескриптором Node. Отсутствие реализации не должно молча создавать ещё один корень.

Основание: прежний default противоречил бы обязательности явных родителей у некорневых типов. Отсутствие реализации в конкретном Java-классе обнаруживается компилятором Java; правильность возвращённого набора остаётся контрактом типа. Это не меняет default-реализацию getProperties().

### Неизменяемые коллекции описания типа без null — принято

Коллекции, возвращаемые getBaseTypes(), getNamedSlots() и getSlots(), неизменяемы, никогда не равны null и не содержат null-элементов. Рабочие названия методов схем сохраняются до отдельного согласования.

Пустой набор родителей допустим только для единственного корневого типа. Пустой набор именованных слотов допустим при отсутствии именованных мест; полный список может при этом содержать безымянные места. Пустой полный список допустим для типа без слотов.

Пример: у конкретного Parts(Node*, Node*) набор именованных слотов пуст, но полный список содержит два дескриптора. Возврат null или коллекции с null-дескриптором нарушает контракт типа. Для отсутствующего тега используется предусмотренное дескриптором представление отсутствия, а не null вместо всего дескриптора.

### Названия методов схем и дескрипторов — принято

Закреплены сигнатуры:

```java
// AbstractType
Set<NamedSlotDescriptor> getNamedSlots();

// Type
List<SlotDescriptor> getSlots();
```

getNamedSlots возвращает полный набор описаний именованных слотов текущего типа; getSlots — полный упорядоченный список описаний всех слотов конкретного типа. Это описания структуры типа, а не содержимое мест конкретного узла. Старый getChildDescriptors() заменяется этими двумя методами.

Названия NamedSlotDescriptor и SlotDescriptor закреплены вместе с показанными сигнатурами; их конкретная Java-иерархия и методы ещё обсуждаются. Ранее названные рабочими имена теперь утверждены.

Для Addition(Expression, Expression) без тегов getNamedSlots() пуст, getSlots() содержит два обязательных описания в порядке операндов. Это не два списка фактических Expression: экземпляры детей доступны у Node.

### null в алгоритмах отношений типов — принято

isSubtypeOf(null) и findCommonBaseType(null) бросают IllegalArgumentException. null является недопустимым аргументом, а не отсутствием родства или общего типа. Для корректных ненулевых аргументов сохраняются ранее согласованные контракты, включая обязательный результат findCommonBaseType.

### Направление проектирования строителя схемы

Автор предложил сохранить удобство текущего ChildDescriptor.Constructor: цепочку required/optional/repeated и проверку уникальности тегов, распространив строитель на согласованное формирование двух представлений новой схемы.

Проверен текущий ChildDescriptor: Constructor накапливает список, а build() через copySchema создаёт неизменяемый снимок и бросает IllegalArgumentException при повторном теге. Дубликаты не удаляются автоматически. Текущий запрет именованных повторяющихся мест новой модели не соответствует.

Новая задача — согласованно строить набор именованных дескрипторов и полный упорядоченный список всех дескрипторов (не только безымянных). Точные имена строителя, объекта результата и способы построения абстрактной схемы пока не согласованы. Выбор records либо классов для дескрипторов также не завершён.

### Единая схема как результат строителя — принято

Автор подтвердил: нужен строитель, возвращающий неизменяемую схему, из которой можно получить два неизменяемых объекта — набор именованных дескрипторов и полный упорядоченный список всех дескрипторов.

Оба представления формируются согласованно из одной схемы. Порядок полного списка соответствует порядку добавления слотов; набор содержит именованную часть этой схемы. Типы детей, теги и кратности в обоих представлениях согласованы. Повторные теги отвергаются, не удаляются автоматически.

Например, цепочка required(Expression, "head"), repeated(Expression), optional(Expression, "tail") даёт список из трёх мест и набор из head и tail. Набор без head или с другой кратностью tail не может быть независимо задан как второе представление этой схемы.

Полученные схема и коллекции не должны меняться при последующих изменениях строителя. Это требование неизменяемого результата, не предписание дублировать объекты или заново создавать коллекции при каждом обращении. Название SlotSchema и детали API пока являются предложением; способ построения схемы абстрактного типа обсуждается отдельно.

### Единый строитель схемы для абстрактных и конкретных типов — принято

Для абстрактного типа используется тот же строитель схемы. В него добавляются только именованные слоты; AbstractType предоставляет из результата набор именованных дескрипторов. Порядок добавления не имеет семантического значения для абстрактного типа.

Конкретный Type использует оба представления результата: набор именованных слотов и полный список с конечным порядком. Отдельный строитель для абстрактных типов не вводится.

Пример: абстрактный тип с местами left: Expression и right: Expression получает одинаковые требования независимо от порядка добавления этих двух именованных мест. У конкретного типа перестановка мест в полном списке меняет их индексы и значима.

Безымянные объявления слотов абстрактного типа остаются недопустимыми по правилам DSL. Универсальность строителя не разрешает обход этого правила; конкретный механизм контроля при использовании строителя ещё не выбран. Имена класса схемы и её строителя пока не закреплены.

### Имена и цепочка API SlotSchema — принято

Закреплены SlotSchema (неизменяемая схема), SlotSchema.Constructor (изменяемый строитель), статический SlotSchema.create() для создания строителя и build() для получения схемы. Методы required, optional и repeated возвращают строитель для цепочки вызовов; каждый имеет варианты с тегом и без него, с аргументами (AbstractType type) и (AbstractType type, String tag).

```java
SlotSchema schema = SlotSchema.create()
    .required(expressionType, "head")
    .repeated(expressionType)
    .optional(expressionType, "tail")
    .build();

Set<NamedSlotDescriptor> named = schema.getNamedSlots();
List<SlotDescriptor> ordered = schema.getSlots();
```

Именованное повторяющееся место поддерживается: repeated(expressionType, "items"). Прежний запрет тега у REPEATED в ChildDescriptor не переносится. Вариант без тега создаёт безымянное место; отсутствие аргумента тега не означает пропуска места.

Это утверждение API проектируемой модели, не заявление о его реализации. Момент обнаружения повторных тегов и точные проверки аргументов строителя ещё предстоит согласовать.

### Повторные теги в SlotSchema.Constructor — принято

Повторный тег отвергается непосредственно при добавлении слота через required/optional/repeated: бросается IllegalArgumentException, состояние строителя остаётся без изменений. Проверка не откладывается до build().

Пример: после required(expressionType, "value") вызов optional(expressionType, "value") бросает исключение; в схеме остаётся только первое место. Даже полное совпадение тега, типа и кратности не разрешает добавление второго места и не приводит к молчаливому объединению.

Безымянные слоты могут повторяться, включая одинаковые типы и кратности: repeated(expressionType), repeated(expressionType) создаёт два разных места. Это построение готовой схемы; объединение унаследованных требований должно быть разрешено до добавления итоговых мест, а не угадываться строителем.

### Проверки аргументов SlotSchema.Constructor — принято

Методы required/optional/repeated отвергают null вместо допустимого типа ребёнка. Именованные перегрузки дополнительно отвергают null и пустую строку вместо тега. Отказ происходит сразу с IllegalArgumentException и без изменения состояния строителя.

Примеры: required(null), required(expressionType, null) и required(expressionType, "") недопустимы. required(expressionType) создаёт безымянное место и допустим. Те же проверки действуют для optional и repeated.

Отсутствие тега задаётся перегрузкой без тега, а не null или пустой строкой. Полная проверка лексики непустых тегов этим решением не устанавливается; ограничения исходника DSL остаются отдельным контрактом.

### Пустая схема, повторное построение и empty() — принято

SlotSchema.Constructor.build() допускает пустую схему и не очищает и не изменяет строитель. После build() можно добавлять новые места и строить следующие схемы; ранее полученные схемы и обе их коллекции остаются неизменными.

Пример: новый строитель выдаёт пустую схему; после required(expressionType) он выдаёт схему с одним безымянным местом. Первая схема остаётся пустой.

По требованию автора добавляется прямой хелпер получения пустой схемы без создания строителя. Для API выбрано имя:

```java
public static SlotSchema empty();
```

SlotSchema.empty().getNamedSlots() возвращает пустой неизменяемый набор, SlotSchema.empty().getSlots() — пустой неизменяемый список. Благодаря неизменяемости разрешено возвращать общий экземпляр пустой схемы; обязательная ссылочная идентичность результатов не вводится. Одна пустая схема пригодна для абстрактного типа без именованных слотов и конкретного типа без слотов.

### Неизменяемые классы дескрипторов — принято

NamedSlotDescriptor и SlotDescriptor проектируются как обычные неизменяемые классы, не records, с закрытыми конструкторами. Создание выполняется через строитель схемы; публичный API дескрипторов предназначен для чтения допустимого типа ребёнка, тега и кратности.

Прямое создание произвольных дескрипторов пользователем API не предоставляется. Это дополняет проверки строителя на некорректные аргументы и повторные теги. Физическое размещение классов и внутренний механизм доступа строителя к закрытым конструкторам ещё предстоит выбрать; решение не предполагает, что отдельный внешний Java-класс может напрямую вызвать чужой private-конструктор.

Точная иерархия классов и сигнатуры методов чтения согласуются далее. Предыдущие эскизы records не являются принятой моделью.

### Методы дескрипторов и Cardinality — принято

Публичные методы NamedSlotDescriptor:

```java
String getTag();
AbstractType getType();
Cardinality getCardinality();
```

Публичные методы SlotDescriptor:

```java
Optional<String> getTag();
AbstractType getType();
Cardinality getCardinality();
```

У NamedSlotDescriptor тег всегда задан и непуст; у SlotDescriptor отсутствие тега представлено Optional.empty(), не null. Допустимый тип ребёнка и кратность всегда заданы. Сохраняется Cardinality с REQUIRED (ровно один), OPTIONAL (ноль или один) и REPEATED (ноль или более).

Например, именованное повторяющееся items имеет getTag() == "items" в именованном представлении и Optional.of("items") в полном; оба возвращают одинаковые допустимый тип и REPEATED. Безымянное обязательное место имеет Optional.empty() и REQUIRED в полном списке, а в набор именованных не входит.

Эти сигнатуры не допускают прямого наследования одного дескриптора от другого с одноимённым getTag(): String и Optional<String> не являются совместимыми ковариантными возвращаемыми типами Java. Внутреннее разделение данных или композиция остаются вопросом реализации.

### Равенство и хэш дескрипторов — принято

NamedSlotDescriptor и SlotDescriptor имеют equals/hashCode по трём полям: тег (включая его наличие для SlotDescriptor), допустимый тип ребёнка и кратность. Равенство рассматривается внутри одного класса; NamedSlotDescriptor не равен SlotDescriptor даже при согласованных значениях. Допустимые типы сравниваются по принятому контракту равенства типов по имени.

Два безымянных SlotDescriptor с одинаковым типом и кратностью равны. Это не объединяет позиции полного списка: например, два обязательных Expression в Addition остаются двумя слотами, хотя их дескрипторы равны. Индекс не входит в равенство дескриптора.

Дескрипторы с разными тегами, типами либо кратностями не равны. Проверка уникальности тегов строителем остаётся отдельным правилом и не заменяется Set-дедупликацией по equals.

### Граница проверки схемы и хелпер из именованного набора — принято частично

SlotSchema.Constructor проверяет локальную корректность схемы: аргументы и уникальность тегов. Родителей типа он не получает и соответствие наследованию не проверяет. Компилятор DSL проверяет сохранение родительских тегов, допустимость уточнения типов и неизменность кратностей; строитель получает итоговую раскладку.

Автор дополнительно предложил хелпер, создающий строитель схемы из существующего набора NamedSlotDescriptor абстрактного типа. Такой импорт переносит именованные описания, а не сам по себе доказывает наследование или объединяет конфликтующие требования нескольких родителей.

Точная сигнатура хелпера и порядок импортированных слотов пока не согласованы: входной Set не задаёт семантического порядка, тогда как результат строителя имеет полный упорядоченный список. Нельзя молча считать порядок итерации произвольного Set порядком конкретной схемы.

### Импорт именованных дескрипторов с определённым порядком — принято

Добавляется перегрузка SlotSchema.create(Set<NamedSlotDescriptor> descriptors), возвращающая SlotSchema.Constructor, заполненный импортированными именованными слотами.

Импортированные слоты сортируются по тегу по возрастанию (естественный лексикографический порядок String); порядок обхода входного Set не определяет порядок списка схемы. Тип ребёнка и кратность каждого дескриптора сохраняются. Последующие required/optional/repeated добавляют места в конец после импортированных.

```java
var builder = SlotSchema.create(abstractType.getNamedSlots());
```

Например, входной набор с тегами tail и head в любом порядке даёт начальный список head, tail. Последующий repeated(expressionType) добавляет третье безымянное место. Повторное добавление head отвергается по общему правилу уникальности тегов.

Если конкретному типу нужен иной порядок, схема строится явной цепочкой вызовов без такого импорта. Хелпер не меняет неупорядоченную семантику набора AbstractType и не проверяет наследование. Подробности отказа при некорректном входном наборе ещё уточняются.

### Проверки и снимок при импорте набора — принято

SlotSchema.create(Set<NamedSlotDescriptor>) бросает IllegalArgumentException, если набор равен null, содержит null или содержит разные дескрипторы с одним тегом. Частично заполненный строитель не возвращается. Уникальность тегов проверяется отдельно от equals элементов Set.

Пустой набор допустим и по начальному состоянию эквивалентен SlotSchema.create(). Импорт фиксирует содержимое набора на момент создания строителя; последующие изменения исходного набора не влияют на строитель и создаваемые им схемы. Неизменяемые дескрипторы допускается разделять без глубокого копирования.

Например, после импорта набора с head и tail очистка исходного изменяемого Set не удаляет эти слоты из строителя. Набор с двумя дескрипторами тега value, различающимися типом либо кратностью, отклоняется, хотя Java Set может содержать оба элемента.

### Прямой доступ к детям места через Node вместо Slot — принято

Автор выбрал разделение: Node хранит детей, Type — описания детей. Отдельный объект/интерфейс Slot, объединяющий дескриптор и список узлов, не вводится. Предложение Slot.getDescriptor()/getNodes() отклонено.

Node предоставляет два getter содержимого места — по индексу схемы и по тегу. Каждый возвращает список детей соответствующего места. Описание получают отдельно из типа. Логические места и их границы сохраняются, даже если отдельной Java-сущности Slot нет. Это уточняет раннюю формулировку о месте как сущности API.

Пример: для Addition место 0 даёт одноэлементный список левого Expression, место 1 — правого. Для известного пустого необязательного или повторяющегося места возвращается пустой список. Списки неизменяемы согласно принятому контракту. Имена getter и поведение по неизвестному тегу необходимо уточнить для нового API: прежняя формулировка Optional места относилась к отвергнутому объектному доступу через Slot. Исключение при неверном индексе места ранее согласовано.

Автор также указал на необходимость простого поиска именованного дескриптора по тегу в типе. Точная сигнатура дополнительного метода и реализация обсуждаются далее.

### Поиск именованного дескриптора по тегу — принято

В AbstractType добавляется Optional<NamedSlotDescriptor> getNamedSlot(String tag). Метод ищет именованный дескриптор текущего типа в его полной схеме; известный тег даёт присутствующий результат, неизвестный — Optional.empty().

Общая default-реализация выполняет поиск в getNamedSlots(). Генератор может переопределить её эффективным поиском (например, switch) с тем же результатом. Возвращаемый дескриптор соответствует элементу набора по принятому равенству; отдельная гарантия ссылочной идентичности не вводится.

Для Mixed с именованными head и tail поиск "head" возвращает его описание, поиск "missing" — Optional.empty(). Безымянное место не может быть найдено по тегу. Поведение null-аргумента ещё предстоит уточнить.

Это метод типа, возвращающий описание; содержимое места по-прежнему предоставляет Node отдельным getter.

### Getter содержимого места Node и ошибки адресации — принято

Закреплены два метода Node:

```java
List<Node> getChildren(int slotIndex);
List<Node> getChildren(String tag);
```

Оба возвращают неизменяемый список фактических детей указанного слота. Известное пустое необязательное или повторяющееся место даёт пустой список. Неизвестный тег либо null в строковой перегрузке приводят к IllegalArgumentException. Индекс вне диапазона слотов приводит к IndexOutOfBoundsException.

Индекс означает индекс в полной схеме Type.getSlots(), а не индекс ребёнка в плоском представлении. Для Addition с двумя местами допустимы 0 и 1; -1 и 2 недопустимы. У Mixed пустое optional возвращает [], но отсутствующий тег missing вызывает исключение — это разные ситуации.

Наличие именованного слота можно проверить отдельно через Type.getNamedSlot(tag). Ранее предложенный Optional объекта Slot заменён данным прямым API; отдельный Slot не вводится. Контракты setter Builder (false при неправильной адресации) этим не меняются.

### null и отсутствующий тег в getNamedSlot — принято

AbstractType.getNamedSlot(null) бросает IllegalArgumentException. Для любого ненулевого отсутствующего тега возвращается Optional.empty(), включая пустую строку (пустые теги в схемах запрещены).

Известный тег возвращает соответствующий NamedSlotDescriptor. Например, при наличии head поиск "head" успешен; "missing" и "" дают Optional.empty(); null вызывает исключение. Default-реализация и оптимизированные переопределения обязаны соблюдать одинаковый контракт.

### Один метод плоского доступа ко всем детям — принято

Автор отклонил сохранение трёх методов getChildCount(), getChild(int) и getChildrenList() в новом API. Для плоского доступа нужен один метод, возвращающий список всех непосредственных детей. Выбрано выразительное имя getAllChildren():

```java
List<Node> getAllChildren();
```

Возвращается неизменяемый список всех фактических непосредственных детей: сначала порядок слотов, внутри слота — порядок детей. Пустые места не добавляют элементов; границы мест в этом представлении не отражаются. Это не рекурсивный список всех потомков.

Для слотов [A], [], [B, C] результат — [A, B, C]. Общее число доступно через size(), плоский индекс — через get(index) возвращённого списка. Отдельные методы Node для этих двух операций не вводятся. getChildren(int slotIndex) и getChildren(String tag) сохраняются для доступа к одному месту.

Список всех детей предназначен для вспомогательного плоского чтения; сериализация сохраняет структуру мест по ранее согласованному контракту. Физический способ построения или кэширования плоского представления не закреплён.

### Сериализованные данные Node — принято

В Node сохраняется String getData(). Метод возвращает сериализованное представление данных согласно datatype и никогда не возвращает null. Для узла без datatype результат — пустая строка.

Примеры: стандартный Int со значением 42 даёт "42"; стандартный String возвращает саму строку, включая допустимую пустую; Addition без datatype даёт "". Для других datatype применяется их собственная сериализация.

Сгенерированный узел хранит нативное значение согласно javaType datatype (например, int), а не обязан хранить дополнительную сериализованную строку. getData() предоставляет строковое представление для общего API; необходимость и способ кэширования не закреплены.

Возврат null нарушает контракт; это не способ обозначения отсутствующих данных. Конкретная диагностика нарушения пользовательским сериализатором рассматривается отдельно.

### Fragment в Node и default — принято

В Node сохраняется:

```java
default Fragment getFragment() {
    return EmptyFragment.INSTANCE;
}
```

Метод никогда не возвращает null. Узел с исходным диапазоном возвращает свой неизменяемый Fragment. Узел без происхождения может использовать default-реализацию без отдельного поля для отсутствующего фрагмента.

Если узел построен Builder, которому передан конкретный Fragment, результат должен предоставлять этот фрагмент; оптимизация хранения не разрешает терять явно заданное происхождение. Возврат null вместо отсутствующего диапазона нарушает контракт. Перенос диапазонов при преобразованиях обсуждается отдельно в Q37.

### Default-реализация getAllChildren — принято

Node.getAllChildren() имеет общую default-реализацию: обходит слоты по порядку полного списка getType().getSlots(), получает содержимое каждого через getChildren(index) и возвращает объединённый неизменяемый список.

Генератор может переопределить метод более эффективной реализацией с тем же результатом. Например, Addition с полями left и right может непосредственно вернуть List.of(left, right), избегая обхода слотов и промежуточных списков.

Для содержимого мест [A], [], [B, C] обе реализации обязаны дать [A, B, C]. Для узла без слотов возвращается пустой неизменяемый список. Результат содержит только непосредственных детей; порядок и неизменяемость сохраняются при любой оптимизации.

### Default-доступ к детям по тегу и поиск индекса в Type — направление принято

Автор поддержал default-реализацию Node.getChildren(String tag), сводящую доступ по тегу к getChildren(int slotIndex), чтобы уменьшить число обязательных реализаций Node.

Для этого в конкретный Type добавляется операция поиска индекса именованного слота в его полном упорядоченном списке. Существующий getNamedSlot(tag) возвращает дескриптор, а не индекс и не заменяет новую операцию. У AbstractType порядок слотов не задан, поэтому индексный поиск относится к Type.

Node сохраняет согласованное поведение: null и неизвестный тег вызывают IllegalArgumentException; известный тег делегируется индексному getter. Генератор может оптимизировать доступ с сохранением контракта.

Точное имя, возвращаемый тип и поведение нового метода поиска индекса при отсутствии тега пока не согласованы. Default-реализация поиска в полном списке и оптимизированные переопределения рассматриваются далее.

### Индекс слота как int и default Node.getChildren(tag) — принято

В Type добавляется default int getSlotIndex(String tag). Индекс известного именованного слота находится в диапазоне от 0 до getSlots().size()-1. Для отсутствующего ненулевого тега возвращается -1; null вызывает IllegalArgumentException. Предложение OptionalInt отклонено.

Общая default-реализация ищет тег в полном упорядоченном списке getSlots(). Генератор может заменить её оптимизированным поиском с тем же контрактом. Безымянные слоты не совпадают ни с каким тегом, включая пустую строку.

Node предоставляет:

```java
default List<Node> getChildren(String tag) {
    int index = getType().getSlotIndex(tag);
    if (index < 0) {
        throw new IllegalArgumentException("Unknown slot: " + tag);
    }
    return getChildren(index);
}
```

Например, у схемы head, безымянное место, tail поиск tail возвращает 2, missing возвращает -1; Node.getChildren("missing") бросает IllegalArgumentException. Известное пустое место возвращает пустой список через индексный getter. null отвергается методом типа. Точный текст сообщения исключения не является фиксированным контрактом.

### Структурное сравнение Node — принято

Два узла структурно равны, если равны их типы по принятому контракту типов, строковые данные getData() и содержимое каждого слота. Слоты сравниваются по порядку полной схемы; в каждом слоте совпадают число детей и порядок структурно равных дочерних узлов. Сравнение рекурсивное.

Границы слотов существенны: содержимое [A], [], [B, C] и [A], [B], [C] структурно различается, хотя плоский список детей одинаков. Fragment и дополнительные свойства узла в структурном сравнении не участвуют: разное происхождение или оформление не меняет результат сравнения.

Имя метода и соотношение структурного сравнения с equals/hashCode этим решением ещё не определены.

### Метод deepCompare и структурный хэш — принятое направление

Сохраняется default boolean deepCompare(Node other): общая реализация структурного сравнения по согласованным правилам, null даёт false. Генератор может оптимизировать реализацию, сохраняя результат. Отдельного изменения контракта equals этим решением не вводится. В текущем core equals/hashCode уже структурные; при адаптации к слотам необходимо сохранить их согласованность.

Автор указал на необходимость структурного хэша, зависящего от типа, данных и детей, с учётом слотов. Текущие NodeStructure.startHash и StructuralHash используют общее число детей, теги вхождений и хэши детей; пустые слоты в этом обходе не представлены. Алгоритм необходимо адаптировать к полной схеме слотов.

Предложение для следующего согласования: смешивать хэш типа и данных, число слотов, затем для каждого слота его размер и структурные хэши детей в порядке следования. Пустой слот также участвует (размер 0). Свойства и Fragment исключаются. Сохранить итеративный обход и вычисление общего дочернего объекта один раз за вызов. Равные структуры должны иметь одинаковый хэш; совпадение хэшей само по себе не доказывает равенство. Точная формула и публичный метод ещё обсуждаются.

### Формула структурного хэша со слотами — принято

Принята формула (арифметика Java int, включая обычное переполнение):

1. h = 31 * node.getType().hashCode() + node.getData().hashCode().
2. h = 31 * h + node.getType().getSlots().size().
3. Для каждого слота в порядке схемы: h = 31 * h + children.size(); затем для каждого ребёнка в порядке слота: h = 31 * h + structuralHash(child).

Пустой слот тоже участвует: добавляется его размер 0. Fragment и свойства не учитываются. Обход остаётся итеративным; хэш общего дочернего объекта можно вычислять один раз за вызов, учитывая его результат при каждом вхождении.

Пример двух повторяющихся слотов Expression: [A], [B, C] даёт последовательность добавлений 1, hash(A), 2, hash(B), hash(C), а [A, B], [C] — 2, hash(A), hash(B), 1, hash(C). Таким образом границы слотов представлены в вычислении даже при одинаковом плоском списке детей. Это не гарантия отсутствия коллизий: равные структуры имеют одинаковый хэш, но совпадение хэшей требует проверки deepCompare.

Эта запись утверждает ранее предложенную формулу. Публичный метод доступа к полному структурному хэшу ещё предстоит согласовать.

### Готовый структурный хэш и стандартные equals/hashCode — принято

Автор отклонил default getStructuralHash(), повторно обходящий поддерево при каждом вызове. Принято обязательное вычисление структурного хэша при создании неизменяемого узла из уже готовых хэшей его непосредственных детей. Используется ранее согласованная формула с количеством слотов и размером каждого слота, включая пустые. Для ребёнка берётся child.hashCode(), без повторного обхода его поддерева.

Доступ предоставляется стандартным hashCode(), который возвращает готовый результат за O(1). Отдельного getStructuralHash() нет. Интерфейс не требует конкретного поля: обычная реализация хранит private final int hash, для фиксированного значения допустима константа. Генератор обязан сохранять согласованную формулу и контракт. Карта хэшей на время алгоритма для обычных неизменяемых узлов больше не требуется. Ранее принятое описание итеративного полного вычисления не означает необходимость такого обхода при получении хэша: оно заменено вычислением при создании узла.

equals(Object) структурный: для другого Node сравниваются тип, данные и содержимое слотов по принятым правилам; разные хэши сразу дают false, одинаковые проверяются через deepCompare. null и объекты, не реализующие Node, дают false. Различие Java-классов реализации само по себе не делает узлы неравными. Fragment и свойства не участвуют. deepCompare остаётся структурным сравнением, которое не может считать совпадение хэшей доказательством равенства.

В Node явно объявляются:

```java
@Override
int hashCode();

@Override
boolean equals(Object other);
```

Default-реализации этих методов Object в Java-интерфейсе невозможны. Общую реализацию можно предоставить базовым классом; сгенерированные классы обязаны соблюдать контракт. Сравнение должно избегать взаимной рекурсии equals и deepCompare: deepCompare реализует проверку структуры, а не делегирует обратно equals того же узла.

### Удаление deepClone из Node — принято

Метод deepClone() удаляется из нового интерфейса Node. Клонирование неизменяемых узлов для получения независимой изменяемой копии не требуется: узлы не изменяются, а поддеревья можно безопасно повторно использовать по ссылке в нескольких местах.

При преобразовании новый узел создаётся через Builder; неизменённые дочерние узлы используются повторно. Структурное сравнение и хэш не зависят от того, представлены одинаковые поддеревья общим объектом или разными структурно равными объектами. Это решение не вводит новые методы Builder.

### Удаление вспомогательных методов обхода детей — принято

Из нового интерфейса Node удаляются getIteratorOverChildren() и forEachChild(action). Для плоского обхода непосредственных детей используются getAllChildren().iterator() и getAllChildren().forEach(action). Для алгоритмов, которым важны границы слотов, сохраняется доступ getChildren(slotIndex) в порядке схемы типа.

Это не вводит рекурсивный обход потомков в getAllChildren(): его согласованный контракт остаётся прежним.

### Удаление getLocalHash из Node — принято

Метод getLocalHash(), учитывавший только тип и данные, удаляется из нового интерфейса Node. Полный структурный hashCode() уже возвращает заранее вычисленное значение за O(1), поэтому отдельный локальный хэш не нужен как более дешёвая проверка перед структурным сравнением. Если отдельному алгоритму требуется сравнить только тип и данные, он обращается к ним напрямую; равенство таких заголовков не означает структурного равенства узлов.

### Делегаты getTypeName и isSubtypeOf в Node — принято

В Node сохраняются два удобных default-метода:

```java
default String getTypeName() {
    return getType().getName();
}

default boolean isSubtypeOf(AbstractType type) {
    return getType().isSubtypeOf(type);
}
```

Методы делегируют операции типу узла, не требуют дополнительного состояния и обязательных реализаций в сгенерированных классах. Контракт isSubtypeOf, включая обработку null, соответствует ранее принятому контракту AbstractType.

### Удаление статического Node.toString(Node) — принято

Статический метод toString(Node), делегировавший форматирование в DraftFormat, удаляется из нового интерфейса Node. Форматирование предоставляется отдельным форматтером. Формат представления дерева с учётом слотов рассматривается отдельно при обсуждении сериализации (Q36).

Это решение касается статического метода интерфейса и само по себе не устанавливает новый контракт экземплярного Object.toString().

### Свойства через отдельные обёртки — уточнение автора, принято

Обычный Node получает свойства из своего Type через default getProperties(). Стандартный Builder ничего не знает о свойствах; добавлять в него методы задания или переноса свойств не требуется.

Дополнительные свойства предоставляются специальной обёрткой узла, обёрткой типа и обёрткой строителя. Работа с дополнительными свойствами и их сохранение при построении относятся к этому механизму, а не к обычным сгенерированным узлам и строителям. Ранние формулировки о собственных свойствах Node следует понимать в контексте такой обёртки.

Автор поручил пересмотреть существующий механизм обёрток в core, поскольку его реализация может требовать переработки. Его точный API и поведение при преобразованиях ещё обсуждаются. Найденные algorithms.normalization.Property и Properties представляют свойства в нормализованном дереве и не являются искомой прозрачной обёрткой; конкретная реализация такой обёртки пока не установлена.

### Найден LabeledTreeBuilder — исходная реализация для пересмотра

Автор указал algorithms.LabeledTreeBuilder; файл проверен в текущем core. Его приватный LabeledNode оборачивает исходный узел, сохраняет Fragment и данные, предоставляет дополненные свойства и список обёрнутых детей. Существующий getType() возвращает original.getType(): отдельных обёрток Type и Builder здесь нет. Поэтому строитель, полученный через этот тип, сам по себе не сохраняет метку данного узла. Это расхождение с описанным автором желаемым механизмом предстоит устранить при пересмотре.

Другие выявленные особенности: используется плоский список детей (нужна адаптация к слотам); выбор узлов выполняется через selected.contains(original), поэтому для обычного HashSet структурно равные разные объекты не различаются. Семантику выбора по объекту или по вхождению нужно согласовать отдельно. Утверждение выше о том, что конкретная реализация не найдена, этой записью уточнено.

### Алгоритмы core вынесены в отдельный план — принято

По указанию автора обсуждение алгоритмов, включая LabeledTreeBuilder и связанные обёртки, отложено в [отдельный план](core-algorithms-review-plan.md). Сейчас завершаются базовые классы. Последнее предложение о сохранении меток через строитель обёртки остаётся открытым вопросом плана, а не утверждённым контрактом.

### Fragment: полуоткрытый диапазон и отсутствие происхождения — принято

Fragment сохраняется как неизменяемый полуоткрытый диапазон [begin, end) одного источника: начало включено, конец исключён. Совпадение позиций begin и end означает диапазон нулевой длины с известным местом в источнике. Это не то же самое, что EmptyFragment.INSTANCE, обозначающий отсутствующее (неизвестное) происхождение.

Например, диапазон в известной позиции перед символом или в конце текста может иметь нулевую длину, но всё равно сохраняет источник и координаты. Отсутствующее происхождение не задаёт такого места. Это уточняет контракт Fragment, уже используемый Node и Builder.

### Проверка границ обычного Fragment — принято

При создании обычного Fragment обе позиции должны быть ненулевыми, принадлежать одному и тому же объекту Source и находиться в пределах этого источника. Допускается позиция непосредственно после последнего символа (конец текста). Начало должно быть не позже конца; равные позиции допустимы согласно контракту диапазона нулевой длины.

Нарушение любого из этих требований приводит к IllegalArgumentException. Конструктор не переставляет перепутанные границы автоматически. Это контракт создания диапазона по заданным началу и концу; поведение вспомогательных методов вычисления охватывающего диапазона рассматривается отдельно.

### Равенство Fragment — принято

Два обычных Fragment равны, если относятся к одному и тому же объекту Source (ссылочная идентичность) и имеют одинаковые координаты начала и конца. Идентичность самих объектов Position не требуется.

Совпадение имени файла и текста у разных объектов Source не делает фрагменты равными: источники могут представлять разные снимки файла. EmptyFragment не равен обычному диапазону нулевой длины с известным источником. hashCode должен быть согласован с этим равенством; конкретная формула хэша фрагмента данным решением не закрепляется.

### Source как неизменяемый снимок — принято

Source представляет неизменяемый снимок исходного текста. Изменение файла на диске не меняет текст уже созданного Source и смысл связанных с ним Position и Fragment. Для новой версии текста создаётся новый объект Source. В частности, Fragment.getCode() не должен незаметно возвращать новое содержимое файла вместо исходного диапазона.

### Система координат Position — принято

Номера строк и столбцов обычной Position начинаются с 1. Столбцы считаются в кодовых единицах UTF-16; табуляция занимает одну единицу. Это координаты текста, не визуальные позиции на экране и не счётчик Unicode code points.

Пример строки a😀b: a находится в столбце 1, 😀 начинается в столбце 2 и занимает две кодовые единицы, b находится в столбце 4, позиция после строки имеет столбец 5. Правила допустимости границы внутри суррогатной пары данным решением отдельно не устанавливаются.

### Граница внутри суррогатной пары — принято

Position допускает позицию между двумя кодовыми единицами UTF-16, составляющими суррогатную пару. Базовый API адресует кодовые единицы и не требует, чтобы каждая граница совпадала с границей Unicode code point.

Парсер, работающий с Unicode code points, отвечает за создание границ между целыми символами. Допуск на уровне Position позволяет также точно представлять диапазоны внешних инструментов. Например, в a😀b позиция столбца 3 допустима, хотя находится внутри пары, представляющей 😀.

### Равенство и порядок Position — принято

Обычные Position равны, если у них один и тот же объект Source и одинаковые строка и столбец. hashCode согласован с этим равенством. Идентичность объектов Position не требуется.

compareTo сравнивает сначала строку, затем столбец в пределах одного объекта Source. Позиции разных источников несравнимы: compareTo бросает IllegalArgumentException. Совпадение имён файлов или содержимого разных Source этого не меняет.

### Переводы строк и точный текст Source — принято

Новую строку начинает только LF (\n). CR (\r) занимает одну кодовую единицу UTF-16 и сам не переключает строку. CRLF сохраняется как два исходных символа: нормализация переводов строк не выполняется. Source.getFragmentAsString и Fragment.getCode возвращают точный исходный текст заданного диапазона.

Пример: в a\r\nb символ b находится в строке 2, столбце 1. В a\rb символ b остаётся в строке 1, столбце 3. Эти правила относятся к координатам исходного текста.

### Крайние позиции и канонические координаты — принято

Каждому допустимому смещению в тексте соответствует ровно одна пара «строка, столбец».

- Пустой текст имеет единственную позицию (1, 1).
- Для "abc" конец текста — (1, 4).
- Для "abc\n" конец текста — (2, 1).
- Позиция сразу после LF представляется только началом следующей строки; альтернативные координаты в предыдущей строке не допускаются.

Таким образом допустимые координаты включают конец текста, но не допускают нескольких представлений одной позиции на границе строк.

### Проверки Source.getFragmentAsString — принято

Source.getFragmentAsString(begin, end) проверяет обе позиции: они ненулевые, принадлежат именно данному объекту Source, имеют допустимые канонические координаты; начало не позже конца. null, чужой источник, недопустимые координаты и обратный диапазон приводят к IllegalArgumentException.

Метод не обрезает диапазон по границам источника и не переставляет начало и конец. При одинаковых допустимых позициях возвращается пустая строка "". В остальных случаях возвращается точный текст полуоткрытого диапазона согласно ранее принятому контракту.

### Имя файла Source — принято

Сохраняется default String getFileName(), возвращающий "" по умолчанию. Если источник связан с файлом, реализация возвращает его имя или путь; иначе — пустую строку. null не допускается.

Имя служит для диагностики и не определяет идентичность Source. Одинаковые имена у двух объектов не делают их одним источником для Position и Fragment.

### Служебная позиция EmptyFragment — принято

EmptyFragment.INSTANCE.getBegin() и getEnd() возвращают специальную позицию (0, 0) со служебным источником. Это единственное исключение из правил координат обычных Position. EmptyFragment.getCode() возвращает "".

Служебная позиция обозначает отсутствие происхождения и не является допустимой границей обычного Fragment. Попытка создать обычный Fragment с такой позицией отклоняется согласно принятому контракту проверки границ (IllegalArgumentException). Диапазон нулевой длины в реальном пустом источнике по-прежнему использует (1, 1) и отличается от EmptyFragment.

### Диагностическое представление Fragment — принято

Сохраняется getPositionAsString() со следующими форматами:
- При наличии имени файла: file.c, 2.3-4.5.
- Без имени файла: 2.3-4.5.
- Для EmptyFragment: ∅.

EmptyFragment должен переопределять getPositionAsString(), чтобы не показывать служебные координаты как обычный диапазон 0.0-0.0. Это диагностическое представление; конец диапазона остаётся исключающим согласно контракту Fragment.

### Хелперы диапазонов и сверка базовых контрактов

Принято сохранить Fragment.fromPositions(), Fragment.fromNodes() и Position.bounds(), перенеся подробный пересмотр в [план алгоритмов](core-algorithms-review-plan.md).

При сверке согласованных интерфейсов отмечено:
- Builder изменяет содержимое слотов, Type задаёт полную схему, Node предоставляет неизменяемые списки содержимого. Геттеры содержимого Builder не добавляются.
- NamedSlotDescriptor и SlotDescriptor остаются разными классами с разными типами getTag(); прямое наследование между ними не предполагается.
- Структурное равенство Node учитывает границы слотов; готовый hashCode использует ту же структуру. Fragment и свойства исключены из обоих.
- Обычные узлы получают свойства из типа. Поведение обёрток рассматривается отдельно.
- Строгий конструктор Fragment не переставляет границы; вычисление охватывающего диапазона хелперами является отдельной операцией.
- EmptyFragment со служебной позицией (0, 0) отличается от реального диапазона нулевой длины.
- Ранние предложения в журнале (Slot, OptionalInt, вычисление полного хэша при запросе) отменены позднейшими решениями и не являются текущим API.

Открытый вопрос базового API: Factory. Ранее согласовано восстановление полного описания типа по имени, включая AbstractType, но точные сигнатуры и ошибки не установлены. Текущий core Factory.getType возвращает Type либо null, а createBuilder для неизвестного имени молча создаёт DraftNode. Этот контракт требует отдельного согласования.

### Factory: AbstractType и заменяемые реализации — уточнение автора

Factory.getType(String name) должен возвращать AbstractType, чтобы фабрика предоставляла как абстрактные, так и конкретные описания типов. AbstractType теперь содержит явный контракт описания типа.

Автоматическое создание драфтового типа как подстановка для неизвестного имени отклонено. Старый fallback Factory.createBuilder, создающий DraftNode, не переносится в новый контракт.

Автор подчеркнул, что фабрики могут иметь разные реализации: пользователь должен иметь возможность предоставить подходящую фабрику, если стандартная не отвечает его требованиям. Предложенная ранее единая политика IllegalArgumentException для неизвестного имени и null пока не считается отдельно согласованной. Следует различать способ поиска/получения типов конкретной фабрикой и общий контракт сообщения о неудаче. Сигнатура и поведение createBuilder также ещё обсуждаются.

### Optional и два поиска типов Factory — принятое направление

Автор принял Optional для результата поиска типа: известный тип возвращается присутствующим значением, неизвестный — Optional.empty(); сам результат никогда не null. null в аргументе имени отвергается с IllegalArgumentException. Предложение возвращать null при отсутствии типа отклонено.

Дополнительно автор потребовал два доступа: к описанию типа как AbstractType и к конкретному Type, оба через Optional. Это позволяет получить строитель из конкретного типа без проверки instanceof в вызывающем коде. Общий поиск должен предоставлять и абстрактные, и конкретные типы; поиск конкретного типа — только Type. Имена методов и default-реализация ещё предлагаются для согласования.

Предлагаемый эскиз: Optional<AbstractType> getAbstractType(String name); default Optional<Type> getType(String name), фильтрующий результат первого метода через Type.class.isInstance и Type.class.cast. Этот эскиз пока не является отдельно утверждённой сигнатурой.

### Согласованный интерфейс Factory — принято целиком

```java
public interface Factory {
    Optional<AbstractType> getAbstractType(String name);

    default Optional<Type> getType(String name) {
        return getAbstractType(name)
            .filter(Type.class::isInstance)
            .map(Type.class::cast);
    }

    default Optional<Builder> createBuilder(String name) {
        return getType(name).map(Type::createBuilder);
    }
}
```

Единственный обязательный метод getAbstractType находит любой тип, включая конкретный. getType предоставляет только конкретный Type: абстрактное или неизвестное имя даёт Optional.empty(). createBuilder для конкретного типа каждый раз создаёт новый независимый Builder; для абстрактного или неизвестного типа возвращает Optional.empty().

Все три метода отвергают null в имени с IllegalArgumentException; в default-методах это обеспечивается контрактом getAbstractType. Результаты Optional никогда не null. Автоматического fallback к DraftNode нет. Пользовательские фабрики могут выбирать способ получения типов при соблюдении общего контракта. Предыдущие промежуточные предложения о сигнатурах Factory заменены этим интерфейсом.

### Ленивая инициализация рекурсивных схем — принято

Допускается ленивое создание схемы: объект типа создаётся раньше схемы, при первом обращении строится и безопасно публикуется полная неизменяемая SlotSchema. Частично заполненная схема наружу не выходит. Статический вложенный holder является допустимым способом реализации, не новым обязательным методом интерфейса.

SlotSchema.Constructor сохраняет ссылки на допустимые типы детей, но не запрашивает их схемы и не обходит их структуру. Конструктор объекта типа также не инициирует построение схемы. Это позволяет описать рекурсивный слот Chain(next: Chain?) без рекурсивного построения схем. Проверки наследования остаются вне строителя схемы.

Эскиз Java (остальные методы Type опущены):

```java
final class ChainType implements Type {
    static final ChainType INSTANCE = new ChainType();

    private ChainType() { }

    private static final class SchemaHolder {
        static final SlotSchema SCHEMA = SlotSchema.create()
            .optional(ChainType.INSTANCE, "next")
            .build();
    }

    @Override
    public String getName() {
        return "Chain";
    }

    @Override
    public Set<NamedSlotDescriptor> getNamedSlots() {
        return SchemaHolder.SCHEMA.getNamedSlots();
    }

    @Override
    public List<SlotDescriptor> getSlots() {
        return SchemaHolder.SCHEMA.getSlots();
    }
}
```

Рекурсия ссылок на типы детей не отменяет запрета циклов наследования и не означает разрешения циклов в готовых узлах. Для реализации с несколькими взаимно ссылающимися типами нужно сохранять тот же принцип: инициализация объекта типа не должна запускать схемы других типов.

### Отдельные классы дескрипторов и package-private конструкторы — принято

NamedSlotDescriptor и SlotDescriptor остаются отдельными публичными неизменяемыми классами. Размещение внутри SlotSchema отклонено, чтобы не удлинять имена типов API.

Их конструкторы имеют package-private доступ. SlotSchema и его строитель находятся в том же пакете и могут создавать дескрипторы. Конструкторы доступны также остальному коду этого пакета; ограничение доступа только одним строителем не требуется. Для внешнего кода публичный способ создания дескрипторов остаётся через SlotSchema.Constructor.

Это уточняет прежнее требование «закрытых конструкторов»: private заменяется на package-private. Вложенным остаётся строитель SlotSchema.Constructor, но не сами дескрипторы.

### Формула хэша типа — принято

Для всех реализаций AbstractType, включая конкретный Type, hashCode() возвращает getName().hashCode(). Это реализация в классе, а не default-метод интерфейса.

```java
@Override
public int hashCode() {
    return getName().hashCode();
}
```

Формула дополняет принятое равенство типов по имени. При соблюдении согласованной формулы хэша Node структурный хэш дерева воспроизводим между запусками при одинаковых именах типов, сериализованных данных и структуре слотов. Это не исключает коллизии и не делает хэш доказательством равенства.
